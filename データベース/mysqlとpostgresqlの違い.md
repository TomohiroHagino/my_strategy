# MySQL と PostgreSQL の違い

## ひとことで言うと
> 2大オープンソースRDB。今はどちらも実用十分で「選んでも間違いではない」。差は **多機能・厳格（PostgreSQL）** か **枯れ・運用容易・読み速い（MySQL）** かの傾向。ただし近年は **PostgreSQL がデフォルト選択** になりつつある。

「どっちが優れているか」より「**どっちが今回の用途・チームに合うか**」で決める話。個別の詳細は各ファイル（[mysql.md](./mysql.md) / [postgresql.md](./postgresql.md)）に譲り、ここは **違いと選定** に集中する。

## ひと目で違い（比較表）
| 観点 | MySQL | PostgreSQL |
|---|---|---|
| デフォルト分離レベル | **REPEATABLE READ** | **READ COMMITTED** |
| 並行制御 | MVCC。InnoDBは **Undoログ** で旧バージョンを管理（追加掃除は基本不要） | MVCC。**追記型**で古い行が溜まり **VACUUM が必要** |
| 接続モデル | **1接続=1スレッド**。接続が軽い | **1接続=1プロセス**。重く、**プーラ（PgBouncer）ほぼ必須** |
| 型システム | 基本型＋ **JSON**。素直で少なめ | **JSONB・配列・range・ENUM・独自型（CREATE TYPE）** と豊富 |
| インデックス種類 | **B-tree中心**（実用上はほぼこれ） | **B-tree / GIN / GiST / BRIN / Hash** ＋部分・式インデックス |
| SQL標準準拠 | **ゆるめ**。暗黙の型変換など歴史的方言が残る | **厳格**。型・制約をきっちり効かせる |
| 拡張性 | **プラグイン／ストレージエンジン**差し替え | **EXTENSION**（PostGIS・pgvector など）でDB自体を育てる |
| レプリケーション | **設定が簡単で枯れている**（binlogベース・読み取りスケール定番） | **物理（ストリーミング）/ 論理** の2系統。やや重め・要知識 |
| ライセンス/ガバナンス | **Oracle傘下**・GPL＋商用。派生に **MariaDB** | **コミュニティ主導**・寛容な **PostgreSQLライセンス**（特定企業の所有物でない） |
| 得意領域 | **読み多いWeb・シンプルなOLTP** | **複雑クエリ・地理空間・JSON・分析寄り** |

> ざっくり覚えるなら「MySQL＝速い・手軽・枯れている」「PostgreSQL＝多機能・厳密・標準準拠」。表のどの行も、この色分けの具体例になっている。

## 性能の傾向
- **単純な読み取り中心**（主キー引き・少量行のSELECT・参照系が大半のWeb）は、**MySQL（InnoDB）が速い場面が多い**。構成がシンプルでレプリカ増設による読み取りスケールも組みやすい。
- **複雑なJOIN・集計・並行書き込み**が多い処理は、プランナの賢さや並行制御の強さで **PostgreSQL が有利**になりやすい。ウィンドウ関数やCTEを多用する分析寄りの処理も得意。

ただしこれは **あくまで傾向**。バージョン（両者とも世代ごとに大きく改善している）、スキーマ設計、インデックスの当て方、ワークロードの偏りで **簡単に逆転する**。「MySQLは遅い」「PostgreSQLは重い」といった一般論を鵜呑みにせず、**自分の代表的なクエリで実測する**のが正解。ベンチマーク記事は前提条件をよく読むこと。

## 運用コストの違い
- **PostgreSQL** は固有の運用ポイントがある:
  - **VACUUM**（追記型MVCCの掃除）。書き込みの多いテーブルで autovacuum が追いつかないと肥大化・性能劣化、最悪 wraparound。監視が要る。
  - **接続プール**。1接続1プロセスなので、多数の短命接続を素で張ると枯渇する。プーラ前提で設計する。
- **MySQL** は相対的に **運用が枯れていて楽**。Undoログ方式なので VACUUM 相当の継続作業がなく、接続も軽い。トラブルが予測しやすく情報も多い。

ただし **マネージドサービス（RDS / Cloud SQL / Aurora など）を使えば、この運用差はかなり縮む**。VACUUM設定やプーラ、レプリケーション・バックアップ・フェイルオーバーの面倒をマネージド側が見てくれるので、自前運用ほどの差にはならない。
- AWS: [../インフラ/aws/](../インフラ/aws/)
- GCP（Cloud SQL）: [../インフラ/gcp/cloud_sql.md](../インフラ/gcp/cloud_sql.md)

## どっちを選ぶ？（判断）
- **迷ったら → 今は PostgreSQL を既定にして大きく外さない**。多機能・SQL標準準拠・拡張（pgvector/PostGIS）で将来の要求にも応えやすく、新規プロジェクトのデファクトになりつつある。
- **WordPress等の既存エコシステム／枯れた運用がほしい／読み多いシンプル構成 → MySQL**。情報・ホスティング・ツールが揃い、当たり前を安定してこなせる。
- **JSON多用・地理空間・ベクトル検索・複雑クエリ・厳密な整合性が要る → PostgreSQL**。JSONB＋GIN、PostGIS、pgvector、厳格な制約がそのまま武器になる。
- **チームの習熟・既存資産がどちらかに寄っている → それに合わせるのが最良**。技術的な優劣の差より、**運用習熟（トラブル対応・チューニング・人材）の差のほうが効く**。両方そこそこなら PostgreSQL を初期値に。
- **大量データの分析が主目的 → そもそもRDBの土俵じゃない**。BigQueryなどの分析基盤を別途検討する（→ [../インフラ/gcp/bigquery.md](../インフラ/gcp/bigquery.md)）。

## ハマりどころ（移行・併用）
「どちらかに慣れた人が、もう片方で事故る」ポイント。移行時も併用時も効いてくる。
- **分離レベルの既定差**：MySQL=`REPEATABLE READ` / PostgreSQL=`READ COMMITTED`。**同じトランザクションでも「他者のコミットがいつ見えるか」が変わる**。MySQL前提のコードをPostgreSQLに移すと、同一トランザクション内で値が変わって見えて挙動が変わることがある（逆も然り）。移行時に明示設定で揃えるか、挙動を必ず確認する。
- **連番の書き方**：MySQL の `AUTO_INCREMENT` ↔ PostgreSQL の `GENERATED ALWAYS AS IDENTITY`（旧 `SERIAL`）。DDLの移植で素直には変換できない。
- **文字コード**：MySQL の `utf8mb4`（`utf8` は3バイトの偽物なので絵文字が消える罠）↔ PostgreSQL の `UTF8`。MySQL側だけの「`utf8` 落とし穴」を知らずに移すと文字化けの原因切り分けで迷う。
- **暗黙の型変換**：MySQLは文字列と数値を勝手に変換する（`'1abc' = 1` が真など）が、**PostgreSQLは厳格で型不一致をエラーにする**。MySQLで通っていた緩いSQLがPostgreSQLで弾かれる／逆にPostgreSQL前提の厳密なSQLがMySQLでは思わぬ通り方をする。
- **識別子の大文字小文字**：PostgreSQLは未クオートの識別子を小文字に畳む。`CREATE TABLE "Users"` のようにクオートで大文字を作ると以後ずっとダブルクオート必須になる。MySQLはテーブル名の大小区別がOS・設定依存。**小文字スネークケースで統一**しておくと両者で事故らない。
- **日付/タイムゾーン型**：PostgreSQLは `TIMESTAMP`（TZ無し）と `TIMESTAMPTZ`（TZ付き）が明確に別物で、基本は `TIMESTAMPTZ`。MySQLは `DATETIME` と `TIMESTAMP` の差（後者はTZ変換・範囲制限あり）。時差の扱いがズレてバグになりやすい代表格。
