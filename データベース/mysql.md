# MySQL

## ひとことで言うと
**世界で最も普及したオープンソースのリレーショナルDB**。Webアプリのバックエンド（LAMP/LEMP）の定番で、読みやすさ・運用の枯れ具合・読み取りの速さが武器。とりあえずMySQLを選んでおけば情報も人材も困らない、という安心感がある。

> 「速くて枯れていて情報が多い」――尖った機能で勝負するより、**当たり前のことを安定してこなす**ことで普及した。

## 役割・立ち位置
- 想定するワークロードは **OLTP**（1行ずつの読み書き、トランザクション処理）。ECの注文、ユーザー登録、SNSの投稿など「1リクエストで少量の行を触る」用途が本領。大量データの分析（OLAP）は [../インフラ/gcp/bigquery.md](../インフラ/gcp/bigquery.md) のような分析基盤の領分。
- ライバルは **PostgreSQL**。よく比較される（→ [mysqlとpostgresqlの違い.md](./mysqlとpostgresqlの違い.md)）。ざっくり「MySQL＝シンプル・速い・運用しやすい」「PostgreSQL＝高機能・SQL標準準拠・厳格」という色分け。
- 歴史を押さえると挙動の理由が腹落ちする:
  - 初期は **MyISAM** がデフォルトエンジン。速いがトランザクションも外部キーも無かった。
  - その後 **InnoDB** が標準になり、トランザクション・外部キー・クラッシュリカバリを獲得（MySQL 5.5以降デフォルト）。
  - 現在はSun→**Oracle傘下**。これを嫌った原作者が **MariaDB** という派生（フォーク）を立ち上げ、互換性を保ちつつ別進化している。
- このドキュメントは **8.0系** を前提（CTE・ウィンドウ関数・`utf8mb4`デフォルト化などが入った世代）。

## ストレージエンジン（InnoDB）
MySQL独特なのが、**テーブルごとにストレージエンジンを差し替えられる**こと。実データの保存方式・ロックの粒度・トランザクション可否が、エンジンによって変わる。

| エンジン | トランザクション | ロック粒度 | 外部キー | 今の扱い |
|---|---|---|---|---|
| **InnoDB**（デフォルト） | あり | 行ロック | あり | 標準。基本これ一択 |
| MyISAM | なし | テーブルロック | なし | 非推奨（昔の遺物） |

- **InnoDB** はトランザクション・行ロック・外部キー・クラッシュリカバリを備える、現代のMySQLの心臓部。迷ったらInnoDBで間違いない。
- MyISAMはテーブル全体をロックするため書き込みが詰まりやすく、クラッシュ時にデータが壊れやすい。**新規で選ぶ理由はない**。古いシステムを引き継いだときに残っていることがある程度。
- 「エンジンを後から `ALTER TABLE ... ENGINE=InnoDB` で差し替えられる」のは他DBにない特徴だが、実務では最初からInnoDBで統一しておくのが正解。

## トランザクションと分離レベル
- InnoDBは **ACID** を満たす。`BEGIN` 〜 `COMMIT` / `ROLLBACK` で複数の更新をまとめて確定・取り消しできる。
- **デフォルトの分離レベルが `REPEATABLE READ`**。ここが要注意ポイントで、**PostgreSQLのデフォルト（`READ COMMITTED`）と違う**。同じトランザクション内なら、他者のコミットが見えず最初のスナップショットを一貫して読み続ける。
- **MVCC**（多版型同時実行制御）により、通常の `SELECT` は行をロックしない（読み取りが書き込みをブロックしない）。
- InnoDB特有の罠として **ギャップロック** がある。範囲条件の更新時に「存在しない隙間」までロックして、想定外のデッドロックや待ちを生むことがある。

| 分離レベル | 概要 |
|---|---|
| READ UNCOMMITTED | 未コミットも見える（ダーティリード）。ほぼ使わない |
| READ COMMITTED | コミット済みだけ見える（PostgreSQLの既定） |
| **REPEATABLE READ** | **MySQLの既定**。トランザクション内で一貫した読み取り |
| SERIALIZABLE | 完全直列化。最も厳格・最も遅い |

## インデックスの勘所
- 基本は **B-treeインデックス**。範囲検索・前方一致・等価検索に効く。
- **主キー＝クラスタインデックス**：InnoDBはデータを **主キーの順序で物理的に並べて保存** する。だから主キー検索は速く、主キーには連番（`AUTO_INCREMENT`）など単調増加する値が向く（ランダムなUUIDを主キーにするとページ分割が増えて遅くなりやすい）。
- **複合インデックスは左端一致**：`(a, b, c)` のインデックスは `a` / `a,b` / `a,b,c` の絞り込みには効くが、`b` だけ・`c` だけでは効かない。WHERE/ORDER BYの列順を意識して並べる。
- **カバリングインデックス**：必要な列がすべてインデックスに含まれていれば、テーブル本体を読まずインデックスだけで結果を返せる（高速）。
- 実行計画は **`EXPLAIN`** で確認する。`type` が `ALL`（フルテーブルスキャン）になっていないか、`key` に狙ったインデックスが使われているかを見る。

```sql
-- 複合インデックスの作成
CREATE INDEX idx_user_created
  ON orders (user_id, created_at);

-- 実行計画を見る（インデックスが使われているか確認）
EXPLAIN
SELECT id, total
FROM orders
WHERE user_id = 101
  AND created_at >= '2026-06-01';
```

## 文字コードの罠（重要）
MySQLで最も有名な落とし穴。**`utf8` は本物のUTF-8ではない**。

- MySQLの `utf8`（= `utf8mb3`）は **1文字最大3バイト** しか扱えず、4バイト必要な **絵文字や一部の漢字（𠮷 など）が保存時に消える・化ける**。
- 正解は **必ず `utf8mb4`**（4バイト対応の本物のUTF-8）を使うこと。MySQL 8.0ではデフォルトが `utf8mb4` になったが、古い設定や移行プロジェクトでは `utf8` のまま残っていることがあるので要確認。
- 照合順序（**collation**）も合わせて決める。`utf8mb4_0900_ai_ci`（8.0既定、大文字小文字・アクセント無視）や、絵文字・各国語をきちんと区別したいなら `utf8mb4_bin` などを選ぶ。

```sql
-- 文字コードは必ず utf8mb4 を指定する
CREATE TABLE messages (
  id         BIGINT AUTO_INCREMENT PRIMARY KEY,
  body       TEXT,
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP
) ENGINE=InnoDB
  DEFAULT CHARACTER SET = utf8mb4
  COLLATE = utf8mb4_0900_ai_ci;
```

> `utf8` と書いてあったら疑え。絵文字が突然消えるバグの9割はこれ。

## レプリケーション / 可用性
- 標準で **プライマリ → レプリカ** の **非同期レプリケーション** が組める。プライマリのバイナリログ（binlog）をレプリカが追いかけて再生する仕組み。
- 用途は主に **読み取りスケール**。書き込みはプライマリ1台、参照系クエリを複数のレプリカに分散させて捌く。
- プライマリ障害時は、レプリカを昇格させて **フェイルオーバー** する。非同期なので、切り替え時に「まだレプリカへ届いていなかった最後の更新」が失われる可能性がある点は理解しておく。
- 自前運用はレプリケーション・バックアップ・フェイルオーバーの面倒を見る必要があるため、実務では **マネージドサービス** が定番:
  - AWS の RDS for MySQL / Aurora MySQL → [../インフラ/aws/](../インフラ/aws/)
  - GCP の Cloud SQL → [../インフラ/gcp/cloud_sql.md](../インフラ/gcp/cloud_sql.md)

## 基本操作
```bash
# 接続（-p のあとにパスワードを書かず、対話で入力するのが安全）
mysql -h 127.0.0.1 -P 3306 -u app_user -p my_database

# ダンプ（バックアップ）
mysqldump -u app_user -p my_database > backup.sql
```

```sql
-- テーブル作成。主キーは AUTO_INCREMENT の連番が定番
CREATE TABLE users (
  id         BIGINT AUTO_INCREMENT PRIMARY KEY,
  name       VARCHAR(255) NOT NULL,
  email      VARCHAR(255) NOT NULL UNIQUE,
  profile    TEXT,
  attributes JSON,                              -- 8.0はJSON型・JSON関数が使える
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP
) ENGINE=InnoDB DEFAULT CHARACTER SET = utf8mb4;

-- 基本CRUD
INSERT INTO users (name, email) VALUES ('Taro', 'taro@example.com');
SELECT id, name FROM users WHERE email = 'taro@example.com';
UPDATE users SET name = 'Jiro' WHERE id = 1;
DELETE FROM users WHERE id = 1;
```

代表的な型: `INT` / `BIGINT`（整数）、`VARCHAR(n)`（可変長文字列）、`TEXT`（長文）、`DATETIME`（日時）、`JSON`（構造化データ）。金額は浮動小数の `FLOAT` を避け、`DECIMAL` を使う。

## 強み / 弱み
**強み**
- **圧倒的な普及率と情報量**：ハマっても検索すればだいたい答えがある。ホスティング・ツール・ノウハウが豊富。
- **運用が枯れている**：枯れているぶんトラブルが少なく予測しやすい。
- **読み取りが速い**：シンプルな構成で参照系を高速にさばける。
- **レプリケーションが簡単**：読み取りスケールを組みやすい。

**弱み**
- **SQL標準への準拠がやや甘い**：独自方言や歴史的な挙動が残る。
- **高度な型・機能はPostgreSQLに劣る**：配列型・豊富な拡張・厳密なチェック制約などは後発・限定的。
- **歴史的な暗黙の型変換の罠**：緩い型変換が原因のバグが起きやすい（次節）。

## ハマりどころ / アンチパターン
- **`utf8` で絵文字が消える**：前述の通り。必ず `utf8mb4`。
- **暗黙の型変換**：文字列と数値を比較すると勝手に変換される。`WHERE col = '1abc'` が `1` として扱われたり、`'0' = ''` の真偽が直感に反したりする。型は揃えて比較する。
- **大文字小文字・ゼロ日付**：デフォルトの照合順序は大文字小文字を区別しない（`'A' = 'a'`）ので、区別したいなら collation で明示する。また `'0000-00-00'` という不正な日付を昔は許していた（`sql_mode` 次第）。8.0では既定で厳格モードだが、移行データに紛れていることがある。
- **巨大OFFSETページング**：`LIMIT 100000, 20` は手前の10万行を読み飛ばすため、ページが深いほど遅くなる。**キーセットページング**（`WHERE id > :last_id ORDER BY id LIMIT 20`）に切り替える。
- **外部キーの付け忘れ**：参照整合性をアプリ任せにすると、孤児レコードが生まれる。InnoDBなら外部キーで縛れるのに使わないのはもったいない。
- **`ON DELETE CASCADE` の事故**：便利だが、親を1行消したら大量の子が連鎖削除されて取り返しがつかない、という事故が起きやすい。CASCADEを付ける範囲は慎重に設計する。
- **文字列カラムへの数値比較でインデックス無効化**：`VARCHAR` のカラムに対し `WHERE phone = 09012345678`（数値リテラル）と書くと、暗黙変換が走ってインデックスが効かずフルスキャンになる。`WHERE phone = '09012345678'` と文字列で渡す。関数でカラムを包む（`WHERE DATE(created_at) = ...`）のも同様にインデックスを殺す。
