# React Native（JS/TS）特有の現象と対策（落とし穴カタログ）

> **JS/TS＋React で RN を書くときに効いてくる**現象を「現象 / なぜ起きる / 対策」で。
> JS共通の罠（巻き上げ・`this`・クロージャ・`==`・浮動小数・await漏れ等）は土台 → **[../../フロントエンド/javascript/落とし穴.md](../../フロントエンド/javascript/落とし穴.md)**、型は [../../フロントエンド/typescript/落とし穴.md](../../フロントエンド/typescript/落とし穴.md)。RN/Reactそのものの罠は [react_native0/pitfalls.md](./react_native0/pitfalls.md)。ここは**JSの仕組みがhooks/モバイル文脈でどう牙を剥くか**に絞る。

---

## 1. 古いクロージャ（stale closure）で古い state を見る
**現象**：`useEffect`/`setInterval`/イベントハンドラの中で参照した `state` が、更新後も**古い値のまま**。
**なぜ**：JSのクロージャは「**定義時点の変数**」を捉える（[JS落とし穴 §クロージャ](../../フロントエンド/javascript/落とし穴.md)）。関数コンポーネントは再レンダー毎に新しいクロージャを作るが、`useEffect(fn, [])` のように依存配列が空だと**最初のレンダー時のクロージャ（＝最初のstate）が固定**される。
```tsx
useEffect(() => {
  const id = setInterval(() => console.log(count), 1000); // count は常に初期値0
  return () => clearInterval(id);
}, []); // ← count を依存に入れていない
```
**対策**：
- **依存配列に参照する値を全部入れる**（`[count]`）。ESLint `react-hooks/exhaustive-deps` で検出。
- 最新値が要るなら**更新関数形式** `setCount(c => c + 1)`（前の値を引数で受ける）や `useRef` に最新値を保持。

## 2. 更新がまとまる/非同期で、直後の state が古い
**現象**：`setState` の直後に state を読むと反映前の値。連続した `setCount(count+1)` を複数回呼んでも1しか増えない。
**なぜ**：state 更新は**非同期＋バッチ**。同一イベント内の複数更新はまとめて適用され、`count` は同じ値を参照する。
**対策**：依存する更新は**関数形式** `setCount(c => c + 1)`。次のレンダーで反映される前提で書く（直後に同期で読まない）。

## 3. `useEffect` の依存配列ミスで無限ループ/未更新
**現象**：依存に毎レンダー新規生成のオブジェクト/関数を入れて**毎回再実行→無限ループ**、逆に入れ忘れて**更新されない**。
**なぜ**：依存比較は `Object.is`（参照比較）。`{}`/`() => {}` はレンダー毎に別参照（[JS落とし穴 §値vs参照](../../フロントエンド/javascript/落とし穴.md)）。
**対策**：関数は `useCallback`、計算値は `useMemo` で参照を安定化。プリミティブを依存に使う。`exhaustive-deps` を有効化。

## 4. 非同期処理の結果をアンマウント後に setState
**現象**：画面を離れた後に `fetch` が返って `setState` → 警告やメモリリーク、クラッシュの温床。
**なぜ**：非同期は完了タイミングが制御外。コンポーネントが消えても Promise は走り続ける。
**対策**：`AbortController` で fetch をキャンセル、`useEffect` のクリーンアップで中断フラグ/abort。RNの画面遷移（React Navigation）では `useFocusEffect` でフォーカス連動。

## 5. ブリッジ越しのシリアライズ制約（JS ↔ ネイティブ）
**現象**：ネイティブモジュールに関数やクラスインスタンスを渡せない、巨大データの受け渡しでカクつく。
**なぜ**：従来アーキは **JSとネイティブが非同期ブリッジでJSONシリアライズ**してやり取りする。関数や循環参照は渡せず、大量データは直列化コストが高い。
**対策**：渡すのは**プレーンなJSON可能値**に限る。大量データはネイティブ側で処理して結果だけ返す。New Architecture（JSI/TurboModules）は同期呼び出しでこの制約が緩むが、設計の基本は同じ。

## 6. 数値・等価・型の罠がモバイルで顕在化
**現象**：金額や座標の浮動小数誤差、`==` での緩い比較、APIレスポンスが型と違って実行時クラッシュ。
**なぜ**：土台はJS/TS。[浮動小数](../../フロントエンド/javascript/落とし穴.md)・[==](../../フロントエンド/javascript/落とし穴.md)・[型は実行時に消える](../../フロントエンド/typescript/落とし穴.md)がそのまま当てはまる。モバイルは**クラッシュがそのままアプリ評価に直結**する。
**対策**：金額は整数（最小単位）、比較は `===`、**APIレスポンスは zod 等で境界検証**してから state に入れる。

## 7. リスト描画の性能（大量データ）
**現象**：`map` で全件を `<View>` 描画して**スクロールが重い・メモリ増**。
**なぜ**：全要素を一度に生成・保持する。JSスレッドとUIの両方を圧迫。
**対策**：**`FlatList`/`SectionList`**（仮想化で可視分のみ描画）。`keyExtractor` で安定キー、`getItemLayout`/`memo` で再描画削減。詳細は [react_native0/lists.md](./react_native0/lists.md)。
