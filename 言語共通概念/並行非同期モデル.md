# 並行・非同期モデル（言語横断）

> 「たくさんの処理を同時にこなしたい」とき、各言語が**何を使って並行を表現し、どうやって競合（データ破壊）を防ぐか**を言語をまたいで整理する。
> 各言語の `解説/` からここへリンクする横断ドキュメント。

## 一言で
> 「**並行（concurrency）**」と「**並列（parallelism）**」は別物。各言語は「**どう並行を表現し、どう競合を防ぐか**」が違う。スレッドを直接触る言語、イベントループ1本で回す言語、軽量スレッドを大量に作る言語、所有権で競合を消す言語――同じ「同時実行」でも世界観がまるで違う。

## まず用語
- **並行（concurrency）**：複数のタスクを「**論理的に同時**」に進める。実際には1コアで切り替えているだけでもよい（料理人1人が複数の鍋を交互に見る）。
- **並列（parallelism）**：複数のタスクを「**物理的に同時**」に実行する。CPUコアが複数必要（料理人が複数人いて同時に調理）。
- **CPUバウンド**：計算そのものが重い処理（画像処理・暗号・数値計算）。速くするには**真の並列**（複数コア）が要る。
- **I/Oバウンド**：待ち時間が大半の処理（DB・HTTP・ファイル）。待っている間に他をやれば速くなるので、**並行（非同期）だけ**で十分なことが多い。

👉 ここを混同すると「非同期にしたのにCPU処理が速くならない」「スレッドを増やしたのにI/Oが詰まる」という事故になる。

## モデルのカタログ
- **OSスレッド**：OSが管理する本物のスレッド。複数コアで**真に並列**に動くが、1本が重い（メモリ数MB）ので数千〜は厳しい。共有メモリを直接触るため**ロックが要る**。（Java/Kotlin/Rust/C系）
- **グリーンスレッド／軽量スレッド**：ランタイムが管理する軽量な「スレッドもどき」。数十万本作れる。OSスレッド数本の上に多重化（M:N）される。（Go の goroutine、Java の仮想スレッド、Ruby の Fiber）
- **イベントループ（async-await）**：1本のスレッドで「待ちが入ったら別の仕事へ切り替える」を高速に回す。I/Oバウンドに強いが、**重い計算を挟むと全部止まる**。（JS/TS、Python asyncio、Dart、各言語の async）
- **CSP（goroutine＋channel）**：軽量スレッド同士が**channel（パイプ）でデータを受け渡し**して協調する。「メモリを共有して通信するな、通信してメモリを共有しろ」が合言葉。（Go）
- **actor**：状態を抱えた「アクター」が**メッセージを順番に処理**する。アクターの中身は外から直接触れないので競合が起きない。（Swift の `actor`、Erlang/Elixir、Akka）
- **isolate**：メモリを**まったく共有しない**独立した実行単位。やり取りはメッセージのコピーのみ。データ競合が原理的に起きない。（Dart）
- **所有権＋Send/Sync**：「同じデータを2か所から同時に可変アクセスできない」を**コンパイル時に**保証する。競合するコードはそもそもビルドが通らない。（Rust）

## 11言語比較表
| 言語 | 主な並行手段 | 真の並列か | GILなど制約 | 非同期の書き方 |
|---|---|---|---|---|
| **Java** | OSスレッド＋**仮想スレッド(Loom)** | ✅ できる | なし | `CompletableFuture` / 仮想スレッドで同期的に書く |
| **Python** | `threading` / `asyncio` / `multiprocessing` | △ スレッドは不可、**プロセスなら可** | **GILあり**（同時に1スレッドしかバイトコード実行不可） | `async def` / `await`（asyncio）。CPU並列は `multiprocessing` |
| **Ruby** | `Thread`＋**Ractor** / `Fiber` | △ Threadは不可、**Ractorなら可** | **GVLあり**（GILと同種）。Ractorで回避 | `Fiber` / `async` gem。I/O待ちで切替 |
| **PHP** | 基本は**同期1リクエスト1プロセス** / `Fiber` / Swoole | △ 標準は単発、拡張(Swoole/parallel)で可 | 共有なしモデル（リクエスト毎に独立） | PHP8.1+ `Fiber`、ReactPHP/Swoole で非同期 |
| **Go** | **goroutine＋channel**（CSP） | ✅ できる（GOMAXPROCS） | なし（軽量スレッドを数十万本OK） | goroutineで**同期的に書く**＋channel/`select` |
| **JavaScript** | **単一スレッド＋イベントループ** | ❌ 不可（重い処理は Web/Worker へ） | 単一スレッドゆえ共有競合は基本なし | `async`/`await` / Promise。並列は Worker |
| **TypeScript** | 同上（実行時はJS） | ❌ 不可（同上） | 同上 | `async`/`await`（型が付くだけ、挙動はJS） |
| **Rust** | OSスレッド＋`async`（tokio等） | ✅ できる | なし。**所有権＋Send/Syncで安全** | `async`/`await`＋ランタイム（tokio/async-std） |
| **Dart** | **isolate**（メモリ非共有）＋`async` | ✅ isolateで可 | 1 isolate内は単一スレッド（イベントループ） | `async`/`await` / `Future` / `Stream`。並列は `Isolate` |
| **Kotlin** | **coroutine** / スレッド | ✅ できる（JVM） | なし | `suspend fun`＋`launch`/`async`（構造化並行） |
| **Swift** | `async`/`await`＋**actor** | ✅ できる | なし。**actorでデータ競合を型で防ぐ** | `async`/`await` / `Task` / `actor` / `TaskGroup` |

> **ざっくり**：真に並列できるのは Java / Go / Rust / Kotlin / Swift（と Python/Ruby の「プロセス/Ractor」、Dart の isolate）。**JS/TS は単一スレッドで原理的に並列不可**。**Python/Ruby はGIL/GVLでスレッド並列が封じられている**のが最大の落とし穴。

## 競合をどう防ぐか
複数の実行単位が**同じデータを同時にいじる**と壊れる（データ競合）。防ぎ方は大きく3系統:

### ① 共有メモリ＋ロック
同じメモリを複数スレッドで共有し、危険な区間を**ロック（mutex）で囲って**1人ずつ通す。古典的で強力だが、ロックの掛け忘れ・デッドロックが起きやすい。
- 採用：**Java / Kotlin / Rust / C系**、Python/Ruby も（ただしGIL下なので並列性は限定的）。
- 注意：ロックの順序ミス → デッドロック。掛け忘れ → 競合バグ（再現しにくい最悪の事故）。

### ② メッセージパッシング（channel・actor・isolate）
データを共有せず、**メッセージとして渡す**。受け取った側だけがそのデータを扱うので、同時アクセスが原理的に起きにくい。
- **channel**：Go の goroutine 間。Rust の `mpsc`、Kotlin の `Channel` も。
- **actor**：Swift の `actor`。状態はアクター内に閉じ、外からはメッセージ経由のみ。
- **isolate**：Dart。メモリを一切共有せず、送るときはコピー。
- 利点：ロックを意識しなくてよい。欠点：コピーコスト、設計の組み替えが必要。

### ③ 所有権（コンパイル時保証）
Rust の独自路線。「あるデータを**可変で触れるのは同時に1か所だけ**」を所有権・借用ルールで縛り、**競合するコードはコンパイルが通らない**。実行時のロックも使えるが、まず型レベルで安全が保証される。
- `Send`（別スレッドへ送ってよい型）/ `Sync`（複数スレッドで共有してよい型）をコンパイラが追跡。
- 詳細 → [../フロントエンド/rust/解説/rust1.85.md](../フロントエンド/rust/解説/rust1.85.md)

> 多くの現代言語は ② を「安全な既定」として推している（Go の channel、Swift の actor、Dart の isolate）。① は強力だが事故りやすく、③ は最も固いが学習コストが高い。

## 移行時の事故
[言語間の移行ギャップ.md](./言語間の移行ギャップ.md) の「⑧ 並行モデル」と整合。前の言語の並行観を持ち込むと事故る。

- **JSのシングルスレッド脳でマルチスレッド言語（Java/Go/Rust/Kotlin/Swift）**：「共有変数を競合なんて気にせず触っていい」と思い込む。JSは単一スレッドだから無事だっただけで、マルチスレッド言語では**ロックや channel が必須**。気づかず共有状態を書き換えて競合バグ。
- **GIL前提（Python/Ruby）脳でGo/Java**：「どうせ並列で動かないから雑に書いても安全」が通用しない。Go/Java は**本当に同時実行**されるので、共有マップへの並書きで即クラッシュ（Goは `fatal error: concurrent map writes`）。
- **共有メモリ脳でisolate（Dart）/actor（Swift）**：「グローバル変数を別 isolate から見れば共有できる」と思うが、**isolate はメモリ非共有**。やり取りはメッセージのコピーのみ。actor も外から状態を直接触れない（`await` 越しのアクセスになる）。
- **Go脳でPython**：goroutine感覚で `threading` を量産しCPU並列を期待 → **GILで速くならない**。CPUバウンドは `multiprocessing`、I/Oバウンドは `asyncio` を選ぶ。
- **同期脳で async-await（JS/Python/Dart/Swift…）**：イベントループ上で**重いCPU処理を直書き**すると、その間ループ全体が固まる（UIフリーズ・全リクエスト停止）。重い処理は Worker / isolate / 別スレッドへ逃がす。
- **async関数の伝染を忘れる**：`await` を付け忘れて `Future`/`Promise` がそのまま流れ、「値のはずがオブジェクトだった」バグ。async は呼び出し側まで連鎖する（関数の色が伝染する）。
- **例外脳でGoのgoroutine**：goroutine内で `panic` すると**プロセス全体が落ちる**（呼び出し元では拾えない）。各goroutineで `recover` するか、エラーを channel で返す設計にする。
