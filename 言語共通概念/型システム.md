# 型システム（言語横断）

> 「この値は何で、どんな操作が許されるのか」を、いつ・どれだけ厳密に検査するか。
> 各言語の `解説/` からここへリンクする横断ドキュメント。

## 一言で
型システムは「**いつ・どれだけ**間違いを検出するか」の設計だ。チェックのタイミング（コンパイル時か実行時か）、許す変換の緩さ、型の同一視のしかた、null の扱い――これらを**軸ごとに分けて**捉えると、各言語が一枚の地図に乗る。「型がある／ない」の二択で語ると必ず混乱する。

## 軸の説明
型の話は1次元ではない。最低でも次の軸を**別々に**見る。

**① 静的 vs 動的（いつ検査するか）**
静的型は**コンパイル時**に型を検査する（Java/Go/Rust/TS など）。動的型は**実行時**に値の型を見て動く（Python/Ruby/JS など）。「コードを動かす前に弾くか、動かして初めて落ちるか」の違い。

**② 強い vs 弱い（どれだけ暗黙変換を許すか）**
強い型は暗黙の型変換をあまり許さず、型違いの操作を弾く。弱い型は `"5" + 3` のような変換を黙って通す。**よくある誤解：「強い型＝静的型」ではない。** Python は動的だが強い型（`"5" + 3` はエラー）。JS は動的かつ弱い（`"5" + 3` は `"53"`）。この2軸は独立している。

**③ 公称（nominal）vs 構造的（structural）（型を何で同一視するか）**
公称型は「**名前が同じか**」で互換を判断する（Java/Kotlin/Swift/Rust）。構造的型は「**形（メンバー）が同じか**」で判断する（TS、Go のインターフェース）。同じ `{ name: string }` でも、公称なら別名なら別物、構造的なら形が合えば通る。

**④ null安全（null を型で防ぐか）**
null/nil を**型レベルで区別**し、null になりうる値の操作をコンパイル時に強制チェックする仕組み。Kotlin/Swift/Rust/TS(strict) は持つ。Java/Python などは持たず、null/None は実行時に初めて落ちる（NPE / AttributeError）。

**⑤ 型推論（どこまで型注釈を省けるか）**
コンパイラ/処理系が文脈から型を補う力。Rust/Swift/Kotlin/TS は強く、ローカル変数はほぼ書かなくてよい。Go は控えめ（`:=` の範囲）。Java は近年 `var` で改善。

## 11言語比較表
| 言語 | 静的/動的 | 強い/弱い | 公称/構造的 | null安全 | 型推論 | ジェネリクス |
|---|---|---|---|---|---|---|
| **Java** | 静的 | 強い | 公称 | なし（実行時NPE） | 弱め（`var` は局所） | あり（型消去） |
| **Python** | 動的＋型ヒント | 強い | 公称（実行時はダック） | なし（None→実行時） | 推論なし（注釈は任意） | 型ヒントのみ（`list[int]`） |
| **Ruby** | 動的 | 強い | ダックタイピング | なし（nil→実行時） | なし（RBS/Sorbetは別途） | 言語機能としてはなし |
| **PHP** | 動的＋型宣言 | やや弱い（緩い変換あり） | 公称（クラス/IF） | なし（`?T`はあるが任意） | 弱い | あり（ジェネリクスはdocのみ） |
| **Go** | 静的 | 強い | 公称（構造体）＋構造的（IF） | なし（ゼロ値・nil） | 控えめ（`:=`） | あり（1.18〜） |
| **JavaScript** | 動的 | **弱い**（暗黙変換が多い） | （実質）構造的 | なし（null/undefined） | なし | なし（実行時に型はない） |
| **TypeScript** | 静的 | 強い | **構造的** | あり（strictNullChecks） | 強い | あり（強力） |
| **Rust** | 静的 | 強い | 公称（トレイト境界で抽象） | あり（`Option<T>`） | 強い（局所はほぼ不要） | あり（強力・単相化） |
| **Dart** | 静的（健全） | 強い | 公称 | あり（`?` / sound null safety） | 強い（`var`/`final`） | あり |
| **Kotlin** | 静的 | 強い | 公称 | あり（`?` で型レベル） | 強い | あり（変位指定あり） |
| **Swift** | 静的 | 強い | 公称（プロトコル準拠） | あり（`Optional<T>`） | 強い | あり（強力） |

> **ざっくり**：完全な動的は Ruby / JS。動的だが型ヒント／宣言を足せるのが Python / PHP。静的の中で、**構造的なのは TS（と Go のインターフェース）**、残りは公称。**null安全を持つのは TS(strict) / Rust / Dart / Kotlin / Swift の5つ**。JS だけ「弱い型」で暗黙変換が事故りやすい。

## 公称 vs 構造的
**公称（Java）**：同じ形でも、宣言された名前（型）が違えば代入できない。
```text
interface Named  { String getName(); }
interface Person { String getName(); }   // 形は同じ

Named n = somePerson;   // ✗ コンパイルエラー：Person は Named を implements していない
                        // 「形が同じ」では足りない。名前（継承/実装）の宣言が要る
```
**構造的（TypeScript）**：名前は無関係。形（メンバー）が合えば互換。
```text
interface Named  { name: string }
interface Person { name: string; age: number }

const p: Person = { name: "alice", age: 20 }
const n: Named = p;     // ✓ OK：Person は name を持つ＝Named の形を満たす
                        // どこにも「Named を実装する」とは書いていないのに通る
```
**Go のインターフェース（構造的）**：`implements` を書かない。メソッドの形が合えば自動的に満たす。
```text
type Reader interface { Read(p []byte) (int, error) }

// File に Read メソッドがあれば、宣言なしで Reader として使える（暗黙の充足）
var r Reader = someFile   // ✓ File が Read を持っていれば通る
```
構造体そのものの代入互換は**公称**（型名が違えば別物）だが、インターフェース充足だけが構造的、という二段構え。

## null安全
「null になりうる」を**型に書く**かどうかで、事故のタイミングが変わる。null安全な言語は**コンパイル時**に強制し、ない言語は**実行時**に初めて落ちる。

| 言語 | nullの表現 | 安全な取り出し | 非nullと宣言した型にnullは |
|---|---|---|---|
| **Kotlin** | `String?`（nullableは `?` 必須） | `?.` / `?:` / `if (x != null)` | 入れられない（コンパイルエラー） |
| **Swift** | `Optional<T>` = `T?` | `if let` / `guard let` / `??` | 入れられない |
| **Rust** | `Option<T>`（`Some`/`None`） | `match` / `if let` / `?` / `unwrap_or` | そもそも null という値が言語にない |
| **TypeScript** | `string | null`（strictNullChecks時） | ナローイング / `?.` / `??` | strict下では弾く |
| **Dart** | `String?`（sound null safety） | `?.` / `??` / `!`（危険） | 入れられない |
| **Java** | 区別なし（参照は常にnull可） | （なし。`Optional<T>` は任意の道具） | **入る** → 実行時 `NullPointerException` |
| **Python** | 区別なし（`Optional[T]` は注釈のみ） | （なし。注釈は実行時に強制されない） | **入る** → 実行時 `AttributeError` |

- Kotlin/Swift/Rust/Dart は「null になりうる値を、安全に開封せずに使おうとする」とコンパイルが通らない。バグが**前に倒れる**。
- Rust は特に純粋で、null という値自体が存在しない。「無いかもしれない」は `Option<T>` という普通の型で表す。
- Java/Python は注釈（`@Nullable` / `Optional[T]`）を**書けても言語が強制しない**。守るかは規律次第。

## 移行時の事故
[言語間の移行ギャップ.md](./言語間の移行ギャップ.md) の②（未設定の値）と整合する。型システムの前提がズレると、コンパイルは通るのに（あるいは通らずに）ハマる。

- **動的言語脳で静的言語へ**：Ruby/Python/JS の「とりあえず動かして確かめる」感覚で書くと、Go/Java/Rust は**コンパイルが通らず先に進めない**。型を最初に決める設計が要る。逆に静的脳で動的言語に来ると、型がないぶん**実行時まで間違いに気づけない**（テストで補う発想が要る）。
- **Java脳で TS の構造的型**：「`implements` していないから別物のはず」と思い込むが、TS は**形が合えば勝手に互換**。意図せず別の型を代入できてしまい、設計上の境界が緩く見える。逆に TS脳で Java/Kotlin に来ると「形は同じなのになぜ代入できない」となる（公称だから）。
- **null安全言語から非null安全言語へ**：Kotlin/Swift/Rust の「null は型が守ってくれる」前提で Java/Python を書くと、**null チェックを省いて実行時 NPE / AttributeError**。Java/Python では null/None は自分で警戒し続ける必要がある。
- **Java脳で Kotlin**：Java由来のプラットフォーム型を経由すると `null` がすり抜け、せっかくの null安全が無効化される（[移行ギャップ.md](./言語間の移行ギャップ.md) ②参照）。
- **弱い型（JS）脳で強い型へ**：`"5" + 3` が通る感覚で Python/Java を書くと型エラー。逆に強い型脳で JS に来ると、暗黙変換（`==`、文字列連結）で**黙って意図しない結果**になる（[移行ギャップ.md](./言語間の移行ギャップ.md) ⑥ `==` も関連）。
- **型推論を過信**：Go の `:=` や TS の推論に慣れると注釈をほぼ書かなくなるが、Java（旧来）や Python の関数シグネチャでは明示が前提。推論の効く範囲は言語ごとに違う。

移行時にまず確認する3点：**①動かす前に型を弾くか（静/動）、②型の同一視は名前か形か（公称/構造的）、③null は型で守られるか**。
