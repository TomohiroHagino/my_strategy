# BigQuery（GCP）

## ひとことで言うと
**サーバーレスのデータウェアハウス**。テラ〜ペタバイト級の超大規模データを、サーバーの用意なしに **標準SQL** で分析できるGCPの目玉サービス。データを入れて `SELECT` を投げるだけで、裏側で数千台規模の処理が動く。

## 役割・なぜ必要か
- 普通のRDB（Cloud SQLなど）は「1行ずつの読み書き（OLTP）」が得意だが、「全件を集計する分析（OLAP）」は苦手・遅い・高コスト。BigQueryは後者専用。
- **カラム指向（列指向）ストレージ**：行ではなく列ごとにデータを並べて保存する。集計は「特定の列だけ」を読むことが多いので、必要な列だけスキャンでき桁違いに速い・安い。
- **スキャンしたデータ量で課金**（オンデマンド課金時）。サーバー台数や稼働時間ではなく「クエリが読んだバイト数」が料金の単位。ここが従来DBと最も違う発想。
- ログ分析、行動ログ、売上集計、機械学習の前処理（BigQuery ML でSQLだけでモデル作成も可）など、「大量データをSQLで殴る」用途の定番。

## 基本の使い方（gcloud / コンソール / SQL）
データセット（テーブルの入れ物）→ テーブル、という階層。`プロジェクト.データセット.テーブル` で参照する。

```bash
# データセット作成（ロケーション指定は後から変えられないので注意）
bq --location=asia-northeast1 mk --dataset my_project:analytics

# CSVをテーブルにロード（スキーマ自動検出）
bq load --autodetect --source_format=CSV \
  analytics.access_logs ./logs.csv

# クエリ実行（標準SQL）。--dry_run で「課金されるスキャン量」を事前確認できる
bq query --use_legacy_sql=false --dry_run \
  'SELECT user_id, COUNT(*) FROM `my_project.analytics.access_logs`
   WHERE event_date = "2026-06-01" GROUP BY user_id'
```

```sql
-- パーティション + クラスタリングつきテーブル定義
-- パーティション: 日付などで物理的に区切り、その日だけスキャンできるようにする
-- クラスタリング: 区切った中をさらにソートし、絞り込みを効かせる
CREATE TABLE `my_project.analytics.events`
(
  user_id    INT64,
  event_type STRING,
  payload    STRING,
  created_at TIMESTAMP
)
PARTITION BY DATE(created_at)        -- 日単位パーティション
CLUSTER BY user_id, event_type;      -- よく絞る列でクラスタリング
```

```sql
-- ストリーミング挿入（INSERTでリアルタイム追加）も可能だが、別途課金
INSERT INTO `my_project.analytics.events` (user_id, event_type, created_at)
VALUES (101, 'click', CURRENT_TIMESTAMP());
```

コンソールでは「BigQuery Studio」でSQLを書いて実行、結果をその場で可視化・スプレッドシート連携できる。クエリ実行前に右上に **「このクエリで処理されるバイト数」** が表示されるので必ず見る習慣を。

## 実務での勘所
- **必要な列だけ書く**：`SELECT *` ではなく `SELECT user_id, event_type` と列を絞るだけでスキャン量＝料金が激減する（列指向の恩恵を受けるため）。
- **パーティションで日付を絞る**：`WHERE DATE(created_at) = '2026-06-01'` のようにパーティション列で絞れば、その日のデータしかスキャンされない。全期間スキャンを防ぐ最重要テクニック。
- **クラスタリング**で `user_id` 等のよく使う絞り込みを効かせ、さらにスキャン量を減らす。
- **`--dry_run` / コンソールの推定バイト数**で、実行前に必ずコストを見積もる。
- 取り込みは **バッチロード（無料）** が基本。リアルタイムが要るところだけ **ストリーミング挿入（有料）** に限定する。
- 巨大な生データ（CSV/JSON/Parquet）は [cloud_storage.md](./cloud_storage.md) に置き、BigQueryからロードまたは外部テーブルとして参照する構成が定番。

## ハマりどころ / アンチパターン
- **`SELECT *` でフルスキャン＝高額**：列指向の利点を捨て、全列・全行を読むので料金が跳ね上がる。「ちょっと中身を見たい」も `LIMIT` を付けても**スキャン量は減らない**（LIMITは課金前の絞り込みにならない）。プレビューはコンソールの「プレビュー」タブを使う。
- **パーティションを切っていない／絞っていない**：`WHERE` で日付を指定してもパーティション列でなければ全期間スキャン。設計時点でパーティションキーを決めておく。
- **課金単位を「行数」と勘違い**：課金は **スキャンしたバイト量**。1行も返らないクエリでも、読んだ列×行のバイトに対して課金される。
- **ストリーミング挿入の多用**：リアルタイム挿入は1件単位で課金が乗り、バッチロード（無料）より高くつく。ログを1行ずつ流すと地味に高額化。
- **オンデマンドとスロット課金の混同**：従量（スキャン量）課金と定額（スロット予約）課金で最適化方針が逆。まずはオンデマンドで、コストが読めてきたら定額を検討。
- **ロケーション不一致**：データセットのロケーション（例 `asia-northeast1`）は後から変更不可。別リージョンのテーブル同士は同じクエリで結合できない。
