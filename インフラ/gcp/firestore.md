# Firestore（GCP）

## ひとことで言うと
Googleのフルマネージドな**NoSQL ドキュメントデータベース**。データを「**コレクション**（入れ物）の中の**ドキュメント**（JSONライクなキー値の塊）」として持つ。Firebase SDK経由でモバイル/Webから直接読み書きでき、**リアルタイム同期**（変更が即座にクライアントへプッシュ）が標準で付く。

## 役割・なぜ必要か
- 「スキーマがゆるく、機能ごとにデータ形が変わる」アプリ（チャット、フィード、ユーザープロフィール等）に向く。テーブル定義を固める前に書き始められる。
- **リアルタイム同期**：チャットや共同編集のような「他人の更新を即反映」したいUIを、ポーリングなしで実現できる。
- **モバイル/Web SDK（Firebase）から直結**：バックエンドAPIを経由せずクライアントが直接DBを読み書きでき、セキュリティルールで認可をかける。サーバーレス開発と相性が良い。
- 水平スケールが効き、ドキュメント数が増えても性能が落ちにくい（その代わりRDB的な集計は苦手）。

## 基本の使い方（gcloud / コンソール）
```bash
# Firestore データベースを作成（Nativeモードを推奨）
gcloud firestore databases create \
  --location=asia-northeast1 \
  --type=firestore-native

# 複合インデックスの一覧/作成（クエリに必須なことが多い）
gcloud firestore indexes composite list
```

```javascript
// Web SDK（Firebase）からの読み書きとリアルタイム購読
import { getFirestore, collection, addDoc, query, where, onSnapshot } from "firebase/firestore";
const db = getFirestore();

// 書き込み（users コレクションにドキュメント追加）
await addDoc(collection(db, "users"), { name: "Taro", age: 28, active: true });

// クエリ + リアルタイム購読（active な user を監視、変更が即届く）
const q = query(collection(db, "users"), where("active", "==", true));
onSnapshot(q, (snap) => {
  snap.forEach((doc) => console.log(doc.id, doc.data()));
});
```
コンソールなら「Firestore → データ」でコレクション/ドキュメントをGUIで追加・編集でき、「インデックス」タブで複合インデックスを管理する。

## 実務での勘所
- **クエリは“事前に作ったインデックス”が前提**。等値1つ程度は自動だが、複数フィールドの絞り込みや並べ替えを混ぜると**複合インデックス**が要る。`firestore.indexes.json` で定義してデプロイすると管理が楽。
- **セキュリティルール（Security Rules）で認可する**。クライアント直結なので、ここを書かないと「誰でも全データ読み書き可」になる。必ずルールを書く。
- **データモデリングは“読み取りクエリから逆算”**。後からのJOINがないので、表示したい形に合わせて非正規化（重複保持）するのが定石。
- **集計はコストと相性に注意**。件数カウントや合計は集計クエリ/カウンタドキュメントで設計する。RDB的なGROUP BYは持たない。
- 大量バッチ更新は**バッチ書き込み/トランザクション**でまとめる（1書き込みごとの課金とレート制限を意識）。

## ハマりどころ / アンチパターン
- **インデックス未作成のクエリで実行時エラー**：複合条件を投げると「このクエリにはインデックスが必要」とエラーになる。コンソールのエラーリンクから作成 or 事前定義しておく。
- **料金は“読み書き回数 × ドキュメント数”課金**。一覧で毎回全件読むUIや、リアルタイム購読の貼りすぎで読み取り課金が跳ねる。取得件数を絞る・ページングする。
- **巨大ドキュメント / 深いネスト**：1ドキュメントに配列を無限に足す設計は更新衝突とサイズ上限で詰まる。サブコレクションへ分ける。
- **RDBのつもりで正規化**：参照を辿る読み取りが増え、回数課金で不利。表示単位で持つ。→ [cloud_sql.md](./cloud_sql.md)
- **ホットスポット**：連番IDや時系列でキーを集中させると書き込みが偏る。IDは自動生成（分散）を使う。
