# ハンズオン：GCP を「課金ゼロ」でエミュレータで触る

> **このファイルの位置づけ**：他のファイル（[getting_started.md](./getting_started.md) / [firestore.md](./firestore.md) 等）は「分かっている人が引く辞書」。
> これは**手を動かして1回成功するための実習**。上から順にコピペすれば、0から動くところまで行けます。

## 💰 課金に関する注意（最初に必ず読む）
- **この実習は課金ゼロで完結します。** 本物のGCP（あなたのプロジェクト・クレジットカード）には一切アクセスしません。
- 使うのは **エミュレータ**：
  - **Firestoreエミュレータ**（`gcloud` 同梱）＝ FirestoreをPC内で再現。
  - **fake-gcs-server**（dockerイメージ）＝ Cloud StorageをPC内で再現。
- どちらも自分のPCの中の偽GCPに対して操作するので、請求は発生しません。
- 本物のGCPでやる場合の注意（無料枠＋必ず削除）は末尾にまとめます。
- それでも最後は **必ず片付け**（プロセス停止・コンテナ削除）まで行ってください。下記「必ず片付ける」章を実行すれば完全に消えます。

## ゴール（終わったら何ができる？）
- **Firestoreエミュレータ**を起動して、**ドキュメントをCRUD（作成・取得）できる**
- **fake-gcs-server**（Cloud Storage代替）を起動して、**ファイルをupload/downloadできる**
- わざと **エミュレータに繋がない状態でアクセスして失敗 → 自分で直せる**
- ここまでやると [firestore.md](./firestore.md) / [cloud_storage.md](./cloud_storage.md) / [getting_started.md](./getting_started.md) が「読める」ようになる

**所要時間**：20〜30分　**前提**：Docker と Python（pip）、`curl` が動くこと（gcloud は無くても進めます）

## 準備：Docker と pip が使えるか確認
```bash
docker version
```
**成功**：`Client:` と `Server:` の両方にバージョンが出る。
**失敗**：`Cannot connect to the Docker daemon` → Docker Desktop（またはdockerサービス）が起動していない。起動してから再実行。

```bash
python3 -m pip --version && curl --version | head -1
```
**成功**：pipのバージョンと `curl X.X.X ...` が出る。
**失敗**：pipが無ければ `python3 -m ensurepip --upgrade`。curlが無ければ OS のパッケージで入れる。

作業用フォルダを作る:
```bash
mkdir -p ~/gcp-handson && cd ~/gcp-handson
```

## パートA：Cloud Storage を fake-gcs-server で触る（dockerだけで完結）
> こちらは gcloud 不要。dockerとcurlだけで動くので先にやります。

### ステップA-1：fake-gcs-server を起動する
**やること**：Cloud Storage互換のサーバを自分のPCで起動する。
**なぜ**：Cloud Storage＝GCPで最も使うストレージ。これをPC内で再現し、本物に触れず課金もされずに「バケット→オブジェクト」を体験する。
```bash
docker run -d --name fake-gcs -p 4443:4443 \
  fsouza/fake-gcs-server -scheme http -port 4443
```
- `-p 4443:4443`＝サーバの入口をPCに繋ぐ。`-scheme http`＝（実習簡略化のため）HTTPで待受。

起動を確認:
```bash
sleep 3
curl -s http://localhost:4443/storage/v1/b
```
**成功**：`{"kind":"storage#buckets","items":...}` のようなJSON（または空の `items`）が返る。
**失敗**：
- 接続拒否 → まだ起動中。あと数秒待って再実行。`docker logs fake-gcs | tail -5` を確認。
- `port is already allocated` → `docker rm -f fake-gcs` してから `-p 4444:4443` に変えて起動し直し、以降の `4443` を `4444` に読み替える。

### ステップA-2：バケットを作る
**やること**：オブジェクトを入れる箱（バケット）を1つ作る。
**なぜ**：Cloud Storageでは、ファイル（オブジェクト）は必ずバケットの中に入る。まず箱を用意する。
```bash
curl -s -X POST \
  "http://localhost:4443/storage/v1/b?project=handson" \
  -H "Content-Type: application/json" \
  -d '{"name": "handson-bucket"}'
```
**成功**：`{"kind":"storage#bucket","name":"handson-bucket",...}` が返る。
**失敗**：`Conflict` / `already exists` → 既に作成済み。次へ進んでよい。

バケット一覧で確認:
```bash
curl -s http://localhost:4443/storage/v1/b | python3 -m json.tool
```
**成功**：`"name": "handson-bucket"` が一覧に見える。

### ステップA-3：ファイルをupload（put）する
**やること**：ローカルのファイルをバケットに入れる。
**なぜ**：「オブジェクトを置く」がCloud Storageの最重要操作。
```bash
echo "hello cloud storage $(date)" > sample.txt
curl -s -X POST \
  "http://localhost:4443/upload/storage/v1/b/handson-bucket/o?uploadType=media&name=sample.txt" \
  -H "Content-Type: text/plain" \
  --data-binary @sample.txt
```
- `uploadType=media`＝中身そのものを送る方式。`name=sample.txt`＝バケット内でのオブジェクト名（キー）。

**成功**：`{"kind":"storage#object","name":"sample.txt",...}` が返る。
**失敗**：`No such bucket` → バケット名のtypo。ステップA-2のバケット作成からやり直す。

### ステップA-4：download（get）する
**やること**：今置いたファイルを取り戻す。
```bash
curl -s "http://localhost:4443/storage/v1/b/handson-bucket/o/sample.txt?alt=media"
```
**成功**：`hello cloud storage ...`（さっき書いた内容）が表示される。
→ **これが「Cloud Storageに置いたファイルを取り戻した」証拠**。本物のGCPでも概念は同じ（`gsutil cp` / SDKで同じことをする）。

## パートB：Firestore をエミュレータで触る（gcloud が必要）
> こちらは `gcloud` のFirestoreエミュレータを使います。gcloud が無い場合はパートBを飛ばしてOK（パートAだけでもCloud Storageは体験できています）。

### ステップB-1：gcloud と エミュレータ部品を確認・用意
```bash
gcloud --version | head -1
```
**成功**：`Google Cloud SDK XXX.X.X` が出る → 次へ。
**失敗**：`command not found: gcloud` → gcloud未インストール。パートBは飛ばして「必ず片付ける」へ進んでよい（本物のインストール手順は [getting_started.md](./getting_started.md)）。

Firestoreエミュレータ本体（cloud-firestore-emulator）を入れる:
```bash
gcloud components install cloud-firestore-emulator beta --quiet
```
**成功**：インストールが完了する（既に入っていれば `All components are up to date.`）。
**失敗**：`you cannot perform this action because the Cloud SDK ... managed by an external package manager` → OSのパッケージ版gcloudだとcomponents追加が制限されることがある。その場合は `sudo apt-get install google-cloud-cli-firestore-emulator`（Debian/Ubuntu系）等で入れる。
**補足**：エミュレータは内部でJavaを使う。`java -version` が通らなければ JDK（例：`default-jre`）を入れる。

### ステップB-2：Firestoreエミュレータを起動する
**やること**：FirestoreをPC内で起動する。
**なぜ**：Firestore＝GCPの代表的NoSQL。これをローカルで動かし、本物に触れず「コレクション→ドキュメント」を体験する。

**この端末はエミュレータ専用**にします（別の端末で操作する）。
```bash
gcloud beta emulators firestore start --host-port=localhost:8085
```
**成功**：`Dev App Server is now running.` や `running on localhost:8085` のような行が出て、起動したまま止まる（これが正常。閉じないこと）。
**失敗**：`port ... already in use` → `--host-port=localhost:8086` に変えて、以降の `8085` を `8086` に読み替える。

### ステップB-3：別の端末でドキュメントをCRUDする
**新しい端末を開いて**、エミュレータに向け先を固定する:
```bash
cd ~/gcp-handson
export FIRESTORE_EMULATOR_HOST=localhost:8085
export FIRESTORE_PROJECT_ID=handson-project
```
- `FIRESTORE_EMULATOR_HOST` を設定すると、各種SDK/RESTが**自動でエミュレータに向く**（本物に飛ばない安全装置）。

ドキュメントを**作成（Create）**する（RESTで直接）:
```bash
curl -s -X POST \
  "http://localhost:8085/v1/projects/${FIRESTORE_PROJECT_ID}/databases/(default)/documents/users?documentId=u001" \
  -H "Content-Type: application/json" \
  -d '{"fields": {"name": {"stringValue": "Taro"}, "age": {"integerValue": "20"}}}'
```
- `users` がコレクション、`documentId=u001` がドキュメントID。値は `{"stringValue": ...}` のように **型を明示**するのがFirestore RESTの書式。

**成功**：`{"name": ".../documents/users/u001", "fields": {...}, ...}` が返る。
**失敗**：`Connection refused` → エミュレータが起動していない／ポート違い。ステップB-2の端末で `running on localhost:8085` が出ているか確認。

ドキュメントを**取得（Read）**する:
```bash
curl -s "http://localhost:8085/v1/projects/${FIRESTORE_PROJECT_ID}/databases/(default)/documents/users/u001"
```
**成功**：`"name": "Taro"`, `"age": "20"` を含むJSONが返る。
→ **これが「Firestoreにドキュメントを書いて読めた」証拠**。コレクション/ドキュメントというFirestoreの構造を体験できた。

## ステップ：わざと失敗させて、直す
**なぜ**：実務で必ず出会う「向き先の設定ミス」を、安全な場所で起こして直すと一生忘れない。

向き先を**わざと外して**（ポートを変えて）アクセスしてみる:
```bash
curl -s "http://localhost:9999/storage/v1/b"
```
**結果**：`curl: (7) Failed to connect to localhost port 9999` のような接続失敗が返る。
**読み解き**：そこには誰も待っていない＝**ポート/ホストの指定ミス**。本物のGCPでも「エンドポイント・プロジェクトID・リージョンの指定ミス」は頻出の原因。

正しいポートでやり直す:
```bash
curl -s "http://localhost:4443/storage/v1/b" | python3 -m json.tool
```
**成功**：バケット一覧が返る。→ 原因＝向き先の不一致、を体験で理解できた。

## 必ず片付ける（このまま閉じない）
**エミュレータ類はPC内なので課金は発生しませんが、プロセス・コンテナが残り続けるとメモリ/ポートを占有します。** 必ず消しましょう。
```bash
# Cloud Storage（fake-gcs-server）コンテナを止めて削除（中のバケットも消える）
docker rm -f fake-gcs

# Firestoreエミュレータは、起動した端末で Ctrl+C で停止。
# 残ってしまった場合（別端末から強制停止）:
pkill -f cloud-firestore-emulator 2>/dev/null || true

# 環境変数を解除（このシェルだけ）
unset FIRESTORE_EMULATOR_HOST FIRESTORE_PROJECT_ID

# 作業フォルダごと消すなら
rm -rf ~/gcp-handson
```
**確認**：`docker ps -a | grep fake-gcs` で何も出なければCloud Storage側は完全に消えている。

## 本物のGCPでやる場合の注意（無料枠＋必ず削除）
| 項目 | エミュレータ（この実習） | 本物のGCP |
|---|---|---|
| 操作対象 | PC内の偽GCP | あなたの**プロジェクト**内の実リソース → [getting_started.md](./getting_started.md) |
| 認証 / IAM | ダミーで素通り | `gcloud auth login` ＋ IAM権限が必須。最小権限が鉄則 → [iam.md](./iam.md) |
| API有効化 | 不要 | サービスごとに `gcloud services enable ...` が必要 → [getting_started.md](./getting_started.md) |
| 課金 | **ゼロ** | **無料枠（Free Tier）の範囲なら基本無料**。ただし超過・放置で課金。予算アラート必須 |
| 片付け | プロセス停止・コンテナ削除 | バケット/ドキュメント/**プロジェクト自体**を削除しないと課金が続きうる → [pitfalls.md](./pitfalls.md) |

> 本物に移るときは、まず [getting_started.md](./getting_started.md) でプロジェクト作成・API有効化・予算アラートを整えてから。検証が終わったら**プロジェクトごと削除**するのが一番安全。
