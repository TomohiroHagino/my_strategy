# 比較（nginx / Apache / Caddy / Envoy / Traefik / HAProxy / クラウドLB）（Webサーバ）

## ひとことで言うと
「前段に何を置くか」の選択肢の住み分け。**単一サーバの前段なら nginx / Caddy**、**コンテナ/k8s なら Traefik / Envoy（Ingress）**、**マイクロサービス間の通信制御なら Envoy**、**AWSフルマネージドなら ALB＋CloudFront**。用途で選ぶ。

## 役割・なぜ必要か
- どれも「リバースプロキシ/ロードバランサ」だが、得意領域・設定方法・動的さが違う。ミスマッチな選択（単純配信にEnvoy等）は運用を重くする。

## 比較表
| ツール | 処理モデル | 設定方法 | TLS自動 | 動的サービス発見 | HTTP/3 | 得意領域 | 学習コスト |
|---|---|---|---|---|---|---|---|
| **nginx** | イベント駆動 | 設定ファイル | 別途certbot | △（要reload） | ○ | 静的配信・LB・万能 | 低〜中 |
| **Apache** | MPM選択 | 設定＋.htaccess | certbot | × | △ | .htaccess・mod_php資産 | 中 |
| **Caddy** | イベント駆動(Go) | Caddyfile（極小） | **自動(既定ON)** | △ | ○ | 個人〜中小・即HTTPS | **最低** |
| **Envoy** | イベント駆動(C++) | YAML/**xDS API** | 別途 | **◎（動的）** | ○ | サービスメッシュ・gRPC | **高** |
| **Traefik** | イベント駆動(Go) | **ラベル/自動検出** | **自動** | **◎（k8s/Docker）** | ○ | コンテナ/k8s Ingress | 中 |
| **HAProxy** | イベント駆動 | 設定ファイル | 対応 | △ | △ | L4/L7 LBの定番・高性能 | 中 |
| **クラウドLB/CDN** | マネージド | コンソール/IaC | **マネージド** | ◎ | ○ | AWS/GCPフルマネージド | 低（IaCは別） |

## 各ツールの要点
- **nginx**：迷ったらこれ。静的・プロキシ・LB・キャッシュを1つで。情報量が最多。→ [nginx.md](./nginx.md)
- **Apache**：既存資産・共有ホスティング・WordPress。新規での第一候補ではない。→ [apache.md](./apache.md)
- **Caddy**：Let's Encryptを**自動**でやる。設定が数行。個人サイト〜中小で楽。
  ```caddyfile
  example.com {
      reverse_proxy localhost:3000   # これだけでHTTPSも自動
  }
  ```
- **Envoy**：サービスメッシュ（Istio）のデータプレーン。**xDSで動的設定**、gRPC/mTLS/リトライ/サーキットブレーカが強力。単純な前段には過剰。
- **Traefik**：Dockerやk8sの**ラベル/アノテーションから自動でルーティング**を生成。コンテナ環境で設定レス運用。
  ```yaml
  # docker-compose のラベルだけでルーティング
  labels:
    - "traefik.http.routers.app.rule=Host(`example.com`)"
  ```
- **HAProxy**：L4/L7ロードバランサの old but gold。高スループット・細かいヘルスチェック。
- **クラウドLB/CDN**：AWS=**ALB**(L7)/**NLB**(L4)/**CloudFront**(CDN)、GCP=Cloud Load Balancing/Cloud CDN。証明書・スケール・冗長化をマネージドで。→ [../aws/cloudfront_route53.md](../aws/cloudfront_route53.md) / [../aws/containers.md](../aws/containers.md)

## 選び方フロー
```
 単一VPS/VMの前段が欲しい
   ├ とにかく楽にHTTPS         → Caddy
   └ 細かく制御・情報量重視     → nginx

 コンテナ/Kubernetes
   ├ Ingressを手軽に（自動検出） → Traefik / Ingress-nginx
   └ サービスメッシュ・gRPC制御  → Envoy（Istio）

 マイクロサービス間の通信制御   → Envoy（リトライ/CB/mTLS）

 AWSにフルマネージドで寄せる    → CloudFront → ALB →（必要なら）nginx → アプリ
```

## Ingress Controller との関係
- Kubernetesでは、これらが **Ingress Controller** として動き、`Ingress`/`Gateway` リソースの宣言に従って外部トラフィックをServiceへ振り分ける。
- 代表：**ingress-nginx**（nginxベース）、**Traefik**、**Envoy系（Contour / Gateway API）**。
- k8s環境では「nginxを手で書く」より、Ingressリソース＋Controllerで宣言的に管理するのが主流。→ [../aws/containers.md](../aws/containers.md)

## 実務での使い方・定番パターン
- **個人/小規模**：Caddy（自動HTTPS）か nginx。
- **既存PHP/レンタルサーバ**：Apache（.htaccess）。
- **Docker Compose**：Traefik でラベルベース、または nginx を1つ前段に。
- **Kubernetes**：ingress-nginx か Traefik、メッシュ要件があれば Envoy/Istio。
- **AWS**：ALB＋CloudFrontに寄せ、必要なら裏で nginx を静的配信＋整形に使う。

## ハマりどころ / アンチパターン
- **用途過剰**：単純配信にEnvoy/Istioを持ち込み運用が重くなる。要件に合わせて段階を選ぶ。
- **Caddyの自動TLSが詰む**：閉域・レート制限・80/443塞ぎでLet's Encrypt検証に失敗。DNS-01やステージング環境で確認。
- **二重持ちで責務が曖昧**：クラウドLBとnginxの両方でルーティング/TLS/キャッシュを持ち、どこで何をしているか不明に。役割を明確に分ける。
- **k8sで手書きnginxに固執**：IngressリソースやGateway APIを使わず運用が属人化。
