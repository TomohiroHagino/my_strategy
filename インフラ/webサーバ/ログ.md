# ログ（アクセスログ・エラーログ）（Webサーバ）

## ひとことで言うと
誰が何にアクセスし、どこで失敗・遅延したかを記録する設定と読み方。**アクセスログ**（全リクエスト）と**エラーログ**（異常）の2系統。`$request_time` と `$upstream_response_time` を出しておくと「Webサーバ滞留かアプリ遅延か」を切り分けられる。

## 役割・なぜ必要か
- 障害時の一次情報。ステータス分布・遅いURL・攻撃の痕跡をここから読む。→ [../障害対応/ログと監視.md](../障害対応/ログと監視.md)
- 性能チューニングの計測元（どのURLが遅いか）。→ [チューニング.md](./チューニング.md)

## nginx のログ設定
```nginx
# httpコンテキスト：combined を拡張して処理時間を出す
log_format main '$remote_addr - $remote_user [$time_local] '
                '"$request" $status $body_bytes_sent '
                '"$http_referer" "$http_user_agent" '
                'rt=$request_time uct=$upstream_connect_time urt=$upstream_response_time '
                'cache=$upstream_cache_status';

access_log /var/log/nginx/access.log main;
error_log  /var/log/nginx/error.log warn;   # debug/info/notice/warn/error/crit
```
JSON形式（ログ集約基盤に流すなら推奨）:
```nginx
log_format json escape=json '{"time":"$time_iso8601","ip":"$remote_addr",'
  '"method":"$request_method","uri":"$request_uri","status":$status,'
  '"rt":$request_time,"urt":"$upstream_response_time","ua":"$http_user_agent"}';
access_log /var/log/nginx/access.json json;
```
ヘルスチェックをログから除外（ログ汚染対策）:
```nginx
map $request_uri $loggable { ~^/healthz$ 0; default 1; }
access_log /var/log/nginx/access.log main if=$loggable;
```

## Apache のログ設定
```apache
LogFormat "%h %l %u %t \"%r\" %>s %b \"%{Referer}i\" \"%{User-Agent}i\" rt=%D" combined
CustomLog /var/log/apache2/access.log combined
ErrorLog  /var/log/apache2/error.log
LogLevel  warn
```
- `%D` はマイクロ秒の処理時間。

## ログの読み方
| 着眼 | 見るもの |
|---|---|
| 異常の量 | `$status` 分布（4xx/5xx の急増） |
| 遅延の所在 | `$request_time`（全体） vs `$upstream_response_time`（アプリ） |
| キャッシュ効率 | `$upstream_cache_status`（HIT/MISS率） |
| 攻撃痕跡 | 同一IPの大量404、怪しいUA、`/.env`等への試行 |
- **`request_time` ≫ `upstream_response_time`** ＝ nginx側の滞留（バッファ・ネットワーク・遅いクライアント）。
- **`upstream_response_time` が大きい** ＝ アプリ/DBが遅い。→ [../障害対応/切り分け.md](../障害対応/切り分け.md)

解析ワンライナー（一次調査）:
```bash
# ステータスコード分布
awk '{print $9}' access.log | sort | uniq -c | sort -rn

# 遅いURL上位（mainフォーマットの rt= フィールドを抽出）
awk -F'rt=| ' '{print $0}' access.log | grep -oE 'rt=[0-9.]+ "[^"]+"' | sort -rn | head

# アクセス数上位IP
awk '{print $1}' access.log | sort | uniq -c | sort -rn | head
```

## ローテーション
```
# /etc/logrotate.d/nginx
/var/log/nginx/*.log {
    daily
    rotate 14
    compress
    delaycompress
    missingok
    notifempty
    sharedscripts
    postrotate
        # ファイルを切り替えたらnginxにFD再オープンを通知
        [ -f /run/nginx.pid ] && kill -USR1 $(cat /run/nginx.pid)
    endscript
}
```
- nginxは `USR1`、Apacheは `graceful` でログFDを開き直す（これを忘れると回転後に書き込めない/古いファイルに書き続ける）。

## コンテナでのログ
```nginx
# ファイルではなく標準出力/エラーへ（公式イメージは既定でこれ）
access_log /dev/stdout main;
error_log  /dev/stderr warn;
```
- コンテナは**ログを標準出力に出し、収集はランタイム/基盤側**に任せる（ファイルに書くと消える）。→ [../docker/](../docker/)

## 集約・可観測性
```
 nginx/Apache → (Fluent Bit / Vector) → Loki / CloudWatch Logs / Elasticsearch
                                          → Grafana / Kibana で可視化・アラート
```
- 構造化（JSON）ログにしておくとフィールド検索・集計が容易。
- メトリクス/トレースと合わせて可観測性を構成。→ [../../DevOps/observability.md](../../DevOps/observability.md)

## 実務での使い方・定番パターン
- **処理時間フィールドは必ず入れる**（`$request_time`/`$upstream_response_time`）。後からの障害解析・遅延調査の質が段違い。
- **ヘルスチェック/静的はログ除外 or `access_log off`** でノイズとI/Oを減らす。
- **本番はJSON＋集約基盤**、ローカルは人間可読の combined、と使い分け。
- 個人情報（トークン・メール）をURL/ヘッダに出さない（ログに残る）。

## ハマりどころ / アンチパターン
- **ローテ未設定でディスク満杯**：`access_log` が肥大化しディスクフルでサービス停止。logrotate必須。
- **回転後に書けない**：`USR1`/`graceful` 忘れで古いFDに書き続ける。
- **プロキシ下でIPが全部プロキシ**：`real_ip` 復元前のIPを記録してしまう。→ [リバースプロキシ.md](./リバースプロキシ.md)
- **ヘルスチェックでログ汚染**：毎秒の監視で本物のアクセスが埋もれる。除外する。
- **コンテナでファイル出力**：再起動で消える。標準出力へ。
- **`error_log` レベル不適**：`error`だけだと予兆を逃す、`debug`だと量が爆発。通常は`warn`。
