# Webサーバの仕組み（リクエスト処理モデル）（Webサーバ）

## ひとことで言うと
Webサーバが1台で同時に多数の接続を捌くための**内部処理モデル**の話。大きく「接続ごとにプロセス/スレッドを割り当てる方式（Apache prefork/worker）」と「少数のプロセスがイベントループで多数を多重処理する方式（nginx）」の2系統があり、後者が高同時接続に強い。

## 役割・なぜ必要か
- 同じ「HTTPを受けてアプリに渡す」でも、**捌き方の設計**でメモリ消費・最大同時接続・レイテンシが大きく変わる。
- nginx が主流になった理由も、Apache の MPM 選択も、すべてこの処理モデルの違いに根がある。設定チューニングもここを理解していないと勘所が掴めない。

## HTTPリクエストが処理される一周
```
1. TCP接続確立（3-way handshake）         ← OSのlisten queue（backlog/somaxconn）
2. TLSハンドシェイク（HTTPSなら）          ← 証明書・暗号スイート交渉（重い）
3. HTTPリクエスト受信・解析               ← メソッド/パス/ヘッダ/ボディ
4. ルーティング（どのserver/locationか）   ← バーチャルホスト・location判定
5a. 静的 → ファイルを読んで返す           ← sendfileでカーネル内転送
5b. 動的 → 裏のアプリへプロキシ           ← upstream/FastCGIへ転送し応答を待つ
6. レスポンス送信（gzip圧縮・ヘッダ付与）
7. 接続をkeep-aliveで再利用 or クローズ
```
このうち **2(TLS)** と **5b(アプリ待ち)** が時間を食う。だから「TLSは前段で終端」「アプリは静的処理から解放」という設計になる。

## 2つの処理モデル
### A. プロセス/スレッド型（Apache prefork / worker）
- 接続（または同時処理ぶん）に対して**1プロセス or 1スレッドを占有**させる。
- 分かりやすく、ブロッキング処理（mod_php等）と相性が良い。
- 弱点：接続数ぶんメモリを使う。1万接続なら1万プロセス相当 → メモリ枯渇。これが **C10K問題**（1万同時接続でプロセス型が破綻する問題）。
```
 接続1 → プロセスA（待っている間もメモリ占有）
 接続2 → プロセスB
 接続3 → プロセスC   … 接続が増えるほどプロセスも増える
```

### B. イベント駆動型（nginx / Apache event MPM）
- 少数のワーカープロセス（通常CPUコア数）が、**イベントループ（epoll/kqueue）**で何千もの接続を1プロセスで多重処理する。
- 「待ち（I/O）」の間は他の接続を処理し、準備できたものだけ進める（ノンブロッキング）。
- 強み：接続が増えてもプロセスは増えない＝メモリ効率が高く、高同時接続に強い。
```
 ワーカー1（epoll）┬ 接続1（待ち）
                   ├ 接続2（送信中）
                   ├ 接続3（受信中）   … 1プロセスで数千接続を回す
                   └ …
```

## モデル比較
| 観点 | プロセス/スレッド型 | イベント駆動型 |
|---|---|---|
| 代表 | Apache prefork/worker | **nginx** / Apache event |
| 同時接続あたりの資源 | プロセス/スレッド1つ | 接続ごとは軽い（FD1つ程度） |
| 高同時接続（C10K以上） | 弱い（メモリ枯渇） | **強い** |
| ブロッキング処理 | 得意（mod_php等） | 苦手（裏でFPM等に逃がす） |
| プログラミング難度 | 素直 | ノンブロッキング前提で複雑 |
| 設定の勘所 | プロセス数・スレッド数 | worker数・worker_connections |

## nginx のプロセス構成
```
 master プロセス（root）          ← 設定読込・worker管理・ログFD保持・無停止リロード
   ├ worker プロセス（CPU#0）     ← 実際にリクエストを処理（epollループ）
   ├ worker プロセス（CPU#1）
   └ cache manager / loader       ← proxy_cache の管理
```
- `master` は権限の高い処理（ポートbind・設定再読込）だけ。実処理は非特権の `worker`。
- 設定変更は `nginx -s reload`：master が新workerを起動し、旧workerは処理中の接続を終えてから終了する（**無停止リロード**）。

## 実務での使い方・定番パターン
- **新規は基本イベント駆動（nginx）**。静的配信・リバースプロキシ・高同時接続のどれも有利。
- **動的言語の実行はアプリサーバへ分離**：nginx/Apache(event) はI/O多重に徹し、PHP/Ruby/Python の実行は **PHP-FPM / Puma / Gunicorn** に逃がす。→ [アプリサーバ.md](./アプリサーバ.md)
- **worker数 = CPUコア数**が基本（`worker_processes auto`）。1コアを1ワーカーが専有してコンテキストスイッチを減らす。→ [チューニング.md](./チューニング.md)
- Apacheを使うなら **event MPM ＋ PHP-FPM** が現代的（prefork+mod_php は高負荷で詰む）。→ [apache.md](./apache.md)

## ハマりどころ / アンチパターン
- **prefork + mod_php で高同時接続 → メモリ枯渇 → OOM**：接続数ぶんプロセスが要る。event MPM＋FPMへ。
- **イベント駆動の中でブロッキング処理を書く**：1つの重い同期処理が、そのワーカーが抱える全接続を巻き込んで遅延させる。重い処理はアプリ側/非同期へ。
- **listen queue（backlog/somaxconn）が小さい**：接続が一気に来るとTCPの受付段階で取りこぼす。OSパラメータを上げる。→ [チューニング.md](./チューニング.md)
- **worker_connections だけ上げてFD上限を上げない**：`worker_rlimit_nofile`/OSの`ulimit -n`が頭打ちになる。
- **「Webサーバが遅い」と思ったら実はアプリ待ち**：`$upstream_response_time` を見る。滞留の主因を取り違えない。→ [ログ.md](./ログ.md)
