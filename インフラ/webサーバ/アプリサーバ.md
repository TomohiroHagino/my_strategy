# アプリサーバ（Webサーバとの違い）（Webサーバ）

## ひとことで言うと
アプリ本体（Rails / Django / Laravel / Express…）を実際に**言語ランタイム上で実行するプロセス**。nginx/Apacheは前段でI/Oを捌く受け口で、その裏で動的処理を担うのがアプリサーバ（Puma / Gunicorn / PHP-FPM / Tomcat 等）。両者は役割が違い、組み合わせて使う。

## Webサーバ と アプリサーバの役割分担
| 担当 | Webサーバ（nginx/Apache） | アプリサーバ（Puma等） |
|---|---|---|
| 静的ファイル配信 | ◎ 得意 | △ 可能だが非効率 |
| TLS終端・gzip | ◎ | ×（普通やらない） |
| ロードバランス | ◎ | ×（前段に任せる） |
| 言語コード実行 | ×（できない） | ◎ 本体 |
| DB/セッション/業務ロジック | × | ◎ |
| 同時接続の多重化 | ◎ イベント駆動 | 言語/方式による |
```
 nginx/Apache（前段：TLS・静的・LB） → アプリサーバ（言語実行） → DB/Redis
```
- なぜ分けるか：アプリサーバ単体は静的配信・TLS・大量接続が苦手。前段にWebサーバを置き、**動的処理だけをアプリサーバに集中**させると速く・安全・スケールしやすい。
- 例外：Goは標準ライブラリのHTTPサーバが高速で、Webサーバ無しで直接公開する構成もある（それでもTLS/LBで前段を置くことは多い）。

## 言語別の代表アプリサーバ
| 言語 | 代表 | 方式 | 補足 |
|---|---|---|---|
| Ruby | **Puma** | マルチスレッド＋クラスタ(worker) | Rails標準。Unicornはprefork（既存） |
| Python | **Gunicorn** / Uvicorn | prefork worker / ASGI | WSGI=Gunicorn、ASGI(async)=Uvicorn。uWSGIは旧定番 |
| PHP | **PHP-FPM** | FastCGIプロセスマネージャ | Webサーバから fcgi で接続 |
| Node | プロセス自体 | イベントループ | `cluster`/PM2 でコア数ぶん多重化 |
| Java | **Tomcat** / Jetty | スレッドプール | Spring Bootは組込Tomcatを内蔵 |

### Ruby: Puma
```ruby
# config/puma.rb
workers Integer(ENV.fetch("WEB_CONCURRENCY", 2))  # プロセス数（=コア数目安）
threads 5, 5                                       # 1プロセス内スレッド数
bind "unix:///run/puma.sock"                       # UNIXソケットで待受
preload_app!                                       # メモリ共有（CoW）
```
→ Railsの周辺は [../../バックエンド/ruby/rails/周辺インフラ/](../../バックエンド/ruby/rails/周辺インフラ/)

### Python: Gunicorn / Uvicorn
```bash
# WSGI（Django同期）
gunicorn app.wsgi:application --workers 3 --bind unix:/run/gunicorn.sock
# ASGI（FastAPI/Django async）
gunicorn app.asgi:application -k uvicorn.workers.UvicornWorker --workers 3 --bind 0.0.0.0:8000
```
- workers数の目安は `2 × CPUコア + 1`（同期I/O中心の場合）。

### PHP: PHP-FPM
```nginx
# nginx から FastCGI で PHP-FPM へ
location ~ \.php$ {
    fastcgi_pass unix:/run/php/php8.3-fpm.sock;   # or 127.0.0.1:9000
    fastcgi_index index.php;
    include fastcgi_params;
    fastcgi_param SCRIPT_FILENAME $document_root$fastcgi_script_name;
}
```
```ini
; /etc/php/8.3/fpm/pool.d/www.conf — プロセス数を独立制御
pm = dynamic
pm.max_children = 20      ; 同時PHP実行の上限（メモリから逆算）
pm.start_servers = 4
```

## 接続方式：UNIXドメインソケット vs TCPポート
| 方式 | 書き方 | 速さ | 用途 |
|---|---|---|---|
| UNIXソケット | `unix:/run/puma.sock` | 速い（カーネル内） | **同一ホスト**にWebサーバとアプリが同居 |
| TCPポート | `127.0.0.1:3000` / `10.0.0.5:3000` | やや遅い | **別ホスト/別コンテナ**、LBで複数台 |
```nginx
upstream app {
    server unix:/run/puma.sock;     # 同居ならソケット
    # server 127.0.0.1:3000;        # 別プロセス/コンテナならTCP
}
```
- コンテナ構成（Compose/ECS）はネットワーク越しになるので**TCP**が基本。
- 同一VM上に同居させるなら**ソケット**がオーバーヘッド小。

## ワーカ/スレッドのチューニング指針
- **プロセス数（worker）= CPUコア数が出発点**。CPUバウンドはコア数、I/Oバウンドはやや多めでも可。
- **メモリから上限を逆算**：`worker数 × 1プロセスのメモリ ≦ 搭載メモリ`。超えると **OOM Killer** に殺される。
- **スレッド（Puma/Tomcat）**：I/O待ちを並行化できるGVL/スレッド安全前提で増やす。Rubyはスレッドとworkerの併用。
- **DB接続数との整合**：`総worker数 × スレッド数 ≦ DBの最大接続数`。超えるとDB側で接続枯渇。→ [../aws/rds.md](../aws/rds.md)
- **環境変数で外出し**：`WEB_CONCURRENCY` / `--workers` をデプロイ環境ごとに調整。

## 実務での使い方・定番パターン
- 構成テンプレ：
  - `nginx → Puma(UNIXソケット) → Rails`
  - `nginx → PHP-FPM(fcgi) → Laravel`
  - `ALB → Gunicorn(TCP) → Django`（コンテナ）
  - `nginx → 組込Tomcat(TCP) → Spring Boot`
- **グレースフルリスタート**：デプロイ時に接続を切らずに入れ替え（Pumaの`phased-restart`、FPMの`reload`、systemdの`reload`）。
- **ヘルスチェック用エンドポイント**（`/healthz`）をアプリに用意し、前段/LBから監視。→ [リバースプロキシ.md](./リバースプロキシ.md)
- **タイムアウトを多段で揃える**：nginx `proxy_read_timeout` ＞ アプリのリクエストタイムアウト、にしすぎず内側を短く。

## ハマりどころ / アンチパターン
- **502 Bad Gateway**：ソケットのパス/権限違い、アプリ未起動、ポート相違。`upstream` と実待受・`ls -l /run/*.sock` を確認。
- **ソケット権限**：nginxユーザ（`www-data`/`nginx`）がソケットを読めないと502。FPM/Pumaのソケット所有者・mode を合わせる。
- **worker過多でOOM**：メモリを超えるworker数。逆算して上限設定。
- **DB接続枯渇**：worker×スレッドがDB max_connectionsを超過。プールサイズと整合させる。
- **preforkでメモリ肥大**：`preload_app!`/CoWを使わないと各workerがフルにメモリ確保。
- **タイムアウト不整合**：アプリは処理継続中なのにnginxが504で切る（または逆）。内側を短く設計。
- **アプリサーバで静的配信**：遅い。静的は前段nginxに任せる（`root`）。
- **グレースフル未設定**：デプロイのたびに進行中リクエストが切れる。
