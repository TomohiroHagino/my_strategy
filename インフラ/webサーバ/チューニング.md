# チューニング（性能設定）（Webサーバ）

## ひとことで言うと
Webサーバ/リバースプロキシの**さばける量と速さを引き上げる設定群**。ワーカ数・同時接続・keepalive・バッファ・圧縮・キャッシュ・OS資源を調整する。原則は「**計測してから直す**」。当て推量で値を盛らない。

## 役割・なぜ必要か
- デフォルト設定は安全側に控えめ。本番のトラフィックに合わせて引き上げないと、本来の性能が出ない/早期に飽和する。
- ただし闇雲に上げると別の上限（FD・メモリ・CPU）に当たって逆効果。**ボトルネックを特定→1つずつ**が鉄則。→ [../負荷検証/](../負荷検証/)

## ワーカ設定（nginx）
```nginx
worker_processes  auto;          # = CPUコア数（1コア1ワーカーでCS削減）
worker_rlimit_nofile 65535;      # ワーカが開けるFD上限（OS側も合わせる）
events {
    worker_connections 4096;     # 1ワーカーあたり最大接続
    multi_accept on;
}
```
- **最大同時接続の概算** ＝ `worker_processes × worker_connections`。
  例：4コア × 4096 ≒ 16,384。ただしリバースプロキシは1リクエストで「クライアント側＋upstream側」の2接続を使うので実効は約半分。
- `worker_connections` を上げても **FD上限**（`worker_rlimit_nofile`／OSの`ulimit -n`）が低いと頭打ち。

## keepalive（接続再利用）
```nginx
# クライアント↔nginx
keepalive_timeout  65;
keepalive_requests 1000;         # 1接続で捌くリクエスト数

# nginx↔upstream（毎回TCP/TLSを張り直さない）
upstream app { server 127.0.0.1:3000; keepalive 32; }
location / {
    proxy_http_version 1.1;
    proxy_set_header Connection "";   # これが無いとkeepaliveが効かない
}
```
- 効果：TCP 3-way handshake と TLS handshake の繰り返しを削減＝レイテンシ低下・CPU節約。

## バッファ
```nginx
client_max_body_size   20m;      # アップロード上限（小さいと413）
client_body_buffer_size 128k;
large_client_header_buffers 4 16k;  # 長いCookie/ヘッダ対策（小さいと400/414）

proxy_buffer_size   16k;         # 応答ヘッダ用
proxy_buffers       8 16k;       # 応答ボディ用
proxy_busy_buffers_size 32k;
```
- 小さすぎ：ヘッダ溢れで400/414、応答がディスク一時ファイル化して遅延。
- 大きすぎ：メモリを無駄に消費。実トラフィックのサイズ分布で決める。

## gzip / brotli（圧縮）
```nginx
gzip            on;
gzip_comp_level 5;               # 1〜9。上げるほどCPU↑・サイズ↓（5前後が実用）
gzip_min_length 1024;            # 小さすぎる応答は圧縮しない
gzip_types text/plain text/css application/json application/javascript
           image/svg+xml;
gzip_vary on;
# 事前圧縮済み(.gz)を返す（CPUを使わない）
gzip_static on;
```
- 画像/動画/zip は**圧縮済みなので対象外**（二重で無駄）。
- `gzip_comp_level` を9に上げるとCPU飽和することがある。帯域とCPUのトレードオフ。

## 静的配信の最適化
```nginx
sendfile      on;                # カーネル内でファイル→ソケット転送
tcp_nopush    on;                # sendfileと併用しパケットをまとめる
tcp_nodelay   on;                # keepalive応答を遅延させない
open_file_cache max=10000 inactive=60s;   # ファイルディスクリプタをキャッシュ

location ~* \.(jpg|png|css|js|woff2)$ {
    expires 30d;
    add_header Cache-Control "public, immutable";
    access_log off;              # 静的のログは切ってI/O節約
}
```

## proxy_cache（リバースプロキシキャッシュ）
```nginx
# httpコンテキスト
proxy_cache_path /var/cache/nginx levels=1:2 keys_zone=app:10m
                 max_size=1g inactive=60m use_temp_path=off;

location /api/ {
    proxy_pass http://app;
    proxy_cache app;
    proxy_cache_key "$scheme$host$request_uri";   # Cookieは入れない（ヒット率低下）
    proxy_cache_valid 200 1m;                       # 200応答を1分キャッシュ
    proxy_cache_use_stale error timeout updating;   # 裏が落ちても古い応答で凌ぐ
    add_header X-Cache-Status $upstream_cache_status;  # HIT/MISS可視化
}
```
- **マイクロキャッシュ**：`proxy_cache_valid 200 1s;`（1秒だけ）でも、秒間大量の同一リクエストを1回に集約でき、スパイクを吸収できる。
- **POST/ログイン後はキャッシュしない**：`proxy_no_cache`/`proxy_cache_bypass` で除外。

## HTTP/2・HTTP/3
```nginx
listen 443 ssl;
http2 on;                        # 多重化（1接続で並行リクエスト）
# HTTP/3(QUIC)はビルド対応が要る
# listen 443 quic reuseport;  add_header Alt-Svc 'h3=":443"';
```
- HTTP/2でヘッドオブラインブロッキングが緩和、HTTP/3はパケロス耐性が向上。

## OSレベル
```bash
# ファイルディスクリプタ上限（nginxのworker_rlimit_nofileと整合）
ulimit -n                        # 確認
# systemd: /etc/systemd/system/nginx.service.d/override.conf
[Service]
LimitNOFILE=65535
```
```bash
# カーネルパラメータ（/etc/sysctl.conf）
net.core.somaxconn = 1024        # listen queueの上限（バースト取りこぼし対策）
net.ipv4.ip_local_port_range = 1024 65535   # ephemeral port枯渇対策
net.ipv4.tcp_tw_reuse = 1
```
- 高負荷で「接続が詰まる」原因がアプリでなく**OS上限**のことは多い。

## 計測（直す前に見る）
```nginx
# 稼働状況
location /nginx_status { stub_status; allow 127.0.0.1; deny all; }
# ログに時間を出す（滞留 vs アプリ処理の切り分け）
log_format perf '$remote_addr "$request" $status '
                'rt=$request_time uct=$upstream_connect_time urt=$upstream_response_time';
```
- `$request_time`（全体）と `$upstream_response_time`（アプリ）の差＝nginx滞留。差が大きければバッファ/ネットワーク、`upstream`が大きければアプリが遅い。→ [ログ.md](./ログ.md) / [../負荷検証/結果分析.md](../負荷検証/結果分析.md)

## 実務での使い方・定番パターン
- **手順**：負荷試験で飽和点を出す → ログ/`stub_status`でボトルネック特定 → 該当パラメータを1つ調整 → 再計測。→ [../負荷検証/実施手順.md](../負荷検証/実施手順.md)
- **まず効く順**：keepalive（upstream含む）＞ gzip/静的キャッシュ ＞ proxy_cache ＞ worker/FD ＞ OSパラメータ。
- **コンテナ**：`worker_processes auto` はホストの全コアを見るため、CPU制限付きコンテナでは明示指定が安全。

## ハマりどころ / アンチパターン
- **worker_connections だけ上げる**：FD上限（`worker_rlimit_nofile`/`ulimit`）で頭打ち。両方上げる。
- **gzip_comp_level 9**：CPU飽和。実用は4〜6。
- **proxy_buffer不足**：応答がディスク一時ファイル化し遅延。サイズ分布に合わせる。
- **キャッシュキーにCookie**：個別化してヒット率が激減。キーから外す。
- **マイクロキャッシュ事故**：認証後・個人情報をキャッシュして他人に表示。POST/ログイン後を必ず除外。
- **somaxconn 据え置き**：バースト時にTCP受付で取りこぼす。
- **計測せず値を盛る**：別の上限に当たって逆に遅くなる。必ず計測ベース。
