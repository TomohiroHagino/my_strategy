# リバースプロキシ / ロードバランス / TLS終端（Webサーバ）

## ひとことで言うと
クライアントとアプリの間に立って受けたリクエストを裏のアプリへ取り次ぐ仕組みが「リバースプロキシ」。その立ち位置を使って **ロードバランス（振り分け）**・**TLS終端（HTTPS処理）**・**キャッシュ/圧縮/レート制限** をまとめて引き受ける。nginx / Apache / HAProxy / ALB / Envoy がこの役割を担う。

## フォワードプロキシとの違い
- **フォワードプロキシ**：クライアント側に立ち、社内→外部の出口を代理（誰が外に出るかを制御/隠す）。
- **リバースプロキシ**：サーバ側に立ち、外部→アプリの入口を代理（**裏に何台アプリがあるか・実体を隠す**）。
```
 フォワード:  [社内PC群] → [forward proxy] → インターネット
 リバース:    クライアント → [reverse proxy] ┬ [アプリ1]
                                            ├ [アプリ2]   ← 外からは1つに見える
                                            └ [アプリ3]
```

## 役割・なぜ必要か
1. **ロードバランス**：複数アプリへ分散。1台あたりの負荷を下げ、台数で性能を伸ばす（水平スケール）。
2. **TLS終端**：HTTPS復号をまとめて行い内部を軽量化。証明書管理も1箇所。
3. **単一の入口**：`/api`→backend、`/`→SPA とパスで振り分け、複数サービスを1ドメインに集約。
4. **守りと最適化**：レート制限・gzip・キャッシュ・ヘルスチェックで落ちた台を自動排除。→ [セキュリティ.md](./セキュリティ.md) / [チューニング.md](./チューニング.md)
5. **アプリの隠蔽**：内部構成（ポート/台数/実装）を外から見えなくする。

## ロードバランスのアルゴリズム
| アルゴリズム | nginx記法 | 挙動 | 適する場面 |
|---|---|---|---|
| ラウンドロビン（既定） | （無指定） | 順番に均等 | 各台が同等・処理時間が一定 |
| 重み付き | `server x weight=3;` | 比率で配分 | スペック差のある台 |
| 最少接続 | `least_conn;` | 接続数が最少の台へ | 処理時間にばらつき |
| IPハッシュ | `ip_hash;` | 同一IPは同一台へ | スティッキーが要る（非推奨寄り） |
| 汎用ハッシュ | `hash $request_uri consistent;` | キーで固定（コンシステント） | キャッシュ局所性を上げたい |
| ランダム | `random two least_conn;` | ランダム＋2択比較 | 大規模分散 |
```nginx
upstream backend {
    least_conn;
    server 10.0.0.11:3000 weight=2 max_fails=3 fail_timeout=10s;
    server 10.0.0.12:3000          max_fails=3 fail_timeout=10s;
    server 10.0.0.13:3000 backup;          # 通常使わず、全滅時のみ
    keepalive 32;                          # upstream接続の再利用
}
```

## ヘルスチェック
- **受動（passive）**：実トラフィックの失敗を見て切り離す（nginx OSS標準）。
  `max_fails=3 fail_timeout=10s`（10秒で3回失敗したら10秒間外す）＋ `proxy_next_upstream` で次の台へ再試行。
- **能動（active）**：定期的に `/healthz` を叩いて事前に判定（nginx Plus / HAProxy / ALB が標準対応）。
```nginx
location / {
    proxy_pass http://backend;
    proxy_next_upstream error timeout http_502 http_503;
    proxy_next_upstream_tries 2;
}
```
- アプリ側に**軽量な `/healthz`**（DB疎通までやるかは設計）を用意。→ [アプリサーバ.md](./アプリサーバ.md) / [../障害対応/ログと監視.md](../障害対応/ログと監視.md)

## TLS の扱い（3パターン）
```
 ① 終端して内部HTTP   : client =HTTPS=> [proxy] -HTTP-> app   （最も一般的・軽量）
 ② 終端して内部も再暗号: client =HTTPS=> [proxy] =HTTPS=> app  （内部も暗号必須の規制環境）
 ③ パススルー(L4)     : client =====HTTPS=====> app          （proxyは中身を見ない）
```
| 方式 | 復号場所 | 中身でルーティング | 用途 |
|---|---|---|---|
| ① 終端 | プロキシ | できる（L7） | 通常のWeb |
| ② 再暗号 | プロキシ→再暗号 | できる | 内部も暗号化が要件 |
| ③ パススルー | アプリ | できない（SNIのみ） | エンドツーエンド暗号・mTLS |
- ①が基本。終端後、裏アプリへ **`X-Forwarded-Proto: https`** を伝えないと、アプリが「HTTPだ」と誤認しリダイレクトループになる。

## X-Forwarded-* と本物IPの復元
| ヘッダ | 意味 |
|---|---|
| `X-Forwarded-For` | 元クライアントIP（カンマ区切りで多段） |
| `X-Forwarded-Proto` | 元のスキーム（http/https） |
| `X-Forwarded-Host` | 元のHost |
| `Forwarded`（RFC7239） | 上記を統合した標準ヘッダ |
```nginx
# 前段にALB/CDNがある時、その先の本物IPを復元
set_real_ip_from 10.0.0.0/8;     # 信頼する前段の範囲
real_ip_header   X-Forwarded-For;
real_ip_recursive on;
```
- **信頼できる前段からのみ**採用する（外部が自由に詐称できるため）。→ [セキュリティ.md](./セキュリティ.md)

## L4 と L7
| 層 | 見るもの | できること | 代表 |
|---|---|---|---|
| **L4（TCP/UDP）** | IP・ポート | 高速・中身を見ない振り分け、TLSパススルー | NLB / HAProxy(tcp) / nginx stream |
| **L7（HTTP）** | パス・ヘッダ・Cookie | パスで振り分け・書き換え・キャッシュ | ALB / nginx / Apache |
```nginx
# L4（TCP）ロードバランスは stream ブロック
stream {
    upstream db { server 10.0.0.21:5432; server 10.0.0.22:5432; }
    server { listen 5432; proxy_pass db; }
}
```

## バッファリングとストリーミング
```nginx
location /api/      { proxy_buffering on;  }   # 既定：応答を貯めてから返す（遅い裏を吸収）
location /events/   { proxy_buffering off; }   # SSE/ストリーミングは即時に流す
location /upload/   { proxy_request_buffering off; }  # 大きいアップロードを貯めない
```
- `proxy_buffering on`（既定）のままだと **SSE / チャンク配信が固まる**。ストリーミングは off。

## タイムアウトと接続再利用
```nginx
proxy_connect_timeout 5s;    # 裏への接続確立
proxy_send_timeout    60s;   # 裏へ送る間隔
proxy_read_timeout    60s;   # 裏からの応答待ち（重いAPIで504の主因）

# upstream keepalive を効かせる（毎回TCP/TLSを張り直さない）
proxy_http_version 1.1;
proxy_set_header Connection "";
```
- **多段タイムアウト設計**：内側（アプリ）を短く、外側（プロキシ）をやや長く。逆だと「アプリは処理中なのにプロキシが切る」504が増える。

## gateway系エラーの意味
| コード | 意味 | よくある原因 |
|---|---|---|
| **502** Bad Gateway | 裏から不正な応答/接続不可 | アプリ停止・ポート/ソケット違い |
| **503** Service Unavailable | 受けられない | 全upstreamがdown・過負荷・メンテ |
| **504** Gateway Timeout | 裏の応答待ちで時間切れ | アプリが遅い・`proxy_read_timeout`超過 |
→ 切り分けは [../障害対応/切り分け.md](../障害対応/切り分け.md)

## 実構成例（LB＋ヘルスチェック＋keepalive＋XFF一式）
```nginx
upstream app {
    least_conn;
    server 10.0.0.11:3000 max_fails=3 fail_timeout=10s;
    server 10.0.0.12:3000 max_fails=3 fail_timeout=10s;
    keepalive 32;
}
server {
    listen 443 ssl http2;
    server_name example.com;
    ssl_certificate     /etc/letsencrypt/live/example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/example.com/privkey.pem;

    location / {
        proxy_pass http://app;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_next_upstream error timeout http_502 http_503;
        proxy_read_timeout 60s;
    }
}
```

## 実務での使い方・定番パターン
- **セッションは外部化（Redis）**：スティッキー(`ip_hash`)依存だと負荷が偏る。状態を外に出して台を均等に使う。
- **クラウドはマネージドLB**：AWS=ALB/NLB、GCP=Cloud Load Balancing。証明書はACM等で自動管理。自前nginxを置くかマネージドに寄せるかを設計時に決める。→ [../aws/cloudfront_route53.md](../aws/cloudfront_route53.md)
- **段構成**：CDN(CloudFront) → ALB → nginx → アプリ、のように役割を重ねることもある（責務は明確に）。
- **Blue/Green・カナリア**は前段の振り分けで実現。→ [../../DevOps/deploy_strategies.md](../../DevOps/deploy_strategies.md)

## ハマりどころ / アンチパターン
- **リダイレクトループ**：TLS終端後にアプリがHTTPと誤認。`X-Forwarded-Proto` を見るよう設定。
- **本物IPが取れない**：ログが全部プロキシIP。`real_ip` で復元。
- **スティッキー依存の偏り**：`ip_hash`で特定台に集中。セッション外部化で解消。
- **ヘルスチェック未設定**：落ちた台へ振り続け一部失敗。`max_fails`＋active checkを。
- **タイムアウト不整合**：内側が長く外側が短いと504多発。内側を短く。
- **二重圧縮 / 二重TLS**：プロキシとアプリ両方でgzip/TLSして無駄。終端は1箇所に。
- **keepalive未設定**：毎回TCP/TLSを張り直し遅い。upstream `keepalive`＋HTTP/1.1。
- **buffering onでストリーミングが固まる**：SSE/長応答は `proxy_buffering off`。
