# よくある罠（pitfalls）（負荷検証）

## ひとことで言うと
負荷検証で結果を台無しにする・事故を起こす定番の落とし穴。**本番に負荷をかけて事故**／**テスト環境が本番と別物**／**平均で判断**／**ウォームアップなし**／**負荷クライアント側がボトルネック**／**1回で断定**／**1エンドポイントだけ**。どれも「測ったのに信用できない/危険」を生む。

## 役割・なぜ必要か
- 負荷試験は手間がかかる。**間違った前提で測ると、その手間が無駄になる**だけでなく、本番事故という最悪の結果も招く。
- 罠を先に知っておけば、計画・実施の各段で回避できる。多くは「**本番相当で・分布で・段階的に・複数回**」を守れば防げる。

## 基本（罠と回避策）

### 罠①：本番に負荷をかけて事故
**最悪の罠**。本番に負荷試験をかけ、実ユーザーを巻き込んでサービスを落とす。
```
✗ 「本番でしか正確に測れないから」と本番に大負荷
✓ 本番相当(staging)で測る。どうしても本番なら：
   - 低負荷・短時間・閑散時間帯・関係者周知
   - 即停止できる手元（kill用意）・監視を張りながら
   - フィーチャーフラグやカナリアで影響を限定
```
→ 実施前チェックで「対象URLがstagingか」を必ず確認。→ [実施手順.md](./実施手順.md)

### 罠②：テスト環境 ≠ 本番（結果が当てにならない）
```
✗ 1台のしょぼいstaging・データ100件・外部依存モックなしで測り「捌ける」
✓ スペック/台数/DBデータ件数/ネットワーク構成/オートスケール設定を本番に寄せる
   違うなら差分を記録し、結果を割り引いて解釈する
```
特に**DBのデータ件数**が違うと、索引の効きが変わりクエリ速度が別物になる。→ [計画.md](./計画.md)

### 罠③：平均で判断（テールを見落とす）
```
✗ 「平均レイテンシ 180ms、速い！」→ 実は p99 が 3秒で100人に1人が激遅
✓ p50/p90/p95/p99 の分布で見る。SLOは p95/p99 で定義する
```
→ [指標.md](./指標.md)。レイテンシは平均が嘘をつく代表格。

### 罠④：ウォームアップなしで計測
```
✗ 起動直後・キャッシュ空・プール未確立・JIT前・スケール未起動の数字で評価
✓ 低負荷で温めてから本計測。ウォームアップ中の数字は集計から除外
```
→ [実施手順.md](./実施手順.md)

### 罠⑤：負荷クライアント側がボトルネック
**サーバの限界と誤認する代表格**。負荷をかけるマシン自身が先に詰まっている。
```
✗ 1台のノートPCから k6 で10万RPSを出そうとし、PCのCPU/帯域/FDが先に天井
  → 「サーバは2000RPSが限界」と誤認（実はサーバはもっと捌けた）
✓ 負荷側のCPU/メモリ/帯域/ファイルディスクリプタも監視する
  足りなければ負荷源を分散（k6 cloud / 複数マシン / Locust worker / k8s）
  keep-alive を有効にしてハンドシェイクの往復を減らす
```
```bash
# 負荷生成マシン側も観測する（ここが100%なら結果は無効）
top -bn1 | head -5 ; ulimit -n ; ss -s
```
→ [ツール.md](./ツール.md)

### 罠⑥：1回の結果で断定
```
✗ 1回走らせて「飽和点は800RPS」と結論
✓ ネットワーク/スケール/GCのゆらぎがある。複数回回して再現性を確認
  結果がばらつくなら、その原因（過渡状態・他テナント影響）も調べる
```

### 罠⑦：1エンドポイントだけ叩く
```
✗ /health や軽い1本だけを連打して「10000RPS出た、余裕」
✓ 実際のユーザーの流れ（ログイン→一覧→詳細→購入）をシナリオ化
  重い処理・DB書き込み・外部API呼び出しを含む現実的な経路で測る
  エンドポイント比率も実トラフィックに合わせる
```
→ [計画.md](./計画.md) のシナリオ設計。

### その他の罠
```
□ think time を入れない    → 非現実的な瞬間負荷。VU数の意味も壊れる
□ check を書かない         → 200だがエラーページ、を見逃す（中身を検証）
□ サーバ側監視を並行しない → 「遅い」止まりで原因に届かない
□ 飽和点付近の段が粗い     → 曲線の折れ目を読めず飽和点を見落とす
□ 試験データを片付けない   → 次回の試験を汚す・本番に混入する
□ オートスケール残骸を放置 → 縮退せずクラウド課金が増え続ける
□ エラーをステータス別に分けない → 503/504/500を一緒くたにして対処を誤る
□ 改善後に再測定しない     → 直した「つもり」で本番へ
```

## 実務での使い方・定番パターン
- **回避策をチェックリスト化**：「staging対象か」「ウォームアップしたか」「負荷側に余力あるか」「分布で見たか」「複数回回したか」を実施前後に確認。→ [../障害対応/チェックリストとランブック.md](../障害対応/チェックリストとランブック.md)
- **疑わしい結果は前提を疑う**：数字が良すぎ/悪すぎたら、まず「環境・シナリオ・負荷側」の前提を点検する（サーバの実力より前に）。
- **本番相当・分布・段階的・複数回**——この4つを合言葉にすると大半の罠を踏まない。

## ハマりどころ / アンチパターン
（このファイル全体が罠の一覧。要点の再掲）
- 本番に大負荷をかけない（**staging で**）
- 平均でなく **p95/p99** で見る
- **負荷側のボトルネック**を疑う（サーバ限界と誤認しない）
- **1回・1エンドポイント**で断定しない
- **ウォームアップ・監視並行・再測定**を省かない
