# ツール（k6 / JMeter / Locust / Gatling / vegeta）（負荷検証）

## ひとことで言うと
負荷をかけるツール。**k6**（JSで書く・モダン・CI向き）、**JMeter**（GUI・歴史が長い定番）、**Locust**（Pythonでシナリオ）、**Gatling**（Scala/高性能・詳細レポート）、**vegeta/wrk/ab**（軽量CLI・1エンドポイントを手早く）。チームの言語・CI事情・シナリオの複雑さで選ぶ。本書は**k6を主軸**に具体例を示す。

## 役割・なぜ必要か
- 大量の同時リクエストを人手で再現するのは不可能。ツールが**仮想ユーザー(VU)**を生成し、指標を集計してくれる。
- ツールごとに「コードで書くかGUIか」「CIに載せやすいか」「どこまで細かくレポートが出るか」が違う。**自動化(CI)したいならコード系（k6/Gatling/Locust）**、手早く1本叩くなら CLI系（vegeta/wrk/ab）。
- スクリプトをコード化（k6/Locust/Gatling）すると、Git管理・レビュー・CI実行ができ、**負荷試験が再現可能な資産**になる。

## 基本（手順・考え方・コード）

### ツールの特徴と使い分け
| ツール | 記述 | 強み | 向く場面 |
|---|---|---|---|
| **k6** | JavaScript | モダン・CI親和・thresholdsで合否自動判定・軽量 | 開発者主導・CIに組み込む・APIの負荷試験 |
| **JMeter** | GUI(XML) | 歴史と実績・プラグイン豊富・非エンジニアでも | 既存資産がある・GUIで組みたい・多プロトコル |
| **Locust** | Python | シナリオを普通のコードで・分散実行・Web UI | Python チーム・複雑な条件分岐シナリオ |
| **Gatling** | Scala/Kotlin/Java | 高性能(少リソースで高負荷)・詳細HTMLレポート | 大規模負荷・きれいなレポートが要る |
| **vegeta** | CLI/Go | 一定レート(RPS指定)を手早く・軽量 | 1エンドポイントを素早く・固定RPS試験 |
| **wrk / ab** | CLI/C | 超軽量・最小手間 | ローカルで瞬間的に叩く・ざっくり把握 |

> 迷ったら **k6**。コードがJSで書きやすく、`thresholds` で合否が自動、CIに載せやすい。

### k6 の具体スクリプト例（これが基本形）
`import http` でHTTP、`options.stages` で負荷の形、`check` で各レスポンス検証、`thresholds` で合否判定。
```javascript
// loadtest.js
import http from 'k6/http';
import { check, sleep } from 'k6';
import { Rate } from 'k6/metrics';

const errorRate = new Rate('errors'); // カスタムメトリクス（独自のエラー率）

export const options = {
  // 負荷の形：ramp-up → 維持 → ramp-down
  stages: [
    { duration: '2m', target: 100 },  // 2分かけて100VUへ
    { duration: '5m', target: 100 },  // 100VUを5分維持（実力測定）
    { duration: '2m', target: 0 },    // ramp-down
  ],
  // 合否の自動判定（満たさなければ k6 は非0終了 → CIが落ちる）
  thresholds: {
    http_req_duration: ['p(95)<300', 'p(99)<800'], // p95<300ms, p99<800ms
    http_req_failed: ['rate<0.01'],                // エラー率<1%
    errors: ['rate<0.01'],
  },
};

const BASE = 'https://staging.example.com';

export default function () {
  // 一覧を取得
  const list = http.get(`${BASE}/items`);
  const ok = check(list, {
    'status is 200': (r) => r.status === 200,
    'body not empty': (r) => r.body.length > 0,
  });
  errorRate.add(!ok);

  sleep(Math.random() * 2 + 1); // think time 1〜3秒

  // 詳細を取得（一覧から拾ったIDで）
  const detail = http.get(`${BASE}/items/12345`);
  check(detail, { 'detail 200': (r) => r.status === 200 });

  sleep(1);
}
```
```bash
# 実行（スクリプトのoptions通りに走る）
k6 run loadtest.js

# 実行時にVU/期間を上書き（簡易確認）
k6 run --vus 50 --duration 30s loadtest.js

# 結果をJSON/CSVに出して後で分析（→ 結果分析.md）
k6 run --out json=result.json loadtest.js
k6 run --out csv=result.csv loadtest.js

# 出力サマリ例：
#   http_reqs............: 60000  1000/s            ← スループット(RPS)
#   http_req_duration....: avg=140ms p(95)=280ms p(99)=620ms
#   http_req_failed......: 0.30%
#   checks...............: 99.70%
```

### 他ツールの最小例（雰囲気）
```bash
# vegeta：固定 100 RPS を 30秒（一定レート試験に強い）
echo "GET https://staging.example.com/items" | \
  vegeta attack -rate=100 -duration=30s | vegeta report

# wrk：4スレッド・100接続・30秒
wrk -t4 -c100 -d30s https://staging.example.com/items

# ab（Apache Bench）：合計10000リクエスト・同時100
ab -n 10000 -c 100 https://staging.example.com/items
```
```python
# Locust：locustfile.py（Pythonでシナリオ）
from locust import HttpUser, task, between
class WebUser(HttpUser):
    wait_time = between(1, 3)  # think time
    @task(9)                   # 重み9：閲覧が多い
    def list_items(self):
        self.client.get("/items")
    @task(1)                   # 重み1：詳細
    def view_item(self):
        self.client.get("/items/12345")
# 実行： locust -f locustfile.py --headless -u 100 -r 10 -t 5m --host https://staging.example.com
```

## 実務での使い方・定番パターン
- **k6 + thresholds を CI に組み込む**：`thresholds` を満たさないと非0終了するので、性能リグレッションをプルリクで止められる。
- **スクリプトはGit管理**：シナリオをコードで持つと、レビュー・再実行・差分追跡ができる。負荷試験が「資産」になる。
- **環境はパラメータ化**：BASE URL・VU数・期間を環境変数（`__ENV`）で切り替え、staging/小規模/大規模を1スクリプトで回す。
- **負荷生成側を1台に頼らない**：大きな負荷は1マシンでは出せない（負荷側がボトルネック）。k6 Cloud / 分散実行（Locust worker, Gatling, k6 operator on k8s）で**負荷源を複数**にする。→ [pitfalls.md](./pitfalls.md)
- **手早い確認は vegeta/wrk/ab、本格シナリオは k6/Locust/Gatling** と使い分ける。

## ハマりどころ / アンチパターン
- **負荷クライアント側が先に詰まる**：1台のCPU/帯域/FD上限で頭打ちになり、「サーバの限界」と誤認。**負荷側のリソースも監視**し、足りなければ分散。→ [pitfalls.md](./pitfalls.md)
- **think time を入れない**：sleepなしのスクリプトは非現実的な瞬間負荷になり、VU数と実RPSの関係も崩れる。
- **check を書かない**：ステータスだけ200でも中身がエラーページのことがある。**レスポンス内容も検証**（`check`）。
- **DNS/接続の再利用を考えない**：keep-alive無効だと毎回TCP/TLSハンドシェイクが入り、サーバでなくその往復がボトルネックに見える。
- **GUIツール(JMeter)をGUIのまま大規模に回す**：JMeterはGUI実行だと重い。大規模は**非GUI（CLI）モード**で。
- **ツールの出すレイテンシに自分の処理時間が混入**：`check` 内で重い処理を書くと計測がぶれる。検証は軽く。
