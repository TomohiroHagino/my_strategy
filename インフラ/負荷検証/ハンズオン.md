# ハンズオン：k6 でアプリに負荷をかけて飽和点を見る

> **このファイルの位置づけ**：他のファイル（[指標.md](./指標.md) / [ツール.md](./ツール.md) 等）は「分かっている人が引く辞書」。
> これは**手を動かして1回成功するための実習**。上から順にコピペすれば、0から動くところまで行けます。

## ゴール（終わったら何ができる？）
- 題材アプリに **k6 で負荷をかけられる**（`script.js` の `vus`/`duration` を自分で書く）
- 結果の **p95 / エラー率 / RPS を読める**
- 負荷を段階的に上げて **飽和点（これ以上RPSが伸びず、レイテンシだけ悪化する点）を観測できる**
- わざと **同時数を上げてエラー率が跳ねる様子**を見る
- ここまでやると [指標.md](./指標.md) / [実施手順.md](./実施手順.md) / [結果分析.md](./結果分析.md) が「読める」ようになる

**所要時間**：20〜30分　**前提**：Docker が動くこと（k6 も Docker で動かすので、ローカルへの k6 インストールは不要）

---

## 準備：Docker が使えるか確認
```bash
docker version
```
**成功**：`Client:` と `Server:` の両方にバージョンが出る。
**失敗**：`Cannot connect to the Docker daemon` → Docker Desktop（または docker サービス）を起動してから再実行。

作業用フォルダを作る:
```bash
mkdir -p ~/k6-handson && cd ~/k6-handson
```

---

## ステップ1：題材アプリ（負荷をかける相手）を立てる
**やること**：受け取ったリクエストの中身を返すだけの軽量アプリ `traefik/whoami` を起動する。
**なぜ**：負荷をかけるには**叩く相手**が要る。whoami は依存が無くすぐ立つので題材に向く。

```bash
docker run -d --name target -p 8080:80 traefik/whoami
curl -s http://localhost:8080 | head -3
```
**成功**：`Hostname: ...` などが返る。→ 相手が立った。
**失敗**：
- `port is already allocated` → 8080 が使用中。`-p 8081:80` に変えて起動（以降の URL も 8081 に読み替え）。
- 何も返らない → `docker ps` で `target` が `Up` か確認。

> 自分の Docker アプリを題材にしてもよい（→ [../docker/ハンズオン.md](../docker/ハンズオン.md) で作った `myapp`）。その場合は `-p 8080:3000` で起動し、URL は同じ 8080 を使う。

## ステップ2：いちばん小さい負荷スクリプトを書く
**やること**：「10人が30秒間ずっとアクセスし続ける」だけのスクリプトを書く。
**なぜ**：まず**1回成功させる**のが目的。`vus`（同時ユーザー数）と `duration`（時間）の最小形を体で覚える。

```bash
cat > script.js <<'EOF'
import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = {
  vus: 10,            // 同時ユーザー数（同時に走る仮想ユーザー）
  duration: '30s',    // 30秒間まわす
};

const BASE = 'http://target:80';   // ← Dockerネットワーク内ではサービス名で繋ぐ

export default function () {
  const res = http.get(BASE);
  check(res, { 'status is 200': (r) => r.status === 200 }); // 中身も検証
  sleep(1);           // think time（実ユーザーっぽく1秒待つ）
}
EOF
```
- `vus`＝かける側の同時数、`duration`＝時間。`check`＝レスポンスが正しいかの検証（→ [ツール.md](./ツール.md)）。
- `BASE` を `http://target:80` にしているのは、**k6 を同じ Docker ネットワークに入れて、サービス名 `target` で叩く**ため（次ステップ）。

---

## ステップ3：k6 を Docker で実行する（1回成功させる）
**やること**：`grafana/k6` イメージで `script.js` を走らせる。
**なぜ**：ローカルに k6 を入れなくても、Docker だけで負荷試験ができる。

題材アプリと k6 を**同じネットワーク**に入れるため、ネットワークを作って target を繋ぎ直す:
```bash
docker network create loadnet
docker network connect loadnet target     # 既存の target をネットワークに追加
```
k6 を実行（カレントの `script.js` をコンテナに渡して走らせる）:
```bash
docker run --rm -i --network loadnet \
  -v "$PWD/script.js:/script.js:ro" \
  grafana/k6 run /script.js
```
- `--network loadnet`＝target と同じネットワーク、`-v`＝スクリプトをコンテナへマウント、`--rm`＝終わったら自動削除。

**成功**：30秒後にサマリが出る。読むべき3つ:
```
  http_reqs..............: 300    9.9/s              ← スループット(RPS)
  http_req_duration......: avg=2ms  p(95)=4ms ...    ← レイテンシ（p95を見る）
  http_req_failed........: 0.00%                     ← エラー率
  checks.................: 100.00%                    ← status 200 だった割合
```
**読み解き**：
- **RPS**（`http_reqs` の `/s`）＝1秒あたり捌けた数。今は VU=10 + sleep(1) なので約10 RPS。
- **p95**（`http_req_duration` の `p(95)`）＝95%のリクエストはこの値以下。**平均でなくここを見る**（→ [指標.md](./指標.md)）。
- **エラー率**（`http_req_failed`）＝失敗の割合。今は 0%。
**失敗**：
- `dial tcp: lookup target ... no such host` → target がネットワークに繋がっていない。`docker network connect loadnet target` を実行したか確認。
- `connection refused` → target が落ちている。`docker ps` で確認、必要なら `docker start target`。

## ステップ4：負荷を段階的に上げて「飽和点」を探す（本題）
**やること**：VU を一定でなく、`stages` で **0→50→100→200 と階段状に上げる**。
**なぜ**：飽和点は「上げていったらどこで頭打ちになるか」でしか分からない。これがキャパシティ試験の基本形（→ [実施手順.md](./実施手順.md)）。

スクリプトを書き換える:
```bash
cat > ramp.js <<'EOF'
import http from 'k6/http';
import { check } from 'k6';

export const options = {
  // 負荷を階段状に上げる（ramp-up）。各段で RPS が伸びるか頭打ちかを見る
  stages: [
    { duration: '20s', target: 50 },   // 20秒で 50VU へ
    { duration: '20s', target: 100 },  // 100VU へ
    { duration: '20s', target: 200 },  // 200VU へ
    { duration: '10s', target: 0 },    // ramp-down
  ],
};

const BASE = 'http://target:80';

export default function () {
  const res = http.get(BASE);
  check(res, { 'status is 200': (r) => r.status === 200 });
  // ここでは think time を入れない＝めいっぱい叩いて限界を探る
}
EOF
```
> ステップ2と違い **`sleep` を入れていない**。「実ユーザー再現」ではなく「限界探索」なので、VU あたり全力で叩かせる。

実行（途中経過も見たいので JSON サマリも出す）:
```bash
docker run --rm -i --network loadnet \
  -v "$PWD/ramp.js:/ramp.js:ro" \
  grafana/k6 run --summary-trend-stats="avg,p(95),p(99)" /ramp.js
```
**成功**：サマリで以下を読む。
```
  http_reqs..............: 180000  2500/s   ← 全体の平均RPS（ピークはもっと高い）
  http_req_duration......: avg=18ms p(95)=60ms p(99)=120ms
  http_req_failed........: 0.00%
  vus....................: ...     max=200  ← 最大同時数
```
**読み解き（飽和点の見方）**：
- VU を 50→100→200 と上げたとき、**RPS が比例して伸び続けるなら、まだ飽和していない**。
- どこかで **RPS が頭打ちになり、p95/p99 だけ跳ね上がる**点があれば、そこが**飽和点**（→ [結果分析.md](./結果分析.md) のスループット曲線）。
- whoami は非常に軽いので、PC によっては 200VU でもまだ余裕なことがある。その場合は **次ステップでさらに上げる**。

## ステップ5：わざと同時数を上げてエラー率を跳ねさせる
**なぜ**：「エラー率が跳ねる瞬間」を一度見ておくと、本番でエラー率が立ち上がったときに**限界のサイン**だと即わかる（→ [指標.md](./指標.md)）。

負荷側（k6）か相手側のどちらかが先に詰まれば、エラー率や接続失敗が出る。VU を大きく上げてみる:
```bash
cat > overload.js <<'EOF'
import http from 'k6/http';
import { check } from 'k6';

export const options = {
  stages: [
    { duration: '15s', target: 500 },
    { duration: '20s', target: 1500 },  // かなり高い同時数まで上げる
    { duration: '15s', target: 3000 },  // さらに上げて壊れ方を見る
    { duration: '10s', target: 0 },
  ],
};
const BASE = 'http://target:80';
export default function () {
  const res = http.get(BASE);
  check(res, { 'status is 200': (r) => r.status === 200 });
}
EOF

docker run --rm -i --network loadnet \
  -v "$PWD/overload.js:/overload.js:ro" \
  grafana/k6 run /overload.js
```
**観測ポイント**：VU を上げていくと、ある点から
- `http_req_failed` が **0% から跳ね上がる**（接続失敗・タイムアウトが混じる）
- `http_req_duration` の **p95/p99 が急激に悪化**する
- `http_reqs` の RPS が **頭打ち**になる
**この3つが同時に起きた負荷が、実用上の限界（飽和点の近く）**。

> 注意：ここで詰まっているのが**相手（whoami）**なのか、**負荷をかけている k6 や PC 側**なのかは区別が要る。`docker stats` を別ターミナルで見ると、どちらの CPU が張り付いているか分かる:
> ```bash
> docker stats --no-stream
> ```
> 負荷クライアント側が先に詰まっているのに「サーバの限界」と誤認するのは典型的な罠。→ [pitfalls.md](./pitfalls.md)
