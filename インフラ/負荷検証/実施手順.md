# 実施手順（実行の進め方）（負荷検証）

## ひとことで言うと
負荷試験の走らせ方。**ベースライン測定**（軽い負荷で正常値を取る）→ **ramp-up**（段階的に負荷を上げる）→ **限界探索**（飽和点・限界まで上げる）、の順で進める。**監視を並行**して走らせ、**本番相当(staging)で**、**ウォームアップ**してから本計測する。

## 役割・なぜ必要か
- いきなり最大負荷をかけると、何が起きたか分からないまま壊れる。**段階を踏む**から、どの負荷でどう変化したかが読める。
- ベースライン（基準値）がないと「遅くなった」が言えない。**まず正常値を測る**。
- ウォームアップなしの初回は、JITコンパイル・キャッシュ未構築・コネクションプール未確立・オートスケール未起動で**不当に遅い**。本番の定常状態を測れない。

## 基本（手順・考え方・コード）

### 実施の流れ
```
0. 事前準備（環境・データ・監視・SLO）   ← 計画.md で整える
        ↓
1. ベースライン測定（軽い負荷で正常値）
        ↓
2. ウォームアップ（キャッシュ/プール/JIT/スケールを温める）
        ↓
3. ramp-up（段階的に負荷を上げる：100→200→400…）
        ↓
4. 目標負荷を維持（SLOを満たすか評価）
        ↓
5. 限界探索（飽和点・壊れる点まで上げる：ストレス/キャパシティ）
        ↓
6. ramp-down ＋ 後片付け（ログ・メトリクス回収）→ 結果分析.md
※ 全工程で 監視を並行（負荷側 ＋ サーバ側） ※ 本番相当(staging) で実施
```

### 0. 開始前チェック（走らせる前に必ず）
```
□ 対象は staging（本番相当）か？ 本番URLを向いていないか（事故防止）
□ 監視ダッシュボードを開いたか（CPU/メモリ/DBコネクション/エラー率）
□ 関係者に周知したか（同じ環境を使う他チームを巻き込まない）
□ テストデータ投入済み・SLO（合格条件）が決まっているか → 計画.md
□ 負荷生成側（ツールを動かすマシン）にも余力があるか
```

### 1. ベースライン測定（正常値を取る）
軽い負荷で「壊れていない状態の数字」を記録する。後の比較の基準になる。
```bash
# 例：10VUで1分。これが「正常時の p95 / RPS」
k6 run --vus 10 --duration 1m loadtest.js
# → p95=120ms, RPS=80, エラー率0% など。これをメモして基準にする。
```

### 2. ウォームアップ
本計測の前に低めの負荷をかけ、定常状態に持っていく。stages の最初の段がこれを兼ねる。
```javascript
export const options = {
  stages: [
    { duration: '2m', target: 30 },  // ← ウォームアップ：キャッシュ/プール/スケールを温める
    { duration: '3m', target: 200 }, // ramp-up（ここから本計測）
    { duration: '10m', target: 200 },// 維持
    { duration: '2m', target: 0 },
  ],
};
```
> ウォームアップ中の数字は**集計から除外**する（過渡状態なので）。

### 3〜5. ramp-up と限界探索
段階的に上げ、各段で指標を記録する。飽和点を探すなら段を多めに刻む。→ [種類と目的.md](./種類と目的.md)
```bash
# キャパシティ試験：段階的に上げ続け、各段のRPS/p95/エラー率/CPUを記録
k6 run --out csv=capacity.csv capacity.js
# 各段で：VU↑に対してRPSが伸びる間は健全。RPSが頭打ち＆p95急上昇＝飽和点。
```

### 監視を並行させる（最重要）
負荷側の数字（k6）と**同じ時間軸で**サーバ側を見る。これがないと「遅い理由」が分からない。
```bash
# 負荷をかけている最中に、サーバ側を別ターミナルで観測する例
# CPU/メモリ/ロードアベレージ
ssh app-host 'top -bn1 | head -15; free -m'
# DBコネクション数（PostgreSQL）
psql -h db -U app -c "SELECT count(*), state FROM pg_stat_activity GROUP BY state;"
# 確立済みソケット数（接続の詰まり）
ssh app-host 'ss -tn state established | wc -l'
```
クラウドではダッシュボードで重ねるのが楽。→ [../aws/monitoring.md](../aws/monitoring.md)
```
負荷側(k6)        ：RPS, p95/p99, エラー率, VU
サーバ側(監視)    ：CPU%, メモリ, DBコネクション, スレッド/ワーカー数, ディスクI/O
→ この2つを同じグラフ時間軸に並べる。RPSが頭打ちになった瞬間、
   何が100%に張り付いたか（CPU? DBコネクション?）でボトルネックが即わかる。
```

### 6. 後片付け
```
□ k6の結果(JSON/CSV)・サーバ側メトリクス・ログを回収（時間帯を揃えて保存）
□ テストデータ/負荷の残骸を片付ける（次回の試験を汚さない）
□ オートスケールで増えたインスタンスが縮退したか確認（コスト）
```

## 実務での使い方・定番パターン
- **小さく始めて広げる**：1エンドポイント→主要フロー→全体。最初から全部やると切り分けできない。
- **1回で断定しない・複数回**：ネットワークやスケールのゆらぎで毎回ぶれる。**数回回して再現性**を見る。→ [pitfalls.md](./pitfalls.md)
- **負荷側のリソースも見る**：ツールを動かすマシンのCPU/帯域/FDが先に上限に達していないか。達していたら**負荷源を分散**。→ [ツール.md](./ツール.md)
- **限界探索は「壊れ方」も観察**：限界を超えたとき、緩やかに503で劣化するか、全断・カスケードするか。→ [../障害対応/よくある障害パターン.md](../障害対応/よくある障害パターン.md)
- **記録を残す**：いつ・どの環境・どのスクリプト・結果。再現と比較のために必須。→ [../障害対応/チェックリストとランブック.md](../障害対応/チェックリストとランブック.md)

## ハマりどころ / アンチパターン
- **本番に負荷をかける**：実ユーザーを巻き込む事故。**staging（本番相当）で**。どうしても本番なら低負荷・限定時間・周知・即停止できる準備を。→ [pitfalls.md](./pitfalls.md)
- **ウォームアップなしで初回計測**：JIT/キャッシュ/プール/スケール未準備で不当に遅い。**温めてから本計測**。
- **監視を並行しない**：負荷側だけ見て「遅い」止まり。**サーバ側を同時刻で**見ないと原因に届かない。
- **いきなり最大負荷**：何が起きたか読めない。**段階的に上げる**。
- **負荷側がボトルネック**：1台で大負荷を出そうとして、ツール側が先に詰まる。**分散 or レート確認**。
- **1回の結果で結論**：ゆらぎを断定にしない。**複数回・再現性確認**。
