# チューニング（性能改善カタログ）（負荷検証）

## ひとことで言うと
分析で見つけたボトルネックを直す手段の一覧。改善対象は4層——**アプリ**（N+1・重い処理・キャッシュ・非同期化）/ **DB**（インデックス・コネクションプール・スロークエリ・リードレプリカ）/ **インフラ**（スケールアウト/アップ・オートスケール・CDN）/ **ネットワーク**（keep-alive・圧縮）。症状から対処を引く。

## 役割・なぜ必要か
- 飽和点を上げる（より多く捌けるようにする）には、**律速になっている層**を直す必要がある。闇雲に台数を増やしても、DBが天井なら無駄。
- 改善は**1つずつ**。複数同時に変えると、何が効いたか分からず再現性が消える。→ [../障害対応/切り分け.md](../障害対応/切り分け.md)
- 「直したら再測定」が必須。律速は移動するので、1つ潰すと次のボトルネックが現れる。→ [結果分析.md](./結果分析.md)

## 基本（手順・考え方・コード）

### 症状 → 対処 早見表
| 症状（結果分析で判明） | 第一容疑 | 対処（層） |
|---|---|---|
| p95/p99 だけ悪化 | スロークエリ・GC・プール待ち | DBインデックス / プール拡大 / GCチューニング |
| CPU 100% で頭打ち | 重い処理・非効率コード | アプリ最適化 / キャッシュ / スケールアウト |
| DBコネクション上限 | プール枯渇・遅いクエリが占有 | プール調整 / スロークエリ解消 / リードレプリカ |
| 504/タイムアウト | 下流（DB・外部API）が遅い | 下流高速化 / タイムアウト＆リトライ設計 / 非同期化 |
| 503 急増 | 受けきれない（スケール不足） | オートスケール / 最小台数増 / キュー導入 |
| メモリ漸増→停止（ソーク） | メモリ/コネクションリーク | リーク修正 / プール上限 / 定期再起動は対症 |
| 帯域飽和・遅い大レスポンス | 圧縮なし・巨大レスポンス | gzip/brotli / ページング / CDN |

### ① アプリ層
```
□ N+1クエリ      ：ループ内で都度クエリ → JOIN / バッチ取得（eager loading）に
□ 重い処理       ：同期で重い計算/外部API待ち → 非同期化・ジョブキューに逃がす
□ キャッシュ     ：同じ結果を毎回計算/取得 → メモリ/Redisでキャッシュ（TTL設計）
□ コネクション   ：毎回新規接続 → プール再利用（DB/HTTPクライアント）
□ シリアライズ   ：巨大JSONの生成が重い → 必要フィールドだけ・ストリーミング
□ ロック競合     ：共有資源の排他で直列化 → ロック粒度を細かく・楽観ロック
```
```sql
-- N+1の典型（アプリのループで N回）→ JOINで1回に
-- Bad: for each order: SELECT * FROM items WHERE order_id = ?
-- Good:
SELECT o.*, i.* FROM orders o JOIN items i ON i.order_id = o.id WHERE o.user_id = ?;
```

### ② DB層（負荷試験で最頻のボトルネック）
```
□ インデックス   ：WHERE/JOIN/ORDER BY の列に索引。EXPLAINでSeq Scanを潰す
□ スロークエリ   ：slow query log で遅いSQLを特定 → 書き換え/索引/非正規化
□ コネクションプール：アプリ側プール上限とDBのmax_connectionsを整合させる
□ リードレプリカ ：参照が重い → 読み取りをレプリカへ分散（書き込みはプライマリ）
□ N+1/不要クエリ ：1リクエストあたりのクエリ本数を減らす
```
```sql
-- 遅いクエリの実行計画を見る（Seq Scan が出たら索引を検討）
EXPLAIN ANALYZE SELECT * FROM orders WHERE user_id = 42 ORDER BY created_at DESC;
-- 索引を張る
CREATE INDEX idx_orders_user_created ON orders (user_id, created_at DESC);
-- 接続数の天井確認（飽和したらここが律速）
SHOW max_connections;                                   -- PostgreSQL
SELECT count(*) FROM pg_stat_activity;                  -- 現在の接続数
```
> アプリのプール合計（台数×プールサイズ）が DBの max_connections を超えると、新規接続が弾かれる。**両者を整合**させる。→ [../障害対応/よくある障害パターン.md](../障害対応/よくある障害パターン.md)

### ③ インフラ層
```
□ スケールアウト ：台数を増やす（水平）。ステートレスなら効きやすい
□ スケールアップ ：1台を強く（垂直）。手早いが上限と単一障害点に注意
□ オートスケール ：負荷に応じ自動増減。閾値・最小台数・立ち上がり時間に注意（スパイク試験で検証）
□ CDN            ：静的・キャッシュ可能なものはエッジへ逃がしオリジン負荷を下げる
□ ロードバランサ ：分散方式・ヘルスチェック・コネクション上限を確認
```
```bash
# オートスケールはスパイクで検証（立ち上がりが間に合うか）→ 種類と目的.md
# AWS例：ASGの希望/最小/最大台数とスケールポリシーを確認
aws autoscaling describe-auto-scaling-groups --query \
  'AutoScalingGroups[].[AutoScalingGroupName,MinSize,DesiredCapacity,MaxSize]'
```

### ④ ネットワーク層
```
□ keep-alive   ：接続を再利用しTCP/TLSハンドシェイクの往復を削減
□ 圧縮         ：gzip/brotli でレスポンス転送量を削減（帯域飽和時に効く）
□ ペイロード   ：不要フィールド除去・ページング・画像最適化
□ リージョン   ：クライアントとサーバの距離・跨ぎ通信を減らす
□ HTTP/2,3     ：多重化で接続効率を上げる
```

## 実務での使い方・定番パターン
- **一番低い天井から直す**：律速になっている層を最優先。DBが天井なのにアプリを最適化しても飽和点は上がらない。
- **1つ直して再測定**：効果を測り、次の律速を探す。**測る→直す→測る**ループ。→ [結果分析.md](./結果分析.md)
- **まずアプリ/DBの非効率を潰し、その後でスケール**：非効率なまま台数を増やすと、コストだけ増えてDBがさらに詰まる。**効率化が先、増設は後**。
- **キャッシュとCDNは費用対効果が高い**：読み取り中心なら、キャッシュ層追加で飽和点が大きく上がることが多い。
- **改善は本番反映前に再度負荷試験**：チューニングがリグレッションを生んでいないか、staging で確認。→ [計画.md](./計画.md)

## ハマりどころ / アンチパターン
- **闇雲にスケールアウト**：DBやロック競合が律速なら、アプリを何台増やしても無駄（むしろDB接続が増えて悪化）。**律速を直す**。
- **複数同時に変更**：何が効いたか分からず再現できない。**1つずつ**。→ [../障害対応/切り分け.md](../障害対応/切り分け.md)
- **プールを上げすぎる**：アプリ側プールを盛ると DB の max_connections を超えて接続拒否。**両者を整合**。
- **キャッシュのTTL無策**：古いデータを返す/キャッシュが肥大しメモリ枯渇。**TTLと無効化**を設計。
- **オートスケールの立ち上がり遅延を無視**：スパイクで増える前に落ちる。**最小台数・ウォームプール・予測スケール**で備える。→ [pitfalls.md](./pitfalls.md)
- **再測定しない**：直した「つもり」。**改善後に必ず測り直す**。
