# 結果分析（ボトルネック特定）（負荷検証）

## ひとことで言うと
取れた数字から「**飽和点はどこか**」「**何が律速（ボトルネック）か**」を読む作業。**スループット曲線**で飽和点を見つけ、**レイテンシ分布(p95/p99)**で体感悪化を捉え、**エラー率の立ち上がり**で限界を知り、それらを**サーバ側リソースと相関**させて詰まっている場所を特定する。考え方は障害対応の切り分けと同じ。

## 役割・なぜ必要か
- 数字を出しただけでは意味がない。「**この負荷でCPUが先に詰まる**」「**DBコネクションが天井**」まで言えて初めて、直す場所が決まる。→ [チューニング.md](./チューニング.md)
- 飽和点が分かれば「**1台あたり◯◯ RPS**」が出て、容量計画（必要台数）に直結する。→ [計画.md](./計画.md)
- ボトルネック特定は障害対応の「切り分け」と同じ発想。**経路を順に潰し、リソースの飽和を見る**。→ [../障害対応/切り分け.md](../障害対応/切り分け.md)

## 基本（手順・考え方・コード）

### ① スループット曲線で飽和点を読む
横軸に負荷(VU)、縦軸にスループット(RPS)を取る。**伸びが止まり水平になる点が飽和点**。
```
RPS
 ↑        ┌────────  ← 飽和点。ここから先はVUを増やしてもRPSが増えない
 │      ╱             （＝システムの実効上限。例：約800 RPS）
 │    ╱
 │  ╱  ← 線形に伸びる（健全）
 └──────────────→ VU

同時に レイテンシ(p95) を重ねる：
p95
 ↑              ╱  ← 飽和点を超えると急上昇（待ち行列が伸びる）
 │ ───────────╱
 └──────────────→ VU
```
読み方：**RPSが頭打ち かつ p95が跳ね始める負荷 ＝ 飽和点**。そこが実用上限。Little's Law（同時数≒RPS×レイテンシ）とも整合するか確認。→ [指標.md](./指標.md)

### ② レイテンシ分布を見る（平均でなく裾）
```
p50 が低くても p99 が跳ねている → 大半は快適だが一部が激遅（テールレイテンシ）
  └ 原因候補：GC停止 / 特定スロークエリ / コネクションプール待ち / 一部ノード不調
全体が一様に悪化 → 全体が飽和（CPU・帯域・共通リソースの上限）
ある負荷で段差状に悪化 → そこで何かが切り替わった（スレッド枯渇・スワップ・スケール遅延）
```

### ③ エラー率の立ち上がりを限界のサインに
```
負荷↑ に対して：
  エラー率がほぼ0% → まだ余裕
  エラー率が跳ね上がる点 → 実用限界（飽和点付近のことが多い）
エラーの中身をステータス別に分解：
  503 多発 → 過負荷で受けきれない（キュー溢れ・スケール不足）
  504 多発 → 下流が遅い（DB・外部API・タイムアウト）
  500 多発 → アプリのバグ（負荷で顕在化した例外・OOM）
  接続失敗 → FD/ポート/コネクションプール/SGの上限
```

### ④ リソースと相関させてボトルネックを特定（最重要）
負荷側の頭打ちと、**同時刻のサーバ側リソース**を突き合わせる。100%に張り付いたものが律速。
```
RPSが頭打ちになった瞬間、何が天井か？
  CPU 100%            → アプリの計算が重い / 非効率コード / 暗号処理 → チューニング.md（アプリ）
  メモリ枯渇・スワップ → メモリリーク / キャッシュ肥大 / ヒープ不足
  DBコネクション上限   → プール枯渇 / 遅いクエリで占有 → チューニング.md（DB）
  ディスクI/O 飽和     → ログ過多 / スワップ / 重いクエリのテンポラリ
  ネットワーク帯域     → 大きなレスポンス / 圧縮なし / リージョン跨ぎ
  スレッド/ワーカー枯渇 → 同期I/O待ち / プールサイズ不足
  ※ どれも余裕なのにRPSが伸びない → ロック競合・直列処理・外部API待ち・負荷側がボトルネック
```
```bash
# 負荷中に取った時系列を突き合わせる（例：飽和した時刻 12:34 のDB接続）
psql -h db -c "SELECT count(*), state FROM pg_stat_activity GROUP BY state;"
# CPU/メモリの時系列はダッシュボードで（→ ../aws/monitoring.md）
```

### ⑤ 障害対応の切り分けと同じ進め方
経路（ユーザー→LB→アプリ→DB→インフラ）を順に潰し、USEメソッド（Utilization/Saturation/Errors）でリソースを見る。負荷試験は「壊れる前に同じ切り分けを先取りする」もの。→ [../障害対応/切り分け.md](../障害対応/切り分け.md)
```
症状 → まず疑う（負荷試験でも同じ）：
  レイテンシ p95/p99 悪化  → DBスロークエリ・N+1・GC・リソース飽和
  503 急増                → 過負荷・キュー溢れ・スケール不足
  504/タイムアウト        → 下流が遅い（DB・外部API・スレッド枯渇）
  断続的エラー            → コネクションプール枯渇・一部ノード
  徐々に悪化→停止         → メモリ/コネクションリーク（ソークで出る）
```

## 実務での使い方・定番パターン
- **必ずグラフを重ねる**：RPS・p95・エラー率・CPU・DBコネクションを同一時間軸で並べる。**折れ目が揃う点**が飽和点でありボトルネック発火点。
- **1つ直して再測定**：ボトルネックを1つ潰したら、次の天井が現れる（律速は移動する）。**測る→直す→測る**のループ。→ [チューニング.md](./チューニング.md)
- **飽和点を容量計画に変換**：「1台 800 RPS」が分かれば、目標2400 RPS には3台＋余裕で4台、と逆算できる。
- **「症状と原因を分ける」**：CPU100%は症状。なぜ張り付いたか（重い処理・スロークエリ・トラフィック）まで掘る。→ [../障害対応/切り分け.md](../障害対応/切り分け.md)
- **結果は記録して比較**：前回ベースラインと並べ、リグレッション（劣化）を検出する。

## ハマりどころ / アンチパターン
- **平均レイテンシで「速い」と結論**：p99の跳ねを見落とす。**分布(p95/p99)で見る**。→ [指標.md](./指標.md)
- **負荷側だけで結論**：サーバ側リソースと相関させないと「なぜ遅いか」に届かない。**同時刻のCPU/DB接続を必ず**。
- **飽和点を粗い段で見落とす**：段が粗いと曲線の折れ目が読めない。**飽和点付近は段を細かく**して再試験。
- **最初のボトルネックで満足**：1つ直すと次が出る。律速は移動するので**ループで追う**。
- **負荷側がボトルネックなのにサーバ限界と誤認**：ツール側のCPU/帯域が天井だと、サーバはまだ余裕。**負荷源の余力を確認**。→ [pitfalls.md](./pitfalls.md)
- **1回の結果で断定**：ゆらぎを限界と誤認。**複数回**で再現性を確認。
