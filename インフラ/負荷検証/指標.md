# 指標（メトリクス・KPI）（負荷検証）

## ひとことで言うと
負荷試験で見る数値は、**スループット**(RPS/TPS＝1秒あたり処理数)・**レイテンシ**(応答時間。平均でなく **p50/p90/p95/p99**)・**エラー率**・**同時ユーザー(VU)/同時接続**・**リソース**(CPU/メモリ/DBコネクション)・そして**飽和点**(負荷を上げてもスループットが頭打ちで、レイテンシだけ悪化する点)。この6つを時系列で並べて読む。

## 役割・なぜ必要か
- 「速い・遅い」「捌ける・捌けない」を**数字で定義**しないと、合否を判断できないし、改善の効果も測れない。
- **負荷側の数字（RPS・レイテンシ・エラー率）とサーバ側の数字（CPU・DBコネクション）はセットで見る**。負荷側だけでは「なぜ遅いか」が分からない。→ [../aws/monitoring.md](../aws/monitoring.md)
- 特にレイテンシは**平均が嘘をつく**。平均200msでも、p99が3秒なら100人に1人が激遅。その1人がVIP顧客かもしれない。

## 基本（手順・考え方・コード）

### 6つの主要指標
| 指標 | 意味 | 何が分かる | 単位 |
|---|---|---|---|
| **スループット** | 単位時間あたりの処理数 | システムの処理能力 | RPS（req/s）/ TPS（txn/s） |
| **レイテンシ** | 1リクエストの応答時間 | ユーザー体感の速さ | ms（**p50/p90/p95/p99**で見る） |
| **エラー率** | 失敗した割合 | 安定性・限界の兆候 | %（5xx・タイムアウト・接続失敗） |
| **同時数(VU)** | 同時に走る仮想ユーザー/接続 | かけている負荷の量 | VU / 同時接続数 |
| **リソース** | サーバ側の使用率 | ボトルネックの場所 | CPU% / メモリ / DBコネクション / FD |
| **飽和点** | スループットが頭打ちになる点 | システムの実効上限 | RPS（折れ目の位置） |

### レイテンシは「分布（パーセンタイル）」で見る
平均ではなく**並べたときの位置**で見る。p95＝「95%のリクエストはこの値以下」。
```
p50 (中央値) ：半分のユーザーの体感。「だいたいの速さ」
p90 / p95    ：遅い側の裾。SLOはここで決めることが多い
p99          ：100人に1人の最悪値。テールレイテンシ
max          ：最悪の1件（外れ値・タイムアウト）
```
```
リクエスト応答時間を速い順に並べる：
[120ms ... 180ms ........ 240ms ...... 800ms .. 3200ms]
  p50↑        p90↑         p95↑        p99↑     max↑
平均 = 全部の合計÷件数。少数の3200msに引っ張られても、p50には現れない。
→ だから「平均は速いのにクレームが来る」が起きる。p95/p99 を必ず見る。
```

### Little's Law（リトルの法則）
**同時数 ≒ スループット × レイテンシ**。負荷設計と結果の整合チェックに使う基本式。
```
L（同時に系内にあるリクエスト数）= λ（到着レート＝スループット）× W（平均滞在時間＝レイテンシ）

例1) 1000 RPS で 平均レイテンシ 0.2秒
     → 同時に処理中のリクエスト ≒ 1000 × 0.2 = 200
     → サーバのワーカー/スレッドが200未満なら、そこで詰まる（飽和）

例2) 必要スループット 500 RPS、1リクエスト 0.1秒
     → 同時数 ≒ 50。VU=50 前後で 500 RPS に届くはず。
       届かないなら、どこか（DB・ロック・I/O）で待たされている。
```
> 使い道：「VUをいくつにすれば目標RPSが出るか」の見積もり、「VUを増やしてもRPSが伸びない＝飽和」の判定。

### 飽和点（saturation point）の定義
```
スループット(RPS)
  ↑          ┌─────────  ← ここで頭打ち（飽和点）。これ以上VUを増やしても
  │        ╱              スループットは増えず、レイテンシだけ悪化する
  │      ╱
  │    ╱   ← 線形に伸びる（健全。VUに比例してRPSが増える）
  │  ╱
  └──────────────────→ 負荷(VU)

レイテンシ(p95)
  ↑              ╱  ← 飽和点を超えると急上昇（待ち行列が伸びる）
  │           ╱
  │ ────────╱
  └──────────────────→ 負荷(VU)
```
**飽和点 ＝ スループット曲線が水平になり、レイテンシが跳ね始める点**。ここがシステムの実効上限。読み方は → [結果分析.md](./結果分析.md)

### k6 が出す主要メトリクスの確認
k6 は終了時にこれらを集計表示する。`thresholds` で合否も自動判定できる。
```javascript
export const options = {
  thresholds: {
    http_req_failed: ['rate<0.01'],                 // エラー率 1%未満
    http_req_duration: ['p(95)<500', 'p(99)<1000'], // p95<500ms, p99<1s
  },
};
// 出力例：
//   http_reqs.............: 120000  2000/s     ← スループット(RPS)
//   http_req_duration.....: avg=180ms p(95)=420ms p(99)=950ms  ← レイテンシ分布
//   http_req_failed.......: 0.40%                ← エラー率
//   vus...................: 100     max=100      ← 同時ユーザー
```
サーバ側リソースは負荷ツールでなく**監視側**で取る（CPU/メモリ/DBコネクション）。→ [../aws/monitoring.md](../aws/monitoring.md)

## 実務での使い方・定番パターン
- **3つの黄金シグナルをまず固定**：スループット・レイテンシ(p95/p99)・エラー率。これだけで「実力」はほぼ言える。
- **負荷側とサーバ側を同じ時間軸で重ねる**：RPSが頭打ちになった瞬間にCPUが100%なのか、DBコネクションが上限なのかで、ボトルネックが即わかる。→ [結果分析.md](./結果分析.md)
- **SLOを指標で書く**：「p95 < 300ms かつ エラー率 < 0.1% を 500 RPS で維持」のように、合格条件を数値化する。→ [計画.md](./計画.md)
- **エラー率の「立ち上がり」を限界のサインに**：負荷を上げてエラー率が跳ねた点が、実用上の限界（飽和点と近い）。
- **DBコネクションは見落としがちな天井**：アプリのCPUに余裕があっても、コネクションプール上限で詰まる。必ず監視に入れる。→ [チューニング.md](./チューニング.md)

## ハマりどころ / アンチパターン
- **平均レイテンシで判断する（最頻の罠）**：平均は外れ値を均してしまう。**必ず p95/p99 を見る**。平均しか出さないツール設定は直す。
- **スループットだけ見て満足**：RPSは高くてもレイテンシが3秒・エラー率5%なら実用に耐えない。**3つセット**で見る。
- **サーバ側リソースを取らない**：負荷側の数字だけでは「遅い」は分かっても「なぜ」が分からない。CPU/メモリ/DBコネクションを必ず並行取得。
- **VUとRPSを混同**：VU（同時数）は「かける側の設定」、RPS（スループット）は「捌けた結果」。VUを増やしてもRPSが伸びない＝飽和、と読む（Little's Law）。
- **瞬間値で一喜一憂**：一瞬のスパイクで合否を決めない。**一定時間の維持**で評価する（GC・スケールの過渡を除外）。
- **エラーの中身を見ない**：同じ「エラー率5%」でも、503（過負荷）か 500（バグ）か 504（下流タイムアウト）かで対処が全く違う。**ステータス別に分解**する。
