# 計画（目標設定・シナリオ設計）（負荷検証）

## ひとことで言うと
負荷試験を走らせる前に決めておくこと一式。**目標値(SLO)** を数値で定義し、**現実的なシナリオ**（ユーザーの行動の流れ）を設計し、**本番相当の環境とテストデータ**を用意し、**ピーク負荷を見積もり**、それを実現する **ramp（負荷の上げ方）** を設計する。ここを雑にすると、結果が信用できなくなる。

## 役割・なぜ必要か
- 計画なしの負荷試験は「数字は出たが、合格か不合格か分からない」になる。**先に合格条件（SLO）を決める**から判断できる。
- 本番と違う環境・データで測ると、結果が本番に当てはまらない。**「本番相当」をどこまで寄せるか**が結果の信頼性を決める。
- シナリオが現実とズレると（例：全員がトップページだけ叩く）、本番では起きない／起きる問題を見逃す。**実際のユーザー行動を写す**。

## 基本（手順・考え方・コード）

### ① 目標値(SLO)を数値で決める
「速い」「捌ける」を測定可能な式にする。指標は → [指標.md](./指標.md)
```
SLO例：
  - スループット：ピーク 500 RPS を維持できること
  - レイテンシ  ：p95 < 300ms、p99 < 800ms
  - エラー率    ：< 0.1%
  - 飽和点      ：少なくとも目標ピークの 1.5倍（750 RPS）まで線形
合格条件（k6 thresholds に落とす）：
  http_req_duration: p(95)<300, p(99)<800
  http_req_failed  : rate<0.001
```

### ② ピーク負荷を見積もる
過去実績や事業計画から「最大瞬間風速」を逆算する。月間ではなくピーク秒で考える。
```
日間アクセス数から概算：
  1日 500万 PV、ピーク時間帯にアクセスの 20% が集中、ピークは1時間
  → ピーク時 = 500万 × 0.2 = 100万 リクエスト / 3600秒 ≒ 278 RPS（平均）
  → 秒単位の山はさらに 2〜3倍 ⇒ 設計目標 500〜800 RPS と置く

将来の余裕も乗せる：
  目標 = 現状ピーク × 成長率 × 安全係数(1.5〜2)
イベント（セール・TV）の場合は通常比 5〜10倍を想定することも。
```
Little's Law で必要VUに換算：**VU ≒ 目標RPS × 平均レイテンシ**。→ [指標.md](./指標.md)

### ③ シナリオを設計する（ユーザーの流れ）
1エンドポイント連打ではなく、**実際の行動の連なり**を書く。各ステップの比率も実トラフィックに合わせる。
```javascript
// k6：ログイン→一覧→詳細→カート、の流れを1ユーザーの旅として書く
import http from 'k6/http';
import { check, sleep, group } from 'k6';

export default function () {
  group('login', () => {
    const res = http.post('https://staging.example.com/login',
      JSON.stringify({ user: `u${__VU}`, pass: 'x' }),
      { headers: { 'Content-Type': 'application/json' } });
    check(res, { 'login 200': (r) => r.status === 200 });
  });
  sleep(Math.random() * 3 + 1); // think time：人間の操作間隔（1〜4秒）

  group('browse', () => {
    http.get('https://staging.example.com/items');        // 一覧（多い）
    sleep(2);
    http.get('https://staging.example.com/items/12345');  // 詳細
  });
  sleep(Math.random() * 5 + 2);
}
```
- **think time（思考時間）を入れる**：人間は連打しない。sleep を入れないと非現実的に高い負荷になり、VU数と実RPSの関係も崩れる。
- **エンドポイントの比率を実トラフィックに合わせる**：閲覧9：購入1 など。アクセスログから比率を取る。

### ④ 本番相当(staging)の環境を用意する
**本番には原則やらない**。本番に寄せた別環境で測る。→ [実施手順.md](./実施手順.md)
```
本番に寄せるべき要素（ズレるほど結果が当てにならない）：
  □ インスタンスのスペック・台数（できれば同等。違うなら比率を記録）
  □ DBのスペック・データ件数（件数が違うとインデックス効きが変わる）
  □ ネットワーク構成（LB・CDN・同一VPC内かどうか）
  □ 外部依存（決済・メール等）はモック化するか、サンドボックスを使う
  □ オートスケール設定（本番と同じ閾値・最小/最大台数）
```

### ⑤ テストデータを用意する
```
□ データ量を本番相当に：100件のテーブルと1000万件では、クエリの遅さが別物
□ ユーザーを十分な数：全VUが同一ユーザーだと、ロック競合やキャッシュヒットが偏る
□ カーディナリティ（値のばらつき）を再現：同じ商品IDばかり叩くと実態とズレる
□ 投入は試験前に完了：データ生成自体が負荷にならないように
```

### ⑥ ramp（負荷の上げ方）を設計する
急に最大負荷をかけず、**段階的に上げる**。ベースライン→徐々に増加→目標維持。→ [種類と目的.md](./種類と目的.md) の stages
```javascript
export const options = {
  stages: [
    { duration: '3m', target: 50 },   // ウォームアップ＋ベースライン
    { duration: '5m', target: 200 },  // 徐々に上げる（ramp-up）
    { duration: '10m', target: 500 }, // 目標ピークを維持して評価
    { duration: '3m', target: 0 },    // ramp-down
  ],
};
```

## 実務での使い方・定番パターン
- **チェックリスト化して毎回同じ手順で**：SLO・シナリオ・環境・データ・ramp を1枚にまとめ、再現可能にする。→ [../障害対応/チェックリストとランブック.md](../障害対応/チェックリストとランブック.md)
- **SLOは事業側と合意してから**：「p95 300ms」が誰の要求かを握っておくと、結果の判断がブレない。
- **シナリオはアクセスログから作る**：本番のアクセスログでエンドポイント比率・時間帯分布を取り、それを写す。憶測で作らない。
- **段階的に対象を広げる**：まず1エンドポイント（ベースライン把握）→ 主要フロー → 全体、と広げると原因の切り分けがしやすい。
- **試験のコストも見積もる**：大規模負荷は対象環境のクラウド課金も増える。期間・規模を計画に含める。

## ハマりどころ / アンチパターン
- **SLOを決めずに走らせる**：数字は出るが合否が言えない。**先に合格条件**。
- **環境が本番と違いすぎる**：1台のstagingで測って「捌ける」、本番は構成が別物——結果が当てにならない。**寄せるか、差分を明記**。
- **テストデータが少ない/偏る**：100件のテーブルでは詰まらないクエリが、本番1000万件で激遅。**データ量とばらつきを本番相当に**。
- **think time を入れない**：人間は連打しない。sleepなしは非現実的な負荷になり、VU数の意味も壊れる。
- **ピークを月平均で考える**：負荷は秒単位の山で決まる。**ピーク秒**で見積もる。
- **シナリオが1エンドポイント**：実際は複数の遷移。1本だけ叩いて「OK」は危険。**ユーザーの旅**で設計。→ [pitfalls.md](./pitfalls.md)
