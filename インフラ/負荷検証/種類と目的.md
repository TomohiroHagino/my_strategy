# 種類と目的（負荷検証）

## ひとことで言うと
負荷試験は「何を知りたいか」で5種類に分かれる。**ロード**（想定負荷で性能を測る）/ **ストレス**（限界まで上げ壊れ方を見る）/ **スパイク**（急増耐性）/ **ソーク＝耐久**（長時間で劣化・リーク）/ **キャパシティ**（どこまで捌けるか＝飽和点）。目的が違えば負荷のかけ方も合格基準も変わる。

## 役割・なぜ必要か
- 「とにかく負荷をかける」だけでは、得られる情報がぼやける。**先に問い（何を確かめたいか）を決める**から、結果が判断に使える。
- 種類ごとに**かける負荷の形（プロファイル）**が違う。ロードは一定、ストレスは右肩上がり、スパイクは瞬間的、ソークは長時間一定、キャパシティは段階的に上げる。
- リリース前は「想定ピークを捌けるか（ロード）」、セール前は「急増に耐えるか（スパイク）」「上限はどこか（キャパシティ）」、長期運用前は「劣化しないか（ソーク）」——状況で選ぶ。

## 基本（手順・考え方・コード）

### 5種類の早見表
| 種類 | 何を知るためか | いつやるか | 負荷の形 | 主な合格/観察基準 |
|---|---|---|---|---|
| **ロード(Load)** | 想定負荷での実力（正常系の性能） | 毎リリース前・定期 | 想定ピークを一定時間維持 | p95レイテンシ・エラー率がSLO内 |
| **ストレス(Stress)** | 限界点と「壊れ方」 | 大型イベント前・設計検証 | 限界を超えるまで上げ続ける | どこで・どう壊れるか／復帰するか |
| **スパイク(Spike)** | 急増への耐性 | TV露出・セール開始・通知配信前 | 一気に跳ね上げ→すぐ戻す | 急増直後の失敗率／回復時間 |
| **ソーク(Soak/耐久)** | 長時間での劣化・リーク | 本番投入前・大型変更後 | 中程度を数時間〜数日維持 | メモリ/コネクションの漸増・性能劣化 |
| **キャパシティ(Capacity)** | どこまで捌けるか（飽和点） | 規模見積もり・スケール計画 | 段階的(ramp)に上げ続ける | スループットの頭打ち点＝飽和点 |

### 負荷プロファイルのイメージ
```
ロード      ████████████          一定の高さを維持して実力を測る
ストレス    ▁▂▃▄▅▆▇██▇▆▅   超えるまで上げ、崩れ方と復帰を見る
スパイク    ▁▁▁██▁▁▁██▁▁   瞬間的に跳ね上げる
ソーク      ▆▆▆▆▆▆▆▆▆▆▆▆▆▆  中程度を長時間（リーク検出）
キャパシティ ▁▂▃▄▅▆▇█        段階的に上げ、飽和点を探す
```

### k6 での負荷プロファイルの書き分け（stages）
`stages` の `target`(VU数) と `duration` で形を作る。→ 具体は [ツール.md](./ツール.md)
```javascript
// ロード：想定ピーク100VUを10分維持
export const options = {
  stages: [
    { duration: '2m', target: 100 },  // ramp-up（徐々に上げる）
    { duration: '10m', target: 100 }, // 維持して実力測定
    { duration: '2m', target: 0 },    // ramp-down
  ],
};

// スパイク：20VU→一気に500VU→戻す
export const options = {
  stages: [
    { duration: '1m', target: 20 },
    { duration: '10s', target: 500 }, // 瞬間的に跳ね上げる
    { duration: '3m', target: 500 },
    { duration: '10s', target: 20 },
  ],
};

// ソーク：50VUを4時間維持（リーク検出）
export const options = {
  stages: [
    { duration: '5m', target: 50 },
    { duration: '4h', target: 50 },   // 長時間の劣化を見る
    { duration: '5m', target: 0 },
  ],
};

// キャパシティ：段階的に上げ続け飽和点を探す
export const options = {
  stages: [
    { duration: '2m', target: 100 },
    { duration: '2m', target: 200 },
    { duration: '2m', target: 400 },
    { duration: '2m', target: 800 },  // 各段でRPS/レイテンシを記録し飽和点を読む
    { duration: '2m', target: 1600 },
  ],
};
```

## 実務での使い方・定番パターン
- **まずロード、次にキャパシティ、最後にストレス**。実力 → 上限 → 壊れ方の順で理解が積み上がる。
- **ストレスは「壊れ方」を見るのが本命**。きれいに 503 を返して劣化するのか、全断・カスケード障害になるのかは設計品質。→ [../障害対応/よくある障害パターン.md](../障害対応/よくある障害パターン.md)
- **スパイクは自動スケールの検証**。オートスケールが立ち上がる前の数分を捌けるか（ウォームプール・最小台数）を見る。
- **ソークは短時間試験では絶対に出ない問題を出す**。メモリリーク・コネクションリーク・ディスク漸増・キャッシュ肥大は時間をかけないと見えない。
- **キャパシティ試験の出力はそのまま容量計画になる**：「1台あたり◯◯ RPS」が分かれば、目標ピークから必要台数を逆算できる。→ [計画.md](./計画.md)

## ハマりどころ / アンチパターン
- **種類を決めずに走らせる**：「とりあえず負荷をかけた」結果は、ロードなのかストレスなのか曖昧で判断に使えない。**先に問いを決める**。
- **ロードだけで安心する**：想定内は捌けても、急増（スパイク）やリーク（ソーク）で本番が落ちる。**複数種類を組み合わせる**。
- **ストレスで「壊れた＝失敗」と即断**：限界は必ずある。重要なのは「**上限がいくつか**」と「**壊れ方が安全か**（緩やかに劣化するか／巻き込み事故か）」。
- **ソークを短く切り上げる**：30分で問題なし、は耐久の保証にならない。リークは数時間かけて顕在化する。**本番想定の時間軸**で。
- **キャパシティで段を粗くしすぎる**：100→1000の2段では飽和点が読めない。**飽和点付近は段を細かく**して曲線の折れ目を捉える。→ [結果分析.md](./結果分析.md)
