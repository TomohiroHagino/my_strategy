# 負荷検証（負荷試験・パフォーマンステスト）実務リファレンス（索引）

> **負荷検証＝壊れる前に「限界と性能」を知る**。
> 本番でいきなり捌けるか試すのではなく、本番相当の環境にわざと負荷をかけて「どこまで捌けるか」「どこが詰まるか」「速さは保てるか」を**事前に測る**。
> 各ファイルは「ひとことで言うと → 役割・なぜ → 基本（手順・コード）→ 実務での使い方 → ハマりどころ → 関連」。

## 全体の流れ（4フェーズ）
```
 計画(Plan)         → 実施(Run)             → 分析(Analyze)         → 改善(Tune)
 目標(SLO)/シナリオ   ベースライン→ramp-up     スループット曲線/分布    アプリ/DB/インフラを直す
 本番相当環境/データ   限界探索・監視を並行     飽和点とボトルネック特定  → 再測定して効果確認（ループ）
```
改善したら**もう一度測る**。1回で終わりではなく「測る→直す→測る」を回す。

## 大原則（3つ）
```
 ① 本番には原則やらない。本番相当(staging)で測る。
    └ 本番に負荷をかけると実ユーザーを巻き込む事故になる。環境・データを本番に寄せて再現する。
 ② 平均で判断しない。レイテンシは p95/p99 を見る。
    └ 平均は速く見えても、一部ユーザーが激遅なのを隠す。裾（テール）を見る。
 ③ 監視と相関させる。負荷側の数字だけ見ない。
    └ RPSやレイテンシと、サーバ側のCPU/メモリ/DBコネクションを時系列で重ねて初めて原因が分かる。
```

## 5種類の負荷試験（何を知りたいかで選ぶ）
| 種類 | 何を知るためか | かける負荷 |
|---|---|---|
| **ロード** | 想定負荷での性能（正常系の実力） | 想定ピーク程度を一定時間 |
| **ストレス** | 限界と「壊れ方」 | 限界を超えるまで上げ続ける |
| **スパイク** | 急増への耐性 | 一気に跳ね上げてすぐ戻す |
| **ソーク（耐久）** | 長時間での劣化・リーク | 中程度を数時間〜数日 |
| **キャパシティ** | どこまで捌けるか（飽和点） | 段階的に上げ飽和点を探す |

> 迷ったら **ロード→ストレス→キャパシティ** の順で、まず「実力」次に「限界」を測る。→ [種類と目的.md](./種類と目的.md)

## 押さえる指標
スループット(RPS/TPS)・**レイテンシ p50/p90/p95/p99**・エラー率・同時ユーザー(VU)・リソース(CPU/メモリ/DBコネクション)・**飽和点**。
- **Little's Law：同時数 ≒ スループット × レイテンシ**（例 1000 RPS × 0.2秒 ≒ 同時200リクエスト）。
- **飽和点**＝負荷を上げてもスループットが頭打ちになり、レイテンシだけ悪化し始める点。ここがシステムの実効上限。→ [指標.md](./指標.md)
