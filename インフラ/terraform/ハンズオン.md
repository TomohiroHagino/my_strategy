# ハンズオン：Terraform で S3 を「課金ゼロ」で作って壊す

> **このファイルの位置づけ**：他のファイル（[getting_started.md](./getting_started.md) / [commands.md](./commands.md) 等）は「分かっている人が引く辞書」。
> これは**手を動かして1回成功するための実習**。上から順にコピペすれば、0から動くところまで行けます。

## 💰 課金に関する注意（最初に必ず読む）
- **この実習は課金ゼロで完結します。** 本物のAWS（あなたのアカウント・クレジットカード）には一切アクセスしません。
- 使うのは **LocalStack**（AWSをPC内で再現するエミュレータ）＋ **`tflocal`**（terraform-local）。`tflocal` は **terraformの向き先を自動でLocalStackにする** ラッパーなので、本物に飛ぶ事故が起きません。
- 作るのはLocalStack上の偽S3バケットだけ。請求は発生しません。
- 本物のAWSでやる場合の差分（IAM/リージョン/課金/state）は末尾にまとめます。
- それでも最後は **必ず片付け**（`tflocal destroy` ＋ コンテナ削除）まで行ってください。下記「必ず片付ける」章を実行すれば完全に消えます。

## ゴール（終わったら何ができる？）
- `main.tf` に **S3バケットをコードで宣言**できる
- **`init` → `plan` → `apply`** の流れを自分の手で回せる（それぞれの意味が分かる）
- **`apply` の結果が `awslocal s3 ls` で確認できる**（コードが現実になった証拠を見る）
- **State（`terraform.tfstate`）の存在**を体で理解する
- わざと **`apply`せずに`destroy`／変数未設定**で失敗 → 自分で直せる
- ここまでやると [commands.md](./commands.md) / [state.md](./state.md) / [getting_started.md](./getting_started.md) が「読める」ようになる

**所要時間**：20〜30分　**前提**：Docker・Terraform本体・Python（pip）が動くこと

---

## 準備：3つのツールが使えるか確認
```bash
docker version
```
**成功**：`Client:` と `Server:` の両方にバージョンが出る。
**失敗**：`Cannot connect to the Docker daemon` → Dockerが起動していない。起動してから再実行。

```bash
terraform version
```
**成功**：`Terraform v1.x.x` が出る。
**失敗**：`command not found: terraform` → Terraform未インストール。インストール手順は [getting_started.md](./getting_started.md)。

```bash
python3 -m pip --version
```
**成功**：`pip XX.X ...` が出る。
**失敗**：`No module named pip` → `python3 -m ensurepip --upgrade`。

作業用フォルダを作る:
```bash
mkdir -p ~/tf-handson && cd ~/tf-handson
```

## ステップ1：LocalStack を起動する
**やること**：AWSをPC内で再現する `localstack/localstack` をdockerで起動する。
**なぜ**：Terraformの適用先（偽AWS）。ここに対してS3を作るので、本物に触れず課金もされない。
```bash
docker run -d --name localstack -p 4566:4566 localstack/localstack
```

起動を確認:
```bash
sleep 8
curl -s http://localhost:4566/_localstack/health
```
**成功**：`{"services": {...}}` というJSONが返る（`"s3": "available"` 等）。
**失敗**：接続拒否 → まだ起動中。あと10秒待って再実行。`docker logs localstack | tail -5` に `Ready.` が出れば準備完了。
- `port is already allocated` → `docker rm -f localstack` してから `-p 4567:4566` に変えて起動し直す（`tflocal` は既定で4566を見るため、変えた場合は環境変数 `EDGE_PORT=4567` を設定してから以降のtflocalを実行）。

---

## ステップ2：`tflocal` と `awslocal` を入れる
**やること**：terraformとawsを「自動でLocalStackに向ける」ラッパーを入れる。
**なぜ**：本物の `terraform`/`aws` は認証設定が必要で、間違えると本物に飛ぶ。`tflocal`/`awslocal` は向き先がLocalStack固定なので安全。
```bash
python3 -m pip install --user terraform-local awscli-local
```
- `terraform-local` が `tflocal`、`awscli-local` が `awslocal` を提供する。中身は「LocalStack用のendpoint設定を自動で足して、本物のterraform/awsを呼ぶ」だけ。

確認:
```bash
tflocal --version && awslocal --version
```
**成功**：terraformとawsのバージョンがそれぞれ出る。
**失敗**：`command not found` → `~/.local/bin` にPATHが通っていない。`export PATH="$HOME/.local/bin:$PATH"` を実行してから再確認。

---

## ステップ3：`main.tf` を書く（S3バケットを宣言する）
**やること**：作りたいインフラ（S3バケット）を**コードで宣言**する。
**なぜ**：Terraformは「手順」ではなく「**あるべき最終状態**」を書く（宣言的）。下記は「`handson-tf-bucket` というS3バケットが1つ存在してほしい」という宣言。
```bash
cat > main.tf <<'EOF'
terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}

provider "aws" {
  region = "ap-northeast-1"   # 東京（LocalStackでは形式上の指定）
}

# 後で名前を変えやすいように変数にしておく
variable "bucket_name" {
  type    = string
  default = "handson-tf-bucket"
}

# 作りたいリソース：S3バケットを1つ
resource "aws_s3_bucket" "handson" {
  bucket = var.bucket_name
}

# apply後に作られたバケット名を表示する
output "created_bucket" {
  value = aws_s3_bucket.handson.bucket
}
EOF
```
- `resource "aws_s3_bucket" "handson"`＝「`aws_s3_bucket` 型のリソースを、`handson` という名札で1つ管理する」宣言。
- `variable` ＝後で値を差し替えられる入力。`output` ＝apply後に知りたい値の出力。詳しくは [variables_outputs.md](./variables_outputs.md)。

---

## ステップ4：`init`（準備）
**やること**：このフォルダでTerraformを使えるよう初期化する。
**なぜ**：`init` は **プロバイダ（awsを操作するプラグイン）をダウンロード**し、stateの置き場を用意する。最初の一度だけ必要。
```bash
tflocal init
```
**成功**：`Terraform has been successfully initialized!` と出る。`.terraform/` フォルダと `.terraform.lock.hcl` が作られる。
**失敗**：
- `Could not connect` 系 → LocalStackが起動していない。ステップ1のhealth確認へ。
- プロバイダ取得でネットワークエラー → 接続を確認して再実行。

---

## ステップ5：わざと失敗 ①「applyせずにいきなり消そうとする」
**なぜ**：「まだ何も作ってないのに壊そうとする」と何が起きるかを先に体験すると、`apply`と`destroy`の関係が腹落ちする。
```bash
tflocal destroy -auto-approve
```
**結果**：エラーにはならず `Destroy complete! Resources: 0 destroyed.` と出る。
**読み解き**：`destroy` は「**Stateが管理しているリソース**を消す」コマンド。まだ `apply` していない＝Stateは空なので、**消すものが無い（0 destroyed）**。
→ つまり **「apply で State に記録 → destroy で State の分を消す」** という対応関係がここで分かる。State（対応表）の存在が見えた瞬間。詳しくは [state.md](./state.md)。

---

## ステップ6：`plan`（差分のプレビュー）
**やること**：「今の状態」と「コードのあるべき状態」の差分を**実際には作らずに**見る。
**なぜ**：`plan` は適用前の安全確認。何が増減するかを目で見てから `apply` する習慣が事故を防ぐ。
```bash
tflocal plan
```
**成功**：末尾に `Plan: 1 to add, 0 to change, 0 to destroy.` と出る（`+ resource "aws_s3_bucket" "handson"` の行も見える）。
**読み解き**：`1 to add`＝「バケットを1つ新規作成する予定」。**まだ作っていない**（planは差分を見るだけ）。

---

## ステップ7：`apply`（適用＝実際に作る）
**やること**：planで見た差分を実際に偽AWSへ適用する。
**なぜ**：ここで初めてリソースが**現実に作られ**、Stateに記録される。
```bash
tflocal apply -auto-approve
```
**成功**：`Apply complete! Resources: 1 added, 0 changed, 0 destroyed.` と出て、続けて
`Outputs:` `created_bucket = "handson-tf-bucket"` が表示される。
**失敗**：
- `BucketAlreadyExists` / `BucketAlreadyOwnedByYou` → 既に作成済み。次の確認へ進んでよい。
- `connect: connection refused` → LocalStackが落ちている。ステップ1へ。

`terraform.tfstate` ができたことを確認:
```bash
ls -l terraform.tfstate
```
**成功**：`terraform.tfstate` が存在する。→ **これが State（コードと現実の対応表）の正体**。中に作ったバケットが記録されている。

---

## ステップ8：`awslocal s3 ls` で「コードが現実になった」ことを確認する
**やること**：Terraform以外の手段（awslocal）でも、本当にバケットができているか確かめる。
**なぜ**：「コードに書いた→本当に偽AWSに存在する」という因果を、別ルートで裏取りする。
```bash
awslocal s3 ls
```
**成功**：`handson-tf-bucket` を含む行が出る。
→ **これが「`main.tf` に宣言したものが、`apply` で現実に作られた」証拠**。コード（宣言）→ 現実（リソース）が一本につながった。

---

## ステップ9：わざと失敗 ②「変数を未設定にする」
**なぜ**：Terraformで頻出の「変数が決まっていない」エラーを体験して直す。
`default` を消した変数を一時的に追加し、未設定でplanしてみる:
```bash
cat > extra.tf <<'EOF'
variable "owner" {
  type = string
  # default を書かない＝必須入力
}

output "owner_echo" {
  value = var.owner
}
EOF

tflocal plan -input=false
```
**結果**：`No value for required variable` / `The root module input variable "owner" is not set` というエラーで止まる。
**読み解き**：`default` の無い変数は**必須**。値を渡さないとTerraformは進めない（`-input=false` で対話入力も封じているため即エラー）。本物でも `tfvars` 忘れ・CIでの未設定で頻発する。→ [variables_outputs.md](./variables_outputs.md)

直す（値を渡す）:
```bash
tflocal plan -var="owner=taro"
```
**成功**：エラーが消え、`owner_echo = "taro"` を含むplan結果になる。→ 原因＝必須変数の未設定、を体験で理解できた。

後片付けの邪魔になるので、この実験ファイルは消しておく:
```bash
rm -f extra.tf
```

---

## 必ず片付ける（このまま閉じない）
**LocalStackはPC内なので課金は発生しませんが、まず `destroy` で「Terraform管理のリソースを正しく消す」流れを体験し、その後コンテナも消します。**
```bash
# 1) Terraformが作ったもの（S3バケット）を消す
tflocal destroy -auto-approve
```
**成功**：`Destroy complete! Resources: 1 destroyed.` と出る（ステップ5の `0 destroyed` と比べると、State に記録があった分が消えたと分かる）。

```bash
# 2) 消えたことを裏取り（バケット一覧から消えている）
awslocal s3 ls

# 3) LocalStackコンテナを止めて削除
docker rm -f localstack

# 4) 作業フォルダごと消すなら
rm -rf ~/tf-handson
```
**確認**：`docker ps -a | grep localstack` で何も出なければ完全に消えている。

> `tflocal`/`awslocal` 本体（pipで入れたもの）は残しても無害。消すなら `python3 -m pip uninstall terraform-local awscli-local`。

## 本物のAWSでやる場合の差分（重要）
| 項目 | LocalStack（この実習） | 本物のAWS |
|---|---|---|
| コマンド | `tflocal` / `awslocal`（自動でLocalStackへ） | `terraform` / `aws`（`aws configure` でキー設定が必要） |
| 認証 / IAM | ダミーで素通り | **IAMユーザー/ロールと権限が必須**。最小権限が鉄則 → [../aws/iam.md](../aws/iam.md) |
| リージョン | 形式上のみ | バケットは実際にリージョンへ作られる。指定ミス＝別リージョン事故 |
| 課金 | **ゼロ** | 作ったリソースは**実際に課金**。`destroy` 忘れ＝課金継続 → [pitfalls.md](./pitfalls.md) |
| State | ローカルの `terraform.tfstate` でOK | チームでは**リモートbackend（S3+DynamoDB）が必須**。ローカルstateは事故の元 → [state.md](./state.md) |

> 本物に移るときは、まず [../aws/getting_started.md](../aws/getting_started.md) で IAM・課金アラートを整え、stateは [state.md](./state.md) のリモートbackendへ。`tflocal`/`awslocal` を `terraform`/`aws` に置き換えれば、ほぼ同じ流れが通る。
