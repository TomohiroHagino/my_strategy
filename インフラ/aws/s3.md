# S3（AWS）

## ひとことで言うと
**オブジェクトストレージ**。ファイル（オブジェクト）を**バケット**という入れ物に、ほぼ無制限・高耐久で置けるAWSのストレージサービス。OSのファイルシステムというより「キー（パス文字列）でファイルを保管・取得する巨大な倉庫」。

## 役割・なぜ必要か
- **バケット**＝最上位の入れ物（名前はグローバルで一意）、**オブジェクト**＝中のファイル本体（キー＋データ＋メタデータ）。キーは `images/2026/cat.png` のように見えるが、実体はフラットなキー文字列（疑似的なフォルダ）。
- 用途が広い：アプリのアップロードファイル置き場、ログ・バックアップ、データレイク、そして**静的サイトホスティング**（HTML/CSS/JS/画像をそのまま配信）。
- **11ナイン（99.999999999%）**の耐久性をうたう高信頼ストレージ。容量を気にせず保存できる。
- **バージョニング**：同じキーに上書きしても**過去バージョンを保持**。誤上書き・誤削除からの復旧や監査に有効。
- **ストレージクラス**でコストと取り出し速度を選べる（後述）。**署名付きURL（Pre-signed URL）**で、一時的にだけ特定オブジェクトへのアクセスを許可できる（公開せずに配布・アップロードさせる定番手法）。

## 基本の使い方（CLI / コンソール）
```bash
# バケット作成（名前はグローバル一意・リージョン指定）
aws s3 mb s3://my-unique-bucket-2026 --region ap-northeast-1

# アップロード / ダウンロード / 一覧 / 同期
aws s3 cp ./report.pdf s3://my-unique-bucket-2026/docs/report.pdf
aws s3 cp s3://my-unique-bucket-2026/docs/report.pdf ./
aws s3 ls s3://my-unique-bucket-2026/docs/
aws s3 sync ./dist s3://my-unique-bucket-2026/site/   # ディレクトリ丸ごと

# バージョニング有効化
aws s3api put-bucket-versioning \
  --bucket my-unique-bucket-2026 \
  --versioning-configuration Status=Enabled

# 署名付きURL（既定1時間有効。期限付きで安全に共有）
aws s3 presign s3://my-unique-bucket-2026/docs/report.pdf --expires-in 600

# ストレージクラスを指定して保存（標準より安いIAへ）
aws s3 cp ./old.log s3://my-unique-bucket-2026/logs/old.log \
  --storage-class STANDARD_IA
```
静的サイトホスティング（実務はS3単体公開より CloudFront 経由が推奨）：
```bash
aws s3 website s3://my-unique-bucket-2026/ \
  --index-document index.html --error-document error.html
```

## 実務での勘所
- **Block Public Access（パブリックアクセスブロック）はデフォルトで全部ON**にしておく。公開が必要でもまず**CloudFront + OAC（Origin Access Control）経由**で配信し、バケット自体は非公開に保つのが定石。→ [cloudfront_route53.md](./cloudfront_route53.md)
- アプリからの配布・受け取りは**署名付きURL**で。バケットを公開しなくても、期限付きで個別オブジェクトのDL/ULを許可できる。
- **ライフサイクルルール**で「30日後にIAへ、90日後にGlacierへ、365日後に削除」のように自動で安いクラスへ移行・削除し、コストを抑える。
- アクセス制御は**IAMポリシー＋バケットポリシー**。誰がどのバケット/プレフィックスを読めるかを最小権限で。→ [iam.md](./iam.md)
- **暗号化（SSE-S3 / SSE-KMS）はデフォルトで有効**。機微データはKMS鍵で管理すると監査・権限分離がしやすい。
- 大量アクセス・大容量のログ集約先としても定番。CloudWatch やアクセスログの保存先に。→ [monitoring.md](./monitoring.md)

## ハマりどころ / アンチパターン
- **バケット誤公開による情報漏洩**：最大の事故。Block Public Access を外して「全員に読み取り許可」のバケットポリシーやACLを付け、**個人情報・バックアップ・ソースを丸見え**にする事例が後を絶たない。公開設定を変える時は**本当に公開してよいデータか**を二重確認。原則は「非公開＋CloudFront/署名付きURL」。
- **バケット名はグローバル一意**：全AWSアカウントで重複不可。`test` 等は当然取れない。命名は `会社名-用途-環境-乱数` のように衝突しない規約で。一度作った名前は変更不可（作り直しになる）。
- **ストレージクラス選択ミス**：頻繁にアクセスするデータをGlacierに入れて**取り出しに時間と取り出し料金**がかかる／逆にめったに読まないログを標準のまま放置して**割高**。アクセス頻度で選ぶ。迷うなら **S3 Intelligent-Tiering** に任せる手もある。
- **バージョニング有効のまま放置でコスト増**：上書き・削除のたびに旧バージョンが積み上がる。ライフサイクルで**旧バージョンを期限切れ削除**しないと容量課金が膨らむ。
- **大量の小さなファイルへの高頻度リクエスト**：オブジェクト数自体は無制限だが、リクエスト課金とレイテンシが効く。集約やキャッシュ（CloudFront）を検討。
- **`s3://...website...` をそのまま公開エンドポイントにする**：HTTPSや独自ドメイン、キャッシュ制御が弱い。実務はCloudFrontを前段に。
