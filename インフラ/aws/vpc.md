# VPC（AWS）

## ひとことで言うと
**AWS上に作る、自分専用の仮想ネットワーク**（Virtual Private Cloud）。EC2やRDSなどのリソースを置く「土地（IPアドレス空間）」で、サブネット・ルーティング・ファイアウォールを自分で設計する。

## 役割・なぜ必要か
- クラウドでも「どのサーバーを外部に公開し、どれを内部に隠すか」を決める**ネットワーク設計が必要**。VPCはその器。
- 「**Webサーバーは外から見える／DBは外から見えない**」を実現するのがVPCの主目的。境界を引くことでセキュリティと事故の封じ込めができる。
- 構成要素：
  - **サブネット**：VPCをIP範囲で区切った区画。
    - **パブリックサブネット**：インターネットゲートウェイ（IGW）への経路があり、外部と直接通信できる（公開Webサーバー・ロードバランサ向き）。
    - **プライベートサブネット**：IGWへの直接経路が無く、外から到達できない（DB・内部APIサーバー向き）。
  - **ルートテーブル**：サブネットの「通信の行き先表」。`0.0.0.0/0` をIGWに向ければパブリック、NATに向ければ"出るだけ"のプライベートになる。
  - **IGW（インターネットゲートウェイ）**：VPCとインターネットの出入口。
  - **NATゲートウェイ**：プライベートサブネットのリソースが**外へは出られるが、外からは入れない**ようにする中継。OSアップデートやAPI呼び出しに必要。

## 基本の使い方（CLI / コンソール）
```bash
# VPC本体（10.0.0.0/16）
aws ec2 create-vpc --cidr-block 10.0.0.0/16

# パブリック / プライベート サブネット
aws ec2 create-subnet --vpc-id vpc-0abc --cidr-block 10.0.1.0/24  # public
aws ec2 create-subnet --vpc-id vpc-0abc --cidr-block 10.0.2.0/24  # private

# インターネットゲートウェイを作ってVPCに付ける
aws ec2 create-internet-gateway
aws ec2 attach-internet-gateway --vpc-id vpc-0abc --internet-gateway-id igw-0xyz
```
```bash
# セキュリティグループ（インスタンス単位のファイアウォール）
aws ec2 create-security-group --group-name web-sg --description "web" --vpc-id vpc-0abc

# 443だけ全世界に開ける（in方向のみ書けば戻りは自動＝ステートフル）
aws ec2 authorize-security-group-ingress \
  --group-id sg-0web --protocol tcp --port 443 --cidr 0.0.0.0/0

# DB用SGは「webのSGからの5432だけ」許可（IPでなくSG参照が定石）
aws ec2 authorize-security-group-ingress \
  --group-id sg-0db --protocol tcp --port 5432 --source-group sg-0web
```
- コンソール：VPC → 「VPCを作成」で**VPC・サブネット・ルートテーブル・IGWを一括生成**するウィザードあり。最初はこれで雛形を作るのが楽。

## 実務での勘所
- **セキュリティグループ（SG） vs NACL** の使い分けが要：

  | | セキュリティグループ | ネットワークACL（NACL） |
  |---|---|---|
  | 適用単位 | **インスタンス（ENI）単位** | **サブネット単位** |
  | 状態 | **ステートフル**（戻り通信は自動許可） | **ステートレス**（戻りも明示的に許可が必要） |
  | ルール | **許可**のみ書ける | 許可・**拒否**の両方 |
  | 実務 | **基本はこれで制御** | 特定IP遮断などの補助 |

- **DBのSGは「IPではなくWebサーバーのSGを指定」**する（`--source-group`）。IPがオートスケールで変わっても破綻しない。
- **マルチAZ前提でサブネットは複数AZに**用意する（RDSマルチAZやALBは複数AZのサブネットを要求する）。→ [rds.md](./rds.md)
- VPC内からS3/DynamoDBを呼ぶなら **VPCエンドポイント**を使うと、NAT経由のデータ転送料を避けられる。

## ハマりどころ / アンチパターン
- **public/private の設計ミス**：DBやアプリサーバーをパブリックサブネットに置いて世界に晒す。**公開が必要なもの（LB・公開Web）だけパブリック**、それ以外（DB・内部処理）はプライベートが原則。→ [rds.md](./rds.md)
- **NATゲートウェイの課金**：NATは**起動時間課金＋データ処理量課金**で、放置すると地味に高い。検証用VPCの消し忘れに注意。代替に**NATインスタンス**やVPCエンドポイント検討、不要なら削除。
- **セキュリティグループの開けすぎ**：`0.0.0.0/0` で全ポート許可、SSH(22)を全世界に開放、などは事故の温床。**必要なポートを必要な送信元にだけ**開ける。22は自分のIPかSSM Session Manager経由に。→ [ec2.md](./ec2.md)
- **NACLのステートレスを忘れる**：NACLで`in`だけ許可して`out`（戻り）を拒否のままにし、「通信が片道で止まる」。SGと違い戻りも明示が要る。
- **CIDRが小さすぎ/重複**：`/28` 等で作って後からIPが足りない、オンプレやピア相手とCIDRが重複してVPCピアリングできない。最初に**広め（/16）かつ将来と重ならない範囲**で設計。
