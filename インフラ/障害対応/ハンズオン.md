# ハンズオン：擬似障害を起こして切り分けて直す

> **このファイルの位置づけ**：他のファイル（[初動対応.md](./初動対応.md) / [切り分け.md](./切り分け.md) 等）は「分かっている人が引く辞書」。
> これは**手を動かして1回成功するための実習**。上から順にコピペすれば、0から動くところまで行けます。

## ゴール（終わったら何ができる？）
- ローカルで**擬似障害を自分で起こして、切り分けて、復旧できる**
- 「**症状 → 確認コマンド → 原因 → 復旧**」の型を3パターンで体験する
  - ① アプリを落として **502 / 接続不可** を観測 → 一次切り分け → 復旧
  - ② DB を止めてアプリが **500** → 原因特定 → 復旧
  - ③ **設定ミスで起動しない**（リソース枯渇でない障害）→ 特定 → 復旧
- ここまでやると [初動対応.md](./初動対応.md) / [切り分け.md](./切り分け.md) / [対応判断フロー.md](./対応判断フロー.md) / [復旧手順.md](./復旧手順.md) が「読める」ようになる

**所要時間**：25〜35分　**前提**：Docker が動くこと（それ以外の知識は不要）

> 障害対応の本質は「**まず止血（復旧）、原因究明は後**」「**最近の変更をまず疑う**」「**経路を順に潰す**」。このハンズオンでその型を手で覚えます。

## 準備：題材スタックを立てる（nginx + アプリ + DB）
**やること**：「nginx（前段）→ アプリ → DB」という実務でよくある3段構成を立てる。
**なぜ**：障害の切り分けは「**どの層で壊れているか**」を絞る作業（→ [切り分け.md](./切り分け.md)）。層が複数ないと練習にならない。

```bash
docker version    # まず Docker が動くか確認
mkdir -p ~/incident-handson && cd ~/incident-handson
```
ネットワークと各コンテナを起動:
```bash
docker network create incnet

# DB（PostgreSQL）
docker run -d --name db --network incnet \
  -e POSTGRES_USER=app -e POSTGRES_PASSWORD=secret -e POSTGRES_DB=appdb \
  postgres:16

# アプリ役（whoami：受け取ったリクエストの中身を返すだけ）
docker run -d --name app --network incnet traefik/whoami
```
nginx を「前段」に置く設定を書く:
```bash
cat > nginx.conf <<'EOF'
events {}
http {
  server {
    listen 80;
    location / {
      proxy_pass http://app:80;     # 裏のアプリへ取り次ぐ
    }
  }
}
EOF

docker run -d --name web --network incnet -p 8080:80 \
  -v "$PWD/nginx.conf:/etc/nginx/nginx.conf:ro" \
  nginx:alpine
```
正常を確認（**これが「平常時」の姿。壊れたら何が変わるかを見るための基準**）:
```bash
docker ps                          # web / app / db が3つとも Up
curl -i http://localhost:8080/ | head -5
```
**成功**：`HTTP/1.1 200 OK` と `Hostname: ...`（whoami の出力）が返る。
**失敗**：
- `port is already allocated` → 8080 使用中。`web` を `docker rm -f web` してから `-p 8081:80` で起動（以降 URL も 8081）。
- 502 が返る → `app` が立っていない。`docker ps` で確認、`docker start app`。

## 障害① アプリを落とす → 502 / 接続不可を切り分ける
**シナリオ**：「ユーザーからサイトにアクセスできないと連絡。さて、どこが壊れた？」

### 1. 障害を起こす
```bash
docker stop app
```
### 2. 症状を観測する
```bash
curl -i http://localhost:8080/
```
**症状**：`HTTP/1.1 502 Bad Gateway`。
**読み解き**：**502 は「前段（nginx）は生きているが、裏（app）が応答しない」**を表す。つまり nginx より奥が怪しい。

### 3. 一次切り分け（経路を順に潰す → [切り分け.md](./切り分け.md)）
```bash
docker ps -a                       # どのコンテナが Up でどれが落ちているか
docker logs web | tail -3          # 前段(nginx)のエラーログ
```
- `docker ps -a` → `app` が `Exited`。**ここで原因の層が「app」と確定**。
- `docker logs web` → `connect() failed (111: Connection refused) while connecting to upstream` のような行。**「裏に繋げなかった」＝502 の理由**。

### 4. 復旧（まず止血 → [復旧手順.md](./復旧手順.md)）
```bash
docker start app
sleep 1
curl -i http://localhost:8080/ | head -3
```
**成功**：また `200 OK` と whoami の出力。→ **止血完了**。
**型のまとめ**：

| 症状 | 確認コマンド | 原因 | 復旧 |
|---|---|---|---|
| 502 Bad Gateway | `docker ps -a` / `docker logs web` | 裏のアプリが落ちている | アプリを再起動（`docker start app`） |

> 「接続不可」も試す：`docker stop web` すると `curl` 自体が `Connection refused`（前段ごと死＝502すら返らない）。`docker start web` で復旧。**502 と接続拒否は層が違う**（→ [切り分け.md](./切り分け.md) の症状→疑う層の表）。

## 障害② DB を止める → アプリ 500 → 原因特定 → 復旧
**シナリオ**：「画面は開くがエラーになる。アプリは生きているのに、なぜ？」

> whoami は DB を使わないので、ここは「アプリが DB に依存している」状況を、**アプリから DB への接続可否**で再現する。アプリの代わりに、同じネットワークから DB へ繋ぐ確認を行う。

### 1. 平常時の DB 接続を確認（基準）
```bash
docker run --rm --network incnet postgres:16 \
  psql "postgres://app:secret@db:5432/appdb" -c "SELECT 1;"
```
**成功**：`?column?` の下に `1`。→ DB は受付可能。

### 2. 障害を起こす（DB を止める）
```bash
docker stop db
```
### 3. 症状を観測する（アプリ→DB が失敗する様子）
```bash
docker run --rm --network incnet postgres:16 \
  psql "postgres://app:secret@db:5432/appdb" -c "SELECT 1;"
```
**症状**：`could not connect to server: Connection refused`（実アプリならこれが 500 になって表面化する）。
**読み解き**：**前段・アプリは生きているのに DB だけ死ぬと「アプリ 500」**になる。502（前段から見て裏が死）と違い、500 は「アプリは動いたが処理中にDBで失敗」。

### 4. 原因特定（DB 層に絞る → [切り分け.md](./切り分け.md)）
```bash
docker ps -a | grep db             # db が Exited か
docker logs db | tail -5           # 落ちた理由（停止 or クラッシュ）
```
- `db` が `Exited` で、ログに `database system is shut down` 等 → **DB ダウンと確定**。

### 5. 復旧
```bash
docker start db
sleep 3                            # DBが受付可能になるまで待つ
docker run --rm --network incnet postgres:16 \
  psql "postgres://app:secret@db:5432/appdb" -c "SELECT 1;"
```
**成功**：また `1` が返る。→ 復旧。
**型のまとめ**：

| 症状 | 確認コマンド | 原因 | 復旧 |
|---|---|---|---|
| アプリ 500（接続拒否） | `docker ps -a` / `docker logs db` / DBへ`psql` | DB がダウン | DB を再起動（`docker start db`）、受付可能まで待つ |

> 実務では「DB は生きているがコネクション枯渇で受付不可」もある。症状は似るが、確認は `SELECT count(*) FROM pg_stat_activity;`（接続数が上限張り付き）。→ [よくある障害パターン.md](./よくある障害パターン.md)

## 障害③ 設定ミスで起動しない（リソース枯渇でない障害）
**シナリオ**：「デプロイ後にコンテナが上がってこない。リソースは余っているのに、なぜ？」
**狙い**：障害は「落ちる」だけでなく「**そもそも起動しない**」もある。原因の大半は **直前の変更（設定ミス）**（→ [切り分け.md](./切り分け.md) の「まず最近の変更を疑う」）。

### 1. 障害を起こす（nginx.conf をわざと壊して作り直す）
```bash
# 設定にわざと文法ミスを入れる（"events" を綴り間違え、; を抜く）
cat > nginx.bad.conf <<'EOF'
events {}
http {
  server {
    listen 80
    location / {
      proxy_pass http://app:80;
    }
  }
}
EOF
# ↑ "listen 80" の行末に ; が無い（文法エラー）

docker rm -f web 2>/dev/null
docker run -d --name web --network incnet -p 8080:80 \
  -v "$PWD/nginx.bad.conf:/etc/nginx/nginx.conf:ro" \
  nginx:alpine
```
### 2. 症状を観測する
```bash
docker ps -a | grep web            # web が Up か Exited か
curl -i http://localhost:8080/     # 応答するか
```
**症状**：`web` が `Exited`、`curl` は `Connection refused`（前段ごと起動していない）。
**読み解き**：リソース（CPU/メモリ/ディスク）は余っているのに起動しない → **設定ミスを疑う**。

### 3. 原因特定（起動失敗は必ずログ → [ログと監視.md](./ログと監視.md)）
```bash
docker logs web
```
→ `[emerg] ... unexpected "location" in /etc/nginx/nginx.conf:5` のような**設定エラー行と行番号**が出る。**「直前に変えた設定（5行目付近）」が原因**と確定。
nginx なら起動前に文法チェックもできる:
```bash
docker run --rm -v "$PWD/nginx.bad.conf:/etc/nginx/nginx.conf:ro" nginx:alpine nginx -t
```
→ `[emerg] ... test failed` で**起動せずに誤りを発見**できる（本番投入前にこれをやれば事故らない）。

### 4. 復旧（設定を正しいものに戻す → [復旧手順.md](./復旧手順.md) の「ロールバック」）
```bash
docker rm -f web
docker run -d --name web --network incnet -p 8080:80 \
  -v "$PWD/nginx.conf:/etc/nginx/nginx.conf:ro" \
  nginx:alpine                     # 正しい nginx.conf に戻す
sleep 1
curl -i http://localhost:8080/ | head -3
```
**成功**：また `200 OK`。→ **設定を直前の正常版に戻して復旧**（＝ロールバックの最小形）。
**型のまとめ**：

| 症状 | 確認コマンド | 原因 | 復旧 |
|---|---|---|---|
| コンテナが起動しない | `docker ps -a` / `docker logs web` / `nginx -t` | 設定ファイルの文法ミス（直前の変更） | 正しい設定に戻す（ロールバック） |

> 実務でも「起動しない系」の第一容疑者は**直近の設定・環境変数・デプロイ**。コードを深掘りする前に **まず変更履歴とログ**（→ [切り分け.md](./切り分け.md)）。
