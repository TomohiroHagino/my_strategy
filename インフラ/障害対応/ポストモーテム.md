# ポストモーテム（事後分析・再発防止）（障害対応）

## ひとことで言うと
障害が収束した後に、**何が起きて・なぜ起きて・どう直すか**を文書にまとめ、同じ障害を二度と起こさないための学びを残す活動。**ブレームレス（人を責めない）**が絶対条件で、犯人探しではなく「仕組みの欠陥」を直す。

## 役割・なぜ必要か
- 復旧で「止血」はできても、**根本原因を直さなければ再発**する。ポストモーテムは再発防止のための装置。
- **ブレームレス**にする理由：人を責めると、当事者が情報を隠し、原因が見えなくなり、また同じ事故が起きる。「なぜこのミスが障害になる仕組みだったのか」に焦点を当てると、本当の改善ができる。
- 組織の**学習資産**になる。後から入った人が過去の障害から学べる。

## 基本（手順・考え方）

### 5 Whys（なぜを5回掘る）
症状から「なぜ」を繰り返し、表面でなく**根本原因**に到達する。
```
症状：ログインが30分間できなかった
 Why1: なぜ？ → 認証サービスが落ちた
 Why2: なぜ？ → DBコネクションが枯渇した
 Why3: なぜ？ → デプロイで接続プール上限の設定が消えた
 Why4: なぜ？ → 設定が環境変数管理で、レビューで気づけなかった
 Why5: なぜ？ → 設定変更を検知するテスト/アラートが無かった   ← 根本原因
→ 再発防止：設定の自動テスト＋プール枯渇のアラートを追加（≠「担当者が注意する」）
```
> 「担当者の不注意」で止めない。**仕組みで防げなかった理由**まで掘るのがブレームレスの肝。

### 収束後にやること
```
1. タイムライン確定 ：対応中の時刻つき記録を整理（検知→初動→切り分け→復旧）
2. 根本原因分析     ：5 Whysで掘る。技術＋プロセス両面
3. 影響の定量化     ：何分停止 / 何ユーザー / 何件失敗 / 売上影響
4. 良かった点・改善点：検知/対応で効いたこと・遅れたこと
5. 再発防止アクション：担当者と期限をつけてチケット化（最重要）
6. 共有             ：関係者でレビュー。学びを横展開
```

## 実務での使い方・定番パターン

### ポストモーテム雛形（テンプレ）
```markdown
# ポストモーテム：{障害タイトル}（YYYY-MM-DD）

## サマリー（3行）
- 何が起きたか：
- 影響：（時間 / 対象ユーザー / 件数 / 金額）
- 根本原因：

## 重大度
SEV2 / 発生 14:32 〜 復旧 15:08（36分）

## タイムライン（時刻つき）
| 時刻 | 出来事 |
|------|--------|
| 14:32 | アラート受信（5xxエラー率 急騰） |
| 14:35 | SEV2判定、IC=@taro |
| 14:38 | 14:20のデプロイが原因と推定 |
| 14:41 | ロールバック開始 |
| 14:46 | エラー率 正常化 |
| 15:08 | メトリクス安定を確認し収束宣言 |

## 根本原因（5 Whys）
（症状→Why1→…→根本原因 を記述）

## 影響
- ユーザー影響：全ユーザーがログイン不可（36分）
- ビジネス影響：問い合わせ N件 / 推定機会損失 X円

## 検知と対応の評価
### 良かった点（続けること）
- アラートが2分で発火し検知が早かった
- ロールバック手順が整備されていて止血が速かった
### 改善点（直すこと）
- 設定変更を検知する仕組みが無かった
- 連絡の第一報がやや遅れた

## 再発防止アクション（担当・期限つき）
| # | アクション | 種別 | 担当 | 期限 | 状態 |
|---|-----------|------|------|------|------|
| 1 | 接続プール枯渇のアラート追加 | 検知 | @hanako | 6/20 | 未着手 |
| 2 | 設定値の自動テストをCIに追加 | 予防 | @taro | 6/25 | 未着手 |
| 3 | ロールバック手順をランブック化 | 対応 | @jiro | 6/18 | 進行中 |

## 学び（横展開）
- 同種の設定が他サービスにもある → 横展開で点検
```

### 運用のコツ
- **SEV1/2は必ずポストモーテムを書く**。SEV3も学びがあれば書く。
- **アクションは必ず「担当・期限・チケット」**にする。「気をつける」「注意する」は禁止（再発防止にならない）。アクションが消化されたか追跡する。
- **タイムラインは対応中のリアルタイム記録から作る**。後から記憶で書くと曖昧になる。→ [初動対応.md](./初動対応.md)
- **レビューはブレームレスに**。「誰が」でなく「何が（仕組みが）」を主語にする。
- 作ったポストモーテムは**検索できる場所に蓄積**し、似た障害の時に参照する。

## ハマりどころ / アンチパターン
- **犯人探しになる**：「○○さんがミスした」で終わると、次から情報が隠れて再発する。**人でなく仕組みを責める**。
- **アクションに担当・期限が無い**：「改善する」だけで誰もやらず放置 → 同じ障害が再発。**チケット化して追跡**。
- **「担当者が注意する」で締める**：人の注意力に頼る対策は必ず破られる。**自動化・テスト・アラート**で仕組み化する。
- **書いて終わり（やりっぱなし）**：アクションの消化を追わないと意味がない。定例で進捗を確認する。
- **5 Whysを浅く止める**：「バグだった」で止めず、「なぜバグが検知されず本番に出たか」まで掘る。
- **SEVが低いと何も残さない**：SEV3でも繰り返すなら根本に問題がある。学びがあれば軽くでも残す。
