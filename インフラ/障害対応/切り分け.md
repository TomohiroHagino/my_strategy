# 切り分け（Diagnosis・原因の特定）（障害対応）

## ひとことで言うと
「どの層が壊れているか」をユーザーに近い側からDB/インフラ側へ順に潰していき、**問題の場所を絞り込む**作業。リクエストの経路を二分探索し、**最初に「最近の変更」を疑う**のが鉄則。

## 役割・なぜ必要か
- 障害は「アプリのバグ」とは限らない。DNS・CDN・ロードバランサ・DB・外部API・ネットワークのどこでも起きる。**当てずっぽうで触ると二次災害**になる。
- 復旧（止血）の判断は「原因の層」が分かると速くなる。例：直近デプロイが原因なら即ロールバック、DB枯渇ならコネクション開放やスケール。→ [復旧手順.md](./復旧手順.md)
- 経路を順に確認すれば、**誰がやっても同じ結論**にたどり着ける（属人化を防ぐ）。

## 基本（手順・考え方）

### リクエスト経路に沿った二分探索
ユーザー側から順に「ここまでは正常か？」を確認し、正常/異常の境目を探す。
```
ユーザー → DNS/CDN → ロードバランサ(LB) → アプリ → DB → インフラ(VM/ネットワーク)
   ①         ②            ③            ④      ⑤        ⑥
```
- **境目を見つける**のがコツ。「LBまでは200が返る／アプリで500」なら原因はアプリ〜DB側に絞れる。
- 各層で「**通るか / エラーか / 遅いか**」の3択を確認する。

### 各層の確認コマンド・観点
```bash
# ① ユーザー/クライアント側 ：本当にサーバ側か、特定ユーザー/地域だけか
curl -v -o /dev/null -s -w "code=%{http_code} dns=%{time_namelookup} connect=%{time_connect} ttfb=%{time_starttransfer} total=%{time_total}\n" https://example.com/health

# ② DNS/CDN ：名前解決できるか、向き先は正しいか
dig +short example.com
nslookup example.com
# CDNのキャッシュ/オリジン状態はレスポンスヘッダで確認（x-cache, age, via 等）
curl -sI https://example.com | grep -iE 'x-cache|age|server|cf-|via'

# ③ ロードバランサ ：到達するか、どのバックエンドが不健全か
curl -sI https://example.com/healthz       # LB経由のヘルスチェック
# AWS: ターゲットの健全性 / GCP: バックエンドの状態をコンソール or CLIで確認

# ④ アプリ ：プロセスは生きているか、エラーログは何を言っているか
curl -s http://localhost:8080/health
journalctl -u myapp --since "10 min ago" | grep -iE 'error|exception|panic|timeout'
ps aux --sort=-%cpu | head             # CPU食い / 暴走プロセス
free -m ; df -h                        # メモリ / ディスク逼迫

# ⑤ DB ：接続できるか、コネクション枯渇/スロークエリは出ていないか
# PostgreSQL
psql -h db -U app -c "SELECT count(*) FROM pg_stat_activity;"   # 接続数
psql -h db -U app -c "SELECT pid, state, wait_event, query FROM pg_stat_activity WHERE state <> 'idle' ORDER BY query_start;"
# MySQL
mysql -h db -e "SHOW PROCESSLIST;"  ;  mysql -h db -e "SHOW ENGINE INNODB STATUS\G"

# ⑥ インフラ/ネットワーク ：到達性・経路・遅延
ping -c 3 db ; traceroute db
ss -tnp | grep ESTAB | wc -l           # 確立済みソケット数
```

### まず疑うべきは「最近の変更」
障害の大半は**「直前に何かを変えた」**ことが引き金。経路探索と並行して、必ず確認する。
```
□ デプロイ      ：直近のリリースはいつ？障害の発生時刻と一致しないか
□ 設定変更      ：環境変数 / フィーチャーフラグ / 機密のローテーション
□ インフラ変更  ：スケール / ネットワーク / セキュリティグループ / DNS切替
□ 依存の変化    ：外部APIの障害 / ライブラリ更新 / 証明書の期限
□ トラフィック  ：急なアクセス増（キャンペーン・bot・DDoS）
```
```bash
# デプロイ時刻の確認例
git log --oneline -10 --pretty="%h %ci %s"
kubectl rollout history deployment/myapp     # k8sのデプロイ履歴
# 障害発生時刻 ≒ 変更時刻 なら、その変更が第一容疑者
```

### 切り分けの5つの軸（これで網羅する）
経路（縦）だけでなく、複数の軸を同時にかけると速く絞れる。
| 軸 | 問い | 分かること |
|---|---|---|
| ① レイヤー（経路） | どの層で壊れる？ | 経路を順に潰す（上記） |
| ② 範囲 | 誰が・どこまで影響？ | 全体か一部かで原因が局在 |
| ③ 時間 | いつから？その時に何が？ | 変曲点＝引き金 |
| ④ 変更 | 直近で何を変えた？ | 第一容疑者（上記） |
| ⑤ 症状 | エラー？遅い？落ちた？ | 疑う層が変わる |

### ② 範囲で絞る（影響範囲 → 疑う場所）
| 影響範囲 | まず疑う場所 |
|---|---|
| 全ユーザー・全機能 | 共通基盤（DNS / LB / 認証 / DB / ネットワーク） |
| 特定の1機能だけ | その機能のコード・依存（特定API / 特定テーブル） |
| 特定地域だけ | CDN/エッジ・特定リージョン・回線 |
| 特定デバイス/ブラウザだけ | フロント/クライアント・キャッシュ |
| 特定テナント/ユーザーだけ | データ依存（その人のデータ・権限・上限） |
| 特定インスタンス1台だけ | そのホスト（リソース枯渇・デプロイ漏れ） |
| 特定AZ/ノードだけ | AZ障害・k8sノード障害 |
| 断続的・一部だけ | プール枯渇・GC・一部ノード・キャッシュ不整合 |

### ⑤ 症状で当たりをつける（症状 → まず疑う）
| 症状 | まず疑う |
|---|---|
| 5xx 急増 | アプリ/サーバ（例外・OOM・デプロイ） |
| 4xx（401/403）急増 | 認証・トークン・権限・設定 |
| 429 急増 | レート制限・スロットリング |
| タイムアウト | 下流が遅い/詰まり（DB・外部API・スレッド枯渇） |
| レイテンシ悪化（p95/p99） | DBスロークエリ・N+1・GC・リソース飽和 |
| 接続拒否（Connection refused） | プロセス落ち・ポート・SG/ファイアウォール |
| 完全に応答なし | LB/プロセス全死・ネットワーク断 |
| 断続的にエラー | コネクションプール枯渇・一部ノード・キャッシュ不整合 |
| 徐々に悪化→停止 | メモリリーク・ディスク/コネクション漸増 |
| 決まった時刻に発生 | cron/バッチ・TTL失効・証明書期限・定期ジョブ |

### ③ 時間で絞る
1. メトリクスの**変曲点**（いつから悪化したか）を特定する。
2. その時刻に起きたことを照合：デプロイ / 設定変更 / cron・バッチ / トラフィック変動 / 外部イベント / 証明書・トークンの期限失効。
→ 「変曲点の直前の出来事」が引き金であることが多い。

### リソースの飽和も必ず見る（USEメソッド）
各リソースが上限に張り付いていないか（**飽和＝詰まりの典型症状**）：
```
CPU / メモリ / ディスク(容量・IOPS) / ネットワーク帯域 /
DBコネクション数 / スレッド・ワーカー数 / ファイルディスクリプタ(FD)
```
1つでも100%付近なら、それが律速（ボトルネック）。→ [よくある障害パターン.md](./よくある障害パターン.md)

## 実務での使い方・定番パターン
- **相関を見る**：「いつから」「何と同時に」を揃える。デプロイ時刻・トラフィック増・エラー率の立ち上がりをグラフで重ねると一目でわかる。→ [ログと監視.md](./ログと監視.md)
- **依存サービスのヘルスを一望**：自前のヘルスチェックエンドポイント（`/health` がDB・外部API・キャッシュの状態を返す）を用意しておくと切り分けが一発。
- **「特定条件だけか」を見極める**：全ユーザーか一部か／特定リージョン・特定ブラウザ・特定エンドポイントだけか。範囲が分かると原因の層も絞れる。
- **カスケード障害を疑う**：1つのサービス遅延が、リトライ・タイムアウト連鎖で全体に波及することがある。**最初に倒れたのはどれか**を時系列で探す。→ [よくある障害パターン.md](./よくある障害パターン.md)
- **再現性の確認**：`curl` で安定して再現するか、断続的か。断続的ならコネクションプール枯渇・特定ノード・キャッシュ起因を疑う。

## ハマりどころ / アンチパターン
- **思い込みで犯人を決め打ち**：「たぶんDBだろう」で経路確認を飛ばす → 実はDNS切替ミスだった、など。**経路を順に潰す**。
- **複数箇所を同時にいじる**：あれもこれも変えると、何が効いたか分からず再発防止もできない。**1つ変えて1つ確認**。
- **最近の変更を確認しない**：原因の大半は直近変更なのに、コードの深掘りから始めて時間を浪費。**まず変更履歴**。
- **平均値だけ見る**：レイテンシは平均でなく**p95/p99**を見る。平均は正常でも一部ユーザーが激遅、を見落とす。→ [ログと監視.md](./ログと監視.md)
- **症状と原因の混同**：「CPU 100%」は症状であって原因ではない。**なぜCPUが張り付いたか**（無限ループ・スロークエリ・トラフィック増）まで掘る。
- **本番で破壊的な調査**：原因調査のつもりで再起動・設定変更を乱発し被害拡大。**観測は非破壊**で、変更は止血の判断後に。
