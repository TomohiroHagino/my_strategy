# 障害対応（インシデント対応・SRE）実務リファレンス（索引）

> **障害対応＝本番障害を「検知から再発防止まで」回す一連の動き**。
> クラウドのどのサービスを使っていても、「壊れたとき何をするか」は共通の型がある。それをまとめる。
> 各ファイルは「ひとことで言うと → 役割・なぜ → 基本（手順・考え方）→ 実務での使い方 → ハマりどころ → 関連」。

## 全体の流れ（5フェーズ）
```
 検知(Detection) → 初動(Triage/エスカレ) → 切り分け(Diagnosis) → 復旧(Mitigation) → 再発防止(Postmortem)
 アラートで気づく   影響範囲・SEV判定・招集   どの層が原因か特定   まず止血（戻す/再起動）  ブレームレスに学ぶ
```

## 2つの大原則
```
 ① まず止血（復旧）優先。原因究明は後。
    └ ユーザーの被害を止めるのが最優先。「なぜ壊れたか」より「どう戻すか」を先に動かす。
 ② 人を責めない（ブレームレス）。
    └ 個人のミスではなく「ミスが事故になる仕組み」を直す。責めると情報が隠れ、再発する。
```

## 重大度（SEV）の考え方
障害は「どれだけヤバいか」で対応のスピードと巻き込む人数を変える。最初に必ず判定する。

| SEV | 状態 | 例 | 対応 |
|---|---|---|---|
| **SEV1** | 全停止・重大データ損失・情報漏洩 | サービス全断、決済不能、個人情報流出 | 即招集・24時間体制・経営/顧客連絡 |
| **SEV2** | 主要機能の重大障害 | ログイン不可、主要APIエラー率高騰 | 即対応・ICを立てる・関係者連絡 |
| **SEV3** | 一部機能の障害・回避策あり | 一部画面エラー、性能劣化 | 通常時間帯に対応・記録は残す |
| **SEV4** | 軽微・ユーザー影響ほぼなし | 内部ツール不調、軽微なログ異常 | バックログで対応 |

> 迷ったら**高めに倒す**（後で下げればよい）。「顧客に見えているか」「お金/データに影響するか」で素早く判断。

## 項目（各ファイルへ）

### フェーズ別（検知→再発防止）
- [初動対応.md](./初動対応.md) … アラート受信から最初の5分。影響範囲把握・SEV判定・IC招集・連絡・記録開始。「止血優先」
- [切り分け.md](./切り分け.md) … どの層が原因か特定する手順。ユーザー→DNS/CDN→LB→アプリ→DB→インフラの二分探索。**まず最近の変更を疑う**
- [対応判断フロー.md](./対応判断フロー.md) … **「この状況なら何をするか」の判断フロー＋状況→止血→根本の早見表**（切り分けと復旧の橋渡し）
- [復旧手順.md](./復旧手順.md) … 止血の手段。ロールバック・再起動・スケール・フェイルオーバー・フィーチャーフラグ・DR復元と判断基準
- [ポストモーテム.md](./ポストモーテム.md) … ブレームレスな振り返り。タイムライン・5 Whys・再発防止アクション（担当/期限つき）。雛形あり

### 道具・知識
- [ログと監視.md](./ログと監視.md) … 何を見るか。USE/REDメソッド・メトリクス・構造化ログ・分散トレース。具体的な確認コマンド
- [よくある障害パターン.md](./よくある障害パターン.md) … 「症状→原因→対処」早見表。コネクション枯渇・証明書切れ・カスケード障害ほか
- [チェックリストとランブック.md](./チェックリストとランブック.md) … 初動チェックリスト・連絡テンプレ・ランブック（手順書）の作り方と例
