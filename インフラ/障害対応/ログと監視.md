# ログと監視（障害時に何を見るか）（障害対応）

## ひとことで言うと
障害対応のとき、**メトリクス（数値の時系列）・ログ（出来事の記録）・トレース（1リクエストの経路）**の3点セットで「壊れているか／どこが遅いか／何が起きたか」を読み解くための見方とコマンド集。平常時の監視設計は各クラウドの monitoring 参照、ここでは**障害時の使い方**に絞る。

## 役割・なぜ必要か
- 切り分けの判断は**データで**行う。勘ではなく「エラー率がいつから何倍になったか」で動く。
- **メトリクスで気づき → ログで原因 → トレースで経路**、の順に解像度を上げる。役割が違うので3つとも要る。
- 監視が薄いと**顧客より遅く障害に気づく**。逆に整っていれば、検知から切り分けまでが一気に縮む。

## 基本（手順・考え方）

### 何を見るか：USEメソッドとREDメソッド
```
USE（リソース＝サーバ/DB側を見る）
  Utilization 使用率  ：CPU/メモリ/ディスク/帯域がどれだけ埋まっているか
  Saturation  飽和    ：待ち行列・スワップ・コネクション待ちが発生していないか
  Errors      エラー  ：ハード/カーネル/ドライバのエラー

RED（サービス＝リクエスト側を見る）
  Rate        流量    ：1秒あたりリクエスト数
  Errors      エラー率：失敗したリクエストの割合（5xx率など）
  Duration    遅延    ：レイテンシ（必ず p50/p95/p99 で見る）
```
- **まずREDでサービスの健康を見て、悪ければUSEで原因リソースを探す**、が基本の流れ。
- レイテンシは**平均でなくパーセンタイル**。p99が悪化＝一部ユーザーが深刻に遅い。

### メトリクスの確認（障害時の着目点）
```
□ エラー率（5xx率）   ：いつから跳ねたか。デプロイ時刻と重なるか
□ レイテンシ p95/p99  ：裾が伸びていないか。特定エンドポイントだけか
□ スループット        ：急増（スパイク）か急減（詰まり）か
□ CPU / メモリ        ：張り付き・右肩上がり（メモリリーク疑い）
□ 飽和                ：DBコネクション数、キュー長、スレッドプール待ち
□ ディスク            ：使用率（フルになると書き込み不能で連鎖障害）
```

### ログの確認（構造化ログ前提）
```bash
# エラーを時系列で拾う（プレーンテキストの場合）
grep -iE 'error|exception|panic|fatal|timeout' /var/log/myapp/app.log | tail -50
journalctl -u myapp --since "15 min ago" -p err

# 直近のエラーを件数集計して「何が多いか」を掴む
grep -iE 'error|exception' app.log | sed -E 's/[0-9]+//g' | sort | uniq -c | sort -rn | head

# 構造化ログ（JSON）なら jq で絞る。requestId で1リクエストを追跡
cat app.log | jq -r 'select(.level=="error") | "\(.time) \(.requestId) \(.msg)"' | tail -50
cat app.log | jq -r 'select(.requestId=="abc-123")'    # 1リクエストの全ログ

# k8s / コンテナ
kubectl logs -l app=myapp --since=15m | grep -iE 'error|timeout'
kubectl logs deploy/myapp --previous     # クラッシュ直前のログ（再起動前）
docker logs --since 15m <container> 2>&1 | grep -i error
```

### トレース（分散トレーシング）
- 1リクエストが APIGW→アプリ→DB→外部API… と複数サービスを通る経路を時間軸で分解し、**どこで時間を食ったか**を見る。
- マイクロサービスでは「全体は遅いが各サービスは正常に見える」ことがある。トレースで初めて**ボトルネックの1区間**が分かる。
- `traceId` をログに通しておくと、メトリクス→トレース→ログを横断できる。

## 実務での使い方・定番パターン
- **3つの黄金シグナルから入る**：エラー率 / レイテンシ(p95,p99) / スループット。まずこの3つを1画面のダッシュボードで。
- **構造化ログ＋相関ID**：全ログに `requestId`/`traceId` を入れる。障害時に「このユーザーのこの1回」を端から端まで追える。
- **メトリクスとデプロイを重ねる**：エラー率グラフにデプロイの縦線を入れておくと、原因が変更かどうか一目。→ [切り分け.md](./切り分け.md)
- **ログはメトリクス化して監視**：「ERROR件数」をログ全文検索で毎回数えるのは高コスト。**メトリクスフィルタ**でログ→メトリクス化しアラートを張る。
- **クラウド別の具体操作はリンク先へ**：
  - AWS：CloudWatch メトリクス/アラーム、Logs Insights、X-Ray → [../aws/monitoring.md](../aws/monitoring.md)
  - GCP：Cloud Monitoring、Cloud Logging（Logging クエリ）、Cloud Trace → [../gcp/monitoring.md](../gcp/monitoring.md)

## ハマりどころ / アンチパターン
- **平均レイテンシだけ見る**：平均は正常でもp99が悪化＝一部ユーザー激遅。**必ずパーセンタイル**で見る。
- **ログが非構造（ただのprint）**：障害時に `grep` の正規表現と格闘して時間を浪費。最初から**JSON構造化＋相関ID**にしておく。
- **アラート乱立で狼少年化**：誤報が多いと本物を無視する。閾値・連続回数・欠損データの扱いを調整し、**意味のあるものだけ通知**。→ [初動対応.md](./初動対応.md)
- **ログ保持コストの放置**：保持期間が無期限だとストレージ課金が膨張。**保持期間を必ず設定**。→ [../aws/monitoring.md](../aws/monitoring.md)
- **再起動でログが消える**：クラッシュ直前のログを取らずに再起動 → 原因の手がかりが消える。`kubectl logs --previous` 等で**再起動前のログを先に確保**。
- **トレース未導入でサービスマップが空**：マイクロサービスでボトルネックが特定できない。最低限の**サンプリングトレース**は入れておく。
