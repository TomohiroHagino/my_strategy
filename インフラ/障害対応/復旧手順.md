# 復旧手順（Mitigation・止血の手段）（障害対応）

## ひとことで言うと
壊れたサービスを**まず動く状態に戻す（止血する）**ための具体的な手段一覧と、どれを選ぶかの判断基準。**原因究明より復旧が先**。「直す」より「戻す・逃がす・止める」を優先する。

## 役割・なぜ必要か
- ユーザーの被害時間を最短にするのが目的。**完璧な修正より、今すぐ効く止血**。
- 止血手段は複数ある（戻す/再起動/スケール/切り離す/オフにする/復元）。**症状と原因の層に応じて即決**できるよう、選択肢と判断基準を持っておく。→ [切り分け.md](./切り分け.md)
- 焦って破壊的操作をすると二次災害になる。**手順と判断基準を事前に決めておく**ことで事故を防ぐ。

## 基本（手順・考え方）：止血手段カタログ

### 1. ロールバック（最優先・最頻出）
**直近のデプロイ/変更が原因なら、まず前の状態に戻す。** 原因究明は戻してから。
```bash
# k8s：1つ前のリビジョンへ戻す
kubectl rollout undo deployment/myapp
kubectl rollout status deployment/myapp        # 戻り完了を確認
kubectl rollout history deployment/myapp        # 履歴確認

# Git/CIベース：前の正常タグを再デプロイ
git revert <bad-commit> && git push            # 変更を打ち消すコミット
# あるいは直前の安定タグを再デプロイ（CIのrollbackジョブ等）

# コンテナイメージのタグを前バージョンに戻して再デプロイ
kubectl set image deployment/myapp app=myrepo/app:v1.2.3   # 1つ前のタグ
```
> 注意：**DBマイグレーションを含むデプロイは単純に戻せない**ことがある（カラム削除など）。後方互換を壊さない設計（expand→migrate→contract）が前提。

### 2. 再起動（手早い一時止血）
```bash
kubectl rollout restart deployment/myapp        # ローリング再起動（無停止狙い）
kubectl delete pod <pod>                         # 不健全なPodだけ落として再作成
systemctl restart myapp                          # VM上のサービス
```
- メモリリーク・ハング・コネクション枯渇など**「溜まって詰まった系」**に効く。ただし**再発するので根本修正は別途**。

### 3. スケール（過負荷・容量不足）
```bash
# スケールアウト（台数を増やす：まず試す。横に増やす方が安全）
kubectl scale deployment/myapp --replicas=10
# オートスケールの上限が低すぎないか確認・引き上げ
# スケールアップ（1台を大きく：DBなど横に増やせないもの）→ ダウンタイム伴うことあり
```
> 原則：**スケールアウト（水平）を先に**。スケールアップ（垂直）は再起動を伴いがちで、過負荷時に逆効果になることも。

### 4. フェイルオーバー（冗長構成への切替）
- DBのプライマリ障害→**リードレプリカを昇格**。リージョン障害→別リージョンへ切替。
- 事前に**自動フェイルオーバー**を組んでおくのが理想。手動の場合は手順書（ランブック）化。→ [チェックリストとランブック.md](./チェックリストとランブック.md)

### 5. サーキットブレーカー / 依存の切り離し
- 外部API・依存サービスが不調なら**呼び出しを止めて**フォールバック（キャッシュ応答・縮退機能）に切り替え、カスケード障害を断つ。
- タイムアウト短縮・リトライ抑制で「巻き込まれ」を防ぐ。→ [よくある障害パターン.md](./よくある障害パターン.md)

### 6. フィーチャーフラグでオフ
- 特定の新機能が原因なら、デプロイを戻さずに**その機能だけフラグでオフ**。影響範囲を最小化して即止血できる。
```
例) feature.newCheckout = false  # 管理画面/設定で即切替→該当機能のみ無効化
```

### 7. DR / バックアップ復元（最終手段）
- データ破損・消失時。**バックアップから復元**、ポイントインタイムリカバリ（PITR）など。
- 復元は時間がかかり、**直近データの欠損（RPO）**が発生しうる。実行前に必ずICと影響を確認。
```bash
# 例）PostgreSQL：直前のダンプから復元（破壊的なので慎重に）
pg_restore -h db -U app -d appdb --clean latest.dump
# クラウドDBはスナップショット/PITRからの復元が基本（aws/rds.md, gcp/cloud_sql.md 参照）
```

## 実務での使い方・定番パターン：判断基準
```
直近にデプロイ/変更した？ ──Yes──→ まずロールバック（or フラグでオフ）
        │No
        ▼
詰まり/リーク/ハング？ ──Yes──→ 再起動で一時止血 → 根本は後で
        │No
        ▼
過負荷/容量不足？ ──Yes──→ スケールアウト → 必要ならレート制限
        │No
        ▼
依存先がダウン？ ──Yes──→ 切り離し/サーキットブレーカー/フォールバック
        │No
        ▼
データ破損/消失？ ──Yes──→ フェイルオーバー or バックアップ復元（ICと影響確認）
```
- **「戻せるなら戻す」が最速**：原因が直近変更なら、調査より先にロールバック。多くの障害はこれで止まる。
- **止血と原因究明を並走させる**：止血担当が戻している間に、別の人がログ/トレースで原因を追う。→ [ログと監視.md](./ログと監視.md)
- **復旧の確認をデータで**：「直った気がする」で終わらせない。エラー率・レイテンシが平常値に戻ったことをメトリクスで確認してから収束宣言。
- **作業は全部タイムラインに記録**：何時に何をしたかを残す（ポストモーテムの一次資料）。→ [ポストモーテム.md](./ポストモーテム.md)

## ハマりどころ / アンチパターン
- **原因究明を優先して止血が遅れる**：「なぜ壊れたか分かるまで戻さない」は被害を広げる。**まず戻す**。原因は後で落ち着いて。
- **DBマイグレ込みのロールバックを無計画に**：カラム削除済みだと戻せず壊れる。マイグレは**後方互換を保つ段階適用**で。
- **スケールアップを過負荷時に実行**：再起動を伴い一時的に容量が減って悪化することがある。**まず横に増やす**。
- **再起動で「直った」と誤認**：リーク・コネクション漏れは再起動で消えるが必ず再発。**根本修正をTODOに残す**。
- **本番で確認なしの破壊的操作**：復元・kill・設定変更はICの判断と影響確認の上で。焦って独断実行が二次災害の典型。
- **収束宣言が早い**：見た目が戻っても裏で再発中のことがある。**メトリクスで一定時間安定**を確認してから宣言。
