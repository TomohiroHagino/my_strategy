# よくある障害パターン（症状→原因→対処）（障害対応）

## ひとことで言うと
本番でよく起きる障害を「**症状 → ありがちな原因 → まずやる対処**」の早見表にしたもの。切り分け中に「この症状はこれかも」と当たりをつけ、対処の入口にする。対処の詳細は [復旧手順.md](./復旧手順.md) へ。

## 役割・なぜ必要か
- 障害の多くは**パターンの再演**。過去事例の型を知っていれば、切り分けと止血が一気に速くなる。
- 「症状」から逆引きできると、経験の浅い担当でも初動を外しにくい。
- 各パターンに**確認コマンド**を添え、勘ではなくデータで確定できるようにする。

## 基本（手順・考え方）：早見表

### リソース枯渇系
| 症状 | ありがちな原因 | まずやる対処 |
|---|---|---|
| CPU 100%張り付き・全体が遅い | 無限ループ、スロークエリ、トラフィック急増 | 暴走プロセス特定→再起動 / スケールアウト / 重いクエリを止める |
| メモリ逼迫・OOM Killer発動 | メモリリーク、設定過小、巨大データ読み込み | 再起動で一時止血→リーク調査 / メモリ増強 / ヒープ上限見直し |
| 応答が時間とともに悪化→落ちる | **メモリリーク**（じわじわ増える） | 定期再起動で延命→根本はコード修正。グラフが右肩上がりなら確定 |
| ディスクフルで書き込み不能 | ログ肥大、一時ファイル放置、バックアップ溜まり | 不要ファイル削除→ログローテ設定 / ボリューム拡張 |

```bash
ps aux --sort=-%cpu | head           # CPU食い特定
ps aux --sort=-%mem | head           # メモリ食い特定
dmesg | grep -i 'killed process'     # OOM Killerの痕跡
df -h ; du -sh /var/log/* | sort -rh | head   # ディスク逼迫の犯人
```

### DB系
| 症状 | ありがちな原因 | まずやる対処 |
|---|---|---|
| アプリが「DB接続できない」連発 | **DBコネクション枯渇**（プール上限到達） | 滞留接続をkill / プール上限見直し / リーク（close漏れ）修正 |
| 一部APIだけ激遅 | スロークエリ / **N+1クエリ** / インデックス欠如 | 重いクエリ特定→killまたはインデックス追加 / N+1をJOIN化 |
| DB全体が遅い・ロック待ち | ロング・トランザクション、デッドロック | 長時間トランザクションをkill / バッチを止める |

```bash
# PostgreSQL：接続数とアクティブな重いクエリ
psql -c "SELECT count(*) FROM pg_stat_activity;"
psql -c "SELECT pid, now()-query_start AS dur, state, query FROM pg_stat_activity WHERE state<>'idle' ORDER BY dur DESC;"
psql -c "SELECT pg_terminate_backend(<pid>);"   # 暴走中の1クエリを止める
# MySQL
mysql -e "SHOW PROCESSLIST;" ; mysql -e "SHOW ENGINE INNODB STATUS\G"
```
> **コネクション枯渇**は頻出。アプリ側の接続close漏れ、プール上限 < 同時リクエスト数、Lambda等の同時実行爆発が典型。

### デプロイ・設定系
| 症状 | ありがちな原因 | まずやる対処 |
|---|---|---|
| デプロイ直後に5xx急増 | **デプロイ失敗**（バグ混入、マイグレ失敗、設定漏れ） | 即**ロールバック**（前バージョンへ）。原因究明は戻してから |
| 起動直後にクラッシュループ | 環境変数欠落、依存先未起動、設定不整合 | 直前の設定変更を戻す / 依存先の起動順を確認 |
| 特定機能だけ壊れた | フラグ誤設定、新機能のバグ | **フィーチャーフラグでオフ** / 該当変更をrevert |

### 証明書・DNS・ネットワーク系
| 症状 | ありがちな原因 | まずやる対処 |
|---|---|---|
| 全クライアントでTLSエラー・接続不可 | **証明書の期限切れ** | 証明書を更新・再発行→自動更新を仕込む |
| 名前解決できない・向き先が変 | DNS設定ミス、切替の伝播待ち、TTL | レコードを修正→TTL分待つ / 旧向き先へ戻す |
| 一部ユーザーだけ繋がらない | 経路障害、SG/FW設定ミス、特定リージョン障害 | 設定変更を戻す / クラウドの障害情報を確認 |

```bash
# 証明書の有効期限を確認（期限切れは事前に防げる障害No.1）
echo | openssl s_client -connect example.com:443 -servername example.com 2>/dev/null | openssl x509 -noout -dates
# 期限の監視：日次でチェックしアラート。Let's Encryptは自動更新(certbot)を必ず
dig +short example.com ; nslookup example.com   # DNS確認
```

### 連鎖・外部依存系
| 症状 | ありがちな原因 | まずやる対処 |
|---|---|---|
| 1サービスの遅延が全体に波及 | **カスケード障害**（リトライ嵐・タイムアウト連鎖・コネクション飽和） | 最初に倒れたサービスを特定→止血。サーキットブレーカー作動 / リトライ抑制 |
| 急に全体が重い | 外部API依存ダウン、依存先のレート制限 | 外部依存を切り離す（タイムアウト短縮・フォールバック・キャッシュ） |
| 突然のアクセス急増で過負荷 | **トラフィックスパイク**（キャンペーン、bot、DDoS） | スケールアウト / レート制限 / CDNキャッシュ / 異常元を遮断 |

> **カスケード障害**の怖さ：弱いサービスが落ちる→呼び出し側がリトライ連打→その負荷で次が落ちる…と将棋倒し。**タイムアウト・リトライ上限・サーキットブレーカー**で連鎖を断つのが予防。

## 実務での使い方・定番パターン
- **「最近の変更」と症状を突き合わせる**：デプロイ直後の5xxはまずデプロイ失敗を疑い、即ロールバック。→ [切り分け.md](./切り分け.md)
- **症状が複数なら「最初の1つ」を探す**：カスケードでは末端の症状が派手だが、原因は最初に倒れたサービス。時系列で先頭を見る。
- **事前に潰せるものは監視で予防**：証明書期限・ディスク使用率・コネクション数・メモリ増加トレンドは**閾値アラート**で障害化前に気づく。→ [ログと監視.md](./ログと監視.md)
- **このページは「逆引き索引」として使う**：症状で当たりをつけ、確定はコマンドで、対処は [復旧手順.md](./復旧手順.md) へ。

## ハマりどころ / アンチパターン
- **症状＝原因と決めつけ**：「CPU100%」は症状。**なぜ張り付いたか**（スロークエリ／無限ループ／トラフィック）まで掘らないと再発する。
- **再起動で満足して放置**：メモリリークやコネクション漏れは再起動で一旦治るが**必ず再発**。止血後に根本修正を必ず行う。
- **リトライを安易に増やす**：障害時のリトライ増設はカスケードを悪化させる。**指数バックオフ＋上限＋サーキットブレーカー**とセットで。
- **証明書を手動更新運用**：人手だと必ず忘れて期限切れ。**自動更新＋期限監視**を仕込む。
- **外部依存にタイムアウト無し**：依存先が無応答だと自分のスレッドが食い尽くされ全体停止。**全外部呼び出しにタイムアウト**を。
