# チェックリストとランブック（障害対応）

## ひとことで言うと
障害時に「迷わず動く」ための道具。**チェックリスト**（初動でやることの抜け漏れ防止）、**連絡テンプレ**（社内/顧客/ステータスページの定型文）、**ランブック**（特定障害の手順書）の3点をあらかじめ用意しておく。

## 役割・なぜ必要か
- 障害時は焦って手順を飛ばす。**事前に書いておけば、誰でも・落ち着いて・同じ手順**で動ける。
- 連絡文を毎回ゼロから考えると遅れる。**テンプレ穴埋め**で第一報を数分で出せる。
- ランブックがあれば、**経験の浅い担当でも止血まで到達**できる（属人化を防ぐ）。深夜のオンコールで真価を発揮する。

## 基本（手順・考え方）

### 初動チェックリスト（アラート受信時にこれを開く）
```
■ 検知・確認
  □ アラートは本物か（誤報でないか1分で判断）
  □ いつから発生しているか
■ 影響範囲
  □ 全体か一部か（対象ユーザー/機能/リージョン）
  □ お金・データ・個人情報に影響があるか
■ 重大度
  □ SEVを判定した（迷ったら高め）→ [初動対応.md](./初動対応.md)
■ 体制
  □ IC（指揮官）を1人決めた
  □ 必要な対応者を招集した（1人で抱えない）
  □ 専用チャンネル/ドキュメントを作った
■ 連絡
  □ 第一報を出した（社内）
  □ SEV1/2なら顧客・ステータスページを更新
  □ 次回連絡の時刻を約束した（15分後など）
■ 記録
  □ 記録担当を決め、時刻つきでタイムライン記録を開始
■ 調査・止血（並走）
  □ 最近の変更（デプロイ/設定/トラフィック）を確認 → [切り分け.md](./切り分け.md)
  □ 止血手段を選定（ロールバック等）→ [復旧手順.md](./復旧手順.md)
■ 収束
  □ メトリクスで平常値への復帰を確認
  □ 収束を宣言・連絡
  □ ポストモーテムの起票 → [ポストモーテム.md](./ポストモーテム.md)
```

### 連絡テンプレ

**第一報（社内・5分以内）**
```
【障害発生 SEV{N}】{症状を一言}
発生時刻: {HH:MM}頃 / 影響: {対象ユーザー・機能}
状況: 調査中 / IC: @{担当} / 次報: {N}分後
チャンネル: #incident-{日付}-{識別子}
```

**続報（進捗・定時）**
```
【続報 SEV{N}】{症状}
状況: {ロールバック実施中 など} / 復旧見込み: {あれば}
次報: {N}分後
```

**収束報（社内）**
```
【復旧 SEV{N}】{症状}
復旧時刻: {HH:MM} / ダウン時間: {N}分
暫定原因: {一言} / ポストモーテム: {リンク}（後日）
```

**顧客向け・ステータスページ**（簡潔・約束しすぎない）
```
[調査中] 一部のお客様で{機能}がご利用しづらい事象が発生しています。原因を調査中です。（HH:MM）
[復旧作業中] 原因を特定し、復旧作業を行っています。（HH:MM）
[復旧済み] {HH:MM}に復旧しました。ご迷惑をおかけしました。（HH:MM）
```
> 顧客向けは**内部の生情報を出さない**・**確定していないことを断定しない**・**過度な約束をしない**。事実と現在のステータスだけを淡々と。

### ランブック（手順書）の作り方
特定の障害シナリオに対する**ステップ実行手順**。深夜でもコピペで動けるレベルに具体化する。
```markdown
# ランブック：DBコネクション枯渇

## いつ使う（トリガー）
- アラート「DB connection pool exhausted」発火時
- アプリログに "too many connections" が頻発

## 確認
1. 接続数を見る:  psql -c "SELECT count(*) FROM pg_stat_activity;"
2. 滞留クエリを見る:
   psql -c "SELECT pid, now()-query_start AS dur, state, query
            FROM pg_stat_activity WHERE state<>'idle' ORDER BY dur DESC;"

## 止血（上から順に試す）
1. 長時間滞留している1クエリを止める:
   psql -c "SELECT pg_terminate_backend(<pid>);"
2. 改善しなければアプリをローリング再起動（接続を一旦開放）:
   kubectl rollout restart deployment/myapp
3. 直近デプロイで設定が変わっていれば ロールバック:
   kubectl rollout undo deployment/myapp

## エスカレーション
- 15分で復旧しなければ DBA @hanako を招集

## 関連
[よくある障害パターン.md](./よくある障害パターン.md) / [復旧手順.md](./復旧手順.md)
```

## 実務での使い方・定番パターン
- **チェックリストはチャンネルに固定（ピン留め）**：障害時に即開ける場所へ。ICが上から順に潰す。
- **ランブックは「頻出障害」から作る**：全部は要らない。コネクション枯渇・デプロイ失敗・証明書切れ・主要外部API障害など、起きがちなものを優先。→ [よくある障害パターン.md](./よくある障害パターン.md)
- **ポストモーテムのアクションからランブックを生やす**：障害を1つ経験するごとに、その対処手順をランブック化して資産にする。→ [ポストモーテム.md](./ポストモーテム.md)
- **連絡テンプレはコピペ即送信できる形で保管**：穴埋めだけで出せるように。第一報の速さが信頼を左右する。
- **定期的に「火災訓練」（ゲームデー）**：意図的に障害を起こしてランブックとチェックリストを実地検証する。使えない手順書は本番で役に立たない。
- **オンコール体制と連動**：誰が一次対応か（ローテーション）、エスカレ先は誰かを明記し、チェックリスト内のエスカレ手順とつなぐ。

## ハマりどころ / アンチパターン
- **作って放置で陳腐化**：コマンドやサービス名が古いランブックは本番で詰む。**障害のたびに更新**し、訓練で検証する。
- **抽象的すぎて使えない**：「DBを確認する」では深夜に動けない。**具体的なコマンドと閾値**まで書く。
- **顧客向けに内部情報を出す**：原因の生データや確定前の推測を顧客向けに書くと混乱・不信を招く。**ステータスと事実のみ**。
- **チェックリストが長すぎる**：本当に必要な項目に絞る。長大だと障害時に読まれない。
- **連絡テンプレが無く毎回手作り**：第一報が遅れ、問い合わせが殺到する。**穴埋めテンプレ**を必ず用意。
- **訓練しない**：手順書を一度も実行せず本番初使用 → 想定外で機能しない。**ゲームデーで定期検証**。
