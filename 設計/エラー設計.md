# エラー設計（Result/Option vs 例外の使い分け）

## 一言で
> **「失敗は想定内か例外か」で分ける。想定内の失敗を例外で投げると制御フローが隠れる。**
> 在庫切れやバリデーション違反のような「業務として起こりうる失敗」を例外で飛ばすと、`try/catch` という見えない `goto` で正常系と異常系が絡まり、どこで分岐しているのか追えなくなる。逆に、ぬるぽや配列外参照のような「起きてはならないバグ」を律儀に値で返すのは過剰。**何を値で返し、何を投げるか**の線引きこそがエラー設計の本体。

> ※ 言語ごとの仕組み（`try/catch`、`Result`、`panic`、`error` 値…）の比較は [../言語共通概念/エラー処理.md](../言語共通概念/エラー処理.md) が担当。ここは**設計判断**に寄せる。

---

## 2つの流派
エラーの扱いには大きく2つの思想がある。「投げる」か「返す」か。

| 観点 | 例外（throw / catch） | 値で返す（Result・Option・Goの err） |
|---|---|---|
| **思想** | 失敗は通常フローから「脱出」させる。正常系のコードを失敗処理で汚さない。 | 失敗も**ただの値**。関数の戻り値の一部として明示的に扱う。 |
| **見え方** | シグネチャに失敗が現れない（チェック例外を除く）。呼び出し側からは成功するように見える。 | シグネチャに `Result<T,E>` 等が現れる。**失敗しうることが型に出る**。 |
| **強み** | 正常系が読みやすい。深いネストの底からも一気に脱出できる。共通のエラーハンドリングを境界に集約しやすい。 | ハンドリングを**呼び出し側に強制**できる。失敗の種類が型で網羅される。制御フローが見える。 |
| **弱み** | 制御フローが暗黙的になり追いにくい。握りつぶし（catch して無視）が容易。どこで投げるか型に出ない。 | コードが冗長になりがち（毎回 `if err != nil` / `match`）。多段の伝播が手間。言語サポートが弱いと辛い。 |

- どちらが正解という話ではなく、**「想定内 ⇒ 値」「想定外 ⇒ 例外」**が大枠の指針（次節）。
- 近年は Rust / Go / Kotlin（sealed）などが「値で返す」を強く推す。一方 Java / Python / C# は例外が主役。**言語の文化に逆らいすぎない**のも実務上は大事。

## 「想定内の失敗」と「想定外のバグ」を分ける
この線引きがエラー設計の核。**同じ「失敗」でも性質がまったく違う**。

- **想定内の失敗（expected / recoverable）** … 業務として普通に起こりうる。呼び出し側が**対処する前提**。
  - 在庫切れ、残高不足、バリデーション違反、ユーザーが見つからない、外部APIのタイムアウト。
  - → **値で返す**（`Result` / ドメインのエラー型）か、ドメインモデル上で明示的に表現する。
  - これらを例外で投げると、「正常な業務分岐」が `catch` に隠れ、制御フローが読めなくなる。
- **想定外のバグ（unexpected / programmer error）** … 起きてはならない。起きたらコードが間違っている。
  - null参照、配列外アクセス、不変条件の破れ、ありえない `switch` の default 到達。
  - → **例外で落とす**（fail-fast）。握って継続せず、上位の境界でまとめて捕捉し、ログ＋500等で終わらせる。
  - 律儀に `Result` で返すと、呼び出し側に「起きえないケース」のハンドリングを強制してしまい無駄。

```text
在庫切れ      → 想定内 → Result.Err(OutOfStock) を返す（呼び出し側が在庫補充案内などに分岐）
バリデ違反    → 想定内 → Result.Err(ValidationError) を返す
config未設定  → 起動時に検知して即落とす（fail-fast、後で直すべきバグ/設定ミス）
null参照      → 想定外 → 例外で落ちてよい（握りつぶさず原因を直す）
```

> 迷ったときの問い：**「これは呼び出し側が日常的に対処すべきことか？ それとも直すべきバグか？」** 前者なら値、後者なら例外。

## エラーを型で表現する
「値で返す」流派の最大の利点は、**呼び出し側にハンドリングを強制できる**こと。型がそれを担保する。

- **`Result<T, E>`（Rust / Kotlin等）** … 成功 `Ok(T)` か失敗 `Err(E)` のどちらか。`E` に失敗の種類を載せる。使う前に必ず開封（`match` / `?`）が要る。
- **`Option<T>` / `Maybe`（“無い”を表す）** … 値が「在る/無い」だけを表す。**失敗の理由が要らない不在**（見つからない等）に向く。理由が要るなら `Result` に格上げ。
- **sealed class / union 型でエラーを網羅** … 失敗の種類を**有限集合として列挙**し、`when` / `switch` で網羅チェックを効かせる。新しい失敗を足すとコンパイラが分岐漏れを教えてくれる。

```text
sealed interface WithdrawError
  ├ InsufficientFunds(shortage)
  ├ AccountFrozen
  └ DailyLimitExceeded

withdraw(...) : Result<Receipt, WithdrawError>
   → 呼び出し側は3種すべてを処理しないとコンパイルが通らない
```

- ポイントは「**失敗をドキュメントではなく型に書く**」こと。型に出ていれば、ハンドリング漏れがレビューや実行時ではなく**コンパイル時**に潰れる。
- 仕組みの詳細（各言語の `Result`/`Either`/`Option` の実体）は [../言語共通概念/エラー処理.md](../言語共通概念/エラー処理.md) へ。

## 例外設計の指針
例外を使う場合（あるいは例外文化の言語で書く場合）の勘所。

- **チェック例外の是非** … Java のチェック例外は「ハンドリング強制」という思想自体は正しいが、伝播のたびに `throws` が膨れ、無意味な握りつぶしを誘発しがち。**多用は避け、本当に呼び出し側が対処すべきものだけ**に絞るのが実務的な落とし所。
- **握りつぶし禁止** … `catch (e) {}`（何もしない）は最悪のアンチパターン。少なくとも**ログを残し、再送出するか、意図的に握る理由をコメントで明示**する。「握ってよい例外」は限定的。
- **境界で翻訳（ドメイン例外 ↔ インフラ例外）** … 下層の `SQLException` や `IOException` を、そのまま上層へ漏らさない。境界で**ドメインの言葉の例外/エラーに翻訳**する。さもないと上位がDBの都合を知ることになり、層が癒着する（→ 層の境界の話は [クリーンアーキテクチャ.md](./クリーンアーキテクチャ.md)）。
- **ログと再送出** … 同じ例外を各層で何度もログ出力しない（ログ地獄になる）。**詳細ログは捕捉して対処する最終境界で1回**。途中は文脈を足してラップ再送出（`cause` を保持）する。
- **ユーザー向けメッセージと内部詳細の分離** … スタックトレースや `SQLException` の文言を**ユーザーに見せない**（情報漏洩・体験の両面でNG）。ユーザーには平易なメッセージ＋追跡用ID、内部には詳細ログ、と**出し分ける**。

```text
[内側] InsufficientFundsError（ドメイン例外/エラー）
          ▲ 翻訳（境界で）
[外側] SQLException / TimeoutException（インフラの詳細）

ユーザーには：「処理に失敗しました（ID: 7f3a…）」
ログには    ：例外型・スタック・入力文脈（秘匿情報は除く）
```

## ドメイン層でのエラー
DDD の集約は**不変条件（invariant）を守る**のが仕事。その違反をどう外へ伝えるかは設計判断になる。

- **集約ルートのメソッドで不変条件を守る**のは前提（→ [ddd.md](./ddd.md)）。問題は「破られそうな操作」をどう表現するか。
  - **想定内の業務的拒否**（取消不可・残高不足など）→ **`Result` / ドメインエラーで返す**。呼び出し側のユースケースが分岐できる。
  - **そもそも呼んではいけない呼び出し**（確定済み注文に明細追加など、UI側で防ぐべき操作）→ **例外で落とす**選択もあり。fail-fast でバグを早期に表面化させる。
- どちらに倒すかは**チームの文化と言語**で決め、**集約内で一貫させる**のが大事。同じ集約で「あるメソッドは例外、別のは Result」だと呼び出し側が混乱する。
- **層の境界での翻訳**はクリーンアーキの依存ルールと直結する。ドメインのエラーをそのままHTTPステータスやDBエラーに混ぜない。**ユースケース層 → アダプタ層で翻訳**する（→ [クリーンアーキテクチャ.md](./クリーンアーキテクチャ.md)）。

```text
[ドメイン]  order.cancel(reason) : Result<Unit, CancelError>   ← 業務的拒否は値で
[ユースケース] CancelError を受けて分岐（再試行/ユーザー通知…）
[アダプタ]  CancelError → HTTP 409 / メッセージ に翻訳
```

## よくある誤解・ハマりどころ
- **例外を通常フロー制御に使う**：「ループ脱出に例外」「見つからなければ例外」など。例外は `goto` 同然で、正常系の分岐に使うと**制御フローが隠れ**、しかも遅い。想定内の分岐は値で。
- **`catch (Exception)` で全部握る**：粒度の粗い捕捉は、想定外のバグ（NPE等）まで飲み込んで**握りつぶす**。捕捉は**対処できる型だけ**狭く。広い捕捉は最終境界の「最後の砦」1箇所に限定。
- **null を返してエラーを表す**：`null` は「無い」のか「失敗した」のか「未初期化」なのか曖昧で、呼び出し側のチェック漏れ＝NPEの温床。**`Option`（不在）と `Result`（失敗）を使い分ける**。
- **`Result` を無視できてしまう言語での放置**：Go の `err` を `_` で捨てる、戻り値の `Result` を見ずに握りつぶす等。**型で返しても、無視できる言語では規律で守る**（lint・レビュー・`#[must_use]` 相当の活用）。型に出すこと自体が目的化して、ハンドリングを忘れては本末転倒。
- **エラーの粒度が雑 or 細かすぎ**：全部 `AppError` の文字列1個だと分岐できない。逆に失敗ごとに型を量産すると網羅が苦行。**呼び出し側が分岐したい単位**で切る。
