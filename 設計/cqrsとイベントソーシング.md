# CQRS とイベントソーシング

## 一言で
**CQRS（Command Query Responsibility Segregation）＝ 書き込み（Command）と読み取り（Query）でモデルを分ける設計。** **イベントソーシング（Event Sourcing / ES）＝ 現在の状態ではなく、起きたイベント列を真実（source of truth）として保存する設計。** よく一緒に語られるが、両者は別の関心事を扱う別物。

> **CQRS と ES は別物。混同しない。**
> CQRS は「書きと読みでモデルを割る」話。ES は「状態を保存するかイベントを保存するか」の話。
> **片方だけでも成立する**（CQRSだけ／ESだけ）。両方を同時に採るのは選択の一つにすぎず、義務ではない。

---

## CQRS

**一言で：** 1つのモデルで「書き込み」と「読み取り」の両方をこなそうとせず、**Command（状態を変える操作）用のモデル**と **Query（状態を読むだけの操作）用のモデル**を分離する。

- 書き込み側は業務ルール・不変条件を守ることに集中する（DDDの集約がここに来やすい）。
- 読み取り側はルールを気にせず、**画面・APIが欲しい形に最適化した専用モデル**を素直に作る。
- 「1つの正規化されたモデルで、複雑な書き込みルールも、多様な読み取りニーズも、全部満たす」ことの無理を認め、責務で割るのが発想の核。

```text
                ┌───────────────────────────┐
   Command ───→ │  Write Model（書き込み）   │ ── 業務ルール・不変条件を守る
 （状態を変更）  │  例: 集約 / ドメインモデル │      （正規化・整合性重視）
                └────────────┬──────────────┘
                             │ 反映（同期 or 非同期）
                             ▼
                ┌───────────────────────────┐
   Query   ───→ │  Read Model（読み取り）    │ ── 画面/API向けに最適化
 （状態を取得）  │  例: 専用テーブル/ビュー   │      （非正規化・参照特化）
                └───────────────────────────┘
```

### メリット
- **読み取りを素直に書ける**：JOIN地獄を避け、画面ごとに**専用の読み取りモデル**（非正規化テーブル・マテビュー・検索インデックス）を用意し、ほぼそのまま返せる。
- 書きと読みを**別々にスケール**できる（読み取りレプリカを増やす、Read側だけキャッシュする等）。
- 書き込み側はルールの保護だけに専念でき、ドメインモデルが読み取り都合で歪まない。

### コスト
- **整合性**：Write側とRead側を非同期で同期すると、**Read側が一瞬古い（結果整合性）**。ここを業務・UIが許容できるかが分かれ目。
- **複雑さ**：モデルが2つに増え、同期の仕組み（イベント／プロジェクション／バッチ）も要る。**単純なCRUDに入れると純粋にコスト増**。
- 同期を「同じDB・同期更新」にすればシンプルだが、その場合スケール上の旨味は薄れる（CQRSは必ずしも非同期・別DBではない）。

## イベントソーシング

**一言で：** 「現在の状態」をテーブルに上書き保存するのではなく、**「起きたこと（イベント）」を時系列に追記（append-only）し、それを畳み込んで（fold）現在の状態を導く**。

- 従来：`UPDATE account SET balance = 1500 WHERE id = ...`（**結果だけ**残り、途中経過は消える）。
- ES：`Deposited(1000)`, `Deposited(800)`, `Withdrawn(300)` を順に追記し、**畳み込むと balance = 1500**。過去のイベントは**消さない**。
- イベントは**過去形の事実**（`OrderPlaced`, `PaymentCompleted`）であり、追記のみで更新・削除しないのが原則。

```text
イベントストア（追記のみ・不変の履歴）
  ┌──────────────┬──────────────┬───────────────┐
  │ Deposited    │ Deposited    │ Withdrawn     │  ← 起きた順に append
  │ amount:1000  │ amount: 800  │ amount: 300   │
  └──────┬───────┴──────┬───────┴──────┬────────┘
         └──────────────┴──────────────┘
                        │ 左から畳み込む（replay / fold）
                        ▼
                 現在の状態 balance = 1500
   （状態は「保存物」ではなく、イベント列から導出される計算結果）
```

### メリット
- **完全な履歴・監査**：「いつ・何が・どの順で起きたか」が全部残る。監査ログを別途作る必要が薄い（イベントそのものが監査証跡）。
- **タイムタラベル**：任意の時点まで畳み込めば、**過去のある時点の状態を再現**できる。「先月末時点の残高」を後から正確に出せる。
- 状態を捨てていないので、**後から新しい読み取りモデルを作り直せる**（過去イベントをリプレイして別の集計を生成）。バグで壊れた状態もイベントから再構築できる。

### コスト
- **スキーマ進化**：イベントは永久に残るため、**古い形式のイベントを将来も解釈し続ける**必要がある（イベントのバージョニング／アップキャスト）。安易に形を変えられない。
- **リプレイ**：イベントが増えると毎回ゼロから畳み込むのは重い。**スナップショット**（途中状態の保存）で短絡する設計が要る。
- **最終的整合性**：Read側プロジェクションへの反映は非同期になりがちで、ここでも結果整合性の問題が出る。

## CQRS と ES の関係

両者は独立。**片方だけでも成立する**。組み合わせは設計の選択肢であって必須ではない。

| 構成 | 書き込みの保存形態 | 読み取りモデル | 典型 |
|---|---|---|---|
| **単独CQRS（ESなし）** | **状態を保存**（通常のテーブル更新） | 書きとは別の最適化された専用Read | 「書き込みは正規化DB、読み取りは非正規化ビュー/検索」。最も現実的に多い形 |
| **単独ES（CQRSなし）** | **イベント列を保存** | 同じモデルから畳み込んで読む | イベントから状態を導くが、読み書きでモデルは分けない。小規模なら成立 |
| **CQRS + ES** | **イベント列を保存** | イベントを投影（projection）した専用Read | Write＝イベントストア、Read＝イベントから生成したビュー。両者の旨味が噛み合う組み合わせ |

- ES を採ると「イベントから現在状態を導く（Write）」と「クエリ向けに投影する（Read）」が自然に分かれるため、**ESはCQRSと相性が良い** → だからセットで語られやすい。
- しかし **CQRSにESは不要**（状態保存のままRead/Writeを割ってよい）し、**ESにCQRSは不要**（読み書き同一モデルでもよい）。**「セットで導入しないと意味がない」は誤解**。

## DDDとの相性
- **書き込み側に集約が来る**：集約ルートがCommandを受け、不変条件を守り、**ドメインイベントを発行**する。そのイベントをそのまま永続化すればES、Read側へ流せば読み取りモデルの更新トリガになる。
- **読み取りはQuery側へ逃がす**：参照しかしない画面は集約を通さず、Query側の専用モデルで素直にSQLを書く（DDDの「全部を集約にしようとするな」と同じ話）。
- DDDのドメインイベントと ES のイベントは**自然につながる**が、同一ではない（ドメインイベントは「境界をまたぐ通知」、ESのイベントは「状態の唯一の真実」という役割の違いがある）。→ [ddd.md](./ddd.md)

## よくある誤解・ハマりどころ
- **CRUDアプリに無条件導入**：ロジックが薄く読み書きも素直なアプリにCQRS/ESを入れると、モデル2倍・同期機構・イベント設計のコストだけが乗る。**銀の弾丸ではない**。
- **結果整合性を許容できるか未確認**：「書いた直後に読んだら古い」をUIや業務が受け入れられるか確かめずに非同期CQRS/ESを採ると、**「保存したのに表示されない」クレーム**で詰む。許容できないなら同期反映を選ぶ。
- **イベントのスキーマ変更地獄**：ESではイベントが永久に残る。深く考えず構造を変えると、**過去イベントが読めなくなる／全バージョンの分岐を抱える**羽目に。バージョニングとアップキャスト方針を最初に決める。
- **CQRS=ES と思い込む／必ずセットだと思う**：別物。片方だけでよい場面が多い。**「分散・非同期・別DB」も必須ではない**（同一DB・同期反映のCQRSもある）。
- **銀の弾丸視**：履歴・監査・スケールという旨味の裏に、運用と認知コストの確実な増加がある。**得る価値がコストを上回る場面でだけ使う**。

## 向いている場面 / 向かない場面
- **向いている**：
  - **強い監査要件**（金融・医療・在庫など「何がいつ起きたか」を正確に残す必要） → ES。
  - **複雑なドメイン**で書き込みルールが厚く、読み取りニーズが多様 → CQRS。
  - **読み書きの負荷が非対称**（読み取りが圧倒的に多い等）で別々にスケールしたい → CQRS。
  - 「過去の任意時点を再現したい」「後から集計を作り直したい」 → ES。
- **向かない**：
  - **単純なCRUD**、ロジックが薄い管理画面、PoC・使い捨て。
  - 結果整合性をUI/業務が許容できない、かつ非同期にしたい場面（要件と手段が衝突）。
  - チームがイベント設計・運用に不慣れで、得られる価値が学習・運用コストを上回らない場合。**ここで全部入りにするとコストだけ増える**。
