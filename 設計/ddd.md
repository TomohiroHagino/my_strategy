# DDD（ドメイン駆動設計）

## 一言で
**「ソフトウェアの複雑さの本体は技術ではなく業務（ドメイン）側にある」** という前提に立ち、業務の言葉とコードを一致させながら、複雑な領域を分割して攻める設計のやり方。Eric Evans の同名書（2003）が源流。

> DDD = 「戦略的設計（どう分割し、どこに力を注ぐか）」＋「戦術的設計（モデルをどうコードに落とすか）」の2階建て。
> **戦術（Entity/値オブジェクト…）だけ真似て戦略を飛ばすと、ただの命名規約**になりがち。本体は戦略のほう。

---

## なぜDDDか（何が嬉しいのか）
- 業務が複雑なほど、コードと会話の語彙がズレて伝言ゲームになる。DDDは**同じ言葉（ユビキタス言語）で喋る／書く**ことでズレを潰す。
- 「全部を1つの正しいモデルにする」のは大規模だと破綻する。**領域を区切って、区切りごとに別モデルを許す**ことで現実的にスケールさせる。
- 向く場面 / 向かない場面がはっきりしている（後述）。**CRUDだけのアプリに重い戦術設計を持ち込むと過剰**。

---

## 戦略的設計（まずこっち。地図を描く層）

### ユビキタス言語（Ubiquitous Language）
- ドメインエキスパート（業務の人）と開発者が**同じ単語を同じ意味で使う**。コードのクラス名・メソッド名もその単語にする。
- 例：「注文をキャンセルする」を業務が "取消" と呼ぶなら、コードも `cancel` ではなく `revoke`/`取消` に寄せる、という温度感。**翻訳を挟まない**のが肝。

### 境界づけられたコンテキスト（Bounded Context）★最重要概念
- **1つのモデルが意味を持つ範囲の境界**。同じ「商品」でも、販売コンテキストと在庫コンテキストでは持つ属性も振る舞いも違う ＝ **別モデルとして分ける**。
- 「全社で1つの商品クラス」を目指すと、属性が膨れ上がり誰も理解できなくなる。**境界で割って、境界の中だけ一貫していればよい**とするのがDDDの現実解。
- マイクロサービスの「サービス分割の単位」とよく対応する（必須ではない。モジュラモノリス内の論理境界でもよい）。

### コンテキストマップ（Context Map）
- 複数の境界づけられたコンテキストが**どう関係するか**を描いた地図。代表的な関係：
  - **Shared Kernel**（共有核）… 2コンテキストで一部モデルを共有。変更には両者の合意が要る。
  - **Customer/Supplier**（上流/下流）… 下流が上流に要求を出せる関係。
  - **Conformist**（追従）… 下流が上流の都合に従うしかない（外部APIなど）。
  - **Anti-Corruption Layer（ACL / 腐敗防止層）** … 外部や別コンテキストのモデルを**自分のモデルに翻訳する変換層**を挟み、相手の都合がこちらのドメインに漏れないよう守る。レガシー連携の定番。

### サブドメインの分類（どこに力を注ぐか）
- **コアドメイン** … 競争優位の源泉。**ここに一番良い人と時間を注ぐ**。作り込む。
- **支援サブドメイン（Supporting）** … コアを支えるが差別化要因ではない。そこそこでよい。
- **汎用サブドメイン（Generic）** … 認証・帳票・決済など。**買う／既製品で済ます**のが正解になりがち（自作しない）。

## 戦術的設計（モデルをコードに落とす層）

| 部品 | 役割 | 見分け方 |
|---|---|---|
| **エンティティ（Entity）** | **同一性（ID）で区別**される。属性が変わっても同じ個体。 | 「IDが同じなら同じ人」＝ユーザー、注文 |
| **値オブジェクト（Value Object）** | **属性の値そのもの**で等価。IDを持たず、不変（immutable）。 | 金額・日付範囲・住所・メールアドレス |
| **集約（Aggregate）** | 一貫性を保つべき**かたまり**。外からは**集約ルート（Aggregate Root）経由でのみ**触る。 | 注文(ルート)＋明細行。明細だけ単独で勝手に変えない |
| **ドメインサービス** | どの単体エンティティにも属さない**業務ロジック**の置き場。 | 「口座Aから口座Bへ送金」 |
| **リポジトリ（Repository）** | 集約の**永続化を抽象化**。コレクションのように見せる。 | `OrderRepository.findById()` |
| **ファクトリ** | 複雑な集約の**生成**をカプセル化。 | 不変条件を満たした注文を組み立てる |
| **ドメインイベント** | 「○○が起きた」という**過去形の事実**。境界をまたぐ連携や履歴に使う。 | `OrderPlaced`, `PaymentCompleted` |

### 集約の設計が一番効く（&一番むずい）
- **集約 = トランザクション整合性の単位**。「1トランザクションで1集約だけ更新」を原則にすると設計が締まる。
- 集約は**小さく保つ**。注文に明細1万行をぶら下げると、ロードも更新も重くなる。
- 集約をまたぐ整合性は**結果整合性（ドメインイベント＋非同期）**で解く、というのがモダンDDDの定石。

### 不変条件（invariant）を集約ルートに集める
- 「注文合計はマイナスにならない」「確定後は明細を変更できない」等の**業務ルールを集約ルートのメソッド内で守る**。
- セッターを公開して外から好き放題変えさせると、ルールが各所に散ってドメインモデルが**ただのデータ袋（貧血ドメインモデル / Anemic Domain Model）** に堕ちる。これがDDDで最も嫌われるアンチパターン。

```text
✗ 貧血モデル: order.setStatus("cancelled")   ← ルールはサービス側に散る
✓ 振る舞い:   order.cancel(reason)            ← 取消可否の判定も内部で守る
```

## よくある誤解・ハマりどころ
- **戦術だけDDD**：Entity/ValueObject/Repository を作っただけで「DDDやってます」になりがち。**境界づけられたコンテキストとユビキタス言語が無いと本質は得られない**。
- **リポジトリ＝DAOではない**：DAOはテーブル単位のCRUD。リポジトリは**集約単位**で、ドメインの語彙で会話する。
- **全部を集約にしようとする**：参照しかしない読み取りは集約を通さず**専用の読み取りモデル（CQRSのQuery側）** で素直にSQLを書くほうが速くて楽。
- **クリーンアーキテクチャ／ヘキサゴナルと混同**：DDDは**何を・どう分けてモデリングするか**の話。クリーンアーキは**依存の向きをどう制御するか**の話。**直交していて、よく一緒に使う**（→ [クリーンアーキテクチャ.md](./クリーンアーキテクチャ.md)）。

## 向いている場面 / 向かない場面
- **向いている**：業務ルールが複雑・頻繁に変わる、関係者が多く語彙のズレが事故になる、長期運用する基幹系。
- **向かない**：ほぼCRUD、業務ロジックが薄い管理画面、使い捨て・PoC、小規模で1人が全体を把握できる。**ここで重い戦術設計をやると純粋にコストだけ増える**。
