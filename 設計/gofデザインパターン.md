# デザインパターン（GoF・実務でよく使う10個）

## 一言で
GoF（Gang of Four）の23個のデザインパターンは、**オブジェクト指向設計で繰り返し現れる問題と解法に名前を付けた「カタログ」**（Gamma, Helm, Johnson, Vlissides の同名書、1994）。設計の語彙を共有し、「あれはStrategyで」の一言で意図が伝わるのが本質的な価値。

> パターンは**語彙であって目標ではない**。当てはめにいくと過剰設計になる。
> 「ここで使えそう」ではなく「この問題に既に名前が付いている」と**あとから気づく**順番が健全。先にパターンありきで設計すると、要らない抽象が増えるだけ。

---

## 23個の3分類だけ先に
GoFは目的別に3カテゴリへ分けられている。全部覚える必要はない。**「生成・構造・振る舞いの3つに分かれる」という地図だけ**持っておけば十分。

| 分類 | 何の問題を扱うか | 代表例（網羅ではない） |
|---|---|---|
| **生成（Creational）** | **オブジェクトの作り方**。new を直接書く代わりに生成を隠す・制御する。 | Factory Method, Abstract Factory, Singleton, Builder |
| **構造（Structural）** | **オブジェクトの組み合わせ方**。クラス／インスタンスをどう繋いで大きな構造にするか。 | Adapter, Decorator, Facade, Proxy, Composite |
| **振る舞い（Behavioral）** | **オブジェクト間の責務分担とやり取り**。アルゴリズムや通信をどう割り当てるか。 | Strategy, Observer, Template Method, Command, Iterator |

## よく使う10個

### 1. Strategy（振る舞いの差し替え）
- **何を解決する**：「やることは同じだが、やり方（アルゴリズム）が複数あって切り替えたい」。if/switch でアルゴリズムを分岐させると分岐が肥大化し、新手法の追加で既存コードを触る羽目になる。
- **ざっくり構造**：アルゴリズムを共通インターフェースの裏に隠し、利用側はインターフェースだけ見て、実装を**差し替える**。

```text
利用側 ──→ SortStrategy(interface)
                 ▲
        ┌────────┼────────┐
   QuickSort  MergeSort  BubbleSort   ← 実装を入れ替えるだけ。利用側は不変
```

- **実務での出どころ**：決済手段ごとの計算、割引ルールの切り替え、ソート／圧縮アルゴリズムの選択、リトライ戦略。OCP（拡張に開き修正に閉じる）の典型実装 → [solid.md](./solid.md)。

### 2. Factory Method / Abstract Factory（生成の隠蔽）
- **何を解決する**：`new ConcreteClass()` を利用側に直書きすると、具体クラスへの依存が散る。生成ロジックを一箇所に集め、**何を作るかの判断を隠す**。
- **ざっくり構造**：
  - **Factory Method**：生成を1メソッドに切り出し、サブクラスが「どの具体型を返すか」を決める。
  - **Abstract Factory**：**関連する一群のオブジェクト**（例：Windows用ボタン＋ウィンドウ）をまとめて作る工場。製品ファミリの一貫性を保つ。

```text
client ──→ createButton() : Button   ← 戻り値はインターフェース
                  └ 中で WinButton / MacButton を選ぶ（client は知らない）
```

- **実務での出どころ**：環境（dev/prod）ごとのクライアント生成、DBドライバ差し替え、テスト時のモック注入。DIコンテナはこの発想を仕組み化したもの。

### 3. Singleton（と、その濫用への注意）
- **何を解決する**：「インスタンスは1つだけ。どこからでも同じものにアクセスしたい」。設定・ロガー・コネクションプールなど。
- **ざっくり構造**：コンストラクタを隠し、唯一のインスタンスを内部で保持して返す。

```text
Config.getInstance() ──→ 常に同じ1個を返す（new させない）
```

- **実務での出どころ**：ロガー、アプリ設定、キャッシュ。
- **注意（重要）**：実質**グローバル変数**であり、**最も濫用されるパターン**。隠れた依存になりテストが書きにくくなる（差し替え不可・状態が引き継がれる）。**多くの場合はDIで「1個を共有する」だけで足り、Singletonパターンそのものは不要**。後述の誤解も参照。

### 4. Adapter（IFの食い違いを埋める）
- **何を解決する**：使いたい既存クラスの**インターフェースが、こちらの期待と合わない**。改造せずに繋ぎたい。
- **ざっくり構造**：相手のIFを、こちらが期待するIFに**変換するラッパ**を1枚挟む。

```text
client ──→ Target(期待IF) ←─ Adapter ──→ Adaptee(既存・別IF)
                                  └ 呼び出しを翻訳する
```

- **実務での出どころ**：外部SDK／レガシーAPIを自分のドメインIFに合わせる、新旧ライブラリの差し替え。**DDDの腐敗防止層（ACL）と発想が同じ**——相手の都合を翻訳して自分のモデルに漏らさない → [ddd.md](./ddd.md)。

### 5. Decorator（ラップして機能追加・ミドルウェア）
- **何を解決する**：既存オブジェクトに**機能を後から積み増したい**が、サブクラスで組み合わせを爆発させたくない（ログ付き＋圧縮付き＋暗号化付き…の全組み合わせをクラス化すると地獄）。
- **ざっくり構造**：同じインターフェースを持つラッパで対象を**包み、前後に処理を足す**。包んだものをさらに包める。

```text
write(data)
  Encrypt( Compress( Log( FileWriter ) ) )   ← 同IFのまま層状に積む
```

- **実務での出どころ**：HTTPミドルウェア（認証→ログ→本処理の連鎖）、ストリームの加工（バッファ／圧縮）、React の HOC。**継承より合成**の代表。

### 6. Observer（イベント通知・pub/sub）
- **何を解決する**：あるオブジェクトの状態変化を、**複数の関心側に通知**したい。通知元が受け手を直接知っていると密結合になる。
- **ざっくり構造**：Subject が Observer 群を保持し、変化時に**まとめて通知**。受け手は購読／解除するだけ。

```text
Subject ──notify()──→ ObserverA / ObserverB / ObserverC
（Subject は「誰が聞いているか」の具体型を知らなくてよい）
```

- **実務での出どころ**：UIのイベントリスナ、状態管理（Redux/RxJS）、ドメインイベントの配信、メッセージング（pub/sub）。**疎結合な通知**の基本形。

### 7. Template Method（骨格を固定し穴を埋めさせる）
- **何を解決する**：処理の**大枠（手順の順番）は共通**だが、一部のステップだけ実装を変えたい。
- **ざっくり構造**：基底クラスが手順の骨格を定義し、可変部分を**抽象メソッド（フック）としてサブクラスに埋めさせる**。

```text
parse() {           ← 骨格は固定（順番を握る）
  open()
  readBody()        ← ここだけサブクラスごとに実装
  close()
}
```

- **実務での出どころ**：フレームワークのライフサイクル（テストの setUp/tearDown、各種 `onXxx` フック）。**Strategy が「合成で差し替え」なら、Template Method は「継承で穴埋め」**——目的は近いが手段が逆。

### 8. Facade（複雑なサブシステムに窓口）
- **何を解決する**：複数のクラス／サブシステムを正しい順序で呼ぶのが煩雑。利用側に詳細を晒したくない。
- **ざっくり構造**：**ひとつの簡単な窓口（Facade）**を用意し、内部の複雑な呼び出しをまとめて隠す。

```text
client ──→ OrderFacade.placeOrder()
                 └ 在庫確認 → 課金 → 配送手配 を内部で順に呼ぶ
```

- **実務での出どころ**：アプリケーションサービス層／ユースケース層（複数リポジトリやドメインサービスを束ねる窓口）、外部連携の入口。**クリーンアーキの UseCase 層はしばしば Facade 的**に働く → [solid.md](./solid.md)。

### 9. Repository（GoF外だが実務頻出）
- **何を解決する**：永続化（DB）の詳細を業務ロジックから隠し、**コレクションのように扱える窓口**を提供する。
- **位置づけ**：**GoFには含まれない**（PoEAA／DDD由来）が、実務での登場頻度はGoF上位パターン並み。GoFと混ぜて語られがちなので一言だけ。
- **実務での出どころ**：集約の取得・保存、テスト時のメモリ実装差し替え。**詳しくは → [ddd.md](./ddd.md)**（DAOとの違い・集約単位での扱いを整理してある）。

### 10. Command（操作をオブジェクト化・Undo/キュー）
- **何を解決する**：「何をするか（操作）」を**データとして持ち回りたい**。実行を遅延させたい、履歴に積みたい、取り消したい、キューに溜めたい。
- **ざっくり構造**：操作を `execute()`（必要なら `undo()`）を持つオブジェクトに包む。発行側と実行側を分離する。

```text
Invoker ──→ Command.execute()     ← 操作を「もの」として保持
   履歴: [Cmd1, Cmd2, Cmd3] → undo() で逆順に巻き戻せる
```

- **実務での出どころ**：エディタの Undo/Redo、ジョブキュー／タスクキュー、トランザクション的な操作の記録、CQRS の Command 側。**操作を後で実行・記録・取り消す**用途すべて。

## よくある誤解・ハマりどころ
- **パターン病（当てはめにいく）**：「どこかで使えるはず」と先にパターンを探すと、要らない抽象・インターフェース・工場が増えるだけ。**問題が先、パターンは後**。気づいたら名前が付いていた、が正しい順序。
- **Singleton でグローバル状態地獄**：手軽さゆえ多用され、隠れた依存・テスト困難・状態の引き継ぎを生む。**「1個を共有したい」はDIで満たせる**ことがほとんど。Singletonパターン自体はアンチパターン扱いされることも多い。
- **言語機能で済むのにパターンを持ち出す**：**第一級関数があれば Strategy はただの関数（高階関数）渡しで済む**。Iterator は多くの言語で言語機能（`for...of`／ジェネレータ）に内蔵。GoFは「当時のC++/Javaに足りない機能を設計で補った」側面が強い。
- **GoFは静的OO前提で、現代言語だと不要なものもある**：関数型機能・mixin・DI・メタプログラミングが普及した今、**Strategy/Command の一部やSingletonは言語機能や標準ライブラリで代替**できる。パターンを「知識」として持ちつつ、**安易に手書き実装しない**判断が要る。
