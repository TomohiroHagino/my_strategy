# SOLID原則

## 一言で
**「変更が来たときに、壊れる範囲を最小にする」** ためのオブジェクト指向設計5原則の頭字語。Robert C. Martin（Uncle Bob）が既存の設計原則を5つに整理・命名したもの（2000年前後）。

> SRP / OCP / LSP / ISP / DIP の5つは、**バラバラの教義ではなく「変更に強くする」という1つの目的を別角度から言い換えたもの**。
> 突き詰めると全部「**変更の理由が違うものは混ぜるな・分けて、安定したものに依存しろ**」に収束する。個別の頭文字を暗記するより、この温度感を持っておくほうが効く。

---

## なぜか（何が嬉しいのか）
- ソフトの寿命のほとんどは「書く」より「直す・足す」。**変更コストを下げることが設計の主目的**で、SOLIDはそのための具体的な指針。
- 5つの原則は**結合度を下げ、凝集度を上げる**方向に効く。結果として「ある変更の影響が一箇所に閉じる」「テストで差し替えやすい」状態になる。
- ただし**原理主義化すると過剰分割・過剰抽象でコストが逆に増える**。各原則は「効く場面」を見極めて使う道具であって、達成すべきノルマではない（後述の罠を必ず読む）。

---

## SRP（単一責任の原則 / Single Responsibility Principle）
**一言**：1つのモジュールが**変更される理由は1つだけ**であるべき。「1機能」ではなく「**1つの変更理由＝1人のステークホルダー**」で割る。

```text
✗ 1クラスに複数の変更理由が同居:
   class Employee {
     calculatePay()     // 経理部門の都合で変わる
     saveToDatabase()   // DBA/インフラの都合で変わる
     generateReport()   // 人事部門の都合で変わる
   }
   → 給与計算の修正がレポート出力を巻き込んで壊す事故が起きる

✓ 変更理由ごとに分離:
   class PayCalculator { calculatePay() }       // 経理向け
   class EmployeeRepository { save() }          // インフラ向け
   class ReportGenerator { generate() }         // 人事向け
```

- **効く場面**：1つのクラスを複数の部署・関心事が触りに来るとき。変更がぶつかる箇所を物理的に分けたいとき。

---

## OCP（開放閉鎖の原則 / Open-Closed Principle）
**一言**：**拡張に対して開いて、修正に対して閉じて**いるべき。新しい振る舞いを足すとき、**既存コードを書き換えずに追加だけで済む**形にする。

```text
✗ 種類が増えるたびに既存のif/switchを書き換える:
   function area(shape) {
     if (shape.type === "circle") ...
     else if (shape.type === "square") ...
     // 図形を足すたびにこの関数を改造 = 修正に開いている
   }

✓ 抽象に対して開く（多態で追加するだけ）:
   interface Shape { area(): number }
   class Circle implements Shape { area() {...} }
   class Square implements Shape { area() {...} }
   // 新しい図形 = 新クラスを足すだけ。area()の呼び出し側は無改修
```

- **効く場面**：「種類が今後も増える」と分かっている箇所（支払い手段、通知チャネル、エクスポート形式など）。
- **注意**：増えると分かっていない箇所に先回りで抽象を入れるのは YAGNI 違反。**実際に2回目の分岐が来てから抽象化する**くらいでちょうどよい。

---

## LSP（リスコフの置換原則 / Liskov Substitution Principle）
**一言**：**派生型は、基底型のつもりで使っても破綻しない**こと。「is-a が言えるか」ではなく「**基底型の約束（事前条件・事後条件・不変条件）を守れるか**」で継承の可否を判断する。

```text
✗ 継承はできるが約束を破る（古典例）:
   class Rectangle { setWidth(w); setHeight(h) }
   class Square extends Rectangle { ... }   // 正方形は長方形だ、と思って継承
   // 「幅を変えても高さは変わらない」という長方形の約束を
   // Square が破る（幅を変えると高さも変わる）→ 置換すると壊れる

✗ 振る舞いで破る:
   class Bird { fly() }
   class Penguin extends Bird { fly() { throw "飛べない" } }
   // Bird として扱うコードが fly() を呼ぶと落ちる

✓ 約束を守れる関係だけを継承にする / 守れないなら別の抽象に分ける
   （飛べる/飛べないを別インターフェースに切る等）
```

- **効く場面**：継承やインターフェース実装を設計するとき。**「コンパイルは通るが実行時に契約を破る」継承を弾く**ための判断基準。
- 実感としては、**LSP違反は「親クラスのつもりで呼んだら例外/想定外の挙動」という形で表面化**する。継承よりコンポジションを選ぶ動機にもなる。

---

## ISP（インターフェース分離の原則 / Interface Segregation Principle）
**一言**：クライアントに**使わないメソッドへの依存を強制しない**。**太いインターフェースを、利用者ごとの細いインターフェースに割る**。

```text
✗ 何でも入った太いインターフェース:
   interface Worker { work(); eat(); sleep() }
   class Robot implements Worker {
     work() {...}
     eat() { throw "ロボットは食べない" }   // 使わないのに実装を強制される
     sleep() { throw "..." }
   }

✓ 役割ごとに割る:
   interface Workable { work() }
   interface Feedable  { eat() }
   class Robot implements Workable { work() {...} }     // 必要な契約だけ持つ
   class Human implements Workable, Feedable { ... }
```

- **効く場面**：1つの巨大インターフェース（または巨大な抽象クラス）を、種類の違う複数の実装が共有していて、実装側に「空実装」「未対応例外」が増えてきたとき。
- SRP を**インターフェースの粒度で言い換えたもの**と捉えると分かりやすい。

---

## DIP（依存性逆転の原則 / Dependency Inversion Principle）
**一言**：**上位（業務ルール）が下位（DB・外部I/O等の詳細）に依存してはならない。両者とも抽象に依存せよ**。そして**抽象は詳細に依存してはならない**。

```text
✗ 上位が詳細を直に掴む:
   class OrderService {
     repo = new MySqlOrderRepository()   // 業務ロジックがMySQL実装に直結
   }
   → DBを替える/テストでモックする、が困難

✓ 抽象を上位側に置き、実装を注入する（依存の向きを逆転）:
   interface OrderRepository { save(o) }          // 抽象は上位側が定義
   class OrderService { constructor(repo: OrderRepository) {...} }
   class MySqlOrderRepository implements OrderRepository {...}  // 詳細が抽象に従う
   // 実行時にDIで実装を差し込む
```

- **効く場面**：業務ロジックを DB・外部API・フレームワークから切り離して**単体テストしたい／差し替え可能にしたい**とき。
- これは**クリーンアーキテクチャ／ヘキサゴナルが「依存を内向きにする」ために使う中核の仕掛けそのもの**（→ [クリーンアーキテクチャ.md](./クリーンアーキテクチャ.md)）。
- DDDでリポジトリのインターフェースをドメイン側に置き、実装をインフラ側に置くのも DIP の応用（→ [ddd.md](./ddd.md)）。

## 早見表

| 原則 | 言っていること | 破ると起きること |
|---|---|---|
| **SRP**（単一責任） | 変更理由は1つに。違う関心事を混ぜない | 無関係な修正が相互に巻き込まれて壊れる。1クラスが肥大化 |
| **OCP**（開放閉鎖） | 拡張は追加で。既存を書き換えない | 種類が増えるたびに既存のif/switchを改造し、既存機能を壊す |
| **LSP**（置換） | 派生は基底の約束を守る | 親のつもりで呼ぶと実行時に例外/想定外。継承階層が信用できなくなる |
| **ISP**（IF分離） | 使わないメソッドを押し付けない | 空実装・未対応例外が増殖。インターフェース変更の影響が無関係な実装に波及 |
| **DIP**（依存逆転） | 上位も下位も抽象に依存。詳細に依存しない | 業務ロジックがDB/FWに直結し、差し替え不能・テスト不能になる |

## よくある誤解・ハマりどころ
- **SRPを「1クラス1メソッド」と誤解**：責任は「行数」や「メソッド数」ではなく**変更理由（ステークホルダー）**の単位。理由が同じなら複数メソッドが1クラスにいてよい。逆に1メソッドでも複数の理由を抱えれば違反。
- **原理主義化による過剰分割・過剰抽象**：OCPを真に受けて全ての分岐をinterface＋多態にすると、CRUD程度のコードに**ボイラープレートとインダイレクション（飛び先が追えない）が爆発**する。**「2回目の変更が来てから抽象化」**が現実的。
- **DIPとDI（依存性注入）の混同**：DIPは**依存の向きの設計原則**、DIは**実装を外から渡すテクニック**（コンストラクタ注入・DIコンテナ等）。**DIPを実現する手段の一つがDIだが、DIコンテナを使えばDIP達成、ではない**。抽象を上位側に置けていなければ向きは逆転していない。
- **LSPを「is-a が言えるか」だけで判断**：日本語で「正方形は長方形」と言えても、**契約（事前/事後条件・不変条件）を守れなければ継承してはいけない**。LSPは語感ではなく振る舞いの契約の話。
- **「SOLIDを全部守る」をゴールにする**：SOLIDは**変更コストを下げるための手段**。守ること自体が目的化すると、変更が来ない場所にまで設計コストを払う本末転倒になる。**変更が頻繁に来る／来ると分かっている箇所に集中投下**するのが正解。
- **関数型・軽量スクリプトに無理に適用**：SOLIDはOOP（クラス・継承・インターフェース）が前提の原則。関数中心の設計や使い捨てスクリプトには、そのままの形では当てはまらないことも多い。
