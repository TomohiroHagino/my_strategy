# レイヤードアーキテクチャ

## 一言で
**「責務の異なる関心事を、上から下へ積んだ層（レイヤ）に分け、各層は隣の層とだけ会話する」** という最も古典的で最も普及した構造化のやり方。エンタープライズ系の定番として教科書（PoEAA / Patterns of Enterprise Application Architecture など）で長年語られてきた。

> **最も普及している＝最も誤用されている**アーキテクチャでもある。「フォルダを4つ作って層っぽく並べた」だけで満足し、依存の向きや層の境界が崩れていることが非常に多い。
> 本質は**「上位の層だけが下位の層を知り、下位は上位を知らない」**という一方向の関係。これが守れていなければ層は名前だけになる。

---

## なぜ層に分けるのか
- **関心事の分離**：画面の都合（プレゼン）、処理の流れ（アプリ）、業務ルール（ドメイン）、技術的な永続化（インフラ）は変わる理由もスピードも違う。混ぜると一箇所の変更が全体に波及する。
- **理解しやすさ**：新しく入った人でも「これはどの層の話か」で当たりがつく。コードの置き場所に共通言語ができる。
- **差し替えやすさ**：DBやUIを別の技術に乗り換えるとき、影響範囲が（理想的には）その層に閉じる。
- **テストしやすさ**：ドメイン層だけ取り出して業務ルールを単体テストできる――ただしこれは**依存の向きが正しく制御できていれば**の話で、古典的レイヤードのままだと完全には実現しない（後述）。

---

## 古典的な層
最もよく使われる4層。上から下へ積み、**呼び出しは上から下へ**流れる。

| 層 | 責務 | 例 |
|---|---|---|
| **プレゼンテーション層** | 入出力。画面・APIの境界。リクエストを受け、レスポンスを返す。**業務ルールは持たない**。 | Controller / View / REST ハンドラ / 画面コンポーネント |
| **アプリケーション層** | ユースケースの**流れ（オーケストレーション）**。トランザクション境界、複数ドメイン処理の調整。**判断ロジックは薄く**。 | `OrderApplicationService.placeOrder()` / ユースケースクラス |
| **ドメイン層** | **業務ルールそのもの**。エンティティ・値オブジェクト・ドメインサービス。アプリの心臓。 | `Order.cancel()` / `Money` / 在庫引当の判定 |
| **インフラ層** | 技術的詳細。DB アクセス、外部 API、メッセージング、ファイル I/O。 | リポジトリ実装 / ORM / HTTP クライアント / メール送信 |

```text
┌─────────────────────────────────────────┐
│  プレゼンテーション層 (Presentation)     │  画面 / API・入出力
├─────────────────────────────────────────┤
│  アプリケーション層 (Application)        │  ユースケースの流れ・調整
├─────────────────────────────────────────┤
│  ドメイン層 (Domain)                     │  業務ルールの本体
├─────────────────────────────────────────┤
│  インフラ層 (Infrastructure)             │  DB・外部API・技術詳細
└─────────────────────────────────────────┘
        呼び出しは上 → 下 へ流れる
```

> 補足：層は厳密に「隣としか話せない（Closed Layer）」のか、「飛び越えてよい（Open Layer）」のかという設計選択がある。古典的には**Closed（飛び越え禁止）**が基本。緩めると楽だが、層の意味が薄れる。

## 依存の向き
- **伝統的なレイヤードでは、依存も呼び出しも「上 → 下」**。プレゼンがアプリを呼び、アプリがドメインを呼び、ドメインがインフラを呼ぶ。
- このとき**ドメイン層がインフラ層に依存している**。「業務ルールが、DBやORMという技術詳細に依存する」状態。
- ここが弱点。一番価値が高く寿命が長いドメインが、一番揮発的なインフラに引きずられる。DB を変えるとドメインのテストが壊れる、といった事故が起きる。

```text
[伝統的レイヤード]                 [クリーンアーキ/DIP での進化]

 Presentation                       Presentation
      │ 依存                             │
      ▼                                  ▼
 Application                        Application
      │                                  │      ┌ Repository(interface) を
      ▼                                  ▼      │ ドメイン側に置く
 Domain                             Domain ─────┘
      │ 依存（←ここが問題）              ▲
      ▼                                  │ implements（依存は内向き）
 Infrastructure  ← 一番外で揮発的    Infrastructure ← 一番外へ追い出す
```

- そこで **DIP（依存性逆転の原則）** を入れる。ドメイン側にリポジトリの**インターフェース**を置き、インフラ側がそれを**実装**する。すると依存の矢印が逆転し、**インフラが一番外側（最も内側のドメインに依存する側）**へ追い出される。
- これがまさにクリーンアーキテクチャ／ヘキサゴナル／オニオンが行った進化そのもの。**「層を積む」発想は同じで、依存の向きだけを内向きに直した**のがクリーンアーキだと捉えると橋がかかる。→ [クリーンアーキテクチャ.md](./クリーンアーキテクチャ.md)
- ドメインモデルそのものの作り方（集約・値オブジェクト・ユビキタス言語）は別の関心事で、こちらは [ddd.md](./ddd.md) を参照。レイヤード／クリーンアーキは**置き場所と依存の話**、DDD は**中身のモデリングの話**で直交する。

## MVC / 3層との関係
似た言葉が混ざりやすいので整理する。**レイヤードと同じ粒度の話ではない**点が要点。

| 概念 | 何の話か | レイヤードとの関係 |
|---|---|---|
| **レイヤードアーキテクチャ** | アプリ全体を責務で論理的な層に分ける | 本体。下記2つを包含・整理する枠 |
| **MVC** | **プレゼンテーション層の内部**の構造（Model / View / Controller）。表示と入力処理の整理。 | MVC はレイヤードの**プレゼン層の中の話**。MVC の "Model" がドメイン層を直接指すとは限らない（薄い表示用モデルのこともある） |
| **3層アーキテクチャ（3-tier）** | プレゼン / ロジック / データの**物理的な配置（tier）**寄り。Webサーバ・APサーバ・DBサーバのように**プロセス／マシン境界**を意識した分割。 | "tier" は配置単位、"layer" は論理単位。**論理層（layer）≠ 物理層（tier）**。3層は3つの物理階層に乗せた一形態 |

- ざっくり：**layer = 論理（コードの責務分け）／ tier = 物理（プロセス・サーバの分け）**。日本語だとどちらも「層」になって混ざる。
- MVC は「画面まわりをどう整理するか」なので、レイヤードの一部に内包される下位の関心事。MVC を採用していても、その奥にアプリ層・ドメイン層・インフラ層を別に持つのが普通。

## よくある誤解・ハマりどころ
- **横断的関心事（cross-cutting concerns）の漏れ**：ロギング・認可・トランザクション・キャッシュは特定の層に収まらず全層を貫く。素直に層分割だけしていると各層に散らばってコピペが増える。AOP・ミドルウェア・デコレータなどで**横断的に差し込む**設計を別途用意する必要がある。
- **層をまたぐ素通し（pass-through / lasagna anti-pattern）**：アプリ層が何の判断もせず、ただプレゼンの呼び出しをインフラへ右から左へ受け流すだけになる。**「層は通るが何もしない」**メソッドが量産され、ボイラープレートだけ増えて価値が出ない。層を増やすなら各層に存在理由（責務）を持たせる。
- **ドメイン層がインフラを直接 import して層が無意味化（＝貧血化）**：ドメインのクラスが ORM のエンティティや DB クライアントを直接掴むと、依存の向きが崩れ、ドメインだけのテストができなくなる。業務ルールが薄まり**貧血ドメインモデル（Anemic Domain Model）**に堕ちやすい。DIP でインターフェースを内側に置くのが処方箋。
- **層の数を増やしすぎ**：「念のため」でアダプタ層・DTO 変換層・マッパー層…と増やすと、1つの機能追加で**全層を順に編集する苦行**になる。層は多いほど偉いのではない。**必要な責務の数だけ**にする。
- **層を分ければテストしやすい、という誤解**：分割しても依存が上→下のままなら、ドメインのテストにインフラ（DB）が必要なまま。テスト容易性は層の数ではなく**依存の向き**で決まる。

## 向いている場面 / 向かない場面
- **向いている**：一般的な業務アプリ・Web アプリ全般。チームに馴染みがあり学習コストが低い。フレームワークの標準構成（Controller / Service / Repository）にそのまま乗る。まず最初に選ぶ"無難で堅い"デフォルト。
- **向かない**：
  - 超小規模・PoC・使い捨て：4層フルは過剰。フラットに書いたほうが速い。
  - 業務ルールが複雑で寿命が長く、DB/UI を将来差し替えたい：古典的レイヤードのままだと依存が下向きで詰まる。**クリーンアーキ／DIP へ進化させる**のが定石（→ [クリーンアーキテクチャ.md](./クリーンアーキテクチャ.md)）。
  - 高スループットな読み取りと複雑な書き込みが混在：層を一本道で通すより、読み書きを分ける **CQRS** が効くことがある（→ [cqrsとイベントソーシング.md](./cqrsとイベントソーシング.md)）。
