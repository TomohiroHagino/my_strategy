# デザインパターン（GoF 23個・全部入り）

## 一言で
GoF（Gang of Four）の23個のデザインパターンは、**オブジェクト指向設計で繰り返し現れる問題と解法に名前を付けた「カタログ」**（Gamma, Helm, Johnson, Vlissides の同名書、1994）。設計の語彙を共有し、「あれはStrategyで」の一言で意図が伝わるのが本質的な価値。

> パターンは**語彙であって目標ではない**。当てはめにいくと過剰設計になる。
> 「ここで使えそう」ではなく「この問題に既に名前が付いている」と**あとから気づく**順番が健全。先にパターンありきで設計すると、要らない抽象が増えるだけ。

---

## 3分類の地図
GoFは目的別に3カテゴリ・23個へ分けられている。まずこの地図だけ持っておけばよい。

| 分類 | 個数 | 何の問題を扱うか |
|---|---|---|
| **生成（Creational）** | 5 | **オブジェクトの作り方**。`new` を直接書く代わりに生成を隠す・制御する。 |
| **構造（Structural）** | 7 | **オブジェクトの組み合わせ方**。クラス／インスタンスをどう繋いで大きな構造にするか。 |
| **振る舞い（Behavioral）** | 11 | **オブジェクト間の責務分担とやり取り**。アルゴリズムや通信をどう割り当てるか。 |

### 凡例（実務頻度・自分の体感）
- **★★★ 頻出**：名前を知らなくても自然に書いている。必修。
- **★★ 時々**：状況がハマれば使う。知っておくと強い。
- **★ まれ／知識として**：出番は限られる。「そういうのがある」で十分なことが多い。

## 生成パターン（Creational・5個）

### Factory Method ★★★（生成の隠蔽）
- **何を解決する**：`new ConcreteClass()` を利用側に直書きすると、具体クラスへの依存が散る。生成を1メソッドに切り出し、サブクラスが「どの具体型を返すか」を決める。
- **ざっくり構造**：

```text
client ──→ createButton() : Button   ← 戻り値はインターフェース
                  └ 中で WinButton / MacButton を選ぶ（client は知らない）
```

- **実務での出どころ**：環境（dev/prod）ごとのクライアント生成、DBドライバ差し替え、テスト時のモック注入。DIコンテナはこの発想を仕組み化したもの。OCP/DIPと直結 → [solid.md](./solid.md)。

### Abstract Factory ★★（製品ファミリをまとめて作る）
- **何を解決する**：**関連する一群のオブジェクト**（例：Windows用ボタン＋ウィンドウ＋スクロールバー）を、ばらばらでなく**一貫したセットで**作りたい。
- **ざっくり構造**：`UIFactory.createButton()` / `.createWindow()` を持つ工場を、OS別に実装。利用側は工場1個を受け取れば、混ざらないファミリが揃う。
- **実務での出どころ**：クロスプラットフォームUI、テーマ切り替え、接続先（本番/モック）ごとの一式生成。Factory Method を束ねたものと考えるとよい。

### Builder ★★★（複雑なオブジェクトを段階的に組む）
- **何を解決する**：引数が多い・任意項目が多いオブジェクトを、巨大コンストラクタ（テレスコーピング）で作ると読めない。生成手順を**メソッドチェーンで段階的に**組み立て、最後に確定する。
- **ざっくり構造**：

```text
Pizza.builder()
  .size("L").cheese(true).topping("mushroom")
  .build()                 ← ここで不変条件を検証し、完成品を1個返す
```

- **実務での出どころ**：HTTPリクエスト構築、SQL/クエリビルダ、テストデータ生成（Object Mother）、設定オブジェクト。**不変オブジェクトを安全に作る**定番 → 値オブジェクトの生成は [ddd.md](./ddd.md) とも相性が良い。

### Prototype ★（複製して作る）
- **何を解決する**：生成コストが高い／設定が複雑なオブジェクトを、ゼロから作らず**既存インスタンスをコピー（clone）して**作る。
- **ざっくり構造**：雛形オブジェクトを持っておき、`clone()` で複製してから差分だけ変える。
- **実務での出どころ**：ゲームのエンティティ量産、デフォルト設定からの派生、深いコピーが要るドキュメント複製。**現代言語では `copyWith`／スプレッド／レコードのコピーで代替**されることが多く、明示的なPrototypeの出番は少なめ。

### Singleton ★★（唯一のインスタンス・濫用注意）
- **何を解決する**：「インスタンスは1つだけ。どこからでも同じものにアクセスしたい」。設定・ロガー・コネクションプールなど。
- **ざっくり構造**：

```text
Config.getInstance() ──→ 常に同じ1個を返す（new させない）
```

- **注意（重要）**：実質**グローバル変数**であり、**最も濫用されるパターン**。隠れた依存になりテストが書きにくくなる（差し替え不可・状態が引き継がれる）。**多くの場合はDIで「1個を共有する」だけで足り、Singletonパターンそのものは不要**。後述の誤解も参照。

## 構造パターン（Structural・7個）

### Adapter ★★★（IFの食い違いを埋める）
- **何を解決する**：使いたい既存クラスの**インターフェースが、こちらの期待と合わない**。改造せずに繋ぎたい。
- **ざっくり構造**：

```text
client ──→ Target(期待IF) ←─ Adapter ──→ Adaptee(既存・別IF)
                                  └ 呼び出しを翻訳する
```

- **実務での出どころ**：外部SDK／レガシーAPIを自分のドメインIFに合わせる、新旧ライブラリの差し替え。**DDDの腐敗防止層（ACL）と発想が同じ**——相手の都合を翻訳して自分のモデルに漏らさない → [ddd.md](./ddd.md)。

### Bridge ★（抽象と実装を独立に変える）
- **何を解決する**：「機能の軸」と「実装の軸」が**両方とも増える**とき、継承で組み合わせるとクラスが掛け算で爆発する（円×赤、円×青、四角×赤…）。2軸を**別の階層に分け、合成で繋ぐ**。
- **ざっくり構造**：`Shape`（抽象側）が `Renderer`（実装側）を**持つ**。形と描画方式を独立に足せる。
- **実務での出どころ**：図形×描画API、通知（メール/SMS/Push）×送信チャネル、永続化対象×ストレージ。**継承の爆発を合成で抑える**設計。Strategy と構造は似るが、Bridge は「抽象と実装の分離」が目的。

### Composite ★★（木構造を一様に扱う）
- **何を解決する**：「個」と「集まり」を**同じインターフェースで扱いたい**。フォルダの中にファイルとフォルダが混在しても、再帰的に同じ操作（サイズ計算など）をかけたい。
- **ざっくり構造**：

```text
Component(共通IF)
 ├─ Leaf（ファイル）          ← 単体
 └─ Composite（フォルダ）      ← 子に Component を持つ（再帰）
        size() = 子の size() の合計
```

- **実務での出どころ**：ファイルツリー、UIコンポーネントツリー（DOM/React）、メニュー階層、組織図。**ツリー＝Composite**と覚えてよい。

### Decorator ★★★（ラップして機能追加・ミドルウェア）
- **何を解決する**：既存オブジェクトに**機能を後から積み増したい**が、サブクラスで組み合わせを爆発させたくない（ログ付き＋圧縮付き＋暗号化付き…の全組み合わせをクラス化すると地獄）。
- **ざっくり構造**：

```text
write(data)
  Encrypt( Compress( Log( FileWriter ) ) )   ← 同IFのまま層状に積む
```

- **実務での出どころ**：HTTPミドルウェア（認証→ログ→本処理の連鎖）、ストリームの加工（バッファ／圧縮）、React の HOC。**継承より合成**の代表。

### Facade ★★★（複雑なサブシステムに窓口）
- **何を解決する**：複数のクラス／サブシステムを正しい順序で呼ぶのが煩雑。利用側に詳細を晒したくない。
- **ざっくり構造**：

```text
client ──→ OrderFacade.placeOrder()
                 └ 在庫確認 → 課金 → 配送手配 を内部で順に呼ぶ
```

- **実務での出どころ**：アプリケーションサービス層／ユースケース層（複数リポジトリやドメインサービスを束ねる窓口）、外部連携の入口。**クリーンアーキの UseCase 層はしばしば Facade 的**に働く → [クリーンアーキテクチャ.md](./クリーンアーキテクチャ.md)。

### Flyweight ★（大量の小オブジェクトを共有して軽くする）
- **何を解決する**：同じ内容のオブジェクトを大量に作るとメモリを食う。**変わらない部分（intrinsic）を共有**し、変わる部分（extrinsic）だけ外から渡す。
- **ざっくり構造**：文字の字形（フォントグリフ）は1個を共有し、位置・色だけ呼び出し側が持つ。
- **実務での出どころ**：テキストレンダリングのグリフ、ゲームのパーティクル／タイル、大量ノードのアイコン。**省メモリ最適化が要るときだけ**。早すぎる最適化に注意。

### Proxy ★★（本物の代理・前後にフックを挟む）
- **何を解決する**：本物のオブジェクトへのアクセスを**代理オブジェクト経由**にし、生成の遅延・アクセス制御・キャッシュ・遠隔呼び出しを差し込む。
- **ざっくり構造**：

```text
client ──→ Proxy（同IF）──→ RealSubject
                 └ 認可チェック / 遅延ロード / 結果キャッシュ を挟む
```

- **実務での出どころ**：遅延初期化（lazy）、ORMの遅延ロード、APIクライアントのキャッシュ、RPCスタブ、アクセス制御。Decorator と構造は似るが、**Decorator は機能追加、Proxy はアクセス制御・代理**が目的。

## 振る舞いパターン（Behavioral・11個）

### Chain of Responsibility ★★（処理を数珠つなぎで回す）
- **何を解決する**：1つの要求を、**処理できるハンドラが見つかるまで順に渡す**。送り手は誰が処理するかを知らなくてよい。
- **ざっくり構造**：

```text
request ──→ Auth ──→ RateLimit ──→ Validate ──→ Handler
            各段は「自分で処理 or 次へ渡す」を選ぶ
```

- **実務での出どころ**：HTTPミドルウェアチェーン、イベントのバブリング、ログレベル別ハンドラ、承認フロー。**Decorator と並んでミドルウェアの基礎**。

### Command ★★（操作をオブジェクト化・Undo/キュー）
- **何を解決する**：「何をするか（操作）」を**データとして持ち回りたい**。実行を遅延させたい、履歴に積みたい、取り消したい、キューに溜めたい。
- **ざっくり構造**：

```text
Invoker ──→ Command.execute()     ← 操作を「もの」として保持
   履歴: [Cmd1, Cmd2, Cmd3] → undo() で逆順に巻き戻せる
```

- **実務での出どころ**：エディタの Undo/Redo、ジョブキュー／タスクキュー、トランザクション的な操作の記録、CQRS の Command 側 → [cqrsとイベントソーシング.md](./cqrsとイベントソーシング.md)。

### Iterator ★★★（中身を順に辿る・多くは言語機能）
- **何を解決する**：コレクションの**内部構造を晒さずに要素を順番に走査**したい。
- **ざっくり構造**：`hasNext()` / `next()` を持つ反復子を返す。利用側は構造（配列か木か）を知らずに回せる。
- **実務での出どころ**：ほぼ全言語で**言語機能に内蔵**（`for...of`、`for ... range`、ジェネレータ／`yield`、`Iterable`）。**自前でIteratorクラスを書く場面は少ない**——カスタムコレクションや遅延ストリームを作るときくらい。

### Mediator ★（オブジェクト間のやり取りを仲介役に集約）
- **何を解決する**：多数のオブジェクトが互いを直接参照し合うと**網の目状の密結合**になる。やり取りを**仲介役（Mediator）1か所に集める**。
- **ざっくり構造**：各部品は Mediator にだけ話す。Mediator が「Aが変わったらBとCを更新」を差配する。
- **実務での出どころ**：複雑なフォーム（項目間の連動）、UIコンポーネント間の調整、チャットルーム。やり過ぎると Mediator が神クラス化するので注意。

### Memento ★（状態スナップショットを外に保存して復元）
- **何を解決する**：オブジェクトの**内部状態を、カプセル化を壊さずに保存・復元**したい（Undoのための状態退避）。
- **ざっくり構造**：対象が自分の状態を不透明な「メメント」として吐き出し、後でそれを食わせて戻す。中身は外から覗けない。
- **実務での出どころ**：Undo/Redo の状態側（操作側が Command）、チェックポイント、ゲームのセーブ。イベントソーシングの「状態の復元」とも発想が近い → [cqrsとイベントソーシング.md](./cqrsとイベントソーシング.md)。

### Observer ★★★（イベント通知・pub/sub）
- **何を解決する**：あるオブジェクトの状態変化を、**複数の関心側に通知**したい。通知元が受け手を直接知っていると密結合になる。
- **ざっくり構造**：

```text
Subject ──notify()──→ ObserverA / ObserverB / ObserverC
（Subject は「誰が聞いているか」の具体型を知らなくてよい）
```

- **実務での出どころ**：UIのイベントリスナ、状態管理（Redux/RxJS）、ドメインイベントの配信、メッセージング（pub/sub）。**疎結合な通知**の基本形。

### State ★★（状態ごとに振る舞いを差し替える）
- **何を解決する**：オブジェクトの振る舞いが**内部状態で大きく変わる**とき、`if (state == ...)` の分岐が全メソッドに散る。**状態を別オブジェクトにし、状態自身に振る舞いを持たせる**。
- **ざっくり構造**：

```text
Order の状態: Draft / Paid / Shipped / Cancelled
 order.cancel() の挙動は「今の状態オブジェクト」に委譲
 （Draftなら取消可、Shippedなら例外…を状態側が知っている）
```

- **実務での出どころ**：注文・予約・ワークフローのステートマシン、UIのモード、接続状態。**Strategy と構造は同じ（委譲）だが、State は状態が自分で次の状態に遷移する**点が違う。

### Strategy ★★★（振る舞いの差し替え）
- **何を解決する**：「やることは同じだが、やり方（アルゴリズム）が複数あって切り替えたい」。if/switch で分岐させると肥大化し、新手法の追加で既存コードを触る羽目になる。
- **ざっくり構造**：

```text
利用側 ──→ SortStrategy(interface)
                 ▲
        ┌────────┼────────┐
   QuickSort  MergeSort  BubbleSort   ← 実装を入れ替えるだけ。利用側は不変
```

- **実務での出どころ**：決済手段ごとの計算、割引ルールの切り替え、ソート／圧縮アルゴリズムの選択、リトライ戦略。OCP の典型実装 → [solid.md](./solid.md)。**第一級関数がある言語ではただの関数渡しで済む**（後述の誤解）。

### Template Method ★★（骨格を固定し穴を埋めさせる）
- **何を解決する**：処理の**大枠（手順の順番）は共通**だが、一部のステップだけ実装を変えたい。
- **ざっくり構造**：

```text
parse() {           ← 骨格は固定（順番を握る）
  open()
  readBody()        ← ここだけサブクラスごとに実装
  close()
}
```

- **実務での出どころ**：フレームワークのライフサイクル（テストの setUp/tearDown、各種 `onXxx` フック）。**Strategy が「合成で差し替え」なら、Template Method は「継承で穴埋め」**——目的は近いが手段が逆。

### Visitor ★（構造を変えずに操作を外から足す）
- **何を解決する**：要素の型が固定で**操作だけ増える**とき、各要素クラスにメソッドを足し続けるのは辛い。**操作を Visitor 側に外出し**し、要素を巡って処理する。
- **ざっくり構造**：要素が `accept(visitor)` を持ち、visitor が型ごとの処理（`visitX` / `visitY`）を実装。新しい操作＝新しい Visitor を足すだけ。
- **実務での出どころ**：AST の走査（コンパイラ・linter・コード変換）、ファイル木の集計、シリアライズ。**要素型が安定し操作が増える**ときに強い（逆に要素型が増えると全Visitor修正で辛い＝表現問題）。

### Interpreter ★（簡易言語の文法を木で評価）
- **何を解決する**：独自の**小さな言語・式**を、文法規則を表すクラス群に対応させて評価する。
- **ざっくり構造**：文法の各規則をクラスにし、構文木を再帰的に `interpret()` する。
- **実務での出どころ**：簡単なルールエンジン、検索クエリ、電卓式、設定DSL。**本格的な言語処理では普通はパーサジェネレータ／専用ライブラリを使う**ので、手書きInterpreterの出番はごく小規模なDSLに限られる。

---

## GoF外だが実務頻出：Repository ★★★
- **位置づけ**：**GoFには含まれない**（PoEAA／DDD由来）が、登場頻度はGoF上位パターン並み。GoFと混ぜて語られがちなので併記。
- **何を解決する**：永続化（DB）の詳細を業務ロジックから隠し、**コレクションのように扱える窓口**を提供する。
- **実務での出どころ**：集約の取得・保存、テスト時のメモリ実装差し替え。**詳しくは → [ddd.md](./ddd.md)**（DAOとの違い・集約単位での扱いを整理してある）。

| 振る舞い | State | ★★ | 状態ごとに振る舞いを差し替え |

## よくある誤解・ハマりどころ
- **パターン病（当てはめにいく）**：「どこかで使えるはず」と先にパターンを探すと、要らない抽象・インターフェース・工場が増えるだけ。**問題が先、パターンは後**。気づいたら名前が付いていた、が正しい順序。
- **Singleton でグローバル状態地獄**：手軽さゆえ多用され、隠れた依存・テスト困難・状態の引き継ぎを生む。**「1個を共有したい」はDIで満たせる**ことがほとんど。Singletonパターン自体はアンチパターン扱いされることも多い。
- **言語機能で済むのにパターンを持ち出す**：**第一級関数があれば Strategy はただの関数（高階関数）渡しで済む**。Iterator は多くの言語で言語機能（`for...of`／ジェネレータ）に内蔵。GoFは「当時のC++/Javaに足りない機能を設計で補った」側面が強い。
- **似たパターンの取り違え**：Strategy（合成で差し替え）/ State（状態が自分で遷移）/ Template Method（継承で穴埋め）は構造が近い。Decorator（機能追加）/ Proxy（アクセス制御）/ Adapter（IF変換）も同じラップでも目的が違う。**構造ではなく「目的」で選ぶ**。
- **GoFは静的OO前提で、現代言語だと不要なものもある**：関数型機能・mixin・DI・メタプログラミングが普及した今、**Strategy/Command/Iterator/Prototype の一部やSingletonは言語機能や標準ライブラリで代替**できる。パターンを「知識」として持ちつつ、**安易に手書き実装しない**判断が要る。
