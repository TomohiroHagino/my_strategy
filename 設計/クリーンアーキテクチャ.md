# クリーンアーキテクチャ

## 一言で
**「依存の矢印を、外側（DB・UI・フレームワーク）から内側（業務ルール）へ一方通行で向ける」** ための設計指針。Robert C. Martin（Uncle Bob）が、ヘキサゴナル / オニオン / DCI など先行する同系統の考えを**同心円1枚に整理し直した**もの（2012）。

> 核心は1つだけ：**依存性のルール（The Dependency Rule）＝ ソースコードの依存は必ず内向き。内側は外側を一切知らない。**
> 「層を4つに分ける」こと自体が本質ではない。**業務ルールをDB・FW・UIから切り離して守る**のが目的。

---

## なぜか（何を守りたいのか）
- フレームワークやDBは**詳細**であり、数年で乗り換わる。業務ルール（一番価値があり寿命が長い）が、詳細に依存していると**詳細の都合で壊れる**。
- だから矢印を逆にする：**業務ルールを中心に置き、DBやWebは「あとから挿す差し替え可能なプラグイン」**にする。
- 結果として、**DBやUIなしで業務ロジックを単体テストできる**（一番大きな実利）。

---

## 同心円（内→外）

```
        ┌─────────────────────────────────────────┐
        │  Frameworks & Drivers                    │  ← Web/DB/UI/外部API（詳細・最も揮発的）
        │   ┌─────────────────────────────────┐    │
        │   │ Interface Adapters              │    │  ← Controller / Presenter / Repository実装
        │   │   ┌─────────────────────────┐   │    │
        │   │   │ Use Cases (Application) │   │    │  ← アプリ固有の操作（「注文する」等の流れ）
        │   │   │   ┌─────────────────┐   │   │    │
        │   │   │   │   Entities      │   │   │    │  ← 企業全体の業務ルール（最も安定）
        │   │   │   └─────────────────┘   │   │    │
        │   │   └─────────────────────────┘   │    │
        │   └─────────────────────────────────┘    │
        └─────────────────────────────────────────┘
                 依存の矢印は「→ 内向き」のみ
```

| 層 | 持つもの | 変わりやすさ |
|---|---|---|
| **Entities（エンティティ）** | 最も汎用な業務ルール・データ。アプリをまたいで再利用しうる。 | 最も安定（変わりにくい） |
| **Use Cases（ユースケース/アプリケーション）** | このアプリ固有の操作の流れ（オーケストレーション）。エンティティを呼ぶ。 | アプリ要件で変わる |
| **Interface Adapters** | 内↔外のデータ変換。Controller・Presenter・Gateway・**Repositoryの実装**。 | 接続先で変わる |
| **Frameworks & Drivers** | Web FW・DB・UI・デバイス・外部サービス。 | 最も揮発的 |

---

## 依存を逆転させる仕掛け：DIP（依存性逆転の原則）
内側が外側（DB等）を呼びたいが、矢印は内向きにしたい。この矛盾を解くのが**依存性逆転**：

- **インターフェース（境界）を内側に置く**。実装を外側に置く。
- 内側は自分が定義したインターフェースだけを見る。実行時にDIで外側の実装を差し込む。

```text
✗ 直接依存:   UseCase ──→ MySQLOrderRepository      （内が外を知る＝NG）

✓ 依存性逆転:
   [内側] UseCase ──→ OrderRepository(interface)     ← 境界は内側に置く
                              ▲
                              │ implements（矢印は内向き）
   [外側] MySQLOrderRepository ┘                      ← 実装は外側。DIで注入
```

これにより、**UseCaseのテストではメモリ実装のRepositoryを差し込むだけ**で、DB不要でテストできる。

---

## 制御フローと依存フローは「逆」になる（最初の罠）
- **実行時の流れ**：Web → Controller → UseCase → Repository実装 → DB（外から内へ入って外へ出る）
- **ソースコードの依存**：すべて内向き（UseCaseはControllerもDBも知らない）
- ここが直感に反する。**「呼ぶ＝依存する」ではない**。呼ぶ側が、呼ばれる側の**インターフェース（内側にある）に依存**しているだけ。

---

## DDD との関係（混同しやすい）
- **直交していて、相補的**。よく一緒に使う。
  - **DDD** … *何を*・*どう分けてモデリングするか*（境界づけられたコンテキスト、集約、ユビキタス言語）。
  - **クリーンアーキ** … *依存の向きをどう制御するか*（同心円、DIP）。
- 典型的な合体形：**エンティティ層にDDDのドメインモデル（集約・値オブジェクト）を置き、リポジトリのインターフェースを内側、実装を外側に置く**。→ [ddd.md](./ddd.md)

## 近縁アーキテクチャ（同じ思想の別表現）
| 名前 | 提唱 | 言い換え |
|---|---|---|
| **ヘキサゴナル（Ports & Adapters）** | Cockburn | 内側に「ポート（IF）」、外側に「アダプタ（実装）」。クリーンアーキの境界とほぼ同義 |
| **オニオン** | Palermo | 玉ねぎ状の層。中心にドメイン、外にインフラ。依存は内向き |
| **クリーン** | Martin | 上記を同心円1枚に統合・整理したもの |

**3つは本質的に同じこと**を言っている（依存を内向きに、業務を中心に）。違いは語彙と図の描き方くらい。

## よくある誤解・ハマりどころ
- **層を分ければクリーン、ではない**：レイヤを4つ作っても、矢印が外向き（UseCaseが`import`でDB具体クラスを掴んでいる）なら**全く意味がない**。守るべきは依存の向き1点。
- **小さいアプリで全部やる**：境界・DTO・Mapper・Presenterを律儀に全部作ると、CRUDに対して**ボイラープレートが爆発**する。規模と複雑さに応じて段階導入する。
- **層をまたぐたびに変換オブジェクトが増える**：Entity↔DTO↔ViewModel の変換が冗長になりがち。**価値（テスト容易性・差し替え可能性）が要らない層では潔く省く**判断も要る。
- **「FWに依存しない」を原理主義化**：ORMやWeb FWの恩恵を全部捨てて手書きすると本末転倒。**業務ルールの核だけFWから守れれば十分**なことが多い。

---

## 向いている場面 / 向かない場面
- **向いている**：業務ルールが複雑で寿命が長い、DBや外部サービスを将来差し替えうる、ロジックを厚く単体テストしたい、チームが大きい。
- **向かない**：ほぼCRUD、PoC・使い捨て、ロジックが薄く「FWのレールに乗るのが一番速い」ケース。**ここで全層導入するとコストだけ増える**。
