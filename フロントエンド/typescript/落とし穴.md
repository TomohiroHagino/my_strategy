# TypeScript 特有の現象と対策（落とし穴カタログ）

> **TypeScript だからこそ起きる**現象を「現象 / なぜ起きる / 対策」で。
> JS共通の罠（巻き上げ・`this`・クロージャ・`==`・浮動小数・コールバック地獄・await漏れ等）は土台側 → **[../javascript/落とし穴.md](../javascript/落とし穴.md)**。ここはTSの型システム由来のものに絞る。文法解説は [解説/typescript5.md](./解説/typescript5.md)。

---

## 1. 型は実行時に消える（型≠検証）
**現象**：コンパイルは通るのに、APIレスポンスやフォーム入力が型と違って実行時に壊れる。
**なぜ**：TSの型は**トランスパイル時に削除**される。実行時には素のJSで、外部データの形は誰も保証しない。
```ts
const user = await res.json() as User; // ← 嘘でも通る。実体は any 同然
console.log(user.name.toUpperCase());  // 実際は name が無くて実行時例外
```
**対策**：**システム境界（API/フォーム/環境変数/ファイル）では実行時バリデーション**を挟む。`zod`/`valibot` でスキーマ検証し、検証済みの値から型を導く。型注釈や `as` を「検証の代わり」にしない。
```ts
import { z } from "zod";
const User = z.object({ name: z.string() });
const user = User.parse(await res.json()); // 検証＋型が同時に手に入る
```

## 2. `as`（型アサーション）は実行時チェックではない
**現象**：`value as Foo` でエラーは消えるが、実体が `Foo` でなく後で壊れる。
**なぜ**：`as` は「コンパイラよ、私がFooだと保証する」という**宣言**にすぎず、変換も検証もしない。
**対策**：`as` は最終手段。外部入力には使わず、**型ガード関数**（`x is Foo`）か zod 検証で絞る。`as any`→`as Foo` の二段キャスト（無理やり通す）は特に危険。`as const` は別物（リテラル固定で有用）なので混同しない。

## 3. `any` の伝染
**現象**：1か所 `any` を入れると、そこを経由する値の型安全が連鎖的に崩れる（補完もチェックも効かない）。
**なぜ**：`any` は「型チェックを無効化する」型。代入・演算で周囲に広がる。
**対策**：**`unknown` ＋ 絞り込み**を使う（`unknown` は使う前に必ず型を絞らないと触れない）。`tsconfig` で `noImplicitAny` を有効化。やむを得ず `any` を置くなら範囲を最小化しコメントで理由を残す。

## 4. 構造的型付けと過剰プロパティ
**現象**：余計なプロパティを持つオブジェクトが通る／逆にオブジェクトリテラル直接代入だけ「過剰プロパティ」エラーになり一貫しない。
**なぜ**：TSは**形が合えば同じ型**（名前でなく構造）。ただし**リテラルを直接代入する時だけ**過剰プロパティチェックが働く（変数経由だと素通り）。
```ts
type P = { a: number };
const obj = { a: 1, b: 2 };
const p1: P = obj;            // OK（変数経由は素通り）
const p2: P = { a: 1, b: 2 }; // エラー（リテラル直接は過剰プロパティ検出）
```
**対策**：意図しない余剰を防ぐには境界で zod 等を使う。`exactOptionalPropertyTypes` 等の厳格オプションも検討。「名前が同じなら別物」を期待しない（公称型が要るならブランド型 `type UserId = string & { _brand: 'UserId' }`）。

## 5. ナローイング（絞り込み）が解ける
**現象**：`if (x !== null)` で絞ったのに、コールバック/別関数/再代入の後で `x` が再びユニオンに戻り `null` 扱いになる。
**なぜ**：絞り込みは**制御フロー解析**に依存する。クロージャに入れたり後で再代入されると、コンパイラは値が変わった可能性を考え絞りを破棄する。
```ts
function f(x: string | null) {
  if (x === null) return;
  arr.forEach(() => x.toUpperCase()); // クロージャ内で narrowing が解け得る
}
```
**対策**：絞った値を**`const` の別変数に退避**してから使う（再代入されない＝絞りが維持される）。または関数の冒頭で早期 return／型ガードを関数化。

## 6. `enum` の実行時挙動
**現象**：`enum` がコードを生成し、ツリーシェイクされない・`const enum` がビルド設定で挙動が変わる・数値 enum は逆引きマップを持つ。
**なぜ**：`enum` は型だけでなく**実行時オブジェクトを生成**する独特な機能。
**対策**：多くのチームは **リテラルユニオン**（`type Color = "red" | "blue"`）や **`as const` オブジェクト**で代替する（型は消え、値は素のオブジェクト）。

## 7. `tsconfig` の厳格設定オフで穴
**現象**：`null`/`undefined` を見落とす、暗黙の `any` が紛れる。
**なぜ**：`strict` 系がオフだと型システムの安全機構が大幅に弱まる。
**対策**：**`"strict": true`**（`strictNullChecks` 等を一括有効）。既存コードは段階導入（`noImplicitAny`→`strictNullChecks`…）。

## 8. 型が通っても実行時バグは別問題
**現象**：型エラーゼロでも、ロジックの誤り・外部データ不整合・非同期の取り違えは普通に起きる。
**なぜ**：型は「**形**」を保証するだけで「値の中身・振る舞い」までは保証しない。
**対策**：型に加えて**テスト**と**境界バリデーション**。型は安全装置の一つで万能ではない、と扱う。
