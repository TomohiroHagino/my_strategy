# ワークフロー実践

## ひとことで言うと
**Claude Code で1タスクを安全・確実に回すための「型」**。思いつきで丸投げするのではなく、**探索 → 計画 → 実装 → 検証 → コミット**の流れに乗せる。特に「**計画を承認してから実装」「テストで裏取り」**の2つが、品質と事故防止の効きどころ。

## なぜ必要か / どこで効くか
- エージェントは**自走できる分、暴走もしうる**。いきなり実装させると、的外れな方向に大量の変更を入れて手戻りになる。
- **先に計画を出させて人が承認**すれば、方向違いを実装前に止められる。
- 出力は**確率的でブレる**ので、**テスト・レビューで検証**しないと「できました（実は壊れてる）」を見抜けない。
- 効くのは：**大きめの機能追加 / リファクタ / バグ修正 / 不慣れな領域**。

## 基本フロー（探索→計画→実装→検証）
```
① 探索   コードベースを読ませ、現状と関連箇所を把握（必要ならサブエージェントで調査）
② 計画   plan mode で方針・手順・影響範囲を提示 → 人が承認（破壊的/大規模ほど必須）
③ 実装   承認後にファイル編集・コマンド実行。小さく刻む
④ 検証   テスト/ビルド/型チェック/レビュー（code-reviewer 等）
⑤ 確定   人の指示でコミット/PR（push やデプロイは ask/承認）
```
- **①と②を省かない**のがコツ。いきなり③に行くと手戻りが増える。
- **小さく刻む**：1回の変更を小さくすると、検証もレビューも軌道修正も楽。

## plan mode（計画モード）の使い方
- 「読む・調べる」だけ先に行わせ、**変更前に計画を提示**させる。承認するまでファイルを触らない。
- 大きな設計判断は**拡張思考（think hard 等）と併用**して、深く考えてから計画を出させる。
- 計画に違和感があれば**承認せず差し戻す**。ここが一番安く軌道修正できる地点。

## TDD（テスト先行）と相性が良い
出力がブレるエージェントほど、**先にテストという"正解の定義"を固める**と効く。
```
1. 期待挙動をテストで書かせる（RED：まだ落ちる）
2. テストを通す最小実装をさせる（GREEN）
3. リファクタ（IMPROVE）
4. カバレッジ確認
```
- テストが**検証の自動化**になり、「できました」の真偽を機械的に判定できる。
- バグ修正は **まず再現テスト** を書かせてから直すと、再発防止にもなる。

## コードレビューを挟む
- 変更直後に **code-reviewer**（必要なら security-reviewer / 言語別 reviewer）を当てる（→ [03_サブエージェント.md](./03_サブエージェント.md)）。
- 重要変更は**多視点**（事実確認・シニア視点・セキュリティ・一貫性・冗長性）で並列レビュー。
- レビューは**サブエージェントで分離文脈**で行うと、メインの文脈を汚さず結論だけ受け取れる。

## git / PR の運用
- **コミット・push は人の指示があってから**。勝手に push させない（permissions で push を ask に）。
- デフォルトブランチでの直接作業を避け、**ブランチを切ってから**作業させる。
- PR は「最新コミットだけ」でなく**全コミット履歴と差分（`git diff base...HEAD`）**を踏まえて要約させる。
- 秘密情報・デバッグ出力の混入を**コミット前に検査**（フックで強制できる → [04_フック.md](./04_フック.md)）。

## 自動化との組み合わせ（多層）
```
プロンプト/計画   … その場の意図（plan mode で承認）
CLAUDE.md         … 常時の規約（毎回の前提）
フック             … 必ず走る検証・整形・ガード（決定的）
サブエージェント   … 分離文脈の調査・レビュー
CI/CD             … 最終防壁（フックをすり抜けても止める）
```
- 「**お願い**」で済むこと（方針）と「**強制**」すべきこと（整形・秘密検出・テスト）を分け、後者はフック/CIに落とす。

## ヘッドレス/バッチでの活用（print モード）
- `claude -p "…"` で**1発実行**でき、パイプ・スクリプトに組み込める。
- 例：`git diff | claude -p "この差分をレビューして指摘を箇条書きで"`、定期実行で Issue を仕分け、など。
- CI に組み込むなら、より制御の効く **Agent SDK / API**（→ [08_api_sdk連携.md](./08_api_sdk連携.md)）。

## 強み / 弱み・限界
**強み**：
- **手戻りの最小化**（計画承認）と**品質の担保**（テスト・レビュー）を両立。
- 自動化と人の判断を**役割分担**でき、速度と安全のバランスが取れる。

**弱み・限界**：
- **型を守らないと意味がない**：急いで丸投げすれば結局手戻り。
- **検証が無いと裏取りできない**：テスト不在の領域はリスクが残る。
- 計画・レビューの**追加コスト**（時間・トークン）はかかる。大きさに応じて省略判断。

## ハマりどころ / アンチパターン
- **計画を飛ばして大規模変更** → 方向違いを大量実装。plan mode で承認してから。
- **テストなしで「直った」を信用** → 確率的出力は嘘をつく。検証を回す。
- **巨大な1コミット** → レビュー不能・切り戻し困難。小さく刻む。
- **勝手に push/デプロイを許可** → 不可逆事故。外向き操作は ask。
- **長い1セッションに複数タスク** → 文脈汚染。タスクごとに `/clear`、長引いたら `/compact`。
