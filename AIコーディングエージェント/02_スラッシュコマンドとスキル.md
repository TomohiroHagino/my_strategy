# スラッシュコマンドと Skill

## ひとことで言うと
**よくやる作業を「再利用できる手順」として固める仕組み**。`/command` という呼び出し口（スラッシュコマンド）と、その中身になる**手順書＝Skill**。毎回プロンプトを打ち直す代わりに、**名前を呼べば決まった作法で動く**ようにする。

## なぜ必要か / どこで効くか
- 「PRレビュー」「テスト追加」「リリースノート生成」のような**反復作業**は、毎回プロンプトを書くと**ブレる・抜ける・遅い**。
- 手順を1度コマンド化すれば、**誰が呼んでも同じ品質**で実行でき、チームで共有もできる。
- 効くのは：**定型レビュー / 定型生成 / 環境セットアップ / プロジェクト固有のお作法**。このリポジトリで言えば「**章を書式テンプレ通りに新規作成する**」などがコマンド向き。

## スラッシュコマンドの2種類
```
組み込み（built-in）  … Claude Code が標準提供。/help /clear /compact /model /config /init /review …
自作（custom）        … .claude/commands/<name>.md を置くと /<name> で呼べる
```

### よく使う組み込み（代表例）
| コマンド | 役割 |
|---|---|
| `/help` | ヘルプ |
| `/clear` | 文脈をリセット（タスク切り替え時） |
| `/compact` | 会話を要約圧縮して継続 |
| `/model` | 使用モデル切り替え |
| `/config` | 設定の確認・変更 |
| `/init` | リポジトリを解析して CLAUDE.md の雛形を生成 |
| `/review` | 変更/PR をレビュー |

> 一覧と最新は `/help` と公式ドキュメントで確認（コマンドは増減する）。

## 自作スラッシュコマンド（最小例）
`.claude/commands/` に Markdown を置くだけ。ファイル名がコマンド名になる。
```markdown
<!-- .claude/commands/new-chapter.md -->
---
description: 学習リストの新規トピックを書式テンプレ通りに作成する
---
次のトピックについて、このリポジトリの書式テンプレ
（ひとことで言うと / なぜ必要か / 本文節 / 強み弱み / ハマりどころ / 関連）
に厳密に従って新しい .md を作って。対象トピック: $ARGUMENTS
```
- `$ARGUMENTS` で呼び出し時の引数を受け取れる（`/new-chapter Redisのpub/sub` のように）。
- 中身はただのプロンプト＋手順。**「いつも口で説明していること」をそのまま書き起こす**のがコツ。

### 置き場所（ファイル名＝コマンド名）
```
~/.claude/commands/             ← 全プロジェクトで使える（共通）
└── new-chapter.md              → /new-chapter

<repo>/.claude/commands/        ← このリポジトリ専用
├── release-notes.md            → /release-notes
└── db/
    └── migrate.md              → /db:migrate   （サブフォルダは名前空間になる）
```
- **プロジェクト直下 `.claude/commands/`** はそのリポジトリ専用、**`~/.claude/commands/`** は全プロジェクト共通。
- フォルダで分けると `フォルダ:コマンド名` の名前空間になり、増えても整理できる。

## Skill（スキル）とは
**特定タスクの"深い手順・参照資料"をまとめた単位**。スラッシュコマンドが「呼び出し口」なら、Skill は「**その作業のやり方を詳細に記述した知識ファイル**」。`SKILL.md` を中心に構成され、必要なときに読み込まれて発動する。

```
スラッシュコマンド … 入口（/foo で起動）。短い。
Skill            … 中身の手順・規約・チェックリスト・参照。長くてよい。
```
- 「ルール」が**何をするか（基準・規約）**を定義するのに対し、Skill は**どうやるか（具体手順）**を提供する、という住み分け。
- 例：「TDDワークフロー」「E2Eテストの型」「コードレビュー手順」など、**手順が重い作業**ほど Skill 化が効く。
- 発動は、ユーザーが `/skill名` で明示的に呼ぶ場合と、タスクに合致してエージェントが選ぶ場合がある。

## コマンド/Skill 設計の指針
- **1コマンド＝1目的**。「何でもやる万能コマンド」は精度が落ちる（KISS）。
- **手順を明文化**：前提・やること・成功条件・失敗時の対処まで書くと再現性が上がる。
- **引数で可変部分だけ外出し**：固定の作法は本文に、可変は `$ARGUMENTS` に。
- **プロジェクト固有 vs 共通**を置き場所で分ける（`.claude/` か `~/.claude/`）。
- 既存の組み込み・既製 Skill で足りるなら**自作しない**（YAGNI）。

## 強み / 弱み・限界
**強み**：
- 反復作業の**再現性・速度・共有性**が上がる。属人化を減らせる。
- プロジェクトのお作法を**コードと一緒にバージョン管理**できる（`.claude/` をコミット）。

**弱み・限界**：
- **作りすぎると把握不能**：コマンドが乱立すると「どれを使うか」自体が負担に。
- **中身が古びる**：規約変更に追従しないと、古い作法を再生産してしまう。
- 結局**手順の質がすべて**：曖昧な手順書はブレた結果を量産する。

## ハマりどころ / アンチパターン
- **巨大な万能コマンド** → 目的が散って精度低下。小さく割る。
- **手順を書かず「いい感じに」** → 毎回違う結果。成功条件まで明記する。
- **秘密情報をコマンド本文に直書き** → リポジトリに漏れる。環境変数/シークレットで（→ [05_設定とメモリ.md](./05_設定とメモリ.md)）。
- **使われないコマンドの放置** → 棚卸しして消す。死んだ手順は害。
- **コマンドと CLAUDE.md の責務混同** → 常時効かせたい規約は CLAUDE.md、都度起動の作業はコマンド。
