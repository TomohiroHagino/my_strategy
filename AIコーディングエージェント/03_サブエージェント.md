# サブエージェント

## ひとことで言うと
**メインの会話とは別の"独立した文脈"で動く子エージェント**。専門タスク（調査・レビュー・特定言語のチェックなど）を切り出して任せ、**結果（結論）だけをメインに返す**。文脈を汚さず、並列で、専門特化させられるのが肝。

## なぜ必要か / どこで効くか
- メインのコンテキストウィンドウは有限。**大量のファイルを読む調査**を本流でやると文脈が溢れて本題が押し出される。
- サブエージェントなら**子の文脈で大量に読み込み、要点だけ返す**ので、メインは結論を受け取るだけで済む（＝コンテキスト節約）。
- **独立タスクを並列実行**できる（複数モジュールを同時調査・複数観点で同時レビュー）。
- **役割特化**できる：「セキュリティ専門」「Go専門レビュー」など、専用プロンプト＋限定ツールで精度を上げる。

> 使いどころの本質：**「広く読む必要があるが、メインに全部は要らない」**作業。結論だけ欲しいときに投げる。

## 仕組み（メイン↔サブの関係）
```
┌ メイン会話（あなたとのセッション）─────────────────────────────┐
│  本題のタスクを進行                                              │
│   ├─ Agent("認証モジュールのセキュリティ調査") ─→ 子: 大量Read → 結論を返す
│   ├─ Agent("キャッシュ層の性能レビュー")       ─→ 子: 並列で実行                │
│   └─ Agent("ユーティリティの型チェック")        ─→ 子: 並列で実行                │
│  ← 各サブエージェントの「最終メッセージ＝結論」だけ受け取る                      │
└──────────────────────────────────────────────────────────────────┘
```
- サブエージェントの**最終メッセージがそのまま戻り値**。途中の大量の読み込みはメインに残らない。
- **独立した作業は1メッセージで複数同時起動**＝並列実行（直列にしない）。
- 子はさらに子を呼べない設計が一般的（ネストは浅く保つ）。

## エージェントの種類（典型）
| 種類 | 役割 | 使う場面 |
|---|---|---|
| 汎用（general / Explore） | 調査・検索・横断読み | 「どこに何があるか」を広く探す |
| planner / architect | 計画・設計 | 大きめ機能・リファクタの設計 |
| code-reviewer | コード品質レビュー | 変更直後 |
| security-reviewer | 脆弱性検査 | 認証・入力・外部API・秘密まわり |
| 言語別 reviewer（go/python/rust…） | 言語特化レビュー | その言語の変更 |
| build-error-resolver | ビルド/型エラー修正 | ビルド失敗時 |
| tdd-guide | テスト先行の誘導 | 新機能・バグ修正 |

- 実体は `~/.claude/agents/`（共通）や `.claude/agents/`（プロジェクト）に**Markdown＋frontmatter**で定義。
- frontmatter で `name / description / tools（使えるツールの制限）/ model` を指定でき、**役割に必要な権限だけ**渡せる。

## 自作サブエージェント（最小イメージ）
```markdown
<!-- .claude/agents/doc-style-checker.md -->
---
name: doc-style-checker
description: 学習ノートが書式テンプレに沿っているか検査する。新規/編集した .md の直後に使う。
tools: Read, Grep, Glob
---
あなたは文書校閲者。対象 .md が
「ひとことで言うと/なぜ必要か/本文/強み弱み/ハマりどころ/関連」
の構成と相互リンクの整合を満たすか検査し、逸脱を箇条書きで指摘する。修正案も添える。
```
- `description` が**いつ呼ばれるか**を決める（曖昧だと呼ばれない/誤発動）。tool use の説明文と同じく磨く。
- `tools` を絞ると**事故防止＋精度向上**（レビュー用に書き込み権限を渡さない、など）。

### 置き場所（コマンドと同じ2階層）
```
~/.claude/agents/               ← 全プロジェクト共通
├── code-reviewer.md
├── security-reviewer.md
└── planner.md

<repo>/.claude/agents/          ← このリポジトリ専用
└── doc-style-checker.md        （書式チェックなど、このリポ固有の役割）
```
- 共通で使う汎用レビュアーは `~/.claude/agents/`、リポ固有の役割は `<repo>/.claude/agents/`。

## オーケストレーション（複数を束ねる）
- **並列ファンアウト**：独立調査をまとめて投げ、結果を集約。
- **多視点レビュー**：同じ対象を「事実確認／シニア視点／セキュリティ／一貫性／冗長性」の役割で同時に当てる。
- **パイプライン**：調査→計画→実装→レビューを役割ごとに渡す。
- いずれも**メインは"指揮者"**で、重い読み書きは子に逃がす、というのが基本構図。
```
        メイン会話（指揮者）
              │  独立タスクは1メッセージでまとめて起動＝並列
   ┌──────────┼──────────┐
   ▼          ▼          ▼
 [子] 認証調査  [子] 性能レビュー [子] 型チェック   ← それぞれ別文脈で大量Read
   │          │          │
   └──────────┴──────────┘
              ▼
        結論だけ集約（メインの文脈は汚れない）
```

## 強み / 弱み・限界
**強み**：
- **コンテキスト節約**：大量読み込みを子に隔離し、メインは結論だけ。
- **並列化**で時間短縮。独立作業を同時に進められる。
- **役割特化＋権限最小化**で精度と安全を両立。

**弱み・限界**：
- 子は**メインの会話履歴を引き継がない**（渡した指示しか知らない）。前提は明示的に渡す必要。
- **投げっぱなしは精度劣化**：曖昧な指示だと的外れな結論が返る。
- **コスト増**：エージェントを増やすほどトークン・時間を消費。乱発しない。

## ハマりどころ / アンチパターン
- **文脈を渡さず丸投げ** → 子は背景を知らないので的外れ。必要な前提・対象ファイルを明示。
- **何でもサブエージェント化** → 単純作業はメインで十分。広く読む必要があるときだけ。
- **直列に1個ずつ起動** → 独立なら並列にすべき（時間の無駄）。
- **レビュー用エージェントに書き込み権限** → 勝手に直して事故。`tools` を絞る。
- **結論の鵜呑み** → 子も間違える。重要判断はメインで裏取り。
