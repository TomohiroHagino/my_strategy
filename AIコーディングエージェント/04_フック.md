# フック（Hooks）

## ひとことで言うと
**特定のタイミングで自動実行される、あなたが定義したコマンド**。「ファイルを編集したら整形する」「危険なコマンドはブロックする」などを、**LLMの善意（お願い）ではなくハーネス側で強制**する。エージェントが従うかどうかに依存せず、**決定的に**効く。

## なぜ必要か / どこで効くか
- 「コミット前に必ず整形して」とプロンプトで頼んでも、**LLMは確率的なので忘れる・抜ける**ことがある。
- フックは**ツール実行の前後などに機械的に走る**ので、「毎回必ず」を100%保証できる。
- 効くのは：**自動整形 / Lint・型チェック / 危険操作のガード / 秘密混入の検出 / セッション終了時のビルド検証**。
- 本質：**"守ってほしいこと"はプロンプトでなくフックで強制する**。これがプロンプトとフックの決定的な役割分担。

## 主なフックの種類（タイミング）
| 種類 | 発火タイミング | 典型用途 |
|---|---|---|
| **PreToolUse** | ツール実行**前** | 入力の検証・パラメータ修正・**危険操作のブロック** |
| **PostToolUse** | ツール実行**後** | **自動整形 / Lint / 型チェック** |
| **Stop** | セッション終了時 | 最終的な**ビルド/テスト検証** |
| **UserPromptSubmit** など | 入力送信時ほか | 文脈の注入・前処理（種類は拡張される） |

> `matcher` で「どのツールに効かせるか」を絞れる（例：`Write|Edit` のときだけ整形）。

### いつ発火するか（1ツール実行の前後）
```
ユーザー入力 ─[UserPromptSubmit]→ エージェントが判断
                                      │
                          ツールを呼ぼうとする
                                      │
                            ┌─[PreToolUse]──→ exit 2 ならここで中断（危険操作ブロック）
                            ▼
                    ツール実行（Write / Edit / Bash …）
                            │
                            └─[PostToolUse]──→ 整形・Lint・型チェック
                                      │
                          （会話が続く…繰り返し）
                                      │
                                 [Stop] ──→ セッション終了時にビルド/テスト検証
```

## 設定の形（settings.json）
フックは `settings.json` の `hooks` に登録する（→ [05_設定とメモリ.md](./05_設定とメモリ.md)）。
```jsonc
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Write|Edit",
        "command": "prettier --write \"$FILE_PATH\"",
        "description": "編集したファイルを整形する"
      }
    ]
  }
}
```
- フックは**外部コマンド**。整形・Lint・型チェック・テストなど**既存のツールをそのまま呼ぶ**。
- **ブロックの作法**：PreToolUse のコマンドが**終了コード 2 で終わる**と、その操作を止めてエラーを返す（標準エラーの内容がフィードバックとして渡る）。これで「危険コマンドの拒否」「巨大ファイル書き込みの禁止」などを実装できる。
- 推奨実行順：**整形 → Lint → 型チェック → ビルド検証**。

### どこに書く？ ── フックは階層が"合算"される（重要）
`settings.json` はユーザー全体／プロジェクト／個人の3階層に置けるが（→ [05_設定とメモリ.md](./05_設定とメモリ.md)）、**`hooks` は「具体が一般を上書き」ではなく、全階層が足し算で全部走る**。ここが他の設定値（`model` など単一値＝上書き）との決定的な違い。
```
~/.claude/settings.json            のフック  ┐
<repo>/.claude/settings.json       のフック  ├─ 全部まとめて発火（合算・additive）
<repo>/.claude/settings.local.json のフック  ┘
```
- だから **ユーザー全体に1度書けば、全プロジェクトで効く**（この環境の ECC が整形・コミット品質チェックを全リポで効かせているのはこれ）。
- プロジェクトの `.claude/settings.json` に書くのは「**このリポだけの自動化を上乗せしたいとき**」だけ。ユーザー全体のフックは消えず、**両方走る**。
- 置き場所の使い分け：

| やりたいこと | 置き場所 |
|---|---|
| 全プロジェクトで効かせたい | `~/.claude/settings.json` |
| このリポだけ・チーム共有（コミット） | `<repo>/.claude/settings.json` |
| このリポだけ・自分だけ（gitignore） | `<repo>/.claude/settings.local.json` |

> 注意：プロジェクト直下に直接ではなく **`.claude/` フォルダの中**に置く。`model` や `permissions` の単一値は「具体 > 一般」で上書きされるが、**`hooks` は合算**——混同しやすいので区別する。

## ガードフックの例（危険な書き込みを止める）
```jsonc
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Write",
        "command": "node check-size.js",   // 800行超なら exit 2 で拒否
        "description": "巨大ファイルの書き込みをブロック"
      }
    ]
  }
}
```
- 「**プロジェクトのファイル分割方針（800行上限など）を物理的に守らせる**」のような、規約の強制に向く。
- 同様に「秘密情報パターンの検出で commit を止める」「`rm -rf` 系を拒否」なども PreToolUse で。

## プロンプト / コマンド / フック / ルールの住み分け
```
ルール(CLAUDE.md)   … 「基準・方針」を常時伝える（守るかはLLM次第）
スラッシュコマンド    … 「都度起動する手順」の入口
サブエージェント      … 「分離文脈での専門作業」
フック               … 「必ず・決定的に走らせる処理」（LLMに依存しない強制力）★ここだけ強制
```
- **"自動で・毎回・確実に"が要るならフック**。それ以外（基準を伝える/手順を再利用）は他の仕組み。
- 「今後Xしたら必ずYして」のような**自動化の依頼は、メモリやプロンプトでは果たせない**。フック（＝ハーネス設定）に落とすのが正解。

## 強み / 弱み・限界
**強み**：
- **決定的な強制力**：LLMの気まぐれに左右されない。
- **既存ツールを再利用**：整形・Lint・テストの資産をそのまま使える。
- 規約（ファイルサイズ・秘密検出・整形）を**物理的に担保**できる。

**弱み・限界**：
- **設定ミスが全操作に波及**：重いコマンドを毎ツールで走らせると遅くなる。matcher で絞る。
- **誤ブロックで作業が止まる**：ガードが厳しすぎると正当な操作も弾く。
- **デバッグしづらい**：何が・なぜ走ったか追いにくい。description を明記し、ログを見る。
- フック自体が**任意コード実行**＝信頼できるコマンドだけ登録する。

## ハマりどころ / アンチパターン
- **重い処理を全ツールで実行** → 体感が激重に。`matcher` で対象を絞り、軽い処理に。
- **リモートの一発実行コマンドをフックに** → 供給網リスク。**プロジェクト所有の依存**を使う。
- **ブロックの終了コードを誤る** → 止めたいのに通る/通したいのに止まる。仕様（exit 2 で拒否）を確認。
- **整形と型チェックの順序が逆** → 整形前の状態で型エラーを出して混乱。整形→Lint→型→ビルドの順。
- **「フックがあるから安全」と過信** → カバー外の事故は防げない。CI 側でも再検証（多層防御）。
