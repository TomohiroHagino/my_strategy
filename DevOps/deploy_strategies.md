# デプロイ戦略（DevOps）

## ひとことで言うと
**新バージョンを本番へ「どう切り替えるか」の型。一気に全部置き換える(rolling)・別環境を用意して瞬時に切替(blue-green)・一部のユーザーにだけ先に出す(canary)・コードは出すが機能はスイッチで隠す(feature flag)、の4つ＋戻し方(ロールバック)。**

## 役割・なぜ必要か
- デプロイは**「壊れるかもしれない瞬間」**。新バージョンにバグがあったとき、被害を小さく・戻しを速くするために戦略を選ぶ。
- 選択軸は **①影響範囲を絞れるか ②戻しが速いか ③コスト（環境の二重化）④複雑さ**。サービスの重要度に合わせて選ぶ。
- 「壊れたら戻す」の実行手順そのものは障害対応側にある → [../インフラ/障害対応/復旧手順.md](../インフラ/障害対応/復旧手順.md)。何をすべきかの判断は [../インフラ/障害対応/対応判断フロー.md](../インフラ/障害対応/対応判断フロー.md)。

## 基本（手順・考え方・コード）

### ① Rolling（ローリング）— 順次入れ替え
インスタンスを少しずつ新版に置き換える。デフォルトでよく使う。
```
 旧 旧 旧 旧   →   新 旧 旧 旧   →   新 新 旧 旧   →   新 新 新 新
                 1台ずつ置換（健康チェックを通ったら次へ）
```
- **利点**：追加環境不要（安い）。**欠点**：切替中は新旧が混在／戻すのも順次で遅い。
- 新旧が同時に動ける（DBスキーマ等が後方互換）ことが前提。

### ② Blue-Green（ブルーグリーン）— 2環境を切替
本番相当を2セット用意し、ロードバランサの向き先を一括で切り替える。
```
        ┌─ Blue(現行 v1) ◀── 100% 利用者
  LB ──┤
        └─ Green(新版 v2)     0%（裏で起動・検証）

   切替 ▶  LB の向きを Green へ（瞬時に100%）

        ┌─ Blue(v1)            ◀ 待機（即戻せる）
  LB ──┤
        └─ Green(v2) ◀── 100% 利用者
```
- **利点**：切替が瞬時／**戻しは向き先をBlueに戻すだけ＝最速**。**欠点**：環境を2倍持つのでコスト増。
- 切替直後に問題があれば即ロールバック。AWSなら ALB/ターゲットグループや ECS で実現 → [../インフラ/aws/](../インフラ/aws/)。

### ③ Canary（カナリア）— 一部に先に出す
新版をまず少数（例 5%）のトラフィックに出し、指標を見て問題なければ段階的に拡大。
```
  v2へ流す割合:  5% ─▶ 25% ─▶ 50% ─▶ 100%
                 │      │      │
                 各段階でエラー率/レイテンシ(p95)を監視 → 悪化したら即停止・戻す
```
- **利点**：問題を「全体に出る前」に・少数の被害で捕まえられる。**欠点**：トラフィック分割と監視の仕組みが要る。
- 判断には可観測性が必須（→ [observability.md](./observability.md)）。エラーバジェットを食ったら拡大を止める。

### ④ Feature Flag（フィーチャーフラグ）— デプロイとリリースを分離
**コードは本番に出す（deploy）が、機能はフラグがONのときだけ動く（release）**。
```
 if (flags.isEnabled("new_checkout", user)) {
   newCheckout();     // フラグONのユーザーだけ新機能
 } else {
   oldCheckout();     // それ以外は従来どおり
 }
```
- **利点**：再デプロイ無しでON/OFFできる／特定ユーザーにだけ出せる（A/Bテスト・段階公開）／**戻し＝フラグをOFFにするだけ**。
- **欠点**：フラグが増えるとコードが複雑化（→ [pitfalls.md](./pitfalls.md) のflag乱立）。**使い終わったフラグは消す**。

### ロールバック（戻し）— 戦略ごとの戻し方
| 戦略 | 戻し方 | 速さ |
|---|---|---|
| rolling | 旧版で再度rolling | 遅め（順次） |
| blue-green | LBをBlueに戻す | **最速（瞬時）** |
| canary | 拡大を止めて0%に | 速い |
| feature flag | フラグをOFF | **最速（再デプロイ不要）** |

> 共通原則：**「前に進めて直す」より「まず戻す」**（止血優先）。原因究明はその後。→ [../インフラ/障害対応/](../インフラ/障害対応/)

## 実務での使い方・定番パターン
- **使い分けの目安**
  - 普通のWebアプリ → **rolling**（安くて十分）
  - 重要サービス・即戻したい → **blue-green**
  - 大きな変更・リスクが読めない → **canary**（少しずつ・監視しながら）
  - リリースタイミングを自由にしたい/段階公開/A・B → **feature flag**
- **組み合わせる**：canary でインフラ的に絞りつつ、feature flag で機能を制御、が強い。
- **どの戦略でもDBマイグレーションが鬼門**：新旧が同時に動く前提で**後方互換なスキーマ変更**（列追加→使う→旧列削除を別リリースに分ける）。
- マネージドに寄せると戦略が楽：ECS/CodeDeploy（blue-green/canary）など → [../インフラ/aws/containers.md](../インフラ/aws/containers.md)。

## ハマりどころ / アンチパターン
- **ロールバック手順を試していない**：本番障害の真っ最中に「戻し方が分からない」。平時に必ずリハーサル。
- **DBの破壊的変更を一発でやる**：列削除/型変更を新旧混在中にやると旧版が壊れる。**段階リリース**で後方互換を保つ。
- **canaryなのに監視していない**：少数に出しても指標を見なければ意味がない。自動で悪化検知→停止まで作る。
- **feature flagを消さない**：万年フラグでコードが`if`だらけに。期限を決めて掃除。
- **blue-greenでデータを二重化し忘れる**：アプリは2系統でもDBは1つ、という前提を忘れると切替で不整合。
