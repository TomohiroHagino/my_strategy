# 可観測性（Observability）（DevOps）

## ひとことで言うと
**「外から出ている信号（metrics/logs/traces）だけで、中で何が起きているかを説明できる」状態にすること。さらに、サービス品質を SLI/SLO/エラーバジェット という数字の約束に落として運用する。**

## 役割・なぜ必要か
- デプロイ頻度が上がるほど「出した後に問題が出る」。**速く検知し、原因を素早く特定できる**ことがDevOpsの前提になる。
- 「監視(monitoring)＝あらかじめ決めた異常を見張る」に対し、**「可観測性＝想定外の問いにも答えられるデータが揃っている」**。後者がないと、新種の障害で詰まる。
- canary/段階リリースの「進めるか止めるか」判断もここに依存する → [deploy_strategies.md](./deploy_strategies.md)。
- 具体的な「何のログを見る/どのコマンド」は障害対応側に詳しい → [../インフラ/障害対応/ログと監視.md](../インフラ/障害対応/ログと監視.md)。ここではDevOps視点の枠組みを扱う。

## 基本（手順・考え方・コード）

### 3本柱（metrics / logs / traces）
```
 ┌── metrics（メトリクス）──────────────────────────────┐
 │ 数値の時系列。CPU・RPS・エラー率・レイテンシ。       │
 │ 「いつ・どれだけ」異常か。集計に強い／個別事象は分からない│
 └────────────────────────────────────────────────────┘
 ┌── logs（ログ）───────────────────────────────────────┐
 │ 1イベント1行の記録。何が起きたかの詳細。              │
 │ 構造化(JSON)＋trace_id付きが鉄則。原因の文脈が分かる   │
 └────────────────────────────────────────────────────┘
 ┌── traces（分散トレース）──────────────────────────────┐
 │ 1リクエストが複数サービスを通る経路と各区間の時間。   │
 │ マイクロサービスで「どこが遅い/失敗したか」を特定      │
 └────────────────────────────────────────────────────┘
```
- 使い分け：**metricsで気づく → tracesでどこか絞る → logsで詳細を読む**。
- 横串を通すのが **trace_id（相関ID）**。ログとトレースに同じIDを載せ、3つを行き来できるようにする。
- 計装の標準は **OpenTelemetry**（ベンダー非依存でmetrics/logs/tracesを出す）。

### SLI / SLO / エラーバジェット
```
 SLI (Indicator) : 品質を表す実測値の指標
   例: 「2xx応答の割合」「p99レイテンシが300ms以下のリクエスト割合」

 SLO (Objective) : SLIに対する目標（約束）
   例: 「直近30日で 成功率 99.9% 以上」

 エラーバジェット : 100% − SLO ＝ 許される失敗の量
   例: SLO 99.9% → 0.1% は壊れてよい
       = 30日なら 約43分ぶんのダウンが"予算"
```
- **エラーバジェットが残っている＝攻めてよい（速く出す）。使い切った＝守りに入る（リリース凍結・信頼性改善優先）**。これが「速さと安定の調整つまみ」になる。
- SLIの式の例：`成功率 = 成功リクエスト数 / 全リクエスト数`、`可用性 = 稼働時間 / 全時間`。レイテンシは平均でなく **p95/p99**（外れ値を見るため。→ [../インフラ/負荷検証/指標.md](../インフラ/負荷検証/指標.md)）。

### アラートは「症状」に張る
```
 良い: SLOを脅かす症状にアラート
   「エラー率がエラーバジェットを急速に消費」「p99がSLO閾値超過」
 悪い: 原因の断片にアラート乱発
   「CPU 80%」だけで深夜に起こす（ユーザー影響が無いことも多い）
```
> 起こす基準は**「ユーザーに影響しているか／SLOを脅かすか」**。アラート疲れ(noise)は見逃しを生む。

## 実務での使い方・定番パターン
- **最初に決めるのは「ユーザー体験を表すSLI」1〜2個**（成功率・主要画面のp95）。全部を測ろうとしない。
- **USE/RED で何を見るか整理**：REDメソッド(Rate/Errors/Duration)＝リクエスト視点、USE(Utilization/Saturation/Errors)＝リソース視点。詳細は [../インフラ/障害対応/ログと監視.md](../インフラ/障害対応/ログと監視.md)。
- **ダッシュボードとアラートをコードで管理**（as-code）。Gitに置けばレビュー・履歴・GitOpsに乗る → [gitops.md](./gitops.md)。
- **DORAと併用**：可観測性はMTTR短縮（速く気づく・速く原因特定）に直結 → [dora_metrics.md](./dora_metrics.md)。
- リリース直後は**デプロイマーカー**をグラフに打ち、「いつ出したか」と指標の変化を重ねて見る。

## ハマりどころ / アンチパターン
- **ログを出すだけで構造化しない**：人間が読む文字列ログだと検索/集計できない。**JSON＋trace_id**で出す。
- **アラートが多すぎる**：全部に張ると麻痺して本物を見逃す。症状ベースに絞る。
- **SLOを100%にする**：100%は不可能・超高コスト。99.9%等にしてエラーバジェットを運用に使う。
- **平均レイテンシだけ見る**：平均は遅い少数を隠す。p95/p99を見る。
- **計測しないまま改善を語る**：「速くなった気がする」はDevOpsではない。数字で示す（→ [dora_metrics.md](./dora_metrics.md)）。
- **カーディナリティ爆発**：metricsのラベルにuser_id等を入れて系列数が爆発しコスト/性能事故。高カーディナリティはログ/トレースへ。
