# DevOps文化（CALMS・トランクベース・blameless）（DevOps）

## ひとことで言うと
**DevOpsで一番効くのはツールでなく「働き方」。開発と運用のサイロ(縦割り)を壊し、責任を共有し（You build it you run it）、人を責めず仕組みを直し（blameless）、小さく頻繁に統合する（トランクベース）チームの作り方。**

## 役割・なぜ必要か
- 最新のCI/CDを入れても、**「開発はコードを投げ、運用が受け止める」縦割りのまま**だと速くも安全にもならない。問題は組織の壁にある。
- DevOpsの定義そのものが「DevとOpsの壁を壊す」。だから文化（CALMSのC）が土台。ツール（A/L/M/S）はそれを支える。
- 文化が悪いと数字に出る：責める文化→情報が隠れる→原因不明→再発→MTTR悪化（→ [dora_metrics.md](./dora_metrics.md)）。

## 基本（手順・考え方・コード）

### CALMS（再掲・文化の位置づけ）
```
 C ulture     ← この文書の主題。土台。
 A utomation  → CI/CD（[ci_cd.md] / [ci_tools.md]）
 L ean        → 小さく頻繁・WIP制限・無駄取り
 M easurement → DORA / SLO（[dora_metrics.md] / [observability.md]）
 S haring     → ポストモーテム・ダッシュボード・知見の共有
```

### サイロ解消（縦割りを壊す）
```
【before】壁あり
  開発チーム ──(コードを投げる)── 壁 ──(受け取って運用)── 運用チーム
   速さ重視                              安定重視（変更を嫌う）
   → 対立。障害の押し付け合い

【after】責任共有
  1つのチームが「作る〜動かす〜直す」を持つ
   開発も本番を見る／運用も設計に関わる
   → 共通のゴール（速く＆安定）に向く
```

### You build it, you run it（作った人が運用する）
- 自分が書いたコードの本番アラートを自分が受ける（オンコール）。**「動かす責任」が設計を良くする**（壊れにくく・直しやすく作るようになる）。
- ログ/監視を最初から仕込むインセンティブが生まれる → [observability.md](./observability.md)。

### blameless（人を責めない）ポストモーテム
```
 ✕「○○さんが手順を間違えた」          → 人を責める。情報が隠れる。再発する。
 ◯「その手順は人為ミスが事故に直結する  → 仕組みを直す。確認/自動化/ガードを足す。
    設計だった。ガードを足そう」
```
- 前提：**事故は個人のミスでなく「ミスが事故になる仕組み」が原因**。責めると次から人は隠す。
- 具体の進め方（タイムライン・5 Whys・再発防止アクション）は [../インフラ/障害対応/ポストモーテム.md](../インフラ/障害対応/ポストモーテム.md)。

### トランクベース開発（小さく頻繁に統合）
```
 トランクベース: 短命ブランチ(1日以内)を頻繁にmainへマージ。常にmainがリリース可能
   main ──●──●──●──●──●──  （小さな変更が次々入る・CIが常に回る）
           └┘ └┘ └┘ 数時間で消える小ブランチ

 ✕ 長寿命ブランチ: 大きな機能を数週間別ブランチで育てる
   → マージ時に巨大コンフリクト／その間CIの意味が薄い／レビューも重い
```
- CI（頻繁な統合）の前提条件。未完成の機能を本番に置きつつ隠すには **feature flag** を使う → [deploy_strategies.md](./deploy_strategies.md)。

## 実務での使い方・定番パターン
- **小さく頻繁に出す**を最優先の習慣にする。バッチを小さくするとリードタイム短縮・失敗範囲縮小・戻しが楽（DORA改善）。
- **オンコールを開発も持つ**（無理のないローテーション）。本番の痛みを開発に届けると設計が変わる。
- **ポストモーテムを必ず書き・公開する（Sharing）**。同じ事故を組織全体で防ぐ。担当/期限つきの再発防止アクションまで → [../インフラ/障害対応/ポストモーテム.md](../インフラ/障害対応/ポストモーテム.md)。
- **ダッシュボードを全員に開く**：DORAとSLOを見える所に置き、改善を会話の中心にする。
- **心理的安全性**：「赤いCI/障害を早く言える」空気を作る。隠す方が高くつく。

## ハマりどころ / アンチパターン
- **「DevOpsチーム」という新しいサイロを作る**：DevとOpsの壁を壊すはずが、間に第3の縦割りを増やすと逆効果。DevOpsは役割でなくやり方。
- **ツールだけ入れて文化を変えない**：高機能CI/CDがあっても縦割りと犯人探しが残れば成果は出ない。
- **犯人探し**：一度やると以後ずっと情報が出てこなくなる。仕組みを直すに徹する。
- **大きなブランチを長く育てる**：マージ地獄・統合遅延。小さく刻む。
- **オンコールが一部に偏る/燃え尽き**：負荷を分散し、根本原因（アラート過多・手動作業）を潰す。
