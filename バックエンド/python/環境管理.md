# Python 環境管理 & Docker の棲み分け（図解）

> venv / conda / uv / pyenv / Docker は「**何を・どの層で隔離するか**」が違うだけ。
> 競合しないし、よく一緒に使う。下の図で層を掴めば迷わない。

---

## 0. まず1枚で結論

```
        「Pythonの依存だけ」分けたい        「環境・インフラまるごと」固定したい
                  │                                      │
              venv / conda                            Docker
        （同じPCの中で工具箱を分ける）        （部屋ごとコンテナにして持ち運ぶ）
```

- **venv / conda** … Pythonのパッケージ問題を解決（軽い・PC内）
- **Docker** … OS・システムライブラリ・ミドルウェアごと再現する問題を解決（重い・どこでも同じ）

---

## 1. なぜ隔離が要るのか（衝突の絵）

何も分けず全部システム共通に入れると、バージョンが取り合いになる:

```
        ❌ 隔離なし（共有の引き出しに全部）
   ┌────────────── system python ──────────────┐
   │   プロジェクトA  ──┐                        │
   │                    ├──►  Django ???         │  A は Django4、B は Django5 が欲しい
   │   プロジェクトB  ──┘     （1個しか置けない） │  → どちらかが必ず壊れる
   └─────────────────────────────────────────────┘

        ✅ 隔離あり（プロジェクトごとの工具箱）
   ┌── A/.venv ──┐     ┌── B/.venv ──┐
   │  Django 4   │     │  Django 5   │   それぞれ独立。衝突しない／再現できる
   └─────────────┘     └─────────────┘
```

---

## 2. 隔離の「層」— ここが全部の肝

```
┌─ Docker が固める範囲 ─────────────────────────────┐
│   OS（Ubuntu 等）                                  │
│   システムライブラリ（libpq, ImageMagick, GDAL …） │
│   ミドルウェア（DB・Redis は別コンテナで）          │
│   Python 本体（3.11 など）  ← pyenv / conda もここを扱える
│                                                    │
│   ┌─ venv / conda が固める範囲 ─────────────────┐ │
│   │   Python パッケージ（Django, numpy, …）     │ │
│   │   あなたのアプリのコード                     │ │
│   └──────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────────┘
        ▲ 外側ほど「広く・重く・再現性が高い」
```

- **venv** … いちばん内側（パッケージだけ）
- **conda** … パッケージ＋Python本体＋C/CUDA等のネイティブ依存まで
- **Docker** … その外側、OS・ミドルウェア・インフラまるごと

---

## 3. ツール早わかり表

| ツール | 何を隔離する | 主な用途 | 重さ | Python本体の切替 |
|---|---|---|---|---|
| **venv** | Pythonパッケージのみ | Web開発全般 | 軽い（標準同梱） | ✕（別途pyenv等） |
| **conda** | パッケージ＋Python＋ネイティブ依存 | データ/AI/科学計算 | 重い | ◯ |
| **uv** | パッケージ＋環境（pip/venv代替・高速） | 最近のWeb開発の新定番 | 軽い・爆速 | ◯（Pythonも入れられる） |
| **pyenv** | Python“本体のバージョン”だけ | 3.10/3.11/3.12 を切替 | 軽い | ◎（これが本職） |
| **Docker** | OS・ライブラリ・ミドルウェア丸ごと | チーム/CI/本番で同一環境・デプロイ | 重い | ◯（イメージで固定） |

> ざっくり: **pyenv=Pythonの版**, **venv/uv/conda=パッケージ環境**, **Docker=環境まるごと**。

## 4. それぞれ最小コマンド

```bash
# venv（標準・Web開発の定番）
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install django
pip freeze > requirements.txt     # 再現用に記録
deactivate

# uv（pip+venvを置き換える高速ツール。最近人気）
uv venv && source .venv/bin/activate
uv pip install django

# conda（データ/AI。Python本体ごと環境を作れる）
conda create -n myenv python=3.11
conda activate myenv
conda install numpy pytorch        # C/CUDA依存もまとめて解決

# Docker（OSごと固める）
docker build -t myapp .            # Dockerfile からイメージを作る
docker run -p 8000:8000 myapp      # どのPCでも同じ環境で起動
```

## 5. どれを使う？（判定フローチャート）

```
 何がしたい？
   │
   ├─ ローカルで普通にWeb開発（Django/FastAPI）
   │        └─►  venv（または uv）
   │
   ├─ numpy / PyTorch など重いネイティブ依存でゴリゴリ
   │        └─►  conda（Miniconda）
   │
   ├─ Pythonのバージョン自体を 3.10/3.11 と切り替えたい
   │        └─►  pyenv（＋ venv/uv を併用）
   │
   └─ チーム・CI・本番で「全員まったく同じ環境」にしたい / そのままデプロイ
            └─►  Docker（開発は docker compose で DB/Redis ごと起動）
```

## 6. 組み合わせの実例（開発を compose でまとめて起動）

```
 docker compose up    ←  この1コマンドで↓が全部立ち上がる
 ┌─────────────┐   ┌─────────────┐   ┌─────────────┐
 │  app        │──►│  db         │   │  redis      │
 │ (Django)    │   │ (Postgres)  │   │ (キャッシュ)│
 └─────────────┘   └─────────────┘   └─────────────┘
   各サービス＝1コンテナ。OS・バージョン込みで全員同じ。
```

### 「Dockerの中に venv は要る？」
**ほぼ不要**。コンテナ自体がもう隔離（1コンテナ=1アプリ）なので、イメージ内はシステムPythonに直接 `pip install` でOKという流儀が多い。
※ PATHを明示したい等の理由で中でも venv を切る人もいる（好み・規約レベル）。

## 7. チーム開発ではどうする？（→ Docker compose が基本）

チームのWeb開発では **Docker（compose）を土台にするのが事実上の標準**。この3つが一度に揃うから:

```
 ① 全員同じ環境     Mac/Win 問わず OS・DB・Python版まで同一
 ② CI/本番まで地続き 同じイメージが CI と本番へ → 「自分のPCでは動く」が消える
 ③ 新人が秒で動く    git clone → docker compose up で DB/Redis 込み起動
```

### ⚠️ ただし Docker だけでは足りない（依存固定は別で要る）
```
 Docker         … OS・ミドルウェアを固める
   ＋
 ロックファイル … requirements.txt / poetry.lock / uv.lock で“パッケージ版”を固定
        ↓
   この2つで初めて「完全に同じ」。Docker は venv/ロックの“置き換え”ではなく“補完”。
```

### ⚠️ タダではない（トレードオフ）
- **学習・保守コスト**：Dockerfile / compose を書いて保ち続ける手間。
- **内側の開発ループが遅くなりがち**：特に Mac はファイル同期・再ビルドが重い。
  → 折衷: **DB/Redis は Docker、コード編集とテストはローカル venv で速く回す**。
- **小規模・個人・短期は過剰**なことも（venv で十分）。

### 実務の典型（王道の構成）
```
 ローカル開発:  docker compose up
                ├─ app   (Django / Rails / Laravel)
                ├─ db    (Postgres)
                └─ redis
 依存固定:      uv.lock / poetry.lock / Gemfile.lock をコミット
 CI:            同じ Dockerfile でビルドしてテスト
 本番:          同じイメージを Cloud Run / ECS / k8s へデプロイ
```

**結論**: チームWeb開発は **Docker compose が基本（YES）**。ただし
①依存固定はロックファイルで別途、②速度のためローカル venv 併用もあり（矛盾しない）。

## 8. 一言まとめ

```
 pyenv        venv / uv / conda            Docker
   │                 │                       │
 Pythonのver     Pythonの依存・環境      環境・インフラまるごと
   └──── PC内の話 ────┘              └─ どのマシンでも同じ／デプロイ単位 ─┘
```

- **venv/conda = 「Pythonの依存」問題**
- **Docker = 「環境・インフラまるごと」問題**
- レイヤーが違うので競合せず、**よく一緒に使う**（Dockerの中で pip install、開発は compose で DB/Redis ごと）。
