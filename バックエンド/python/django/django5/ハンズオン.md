# ハンズオン：Django で「投稿一覧が表示される」までを0から作る

> **このファイルの位置づけ**：他のファイル（[getting_started.md](./getting_started.md) 等）は「分かっている人が引く辞書」。
> これは**手を動かして1回成功するための実習**。上から順にコピペすれば、0から動くところまで行けます。

## ゴール（終わったら何ができる？）
- `django-admin startproject` でプロジェクトを作り、開発サーバを起動できる
- `startapp` でアプリを作り、**モデルを定義 → `makemigrations` → `migrate`** でテーブルを作れる
- **管理画面（admin）で投稿を登録**し、**自分のビューで一覧表示**できる
- わざと **「INSTALLED_APPS 登録漏れ」「migrate 忘れ」を起こして、自分で直せる**
- ここまでやると [getting_started.md](./getting_started.md) / [models.md](./models.md) / [request_flow.md](./request_flow.md) が「読める」ようになる

**所要時間**：25〜35分　**前提**：Python 3.10+ が動くこと（`python --version` で確認）。それ以外の知識は不要。

> 用語：Django は **MTV**。**「View」＝処理（他FWのコントローラ役）**、**「Template」＝見た目**。この呼び替えだけ先に頭へ。→ [request_flow.md](./request_flow.md)

## 準備：Python が使えるか確認
```bash
python --version
```
**成功**：`Python 3.10.x` 以上が出る（`3.9` 以下なら Django 5 は動かない）。
**失敗**：
- `command not found` → `python3 --version` を試す。出たら以降 `python` を `python3` に読み替え。
- `3.9` 以下 → 3.10 以上を入れてから再実行。

作業用フォルダを作る:
```bash
mkdir -p ~/django-handson && cd ~/django-handson
```

## ステップ1：仮想環境を作って Django を入れる
**やること**：このプロジェクト専用の隔離環境（venv）を作り、その中に Django を入れる。
**なぜ**：グローバルに入れると他プロジェクトとバージョンが衝突する。プロジェクトごとに隔離するのが Python の鉄則。

```bash
python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
```
**成功**：プロンプトの先頭が `(.venv)` になる。
**失敗**：`(.venv)` が出ない → 上のコマンドを実行したシェルで続ける（別タブだと未有効）。

Django を入れる:
```bash
python -m pip install --upgrade pip
pip install "Django>=5.2,<6.0"
python -m django --version
```
**成功**：`5.2.x` が出る。
**失敗**：`(.venv)` が出ていない状態で `pip install` した → グローバルに入る。`source .venv/bin/activate` してから入れ直す。

## ステップ2：プロジェクトと開発サーバ
**やること**：`startproject` で全体設定（project）を作り、開発サーバを起動する。
**なぜ**：まず「ブラウザに Django のページが返る」状態を目で見るため。

```bash
django-admin startproject mysite .   # 末尾の . でカレントに展開（mysite/mysite/ の二重を避ける）
python manage.py migrate             # 組み込みテーブル（admin/auth等）を作成
python manage.py runserver
```
**成功**：`Starting development server at http://127.0.0.1:8000/` が出て、ブラウザで開くと**ロケット（The install worked successfully!）のページ**が出る。
**失敗**：
- `That port is already in use.` → 別ポートで起動：`python manage.py runserver 8001`。
- `command not found: django-admin` → venv が未有効。`source .venv/bin/activate` 後に再実行。

確認できたら **Ctrl+C で一度サーバを止める**（次でコードを足すため）。

---

## ステップ3：アプリを作って登録する
**やること**：`startapp` で機能単位のアプリ（blog）を作り、`settings.py` に**登録**する。
**なぜ**：Django は「設定の集合（project）」＋「機能の集合（app）」で動く。app は作っただけでは認識されず、**登録**して初めて有効になる。

```bash
python manage.py startapp blog
```

`mysite/settings.py` を開き、`INSTALLED_APPS` の末尾に `"blog",` を足す:
```python
# mysite/settings.py
INSTALLED_APPS = [
    "django.contrib.admin",
    "django.contrib.auth",
    "django.contrib.contenttypes",
    "django.contrib.sessions",
    "django.contrib.messages",
    "django.contrib.staticfiles",
    "blog",                          # ← この行を追加
]
```
> いまは登録した状態で進めます。後の「ステップ7」で**わざと外して**エラーを体験します。

---

## ステップ4：モデルを定義してテーブルを作る
**やること**：投稿（Post）のモデルを書き、`makemigrations` → `migrate` でDBにテーブルを作る。
**なぜ**：これが Django の核＝**ORM**。Python のクラスがそのままテーブルになる。→ [models.md](./models.md)

`blog/models.py` を次の内容にする:
```python
# blog/models.py
from django.db import models

class Post(models.Model):
    title = models.CharField(max_length=200)       # 文字列カラム
    body = models.TextField()                       # 長文カラム
    created_at = models.DateTimeField(auto_now_add=True)  # 作成日時を自動記録

    def __str__(self):
        return self.title          # admin等で見やすい表示名
```

マイグレーション（テーブル設計図）を作って適用:
```bash
python manage.py makemigrations blog
python manage.py migrate
```
**成功**：
- `makemigrations`：`Migrations for 'blog':` → `blog/migrations/0001_initial.py` が出る。
- `migrate`：`Applying blog.0001_initial... OK` が出る。
**失敗**：
- `makemigrations` が `No changes detected` → `INSTALLED_APPS` に `"blog"` を入れ忘れている。ステップ3に戻る。

> **要点**：モデルを足したら必ず **`makemigrations`（設計図を作る）→ `migrate`（DBに反映）** の2段。`migrate` だけではモデル変更は反映されない。→ [migrations.md](./migrations.md)

## ステップ5：管理画面に登録して、データを1件入れる
**やること**：admin に Post を登録し、管理ユーザーでログインして投稿を1件作る。
**なぜ**：Django の強みは**管理画面が自動で付く**こと。まずGUIでデータを入れて中身を確認する。→ [admin.md](./admin.md)

`blog/admin.py` を次の内容にする:
```python
# blog/admin.py
from django.contrib import admin
from .models import Post

admin.site.register(Post)      # admin に Post を表示させる
```

管理ユーザーを作る（対話式。メールは空でEnterでも可）:
```bash
python manage.py createsuperuser
```
- `Username` `Password` を入力（パスワードは画面に表示されないが入力されている）。

サーバを起動してログイン:
```bash
python manage.py runserver
```
ブラウザで **http://127.0.0.1:8000/admin/** を開き、作ったユーザーでログイン。
**成功**：`BLOG > Posts` が見える。`Posts` の「+ Add」から **タイトルと本文を入れて Save**。一覧に1件出れば成功。
**失敗**：`Posts` が出ない → `blog/admin.py` の `register` を書き忘れ。保存して再読込。

確認できたら **Ctrl+C で止める**。

## ステップ6：自分のビューで一覧を表示する（本題）
**やること**：DBの投稿を取り出し、`/posts/` で一覧表示する View と URL を作る。
**なぜ**：これが「ブラウザ → URL → View → Model(ORM) → レスポンス」という Django の流れそのもの。→ [request_flow.md](./request_flow.md)

`blog/views.py` を次の内容にする:
```python
# blog/views.py
from django.http import HttpResponse
from .models import Post

def post_list(request):
    posts = Post.objects.all().order_by("-created_at")   # ORMで全件取得（新しい順）
    lines = [f"<li>{p.title}：{p.body}</li>" for p in posts]
    html = "<h1>投稿一覧</h1><ul>" + "".join(lines) + "</ul>"
    return HttpResponse(html)        # View は HttpResponse を返す
```

アプリ用の `blog/urls.py` を**新規作成**する:
```python
# blog/urls.py
from django.urls import path
from . import views

urlpatterns = [
    path("posts/", views.post_list, name="post_list"),   # /posts/ → post_list
]
```

ルートの `mysite/urls.py` から `blog/urls.py` を繋ぐ:
```python
# mysite/urls.py
from django.contrib import admin
from django.urls import path, include      # include を追加

urlpatterns = [
    path("admin/", admin.site.urls),
    path("", include("blog.urls")),         # この行を追加
]
```

起動して確認:
```bash
python manage.py runserver
```
```bash
# 別タブで（サーバは起動したまま）
curl -s http://127.0.0.1:8000/posts/
```
**成功**：`<h1>投稿一覧</h1>` とステップ5で入れた投稿が `<li>` で返る。
→ **これが「URL → View → ORM → レスポンス」が繋がった証拠**。
**失敗**：
- `Page not found (404)` → `mysite/urls.py` の `include("blog.urls")` を書き忘れ、または `/posts/` の末尾スラッシュ抜け。
- 何も投稿が出ない → ステップ5で Save していない。admin で1件入れる。

## ステップ7：わざと「INSTALLED_APPS 登録漏れ」「migrate 忘れ」を起こして直す
**なぜ**：この2つは Django 初心者が必ずハマる定番エラー。「自分で起こして直す」と一生忘れない。

### 7-1. INSTALLED_APPS 登録漏れ
サーバを Ctrl+C で止め、`mysite/settings.py` の `"blog",` を**一時的にコメントアウト**する:
```python
    # "blog",                        # ← わざと無効化
```
モデルにカラムを足してみる（`blog/models.py` の `Post` に1行追加）:
```python
    author = models.CharField(max_length=50, default="anon")   # 追加
```
```bash
python manage.py makemigrations blog
```
**結果**：`No changes detected in app 'blog'`。
**読み解き**：app が `INSTALLED_APPS` に居ないと、Django はそのモデルを**見ていない**。だから変更も検知されない。これが「モデルを変えたのに反映されない」の典型原因。

**直す**：`settings.py` の `"blog",` のコメントを外す → 再実行:
```bash
python manage.py makemigrations blog
```
**成功**：今度は `Migrations for 'blog':` が出て新しいマイグレーションが作られる。

### 7-2. migrate 忘れ
**makemigrations した直後、まだ migrate していない状態**でアクセスしてみる:
```bash
python manage.py runserver
```
```bash
curl -s http://127.0.0.1:8000/posts/ | head -20
```
**結果**：`OperationalError` 系のエラー（`no such column: blog_post.author` のような行）が返る。
**読み解き**：`makemigrations`（設計図）は作ったが `migrate`（DBに反映）していないので、DBの実テーブルに `author` カラムが無い。**設計図とDBがズレている**状態。

**直す**：Ctrl+C で止め、`migrate` してから再起動:
```bash
python manage.py migrate
python manage.py runserver
```
```bash
curl -s http://127.0.0.1:8000/posts/
```
**成功**：エラーが消えて一覧が返る。→ **「makemigrations → migrate の2段」が腹落ちした**。
