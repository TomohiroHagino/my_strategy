# ハンズオン：Hanami 2 で 0 からアクションを1つ動かす

> **このファイルの位置づけ**：他のファイル（[getting_started.md](./getting_started.md) / [actions.md](./actions.md) 等）は「分かっている人が引く辞書」。
> これは**手を動かして1回成功するための実習**。上から順にコピペすれば、0から動くところまで行けます。

## ゴール（終わったら何ができる？）
- `hanami new` でアプリを作り、`hanami server` で**ブラウザに表示**できる
- **ルート（`config/routes.rb`）とアクション（1クラス）**を1つ書いて、URL に応答できる
- わざと **アクション登録漏れ（ルートとクラス名のズレ）** を起こして、自分で直せる
- ここまでやると [routing.md](./routing.md) / [actions.md](./actions.md) / [dependency_injection.md](./dependency_injection.md) が「読める」ようになる

**所要時間**：20〜30分　**前提**：Docker が動くこと（Ruby を自分で入れる必要はありません）

---

## 準備：Docker が使えるか確認
```bash
docker version
```
**成功**：`Client:` と `Server:` の両方にバージョンが出る。
**失敗**：`Cannot connect to the Docker daemon` → Docker Desktop（またはdockerサービス）が起動していない。起動してから再実行。

作業用フォルダを作る:
```bash
mkdir -p ~/hanami-handson && cd ~/hanami-handson
```

---

## ステップ1：Ruby が入ったコンテナに入る
**やること**：Ruby が最初から入った公式イメージのコンテナに入り、その中で作業する。
**なぜ**：自分のPCに Ruby や Hanami を入れなくても、コンテナの中なら同じ環境がすぐ手に入るため。
```bash
docker run -it --name hanami-dev \
  -p 2300:2300 \
  -v "$PWD:/work" -w /work \
  ruby:3.2 bash
```
- `-p 2300:2300`＝PCの2300番をコンテナの2300番に繋ぐ（Hanami の既定ポート）。
- `-v "$PWD:/work" -w /work`＝今のフォルダをコンテナの `/work` に貸して、そこを作業場所にする。

**成功**：プロンプトが `root@xxxx:/work#` に変わる。
**失敗**：`port is already allocated` → 2300番が使用中。`exit` して `-p 2301:2300` に変えて再実行（その場合ブラウザは http://localhost:2301）。

> **以降の `#` で始まるコマンドは、すべてこのコンテナの中で実行**します。

Hanami をインストール:
```bash
gem install hanami hanami-cli
hanami version
```
**成功**：`v2.x.x` のように表示される。
**失敗**：`Could not find...` → ネットワーク未接続。接続を確認して再実行。

---

## ステップ2：アプリを作って起動し、ブラウザで見る
**やること**：`hanami new` で雛形を生成し、`hanami server` で起動する。
**なぜ**：「Hanami アプリが起動してブラウザに出る」状態をまず目で確認するため。

アプリを生成:
```bash
hanami new bookshelf
cd bookshelf
bundle install
```
- `bookshelf` がアプリ名。この名前がそのままトップのモジュール名 `Bookshelf` になる（後で使う）。
- Hanami 2 は `app/` が中心。`config/routes.rb` にルート、`app/actions/` にアクションを置く。

**成功**：`bookshelf/` フォルダができ、`bundle install` の最後に `Bundle complete!` が出る。

サーバを起動（コンテナ外から繋がるよう全アドレスで待ち受ける）:
```bash
hanami server --host 0.0.0.0
```
- `--host 0.0.0.0`＝コンテナの外（あなたのブラウザ）からアクセスできるようにする。**これを忘れるとブラウザから繋がらない**。

ブラウザで **http://localhost:2300** を開く。
**成功**：Hanami の初期ページ（"Hello from Hanami" のような表示）が出る。
**失敗**：
- ページが出ない → `--host 0.0.0.0` を付け忘れていないか確認。
- 起動しない → `bundle install` 漏れ。`Ctrl + C` で止めて再実行。→ [getting_started.md](./getting_started.md)

確認できたらサーバを止める（`Ctrl + C`）。

---

## ステップ3：ルートとアクションを1つ書く（本題）
**やること**：`/hello` に応答するルートと、それに対応するアクションクラスを書く。
**なぜ**：Hanami 2 の核「**ルートの `to:` がアクションのキーを指し、それが1クラスに対応する**」を体験するため。

### 3-1. ルートを足す
`config/routes.rb` に1行追加する:
```bash
cat > config/routes.rb <<'EOF'
# frozen_string_literal: true

module Bookshelf
  class Routes < Hanami::Routes
    root to: "home.show"

    # /hello で来たら hello.index アクションへ渡す
    get "/hello", to: "hello.index"
  end
end
EOF
```
- `to: "hello.index"` ＝**アクションのコンテナキー**。ドット区切りで、`Actions` を起点に `Hello::Index` を指す。Rails の `"home#index"`（`#`区切り）とは違い、Hanami は `.`（ドット）。→ [routing.md](./routing.md)

### 3-2. 対応するアクションクラスを置く
ルートの `to:` が指す `app/actions/hello/index.rb` を作る:
```bash
mkdir -p app/actions/hello
cat > app/actions/hello/index.rb <<'EOF'
# frozen_string_literal: true

module Bookshelf
  module Actions
    module Hello
      class Index < Bookshelf::Action
        def handle(request, response)
          response.body = "Hello from a Hanami action!"
        end
      end
    end
  end
end
EOF
```
- **重要な対応関係**：`to: "hello.index"` のドット（`hello` → `index`）が、そのままモジュールのネスト（`Hello` → `Index`）とファイルパス（`app/actions/hello/index.rb`）に一致する。Hanami のオートロード（Zeitwerk）はこの一致を前提にする。
- 結果は**戻り値ではなく `response.body = ...` への代入で返す**（`handle(request, response)` のシグネチャは固定）。→ [actions.md](./actions.md)

### 3-3. 起動して確認
```bash
hanami server --host 0.0.0.0
```
ブラウザで **http://localhost:2300/hello** を開く。
**成功**：`Hello from a Hanami action!` が表示される。→ ルートとアクションが1本つながった。
**失敗**：エラーが出る → 次のステップで扱う（むしろ好都合）。

確認できたらサーバを止める（`Ctrl + C`）。

## ステップ4：わざと「アクション登録漏れ（クラス名のズレ）」を起こして、直す
**なぜ**：Hanami で最初に必ずハマるのが「ルートの `to:` と、アクションのクラス名・ファイルパスのズレ」。**自分で起こして直す**と一生忘れない。

ルートはそのままに、**アクションのモジュール名をわざと単数形に間違える**:
```bash
cat > app/actions/hello/index.rb <<'EOF'
# frozen_string_literal: true

module Bookshelf
  module Actions
    module Hell        # ← わざと "Hello" を "Hell" にズラす
      class Index < Bookshelf::Action
        def handle(request, response)
          response.body = "Hello from a Hanami action!"
        end
      end
    end
  end
end
EOF
hanami server --host 0.0.0.0
```
ブラウザで **http://localhost:2300/hello** を開く。
**結果**：`uninitialized constant` / `NameError` 系のエラー、または `"hello.index" is not registered`（アクションが解決できない）というエラーが出る。
**読み解き**：ルートは `to: "hello.index"` で `Bookshelf::Actions::Hello::Index` を探しに行くのに、ファイル内のモジュールは `Hell`（＝`Hello::Index` が存在しない）。**ルートの `to:` の各セグメントと、モジュールのネスト・ファイルパスが一致していない**のが原因。

直す（モジュール名を `Hello` に戻す）:
```bash
cat > app/actions/hello/index.rb <<'EOF'
# frozen_string_literal: true

module Bookshelf
  module Actions
    module Hello       # ← 正しい名前に戻す
      class Index < Bookshelf::Action
        def handle(request, response)
          response.body = "Hello from a Hanami action!"
        end
      end
    end
  end
end
EOF
```
サーバが自動リロードされた後（されない場合は `Ctrl + C` → 再起動）、**http://localhost:2300/hello** を再読み込み。
**成功**：また `Hello from a Hanami action!` が返る。→ 「`to:` の文字列＝モジュールのネスト＝ファイルパス」を一致させる、という Hanami の規約を体験で理解できた。

> 実務でも `to: "books.index"` と書いたのにファイルが `app/actions/book/index.rb`（単数）だった、名前空間が欠けていた、で同じエラーに出会う。**ドットの各セグメント＝モジュールのネスト**と機械的に対応させるのが定石。→ [routing.md](./routing.md) / [actions.md](./actions.md)

## 片付け
サーバを止めて（`Ctrl + C`）、コンテナから出る:
```bash
exit
```
コンテナを消す（作ったファイルは `~/hanami-handson/bookshelf` に残ります）:
```bash
docker rm -f hanami-dev
# フォルダごと消すなら: rm -rf ~/hanami-handson
```
