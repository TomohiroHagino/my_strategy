# ハンズオン：Sinatra で 0 から API を1つ動かす

> **このファイルの位置づけ**：他のファイル（[getting_started.md](./getting_started.md) / [routing.md](./routing.md) 等）は「分かっている人が引く辞書」。
> これは**手を動かして1回成功するための実習**。上から順にコピペすれば、0から動くところまで行けます。

## ゴール（終わったら何ができる？）
- `Gemfile` と `app.rb` を書いて、Sinatra を **起動できる**
- `curl` で叩いて **テキストと JSON を返せる**
- わざと **ポート競合** と **未定義ルートの 404** を起こして、自分で直せる
- ここまでやると [getting_started.md](./getting_started.md) / [routing.md](./routing.md) / [request_response.md](./request_response.md) が「読める」ようになる

**所要時間**：15〜20分　**前提**：Docker が動くこと（Ruby を自分で入れる必要はありません）

---

## 準備：Docker が使えるか確認
```bash
docker version
```
**成功**：`Client:` と `Server:` の両方にバージョンが出る。
**失敗**：`Cannot connect to the Docker daemon` → Docker Desktop（またはdockerサービス）が起動していない。起動してから再実行。

作業用フォルダを作る:
```bash
mkdir -p ~/sinatra-handson && cd ~/sinatra-handson
```

---

## ステップ1：Ruby が入ったコンテナに入る
**やること**：Ruby が最初から入った公式イメージのコンテナに入り、その中で作業する。
**なぜ**：自分のPCに Ruby を入れなくても、コンテナの中なら同じ環境がすぐ手に入るため。
```bash
docker run -it --name sinatra-dev \
  -p 4567:4567 \
  -v "$PWD:/work" -w /work \
  ruby:3.2 bash
```
- `-p 4567:4567`＝PCの4567番をコンテナの4567番に繋ぐ（Sinatra classic の既定ポート）。
- `-v "$PWD:/work" -w /work`＝今のフォルダをコンテナの `/work` に貸して、そこを作業場所にする。

**成功**：プロンプトが `root@xxxx:/work#` に変わる。
**失敗**：`port is already allocated` → 4567番が使用中。`exit` して `-p 4568:4567` に変えて再実行（その場合ブラウザ/curl は 4568 を使う）。

> **以降の `#` で始まるコマンドは、すべてこのコンテナの中で実行**します。

---

## ステップ2：Gemfile を書いて依存を入れる
**やること**：使う gem（Sinatra 本体・サーバ・rackup）を `Gemfile` に書いて入れる。
**なぜ**：Sinatra はマイクロFWで「必要な物だけ自分で足す」ため、最初に依存を明示する。
```bash
cat > Gemfile <<'EOF'
source "https://rubygems.org"
gem "sinatra", "~> 4.0"   # 3系なら "~> 3.0"
gem "puma"                 # 本番想定の定番サーバ
gem "rackup"               # rackup コマンド（Rack 3 で別gem化）
gem "json"                 # JSON 出力用
EOF
bundle install
```
**成功**：最後に `Bundle complete!` が出る。
**失敗**：`Could not find...` → ネットワーク未接続。接続を確認して再実行。

---

## ステップ3：app.rb に1ルート書いて起動する
**やること**：`get "/" do ... end` を1つ書いて、Sinatra を起動する。
**なぜ**：Sinatra の身上「URL ↔ 処理を数行で書く」を体験するため。
```bash
cat > app.rb <<'EOF'
require "sinatra"

# コンテナの外（curl/ブラウザ）から繋がるよう全アドレスで待ち受ける
set :bind, "0.0.0.0"

get "/" do
  "Hello, Sinatra!"
end
EOF
```
- `require "sinatra"` だけで `get` などの DSL がトップレベルに生える（これが **classic スタイル**）。
- `set :bind, "0.0.0.0"` を入れないと、コンテナの中だけで待ち受けてしまい外から繋がらない。

起動:
```bash
ruby app.rb
```
**成功**：`Puma starting...` と `Listening on http://0.0.0.0:4567` のような行が出て、入力待ちになる。

別の操作をするため、**もう1つ別のターミナル**を開いて、同じコンテナに入る:
```bash
docker exec -it sinatra-dev bash
```
そのターミナルで叩く:
```bash
curl -s http://localhost:4567/
```
**成功**：`Hello, Sinatra!` が返る。→ 「URL ↔ 処理」が1本つながった。
**失敗**：`Connection refused` → `set :bind, "0.0.0.0"` を書き忘れている。app.rb を直して起動し直す。

## ステップ4：JSON を返すルートを足す
**やること**：`/api/hello` で JSON を返すルートを追加する。
**なぜ**：小さな REST API＝Sinatra の一番の用途を体験するため。

最初のターミナルで `Ctrl + C` を押してサーバを止め、app.rb を書き換える:
```bash
cat > app.rb <<'EOF'
require "sinatra"
require "json"

set :bind, "0.0.0.0"

get "/" do
  "Hello, Sinatra!"
end

get "/api/hello" do
  content_type :json
  { message: "Hello, JSON!", framework: "Sinatra" }.to_json
end
EOF
ruby app.rb
```
- `content_type :json` ＝「これは JSON だ」とレスポンスヘッダで宣言する。
- `.to_json` ＝Rubyのハッシュを JSON 文字列にする。

別ターミナルで確認:
```bash
curl -s http://localhost:4567/api/hello
```
**成功**：`{"message":"Hello, JSON!","framework":"Sinatra"}` が返る。
**失敗**：`Sinatra doesn't know this ditty` という HTML が返る → ルートのパス（`/api/hello`）の打ち間違い。app.rb と curl の URL を見比べる。

## ステップ5：わざと「ポート競合」と「未定義ルートの404」を起こして、直す
**なぜ**：どちらも Sinatra でよく出会う失敗。**自分で起こして直す**と一生忘れない。

### 5-1. ポート競合（Address already in use）
サーバは**止めずに動かしたまま**、別ターミナルで**もう1つ** app.rb を起動してみる:
```bash
ruby app.rb
```
**結果**：`Address already in use - bind(2) for "0.0.0.0" port 4567`（Errno::EADDRINUSE）で起動に失敗する。
**読み解き**：4567番ポートは**1つのプロセスしか使えない**。すでに起動中なのに、もう1つ同じポートで起動しようとしたのが原因。
**直す**：別ポートで起動する。
```bash
ruby app.rb -p 4568
```
**成功**：今度は `Listening on http://0.0.0.0:4568` で起動できる（PCからは見えないが、コンテナ内 `curl http://localhost:4568/` で確認できる）。実務では「すでに起動中のプロセスを止める」か「別ポートを使う」の二択。確認できたら `Ctrl + C` で止める。

### 5-2. 未定義ルートの 404（Sinatra::NotFound）
最初のサーバ（4567番）が動いている状態で、**定義していないURL**を叩く:
```bash
curl -i http://localhost:4567/nothing-here
```
**結果**：1行目が `HTTP/1.1 404 Not Found`。本文に `Sinatra doesn't know this ditty.` が出る。
**読み解き**：マッチするルートが `app.rb` に**無い**と 404（`Sinatra::NotFound`）になる。
**直す（共通の404ハンドラを用意する）**：サーバを止めて app.rb の末尾に追記する。
```bash
cat >> app.rb <<'EOF'

not_found do
  content_type :json
  { error: "not found" }.to_json
end
EOF
ruby app.rb
```
別ターミナルで再確認:
```bash
curl -i http://localhost:4567/nothing-here
```
**成功**：404 は変わらないが、本文が `{"error":"not found"}` になる。→ 404の原因＝「そのURLのルートが未定義」を体験で理解できた。

> 実務でも404は「ルート定義漏れ」「パスのタイポ」「`/users` と `/users/`（末尾スラッシュ違い）」で起きる。→ [routing.md](./routing.md)

## 片付け
最初のターミナルで `Ctrl + C` を押してサーバを止め、コンテナから出る:
```bash
exit
```
コンテナを消す（app.rb / Gemfile は `~/sinatra-handson` に残ります）:
```bash
docker rm -f sinatra-dev
# フォルダごと消すなら: rm -rf ~/sinatra-handson
```
