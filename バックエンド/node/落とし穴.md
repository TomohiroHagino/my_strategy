# Node.js 特有の現象と対策（落とし穴カタログ）

> **サーバで JS を動かす Node ならでは**の現象を「現象 / なぜ起きる / 対策」で。
> JS共通の罠（巻き上げ・`this`・クロージャ・`==`・浮動小数・コールバック地獄・await漏れ・未処理reject等）は土台側 → **[../../フロントエンド/javascript/落とし穴.md](../../フロントエンド/javascript/落とし穴.md)**。TS固有 → [../../フロントエンド/typescript/落とし穴.md](../../フロントエンド/typescript/落とし穴.md)。ここはランタイム/サーバ文脈に絞る。

---

## 1. イベントループを塞ぐ＝全リクエスト停止
**現象**：1つの重い同期処理（巨大ループ・同期暗号・巨大JSON `JSON.parse`・正規表現の暴走）が走ると、その間**全ユーザーのリクエストが固まる**。
**なぜ**：Node は**シングルスレッドのイベントループ**。同期処理が走っている間、他のコールバックを一切拾えない（ブラウザのUIフリーズのサーバ版）。
```js
// NG: リクエストハンドラ内で重い同期計算 → 他リクエストも待たされる
app.get("/calc", (req, res) => { res.json(heavySyncLoop()); });
```
**対策**：
- 重いCPU処理は **Worker Threads** / 別プロセス / ジョブキューに逃がす。
- 同期API（`fs.readFileSync`・`crypto.pbkdf2Sync` 等）をホットパスで使わない。**非同期版**を使う。
- 正規表現の **ReDoS**（壊滅的バックトラッキング）に注意。入力長制限・安全なパターン。
- 監視: イベントループ遅延（`perf_hooks` の `monitorEventLoopDelay`）を計測。

## 2. 未処理のPromiseリジェクトでプロセスがクラッシュ
**現象**：どこかの `async` の失敗を誰も `catch` せず、`unhandledRejection` でプロセスが落ちる（Nodeの新しめの版は既定でクラッシュ）。
**なぜ**：reject は同期 `throw` と違い、`await`/`.catch()` が無いと伝播先が無い。`setInterval(async ...)` や `app.get('/x', async ...)` で投げた例外は外に出ない経路がある。
**対策**：
- すべての `async` 呼び出しを `await`（try/catch内）か `.catch()`。
- **Express 5** は async ハンドラの例外を自動でエラーミドルウェアへ流す（Express 4 は `express-async-errors` 等のラッパが必要）→ [express/express5/error_handling.md](./express/express5/error_handling.md)。
- 最後の砦：`process.on('unhandledRejection', ...)` と `uncaughtException` でログ＋安全に再起動（握りつぶさない）。

## 3. CommonJS と ESM の混在
**現象**：`require` と `import` を混ぜて `ERR_REQUIRE_ESM`／`Cannot use import statement outside a module`／`__dirname is not defined`（ESM）など。
**なぜ**：Node は **CJS（`require`/`module.exports`）と ESM（`import`/`export`）の2系統**。`package.json` の `"type"` と拡張子（`.cjs`/`.mjs`）で解決が変わる。ESM では `__dirname`/`require` が無い。
**対策**：
- プロジェクトでどちらかに統一（新規は ESM 寄り）。`"type": "module"` を明示。
- ESM で `__dirname` 相当は `import.meta.url` から `fileURLToPath` で作る。
- ESM の `import` は**非同期解決＋トップレベル await可**。CJSの同期 `require` と挙動が違う点を理解。

## 4. ストリームのバックプレッシャ無視でメモリ爆発
**現象**：大きなファイル/レスポンスを一気に読み込み or `data` を貯め込んでメモリ枯渇（OOM）。
**なぜ**：読み込みが書き込みより速いと、消費しきれないデータがバッファに溜まる（バックプレッシャ）。
**対策**：**`pipeline`（`stream/promises`）/ `.pipe()`** で連結し、バックプレッシャを自動処理させる。手書きで `on('data')` を貯め込まない。巨大JSONはストリームパーサで小分け。

## 5. error-first コールバック地獄（歴史的）
**現象**：古いNode API（`fs.readFile(path, (err, data) => ...)` 等）を入れ子で繋いで深くなる。
**なぜ**：Node黎明期のAPIは**error-firstコールバック**規約。合成手段がコールバックしかなかった。
**対策**：`util.promisify` でPromise化、または `fs/promises` 等の **Promise版API**を使い `async/await` に。詳しくは [../../フロントエンド/javascript/落とし穴.md](../../フロントエンド/javascript/落とし穴.md) のコールバック地獄。

## 6. EventEmitter のリスナーリーク
**現象**：`MaxListenersExceededWarning` 警告、長時間稼働でメモリ増。
**なぜ**：`on()` でリスナーを登録し続け、`off()`/`removeListener` で外さないと溜まる（リクエスト毎に登録すると致命的）。
**対策**：使い終わったら `off()`。一回だけなら `once()`。`AbortController`/`signal` でまとめて解除。閾値は `setMaxListeners` だが、まず登録過多の設計を疑う。

## 7. `process.nextTick` / マイクロタスク と `setImmediate` / `setTimeout`
**現象**：実行順序が直感とずれる。`nextTick` を再帰的に積むとI/Oが永遠に後回し（飢餓）。
**なぜ**：`process.nextTick` とPromiseのマイクロタスクは**現在の処理直後・I/Oより先**に走る。`setImmediate` はI/Oフェーズ後、`setTimeout` はタイマーフェーズ。
**対策**：順序に依存しない設計。`nextTick` の多用を避け、譲りたいなら `setImmediate`。重い処理の合間にイベントループへ制御を返す。

## 8. シングルプロセスでCPU/コアを使い切れない
**現象**：マルチコアなのに1コアしか使われず、スループットが頭打ち。
**なぜ**：Nodeは1プロセス1スレッドで実行（イベントループ）。
**対策**：**`cluster`** か **PM2** でコア数分のワーカーを立てる、またはコンテナを水平スケール（ロードバランサ配下に複数インスタンス）。CPU処理は Worker Threads。

## 9. 環境変数・秘密情報・依存の罠
**現象**：`process.env.X` が `undefined`（読み込み順）、秘密がログ/リポジトリに漏れる、`npm install` で意図せぬ更新。
**なぜ**：`.env` の読み込み前に参照、キーのハードコード、`^`/`~` のバージョン緩さ。
**対策**：環境変数は起動時に検証（zod等）。**秘密はコードに書かず環境変数/シークレットマネージャ**（このリポジトリのセキュリティ方針）。`package-lock.json` をコミットし `npm ci` で再現。
