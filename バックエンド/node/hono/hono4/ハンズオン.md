# ハンズオン：Hono で `c.json()` を返し、`app.request()` で確認する

> **このファイルの位置づけ**：他のファイル（[getting_started.md](./getting_started.md) 等）は「分かっている人が引く辞書」。
> これは**手を動かして1回成功するための実習**。上から順にコピペすれば、0から動くところまで行けます。

## ゴール（終わったら何ができる？）
- `npm create hono@latest`（Nodeランタイム）で雛形を作り、`npm run dev` で**起動できる**
- `c.json()` で JSON を返し、`c.req.param()` で**パラメータを受け取れる**
- サーバを立てずに **`app.request()` でルートを呼んで確認**できる（Honoならではのテスト入口）
- わざと **ランタイム取り違え（Workers向けコードをNodeで動かす）/ ポート競合を起こして、自分で直せる**
- ここまでやると [getting_started.md](./getting_started.md) / [context.md](./context.md) / [runtimes.md](./runtimes.md) が「読める」ようになる

**所要時間**：20〜30分　**前提**：Node.js 18 以上が動くこと（`node -v` で確認）。それ以外の知識は不要。

> Hono は「**マルチランタイムの薄いルータ + Context `c`**」。ルート定義はどこでも同じ書き方、違うのは**起動の仕方**だけ。→ [runtimes.md](./runtimes.md)

## 準備：Node が使えるか確認
```bash
node -v
```
**成功**：`v18.x` 以上が出る。
**失敗**：`command not found` または18未満 → Node 18以上を入れる（`nvm install 20` 等）。

作業用フォルダの親:
```bash
mkdir -p ~/hono-handson && cd ~/hono-handson
```

## ステップ1：テンプレから雛形を作る（Nodeランタイム）
**やること**：`npm create hono@latest` で対話式に雛形を作る。**ランタイムは `nodejs` を選ぶ**。
**なぜ**：Hono はランタイムごとに「起動コード」が違う。テンプレがその差分（`@hono/node-server` 等）を用意してくれる。最初はテンプレに乗るのが正解。

```bash
npm create hono@latest my-app
```
対話で聞かれたら:
- **Which template do you want to use?** → `nodejs` を選ぶ（矢印キーで選んで Enter）
- **Do you want to install project dependencies?** → `yes`
- パッケージマネージャ → `npm`

```bash
cd my-app
```
**成功**：`src/index.ts` `package.json` `tsconfig.json` がある。`package.json` に `"type": "module"` と `@hono/node-server` が入っている。
**失敗**：
- ネットワークエラーで止まる → 少し待って再実行。
- `nodejs` 以外（cloudflare-workers 等）を選んでしまった → `cd .. && rm -rf my-app` でやり直し。**このハンズオンは Node 前提**。

## ステップ2：起動して叩く
**やること**：`npm run dev` で開発サーバを立て、`curl` で叩く。
**なぜ**：まず「Honoアプリが HTTP で応答する」状態を確認するため。

```bash
npm run dev
```
**成功**：`Server is running on http://localhost:3000`（テンプレにより文言は多少違う）が出る。別タブで:
```bash
curl -s http://localhost:3000/
```
→ `Hello Hono!` が返る。
**失敗**：
- `address already in use` → ステップ5でわざと起こす内容。今は他のプロセスを止める。
- 何も出ない／起動しない → `npm run dev` のログにエラーが出ていないか確認。

Ctrl+C で止める。

## ステップ3：`c.json()` で JSON を返す
**やること**：JSON を返すルートを足す。
**なぜ**：Hono は Context `c` 1つで入出力を扱う。`c.json()` が基本の返し方。**`return` を忘れない**のが肝。→ [context.md](./context.md)

`src/index.ts` を開く。`import` と `const app = new Hono()` はそのままに、ルートを足す。テンプレの中身はこんな形のはず:
```ts
import { Hono } from 'hono'
import { serve } from '@hono/node-server'   // Nodeテンプレなら起動用にこれがある

const app = new Hono()

app.get('/', (c) => c.text('Hello Hono!'))

// ★ここから追記
app.get('/api/health', (c) => {
  return c.json({ status: 'ok', time: new Date().toISOString() })   // return を忘れない
})
// ★ここまで追記

serve({ fetch: app.fetch, port: 3000 }, (info) => {
  console.log(`Server is running on http://localhost:${info.port}`)
})
```
> テンプレによっては `export default app` 形式のこともある。その場合は `app.get(...)` の追記だけ行えばよい（`serve` 部分はテンプレに従う）。

起動して確認:
```bash
npm run dev
```
```bash
curl -s http://localhost:3000/api/health
```
**成功**：`{"status":"ok","time":"2026-..."}` が返る。
**失敗**：空レスポンス → **`return` を忘れている**。`return c.json(...)` にする。ハンドラは Response を**返す**必要がある。

Ctrl+C で止める。

## ステップ4：パラメータ `/users/:id` と、`app.request()` での確認（本題）
**やること**：ルートパラメータを受け取るルートを足し、**サーバを立てずに `app.request()` で呼んで確認**する。
**なぜ**：Hono は Web標準の `Request`/`Response` ベースなので、`app.request('/path')` でハンドラを直接叩ける。テストやデバッグの強力な入口。→ [context.md](./context.md)

`src/index.ts` にルートを追記:
```ts
app.get('/users/:id', (c) => {
  const id = c.req.param('id')             // :id を取り出す
  return c.json({ userId: id, name: `user-${id}` })
})
```
**まずサーバ経由で確認**:
```bash
npm run dev
```
```bash
curl -s http://localhost:3000/users/1
```
**成功**：`{"userId":"1","name":"user-1"}` が返る。Ctrl+C で止める。

**次にサーバ無しで `app.request()` を試す**。確認用スクリプト `check.ts` を `src/` に作る:
```ts
// src/check.ts
import { Hono } from 'hono'

const app = new Hono()
app.get('/users/:id', (c) => {
  const id = c.req.param('id')
  return c.json({ userId: id, name: `user-${id}` })
})

// サーバを立てずにルートを直接呼ぶ
const res = await app.request('/users/42')   // Response が返る
console.log('status:', res.status)
console.log('body:', await res.json())
```
実行（テンプレに入っている tsx で動かす）:
```bash
npx tsx src/check.ts
```
**成功**：
```
status: 200
body: { userId: '42', name: 'user-42' }
```
→ **これが「サーバを立てずにルートを呼べる」証拠**。テストでもこの `app.request()` をそのまま使う。→ [vitest.md](./vitest.md)
**失敗**：`tsx: not found` → `npx tsx ...` で実行する（テンプレの devDependencies に tsx がある）。無ければ `npm i -D tsx`。

## ステップ5：わざと「ランタイム取り違え」「ポート競合」を起こして直す
**なぜ**：Hono 初心者が必ず出会うのが「ランタイムの取り違え」。「自分で起こして直す」と一生忘れない。

### 5-1. ランタイム取り違え（Workers向けの起動を Node でやる）
Node ランタイムでは `serve({ fetch: app.fetch })` で HTTP サーバを自前起動する必要がある。一方 Workers/Bun/Deno は `export default app` だけで動く（`serve` は不要）。**この2つを取り違える**のが定番事故。

`src/index.ts` の `serve(...)` の**ブロックをコメントアウト**し、代わりに Workers 流の `export default` を置く:
```ts
// serve({ fetch: app.fetch, port: 3000 }, (info) => {
//   console.log(`Server is running on http://localhost:${info.port}`)
// })

export default app          // ← Workers/Bun/Deno 用。Node では listen しない
```
起動:
```bash
npm run dev
```
**結果**：エラーなく終了するか、起動ログが出ても **`curl http://localhost:3000/` が `Connection refused`**。
```bash
curl -s -i http://localhost:3000/        # つながらない
```
**読み解き**：`export default app` は「fetch ハンドラの定義」を渡すだけ。**Node には HTTP サーバを自前で立てる仕組みが無い**ので、誰も 3000 番で listen していない。だからつながらない。Workers ならランタイム側が listen してくれるが、Node は違う。

**直す**：`serve(...)` を復活させ、`export default app` を消す:
```ts
serve({ fetch: app.fetch, port: 3000 }, (info) => {
  console.log(`Server is running on http://localhost:${info.port}`)
})
```
```bash
npm run dev
```
```bash
curl -s http://localhost:3000/
```
**成功**：また `Hello Hono!` が返る。→ **「Node は `serve()` 必須・Workersは `export default`」が腹落ちした**。

### 5-2. ポート競合
**サーバを起動したまま**、別タブでもう1つ起動する:
```bash
npm run dev          # 2つ目
```
**結果**：`EADDRINUSE: address already in use 0.0.0.0:3000`（文言は環境差あり）。
**読み解き**：3000番は1プロセス占有。すでに掴んでいるプロセスがいる。

**直す**：`serve()` の `port` を変えるか、犯人を止める:
```bash
# A) 犯人を止める（mac/Linux）
lsof -i :3000        # PID 確認
kill <PID>

# B) ポートを変える：src/index.ts の serve(...) の port を 3001 にして再起動
```
**成功**：B なら 3001 で起動し `curl http://localhost:3001/` が返る。→ **「ポートは1プロセス占有」を体験**。
