# RAG（検索拡張生成 / Retrieval-Augmented Generation）

## ひとことで言うと
**「質問に関係する文書をまず検索して、その文章をプロンプトに貼り付けてからLLMに答えさせる」** 仕組み。
LLM の弱点である**知識のカットオフ・社内データを知らない・ハルシネーション**を、**学習せずに**埋める定番手段。「LLMに自社データで答えさせたい」のほぼ第一選択。

## なぜ必要か / どこで効くか
- LLM は学習時点までの一般知識しか持たない。**社内規程・最新仕様・ユーザー固有データ**は知らない。
- それらを**ファインチューニングで覚えさせるのは高コスト・更新が大変**。RAG なら**データを差し替えるだけ**で即反映。
- 根拠文書を一緒に渡すので**出典を示せる＝検証・信頼につながる**（「どの文書に基づくか」を返せる）。

> 原則：**最新性・出典が要る → RAG**。**振る舞い/口調/形式を変えたい → プロンプト or ファインチューニング**。RAGは「知識を渡す」手段で「賢くする」手段ではない。

---

## 全体の流れ（2フェーズ）
```
【事前（インデックス作成）】1回 or 定期
 文書 → チャンク分割 → 各チャンクを embedding でベクトル化 → ベクトルDBに保存

【実行（クエリ時）】毎リクエスト
 質問 → embedding でベクトル化 → ベクトルDBで近いチャンクを検索(top-k)
        → 取れた文書をプロンプトの文脈ブロックに注入 → LLM が文書に基づき回答（+出典）
```

## 埋め込み（Embedding）
- テキストを**意味を表す数百〜数千次元のベクトル**に変換したもの。**意味が近い文どうしはベクトルが近い**。
- 検索は「キーワード一致」ではなく**意味の近さ（コサイン類似度など）**で行う＝言い換え・表記ゆれに強い。
- 埋め込みモデルは**クエリ側と文書側で同じモデル**を使う。モデルを変えたら**全文書を作り直す**（混ぜると検索が壊れる）。

## ベクトルDB / 保存先
| 選択肢 | 立ち位置 |
|---|---|
| **pgvector**（PostgreSQL拡張） | 既にPostgresがあるなら最有力。**RDBと同じ場所**でメタデータと一緒に管理できる |
| 専用ベクトルDB（Pinecone / Qdrant / Weaviate / Milvus 等） | 大規模・高QPS・高度なフィルタが要るとき |
| 全文検索エンジン（Elasticsearch/OpenSearch） | キーワード検索＋ベクトルの**ハイブリッド**を1つで |
| インメモリ（FAISS等） | 小規模・PoC・バッチ |

> まずは **pgvector で十分**なことが多い（→ [../データベース/postgresql.md](../データベース/postgresql.md)）。「専用DBが要る」と分かってから移す（YAGNI）。

## チャンク分割（ここで品質が決まる）
長い文書を**検索単位の小片（チャンク）**に切る。**切り方が検索精度を一番左右する**。
- **大きすぎ** → 1チャンクに無関係な内容が混じり、ノイズで精度低下＋トークン浪費。
- **小さすぎ** → 文脈が切れて意味が失われる（表や前後依存が壊れる）。
- 目安：**数百トークン**＋**オーバーラップ**（隣と少し重ねて文脈の断絶を防ぐ）。
- **構造で切る**：見出し・段落・コード単位など、**意味の境界**で切る方が固定長より強い。
- メタデータ（出典・章・日付・権限）をチャンクに付ける → **検索時にフィルタ**できる（後述）。

## 検索精度を上げる手筋
ナイーブな「embedding類似度 top-k だけ」は意外と外す。実務では足す：
- **ハイブリッド検索**：ベクトル検索（意味）＋キーワード検索（BM25・完全一致）を併用。**固有名詞・型番・略語**はキーワードが強い。
- **再ランク（reranker）**：top-k を多めに取り、専用モデルで**質問との関連度を再採点して絞る**。ノイズを落とす効果が大きい。
- **メタデータフィルタ**：「このユーザーが見てよい文書だけ」「2024年以降だけ」と**検索前に絞る**（権限・鮮度）。
- **クエリ書き換え**：質問を検索用に言い換え/分解してから検索（HyDE・multi-query 等）。
- **k の調整**：多すぎ＝ノイズ＋コスト、少なすぎ＝取りこぼし。eval で決める。

## プロンプトへの注入（生成側）
```
あなたは社内アシスタント。以下の文脈情報"だけ"に基づいて答えること。
文脈に答えが無ければ「分かりません」と言う（推測で補わない）。
回答の根拠にした文書の出典を必ず示すこと。

--- 文脈ここから ---
[1] (就業規則 第12条) ...
[2] (FAQ 2024-05) ...
--- 文脈ここまで ---

質問: 有給は何日繰り越せますか？
```
- **「文脈に無ければ"分からない"」を明示** → ハルシネーション抑制の最重要ガード。
- **出典番号を付けて返させる** → ユーザーが検証できる＝信頼性。
- 温度は低め。事実回答にランダム性は要らない。
- 文脈ブロックは区切り記号（`--- ここから/ここまで ---` やタグ）で**データと指示を明確に分離**する。これがプロンプトインジェクション耐性にもなる。

## 強み / 弱み・限界
**強み**：学習不要・**データ更新が即反映**・出典を示せる・ハルシネーションを減らせる・権限制御を検索段で効かせられる。
**弱み・限界**：
- **検索が外すと終わり**（関係文書を取れなければLLMも答えられない）。RAGの失敗の多くは生成でなく**検索の失敗**。
- パイプラインが増える（埋め込み・DB・チャンク・再ランク）＝**運用対象が増える**。
- 外部文書を入れる＝**プロンプトインジェクションの入口**になる（→ [プロンプト設計.md](./プロンプト設計.md)）。
- 大量の文脈注入は**コストとレイテンシを押し上げる**。

## ハマりどころ / アンチパターン
- **チャンクが雑** → 何より先にここを直す。固定長ぶつ切りをやめ、構造と適度なオーバーラップで切る。
- **embeddingモデルを途中で変えて再生成しない** → クエリと文書の空間がズレて検索が壊れる。
- **ベクトル検索オンリーで固有名詞を取りこぼす** → ハイブリッド＋再ランク。
- **「分からない」を許さないプロンプト** → 無理に作話する。「無ければ分からないと言え」を必ず入れる。
- **権限を生成側で頑張る** → 漏えいリスク。**検索段でフィルタ**して、そもそも見せない。
- **何でもRAG** → 口調や形式の問題はRAGでは直らない。プロンプトで直す。
