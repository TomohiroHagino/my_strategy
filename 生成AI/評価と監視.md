# 評価と監視（eval / オブザーバビリティ）

## ひとことで言うと
LLM の出力は**非決定的で正解が一意でない**ため、普通の単体テスト（`expect(x).toBe(y)`）が効きにくい。
だから **「品質を測る仕組み（eval）」と「本番で何が起きたか見る仕組み（トレース）」をセットで持つ**。これが無いと「プロンプトを変えたら良くなった気がする」から抜け出せない。

## なぜ必要か / どこで効くか
- **回帰検知**：プロンプト/モデル/RAGを変えたとき、**他のケースが悪化していないか**を測れる。LLMアプリの変更は副作用が読めない。
- **モデル選定**：「どのモデルが安く十分な質か」をデータで決める（勘でなく）。
- **本番監視**：ハルシネーション・コスト急増・レイテンシ悪化・ツール暴走を**早く気づく**。
- このリポジトリの「テスト必須・観測性」方針（→ [../DevOps/observability.md](../DevOps/observability.md)）のLLM版。

---

## 評価（eval）の作り方
### 1. ゴールデンセット（評価用データ）
- **代表的な入力＋期待される出力/合格基準**を集めた固定データセット。**まず小さく（20〜50件）**でも作る。
- **難しいケース・過去の失敗・エッジケース**を意図的に入れる（ここが回帰しやすい）。
- 本番ログから「失敗した実例」を回収して育てる。**evalは資産**で、増やすほど効く。

### 2. 採点方法（タスクで使い分け）
| 手法 | 向くタスク | 中身 |
|---|---|---|
| **完全一致 / ルール** | 分類・抽出・JSON | ラベル一致、スキーマ検証、正規表現。**安く確実**。まずこれで測れる形に設計する |
| **指標スコア** | 検索・要約・翻訳 | retrieval の precision/recall、類似度など |
| **LLM-as-judge** | 自由文・対話・要約の質 | 別のLLMに「基準に沿って採点させる」 |
| **人手評価** | 最終品質・主観・安全 | サンプリングして人が見る。最も信頼でき最も高コスト |

### 3. LLM-as-judge（LLMで採点）
自由文は機械一致で測れない → **別のLLMに評価基準を渡して点数/合否を出させる**。
- **採点基準（rubric）を明示**：「事実に基づくか/質問に答えているか/出典があるか」を各々判定。
- **judgeにもバイアス**がある（長い回答を高評価しがち等）。**人手評価と突き合わせて校正**する。judgeを盲信しない。
- 生成と評価を**別モデル/別プロンプト**にすると独立性が上がる。

> evalは**CIに組み込む**のが理想。プロンプト/モデルを変えるPRで自動的にスコアが出れば、悪化を止められる（→ [../DevOps/ci_cd.md](../DevOps/ci_cd.md)）。

## ハルシネーション（作話）対策
「もっともらしい嘘」をゼロにはできない。**減らす＋検知する**：
- **根拠を渡す（RAG）＋「無ければ分からないと言え」**（→ [rag.md](./rag.md)）。
- **出典を出させて検証可能に**。出典と本文の整合をjudgeでチェック（groundedness/faithfulness）。
- **温度を下げる**、**自信のなさを言わせる**、**重要回答は2回出して矛盾を見る**（self-consistency）。
- **不可逆・高リスクな出力は人を挟む**（医療/法務/金融）。

## 監視（オブザーバビリティ）
本番LLMアプリで**最低限ログ/計測すべきもの**：
```
入力プロンプト（PIIはマスク）/ 出力 / 使ったモデル
入力・出力トークン数 / 推定コスト
レイテンシ（TTFT・総時間）
ツール呼び出し（名前・引数・結果・回数）   ← エージェント
RAG: 検索クエリ・取れた文書・スコア
エラー（タイムアウト/レート制限/スキーマ違反/リトライ）
ユーザーフィードバック（👍/👎・修正）
```
- **トレース＝1リクエストの全工程を1本の流れで追える**こと（プロンプト→検索→LLM→ツール→出力）。エージェントの多段では必須。
- 専用ツール（LangSmith / Langfuse / Phoenix / Helicone 等）か、既存のメトリクス/ログ基盤に載せる。
- **アラート**：コスト/分、エラー率、p95レイテンシ、👎率に閾値を張る（→ SLO的に）。

## ガードレール（実行時の防御）
評価が「事後/定期」なのに対し、ガードレールは**1回ごとに実行時チェック**：
- **入力**：PII検出/マスク、プロンプトインジェクション検知、禁止トピック。
- **出力**：スキーマ検証、禁止語/有害表現フィルタ、出典の有無、機密漏えいチェック。**通らなければ再生成 or 定型応答**。
- 出力をUIに出す前にサニタイズ（XSS等。Webセキュリティ原則は生成物にも適用）。

## 強み / 弱み・限界
**強み**：変更の良し悪しを**数値で**言える／本番の劣化に早く気づける／モデル選定を根拠づけられる。
**弱み・限界**：evalセット作りに**手間**がかかる／LLM-as-judge は**それ自体が不確実**で校正が要る／全ケースは網羅できない（サンプリングの限界）。

## ハマりどころ / アンチパターン
- **evalを作らず体感で評価** → 改善が積み上がらない。小さくても固定データで測る。
- **judgeを盲信** → 人手と突き合わせて校正する。
- **本番でトークン/コストを記録していない** → 課金事故・遅延に気づけない。最初から計測。
- **PIIをそのままログ** → 情報漏えい。マスクしてから保存。
- **プロンプト変更を無検証でデプロイ** → 静かに別ケースが悪化。eval をCIに。
- **「精度100%」を目標化** → 非決定的タスクで不可能。閾値とフォールバックで設計する。
