# MCP（Model Context Protocol）

## ひとことで言うと
**LLM（やエージェント）に、ツール・データ・プロンプトを"つなぐ"ためのオープンな標準プロトコル**。
「LLMアプリ ← → 外部システム」の接続を**毎回独自に作り込まず、共通の作法で差し替え・再利用できる**ようにする規格。よく **「AI界のUSB-C」** と例えられる（どのホストにも同じ口で挿さる）。Anthropic が提唱し、各社クライアント/SDKが対応を広げている。

## なぜ必要か / どこで効くか
- ツール連携は放っておくと **「クライアント × ツール」の組み合わせ爆発**（N×M問題）になる。各アプリが各APIに独自実装を書くと再利用できない。
- MCP は間に**共通インターフェース**を挟むことで、これを **N＋M** に畳む：**ツール側はMCPサーバを1個作れば、対応する全ホストから使える**。
- 旨味：**作り込みの再利用・差し替え・標準化**。社内ツールを1度MCPサーバ化すれば、IDE・チャット・自作エージェントから同じ口で叩ける。

> 位置づけ：MCP は[エージェント.md](./エージェント.md)の **tool use を「どう接続するか」の標準化レイヤ**。tool use がLLM↔ツールの"会話の仕方"なら、MCP はツールを"どう公開・発見・接続するか"の規約。

## 登場人物（アーキテクチャ）
```
┌─────────────── Host（AIアプリ: IDE / チャット / エージェント）───────────────┐
│   LLM 本体                                                                  │
│   ├─ MCP Client A ──(プロトコル)── MCP Server  (例: ファイルシステム)        │
│   ├─ MCP Client B ──(プロトコル)── MCP Server  (例: GitHub / DB / 社内API)   │
│   └─ MCP Client C ──(プロトコル)── MCP Server  (例: Slack)                   │
└─────────────────────────────────────────────────────────────────────────────┘
```
- **Host（ホスト）**：LLMを動かす本体アプリ。Claude Code・各種IDE・チャット・自作エージェントなど。複数のクライアントを束ねる。
- **Client（クライアント）**：ホスト内にあり、**1つのサーバと1対1**で接続を保つ仲介役。
- **Server（サーバ）**：実際に**ツール・データ・プロンプトを公開する**プログラム。ファイル、DB、GitHub、Slack、社内APIなど“能力”の提供側。

> ポイント：**サーバは「能力を公開するだけ」、実行を起動・許可するのはホスト**。だから権限管理・承認をホスト側に集約できる。

## サーバが公開する3つの基本要素（primitives）
| 要素 | 何か | 誰が主導 | 例 |
|---|---|---|---|
| **Tools（ツール）** | LLMが**呼び出して実行**できる関数（副作用あり得る） | **モデル**が「呼ぶ」と判断 | `create_issue` / `run_query` / `send_message` |
| **Resources（リソース）** | LLMに**読ませる文脈データ**（ファイル/レコード等。URIで指す） | **アプリ/ユーザー**が選んで渡す | `file:///path` / `db://orders/123` |
| **Prompts（プロンプト）** | 再利用可能な**プロンプト/ワークフローのテンプレ** | **ユーザー**が選んで起動 | 「このPRをレビュー」定型 |

- **Tools=モデル駆動**（tool useそのもの）、**Resources=アプリ駆動**（RAGに渡す文脈）、**Prompts=ユーザー駆動**（スラッシュコマンド的）。**「誰がトリガーするか」が3者の本質的な違い**。

### クライアント側が提供する機能（サーバから使える）
- **Sampling**：サーバが**ホストのLLMに推論を依頼**できる（サーバが自前でAPIキーを持たずにLLMを使える）。実行可否はホストが制御。
- **Roots**：サーバがアクセスしてよい**ディレクトリ/URIの範囲**をクライアントが示す（権限の境界）。
- **Elicitation**：処理途中でサーバが**ユーザーに追加入力を求める**。

## 通信のしくみ
- ベースは **JSON-RPC 2.0**（リクエスト/レスポンス/通知のメッセージ規約）。
- 接続時に **capability negotiation（能力交渉）**：互いに「自分は何ができるか」を申告してから使う。
- **トランスポート（運び方）**は主に2つ：

| トランスポート | 使う場面 | 中身 |
|---|---|---|
| **stdio** | サーバを**ローカルで子プロセス起動** | 標準入出力でやり取り。ローカルツール（ファイル/CLI）に最適・最も手軽 |
| **Streamable HTTP** | サーバを**リモート/別プロセス**で動かす | HTTP POST＋必要に応じSSEでストリーミング。リモートMCPサーバ・SaaS提供向け |

> 旧仕様の「HTTP+SSE」単体方式は **Streamable HTTP に置き換わった**。新規はStreamable HTTPで。詳細・最新仕様は公式（modelcontextprotocol.io）で確認する。

## ツール定義（イメージ）
MCPサーバはツールを**名前・説明・入力スキーマ**で公開する。中身は[エージェント.md](./エージェント.md)の関数スキーマと同じ思想。
```jsonc
// server が tools/list で返すツールの一例
{
  "name": "search_orders",
  "description": "注文履歴を検索する。注文に関する質問のとき使う。",
  "inputSchema": {
    "type": "object",
    "properties": {
      "user_id": { "type": "string" },
      "status":  { "type": "string", "enum": ["paid","shipped","canceled"] }
    },
    "required": ["user_id"]
  }
}
```
- LLM は `tools/list` で一覧を取得 → 使うものを選び `tools/call` で呼ぶ → サーバが実行して結果を返す。
- **description が呼び出し精度を決める**のは tool use と同じ（曖昧だと誤呼び出し）。

## 最小のサーバ実装（擬似コード）
公式SDK（TypeScript / Python など）で数十行から書ける。
```python
# Python SDK イメージ
server = MCPServer("orders")

@server.tool()
def search_orders(user_id: str, status: str | None = None) -> list[dict]:
    """注文履歴を検索する。注文に関する質問のとき使う。"""
    rows = db.query(user_id=user_id, status=status)   # ただの普通の処理
    return rows

server.run(transport="stdio")   # ローカルなら stdio で起動
```
- 実体は **「普通の関数にスキーマと説明を付けて公開するだけ」**。難しさは中身のロジック側にある。
- ホスト（例：Claude Code やIDE）の設定にサーバの起動コマンド/URLを登録すると、ツールとして見えるようになる。

## どこで使うか（具体例）
- **開発**：ファイルシステム・git・GitHub・DB・ブラウザ操作を IDE/エージェントから統一的に。
- **社内**：社内API・ナレッジベース・チケット・Slack を1つの口でLLMに接続。
- **SaaS提供側**：自社サービスを**リモートMCPサーバ**として公開し、各種AIクライアントから使ってもらう。
- （このリポジトリの環境でも、各種ツールは MCP 経由で接続される構成。）

## 強み / 弱み・限界
**強み**：
- **標準化＝再利用・差し替え**（N×M→N＋M）。1度作れば多くのホストで動く。
- ツール・データ・プロンプトを**統一インターフェース**で扱える。
- **権限・承認をホストに集約**でき、エコシステム（既製サーバが多数）に乗れる。

**弱み・限界**：
- **新しい標準で発展途上**：仕様・SDK・対応ホストが動く。最新を追う必要あり。
- **層が1枚増える**＝運用・デバッグ対象が増える（プロトコル越しの不具合は追いにくい）。
- 結局**中身のツール実装と安全設計は自前**。MCPは“つなぎ方”を標準化するだけで、安全にしてくれるわけではない。

## セキュリティ（最重要）
MCPは**外部コードに自分の環境への接続口を与える**仕組み。導入＝攻撃面が増える。
- **信頼できるサーバだけ接続**：第三者製MCPサーバは**任意コード実行・データ送出**の経路になり得る。出所を確認。
- **権限最小化＋承認**：ツール実行（特に書き込み・削除・送信・課金）は**ホスト側で許可制／人の承認**。Roots でアクセス範囲を絞る。
- **プロンプトインジェクション／ツール汚染**：サーバが返すツール説明やリソース本文に悪意の指示が混じり得る（"tool poisoning"）。**ツール結果はデータとして扱い、指示として信頼しない**（→ [プロンプト設計.md](./プロンプト設計.md)）。
- **入力検証**：ツール引数はサーバ側で必ず検証（LLMが出した値を無検証で実行しない）。
- **秘密情報**：MCPサーバに渡す認証情報は環境変数/シークレットマネージャで。ログに残さない。
- **監査ログ**：どのサーバの何を・どの引数で呼んだかを全部記録（→ [評価と監視.md](./評価と監視.md)）。

## ハマりどころ / アンチパターン
- **素性不明のMCPサーバをそのまま接続** → 任意コード実行・情報漏えい。信頼境界を引く。
- **ツールのdescriptionが雑** → 誤呼び出し/呼ばない。tool use と同じく説明文を磨く。
- **危険操作を承認なしで自動実行** → 不可逆事故。書き込み系は承認・許可リスト。
- **旧SSE方式に固執** → 新規は Streamable HTTP。仕様は公式で最新確認。
- **「MCPにすれば安全/楽」と誤解** → 標準化されるのは接続だけ。安全・実装責任は自分に残る。
- **何でもMCPサーバ化** → 単一アプリの内部ツールなら直接 tool use で十分。再利用・他ホスト共有が要るときにMCP化する（YAGNI）。
