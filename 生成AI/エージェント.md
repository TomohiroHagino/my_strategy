# エージェント（tool use / 関数呼び出し）

## ひとことで言うと
**LLM に「使えるツール（関数）」を渡しておき、LLM がいつ・どの引数でそれを呼ぶかを判断 → 実際の実行はアプリ側が行い → 結果をLLMに返して続きを考えさせる**仕組み。
これで LLM は「文章を返すだけ」を超えて、**検索する・DBを引く・APIを叩く・計算する・外の世界を操作する**ことができる。「LLMに作業を任せる」の基盤。

## なぜ必要か / どこで効くか
- LLM 単体は**最新情報を知らず・計算が苦手・外部システムに触れない**。これらは**ツールにやらせる**のが正解。
- 「天気は？」「在庫を確認して」「このSQLの結果を要約して」のような**動的・外部依存の質問**に答えるには、実行能力が要る。
- RAG も広義はツール（検索ツール）。エージェントは**複数ツールを自律的に選んで組み合わせる**ところまで広げたもの。

---

## 仕組み（tool use のループ）
```
1. アプリ → LLM に「ツール定義（名前・説明・引数スキーマ）」＋ユーザー入力を渡す
2. LLM     → 「get_weather(city="Tokyo") を呼びたい」という"ツール呼び出し"を返す（まだ実行はしない）
3. アプリ → 実際に get_weather を実行（ここはただの普通のコード）
4. アプリ → 実行結果をLLMに返す（role=tool）
5. LLM     → 結果を踏まえて、最終回答 or 次のツール呼び出しを返す
6.        → ツール呼び出しが無くなる（最終回答）まで 2〜5 を繰り返す
```
ポイント：**LLMは「呼びたい」と言うだけ。実行するのは常にアプリ側のコード**。だから安全制御はアプリ側に置ける。

## ツール定義（関数スキーマ）
LLM に「何ができて・いつ使い・どんな引数か」を**スキーマで**教える。
```json
{
  "name": "search_orders",
  "description": "ユーザーの注文履歴を検索する。注文に関する質問のとき使う。",
  "input_schema": {
    "type": "object",
    "properties": {
      "user_id": {"type": "string"},
      "status": {"type": "string", "enum": ["paid","shipped","canceled"]}
    },
    "required": ["user_id"]
  }
}
```
- **description が命**。LLM はこの説明文を読んで「使うか/引数に何を入れるか」を決める。**曖昧だと誤呼び出し**する。プロンプト設計そのもの。
- 引数は**enumや型で縛る**ほど安定（構造化出力と同じ発想）。

## ReAct（推論と行動の交互ループ）
**Reasoning（考える）→ Acting（ツールを使う）→ Observation（結果を見る）→ また考える**…を繰り返す古典パターン。多くのエージェントの基本形。
```
思考: 注文状況を知るには注文を検索する必要がある
行動: search_orders(user_id="u1", status="shipped")
観察: [出荷済み注文2件...]
思考: 2件あるので最新の追跡番号を答えればよい
回答: 最新の出荷は... 追跡番号は...
```

## MCP（Model Context Protocol）
- **LLM/エージェントに「ツールやデータソース」を接続するための標準プロトコル**。
- ツール（ファイル・DB・社内API・SaaS…）を**MCPサーバ**として実装すると、対応クライアント（IDE・エージェント等）から**共通の作法で**使える。
- 旨味：**ツール連携を毎回作り込まず、再利用・差し替えできる**。エコシステムが共通化に向かっている。
- （このリポジトリの環境でも MCP 経由で各種ツールが接続される構成になっている。）

> 詳しくは独立ファイル → **[mcp.md](./mcp.md)**（Host/Client/Server・3 primitives・トランスポート・サーバ実装・セキュリティ）。

## マルチエージェント
1体に全部やらせず、**役割で分けた複数のLLM**を協調させる構成。
```
オーケストレーター（司令塔）
 ├─ リサーチ担当（検索・収集）
 ├─ コード担当（実装）
 └─ レビュー担当（検証・批判）   ← 別視点で互いをチェック
```
- 効くケース：**並列化できる探索**、**生成と検証を分けたいとき**（自分の出力を別エージェントが批判＝品質が上がる）。
- 代償：**コスト・レイテンシ・複雑さが跳ね上がる**。まず単体＋ツールで足りないか確認してから（KISS/YAGNI）。

## 安全設計（最重要）
エージェントは**外の世界を変えられる＝事故ると実害**。普通のコードより慎重に。
- **権限最小化**：各ツールに必要最小の権限だけ。削除・送金・本番変更は別扱い。
- **危険操作は人の承認（human-in-the-loop）**：不可逆・高影響の操作は**実行前に確認**を挟む。このリポジトリ全体の方針（不可逆操作は確認してから）と同じ。
- **入力/出力の検証**：ツール引数は**アプリ側でバリデーション**（LLMが出した値を無検証で実行しない＝SQLインジェクション等を防ぐ）。
- **ループ上限**：暴走で無限にツールを呼ばないよう**最大ステップ数・タイムアウト・コスト上限**を設ける。
- **プロンプトインジェクション**：ツールが返した外部テキストに悪意の指示が混じりうる。**ツール結果はデータとして扱い、指示として信頼しない**。
- **監査ログ**：いつ・何を・どの引数で呼んだかを**全部トレース**（→ [評価と監視.md](./評価と監視.md)）。

## 強み / 弱み・限界
**強み**：最新情報・計算・外部操作を取り込める。RAG・API・DBを統合できる。複雑なタスクを自律的に分解実行できる。
**弱み・限界**：
- **非決定的に外部へ作用する**＝デバッグ・再現・テストが難しい。
- **多段ループでコスト・レイテンシが膨らむ**（毎ステップがLLM呼び出し）。
- **誤った道に進むと誤りが連鎖**（途中の判断ミスが後段に伝播）。
- 自律性が上がるほど**事故の被害が大きい**。

## ハマりどころ / アンチパターン
- **ツールのdescriptionが雑** → 誤呼び出し/呼ばない。説明文を磨く（最大の改善点）。
- **LLMの出した引数を無検証で実行** → インジェクション・破壊。必ずバリデーション＋許可リスト。
- **ループ上限なし** → 暴走・課金事故。ステップ/時間/コストの上限を必須に。
- **いきなりマルチエージェント** → 複雑すぎて壊れる。単体＋数ツールから始める。
- **不可逆操作を自動実行** → 取り返しがつかない。承認を挟む。
- **トレースを取らない** → 何が起きたか分からず直せない。全呼び出しを記録。
