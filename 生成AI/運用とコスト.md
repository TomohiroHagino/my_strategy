# 運用とコスト（レイテンシ / 課金 / 信頼性）

## ひとことで言うと
LLMアプリは **「遅い・高い・たまに落ちる/詰まる」外部API依存**。プロトタイプは動いても、**本番でコストとレイテンシとレート制限を制御できないと破綻する**。ここはその運用設計。「作って動かす」の先の「運用する」レイヤ。

## なぜ必要か / どこで効くか
- **課金はトークン従量**。ユーザーが増える・履歴が伸びる・contextを詰めるほど**青天井に増える**。
- LLMは**普通のAPIより桁違いに遅い**（秒オーダー）。UX設計とタイムアウト設計が要る。
- 外部API＝**レート制限・障害・モデル廃止**に晒される。落ちても止まらない設計が要る。

---

## コスト（トークン課金の構造）
```
1リクエストの費用 ≒ 入力トークン×入力単価 + 出力トークン×出力単価
```
- **出力単価は入力単価より高い**のが普通 → **長く喋らせない**だけで効く。
- 効くレバー（安い順）：
  1. **モデルを下げる**：分類/抽出/要約は小型モデルで十分なことが多い。**タスクごとに最小のモデル**を当てる（ルーティング）。
  2. **プロンプトを削る**：固定文・冗長な例・巨大JSONを圧縮。Few-shotは効く最小数に。
  3. **履歴を圧縮**：会話は毎回全送りなので、古い履歴を**要約して畳む**。
  4. **出力を短く**：max_tokens＋「簡潔に」指示。構造化出力で無駄な前置きを消す。
  5. **キャッシュ**（下記）。
- **必ず本番でトークン/コストを計測**（→ [評価と監視.md](./評価と監視.md)）。「気づいたら月額が跳ねていた」を防ぐ。

## キャッシュ（最も効く節約＆高速化）
| 種類 | 何をする | 効果 |
|---|---|---|
| **プロンプトキャッシュ**（API機能） | 共通の長い接頭辞（system・固定文脈・ツール定義・RAGの固定部分）を**サーバ側でキャッシュ**し、再送時の入力コスト/処理を大幅減 | 入力が長く定型なほど効く。**接頭辞を固定し、可変部は末尾**に置くのがコツ |
| **完全一致キャッシュ**（自前） | 同じ入力→同じ出力をKVS（Redis等）に保存 | FAQ・定型質問で**LLMを呼ばずに即返す**＝コスト0・激速 |
| **セマンティックキャッシュ** | 「意味が近い質問」をembeddingで判定して再利用 | 言い換え質問にも効く。ただし**取り違えに注意**（閾値設計が要る） |

> Redis をキャッシュ層に使うのは定番（→ [../データベース/redis.md](../データベース/redis.md)）。TTLを必ず付ける。

## レイテンシ（速くする / 速く見せる）
- **ストリーミング**：トークンを逐次返してTTFTを体感短縮。チャットUIはほぼ必須（→ [llm基礎.md](./llm基礎.md)）。
- **出力を短く**：生成時間は出力長に比例。短答なら速い。
- **モデルを下げる**：小型ほど速い。重い推論だけ上位モデルに回す。
- **並列化**：独立した複数呼び出しは並行実行（RAGの複数検索、マルチエージェントの枝）。直列の待ち時間を畳む。
- **プロンプトキャッシュ**：prefillが軽くなりTTFTも改善。
- **投機的に先読み**：候補を先に生成/検索しておく（当たれば速い）。
- **タイムアウトとフォールバック**：遅延時は短い定型応答や別モデルに切替。

## 信頼性（落ちる前提の設計）
外部API依存なので、**失敗を前提に守る**：
- **リトライ＋指数バックオフ**：一時エラー(429/5xx)は待って再試行。**ジッタ**を入れて雪崩を防ぐ。
- **レート制限対策**：RPM/TPM上限に当たる前にクライアント側で**スロットリング・キューイング**。バッチは平準化。
- **フォールバック**：主モデル障害時に**別モデル/別プロバイダ/縮退応答**へ。単一ベンダー依存を避ける設計余地を持つ。
- **冪等性とタイムアウト**：長い生成のタイムアウトを設定。再送時の二重実行（特にツールで副作用があるエージェント）に注意。
- **サーキットブレーカー**：連続失敗時は一時的に呼び出しを止めて回復を待つ。
- **コスト上限/ガード**：1リクエスト・1ユーザー・全体の**上限**を設け、暴走（特にエージェントのループ）で破産しない（→ [エージェント.md](./エージェント.md)）。

## バッチ / 非同期
- **即時性が要らない処理（分類・要約の一括・夜間生成）は非同期バッチ**に回す。
- 多くのAPIに**バッチ実行（割安・低優先）**がある。リアルタイムでないものはそちらでコスト減。
- ジョブキュー（Sidekiq/Solid Queue 等）で**レート制限内に平準化**して流す。

## デプロイ/運用の注意
- **モデルのバージョン固定 vs 追従**：固定すると挙動は安定するが廃止リスク、最新追従だと**勝手に挙動が変わる**。**モデルIDをconfigで管理**し、変更時はevalを通す。
- **モデル廃止（deprecation）に備える**：プロバイダはモデルを終了する。移行を見据え抽象化＋evalを用意。
- **APIキーは環境変数/シークレットマネージャ**。コードに焼かない（このリポジトリのセキュリティ方針）。
- **PIIの送信に注意**：外部APIに個人情報を送る前にマスク/最小化。ログにも残さない。

## 強み / 弱み・限界
**強み**：キャッシュ＋モデルルーティング＋短い出力で**コストは大きく下げられる**。ストリーミングと並列で体感速度も改善できる。
**弱み・限界**：根本的に**外部依存で遅く高い**。完全な低レイテンシ/低コストは構造的に難しく、**UXと設計で吸収する**しかない。

## ハマりどころ / アンチパターン
- **コスト/トークンを計測せず本番投入** → 月額が静かに爆発。最初から計測＋上限。
- **キャッシュ不使用** → 同じFAQに毎回課金。完全一致＋プロンプトキャッシュから入れる。
- **可変部をプロンプト先頭に置く** → プロンプトキャッシュが効かない。**固定を前・可変を後**。
- **リトライ/レート制御なし** → スパイクで429連発・ユーザーにエラー。バックオフ＋スロットリング。
- **単一モデル/単一ベンダー固定で無防備** → 障害・廃止で全停止。フォールバックの余地を残す。
- **同期で重い生成をリクエスト内に** → タイムアウト多発。長物は非同期/バッチへ。
- **エージェントにコスト上限なし** → ループで破産。ステップ/コスト上限必須。
