# LLM基礎（アプリ開発者目線）

## ひとことで言うと
LLM（大規模言語モデル）は **「これまでのテキストの続きとして、次に来そうなトークンを確率で選び続ける」生成器**。
アプリ開発者にとって重要なのは内部の数式ではなく、**入力＝トークン列・出力＝トークン列**で、**課金もコンテキスト上限もレイテンシも全部トークンで効く**という事実。ここを押さえると設計判断がほぼ全部つながる。

## なぜ必要か / どこで効くか
- 料金は「入力トークン×単価＋出力トークン×単価」。**コスト見積もりがトークンで決まる**。
- 入れられる文脈には上限（コンテキストウィンドウ）がある。**RAG・要約・履歴圧縮が必要になる理由がここ**。
- 出力はサンプリングなので**毎回ブレる**。温度などのパラメータで制御し、評価で守る（→ [評価と監視.md](./評価と監視.md)）。

---

## トークン（最重要の単位）
- LLM は文字や単語ではなく **トークン**（サブワード片）で世界を見る。英語はだいたい **1トークン≒4文字≒0.75単語**。
- **日本語は割高**：1文字で1トークン以上を消費しがちで、英語より同じ内容でもトークン数が増える＝**コストもレイテンシも増える**。
- 数字・URL・コードは予想外の切れ方をする。「文字数」で見積もると外す。**必ずトークンで数える**（各社の tokenizer / `count_tokens` API）。

```
"こんにちは世界"  → 日本語はトークン数が文字数に近い〜超える（モデル依存）
"Hello, world!"   → 3〜4トークン程度
```

> 実務メモ：プロンプトに巨大なJSONやログを丸ごと貼ると、**気づかないうちに数千トークン**を毎回送っている。テンプレ化・要約・キャッシュで削る。

## コンテキストウィンドウ（入力＋出力の上限）
- **モデルが一度に扱えるトークン総数の上限**。入力（システム＋文脈＋履歴＋指示）と出力で**合算して**使う。
- 近年は大きい（数万〜100万トークン級のモデルもある）が、**大きい＝何でも詰めて良い、ではない**：
  - 真ん中に置いた情報は見落とされやすい（**Lost in the Middle**）。**重要な指示は冒頭か末尾**に。
  - 詰めるほど**コストとレイテンシが線形に増える**。長文脈は「できる」と「すべき」が別。
- 上限に当たったら：**要約して圧縮 / 古い履歴を捨てる / RAG で必要分だけ注入**。

## 出力を制御するパラメータ
| パラメータ | 意味 | 実務の使い分け |
|---|---|---|
| **temperature**（温度） | 出力のランダムさ。0に近いほど決定的、高いほど多様 | 分類/抽出/コード/JSON → **0〜0.3**。アイデア出し/文章 → 0.7〜1.0 |
| **top_p**（核サンプリング） | 確率上位pまでから選ぶ | 温度と**両方いじらない**。普通は温度だけ動かす |
| **max_tokens**（最大出力） | 出力の上限トークン | **必ず設定**。暴走・課金事故防止。足りないと途中で切れる |
| **stop**（停止文字列） | これが出たら生成停止 | 区切り記号で出力を綺麗に止める |
| **seed**（あれば） | 乱数固定で再現性を上げる | 評価・回帰テストで擬似再現に使う（完全再現は保証されない） |

> temperature=0 でも**完全に決定的とは限らない**（実装・並列計算の都合でわずかにブレうる）。「ほぼ安定」程度に思っておく。

## 推論の流れ（プロンプト→生成）
```
1. プロンプトをトークン化
2. モデルが全トークンを一気に読む（prefill：入力が長いほど重い）
3. 1トークンずつ生成（decode：出力が長いほど遅い・逐次）
4. stop / max_tokens / EOS で停止
```
- **TTFT（最初のトークンまでの時間）** は主に入力長＋prefillで決まる。
- **TPOT（トークンあたりの生成時間）** は出力長に効く。**だから「短く答えさせる」だけでレイテンシが下がる**。
- **ストリーミング**（SSE等でトークンを逐次返す）でTTFTを体感的に短くできる。チャットUIはほぼ必須。

## システムプロンプト / ロール
ほとんどの Chat API は**ロール付きメッセージ列**で送る：
```
system    … 役割・制約・トーン・出力形式の"恒久ルール"（毎回固定）
user      … ユーザー入力
assistant … モデルの応答（履歴として積む）
tool      … ツール実行結果を返す（→ エージェント.md）
```
- **system は最優先で効く土台**。ここに「何者か・禁止事項・出力形式」を置く。
- 会話を続けるには**過去のやり取りを毎回全部送り直す**（APIはステートレス）。だから履歴が伸びるとコストが増える＝圧縮が要る。

## 主要モデルの選び方（提供者横断の考え方）
ベンダーや版は頻繁に変わるので、**固有名で覚えず「層」で選ぶ**：
- **最上位（高知能・高コスト・やや遅い）**：難しい推論・エージェントの司令塔・コード生成の主力。
- **中位（バランス）**：多くのアプリの主力。質とコスト/速度の折り合いが良い。
- **小型（高速・安価）**：分類・抽出・要約・ルーティング・大量バッチ。**まず小型で足りるか試す**。

> Claude を使う場合は最新の **Opus / Sonnet / Haiku** 系から選ぶ（Opus=最上位の推論、Sonnet=主力、Haiku=高速安価）。
> **正確なモデルID・価格・コンテキスト上限・レート制限は変動するので、実装時は必ず公式の最新情報で確認する**（このリポジトリに数値を焼き込まない）。Claude API を実際に叩くコードを書くときは `claude-api` スキルで最新値を引く。

## 強み / 弱み・限界
**強み**：自然言語の理解/生成、要約、分類、抽出、翻訳、コード、ゆるい推論を**学習なしで**こなせる。
**弱み・限界**：
- **ハルシネーション**（もっともらしい嘘）。事実性は保証されない → RAG＋検証で抑える。
- **知識のカットオフ**：学習時点より後を知らない → 最新情報は RAG/tool で渡す。
- **計算・厳密な論理は苦手**寄り → 計算はツールにやらせる。
- **非決定的**：同じ入力でも出力がブレる → eval と低温度で守る。

## ハマりどころ / アンチパターン
- **文字数でコスト/上限を見積もる** → トークンで数える。特に日本語・JSON・コードは膨らむ。
- **max_tokens 未設定** → 出力暴走・想定外課金。必ず上限を置く。
- **履歴を無限に積む** → コスト・レイテンシが青天井。要約/打ち切りを入れる。
- **温度を上げたまま抽出/JSON** → ブレてパース失敗。構造化タスクは温度を下げる。
- **「賢いモデルなら何でも安心」** → 最上位でも嘘はつくし、桁違いに高い。タスクに**最小限のモデル**を当てる。
